# 15 后台数据库升级与连续扫描

## 结论

后台数据库需要同步升级。清算机器人现在不再只依赖本地账号文件，而是把账户发现、扫描进度、健康度历史和合约执行参数拆成不同职责，因此数据库必须具备对应表结构和迁移台账。

## 表结构职责

| 表 | 职责 | 写入策略 |
|---|---|---|
| `liquidation_accounts` | 账号注册表，只保存账号级别的最新状态和去重信息 | 发现 Borrow 账号后立即写入，重复账号 `ON CONFLICT` 更新 |
| `liquidation_discovery_scans` | Borrow 事件扫描窗口和进度 | 只有扫描区块与既有进度连续或重叠时才写入 |
| `liquidation_account_health_scans` | 每次账号健康度扫描历史 | 每次健康度扫描后追加写入 |
| `schema_migrations` | 数据库结构版本台账 | `ensure_database_schema()` 幂等写入 |

## 连续性硬约束

扫描账号和记录扫描进度是两条不同路径：

1. 账号写入必须尽快完成，用于 UI 展示和其他模块消费。
2. 扫描进度必须满足连续性检查后才能写入。
3. 如果发现区块窗口存在缺口，本次发现到的账号仍可进入 `liquidation_accounts`，但 `liquidation_discovery_scans` 不记录该窗口。
4. 下次扫描可以重复扫一段旧区块，直到形成无缝连接的扫描历史。

这个约束的目标是保证数据库里的扫描进度永远表示“可信连续覆盖”，而不是“曾经尝试扫过”。

## 迁移策略

`ensure_database_schema(database_url)` 负责：

1. 创建 `schema_migrations`。
2. 创建或补齐业务表。
3. 创建去重索引。
4. 写入 `20260730_liquidation_runtime_schema` 迁移记录。

后台 `/api/db-summary` 会返回清算相关表计数，并增加：

```json
{
  "schema": {
    "expected_migration_count": 1,
    "expected_migration_applied_count": 1,
    "up_to_date": true
  }
}
```

如果 `up_to_date` 为 `false`，说明后台代码已经升级，但数据库还没有完成对应结构升级，应先触发 `ensure_database_schema()` 或重启后台服务。

## 上线检查

- [ ] 后台启动日志没有数据库建表或补列错误。
- [ ] `/api/db-summary` 中 `schema.up_to_date = true`。
- [ ] `liquidation_accounts` 能实时增长或更新。
- [ ] 存在扫描缺口时，账号仍进入账号表，但 `liquidation_discovery_scans` 不写入断裂窗口。
- [ ] 历史回补任务可以重复扫描旧窗口，并在连续后写入进度。
