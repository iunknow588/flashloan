## 一、裁决摘要（TL;DR）

**可行，建议采纳；但必须对原始设想做三处修正**，否则会踩到「重复广播」这个安全坑。

| # | 议题 | 裁决 | 一句话理由 |
|---|---|---|---|
| `D-1` | 整体可行性 | **可行**（采纳） | 复核记录 **只追加 + 无实时查询**，套利记录 **单调增长 + 需跨月聚合** —— 两者恰好互补，各用各的最优形态 |
| `D-2` | 复核记录是否留在主库 | **留**（只留当前代） | 读路径有 **4 个消费者**且被门禁链高频读取；全搬走 = 改 4 处读路径 = **越界** |
| `D-3` | 复核 JSONL 的角色 | **审计流，不是权威源** | JSONL **可丢、不可查、不可回滚**；任何准入判定都不许读它 |
| `D-4` | 套利记录是否全搬走 | **终结后归档，主库留瘦身行**（否决「全搬走 + 留索引」） | 索引落后 ⇒ 幂等失效 ⇒ **重复广播** = 安全事故 |
| `D-5` | 月归属判据 | 记录 `created_at` 的 **UTC 月**（发起月），**不是**当前时间 | 跨月边界归档错月 = 财务账错月 |
| `D-6` | 精度口径 | `signed_pnl_raw`（**带符号十六进制**）为**唯一权威**，**逐字节原样保留** | 实测 raw 是 `-0x2ee726109c1` 而**非十进制**；`signed_pnl_amount` 是 `REAL`（f64），**必然丢精度** |
| `D-7` | 反压策略 | **分级**：JSONL 可丢 / 月库背压 | 「套利记录强制同步写」会卡死主线程，违反「不能因为写盘卡死套利计算」 |
| `D-8` | 保留期 | **默认 30 天**（原始建议 7 天） | 复核记录是**审计凭据**，7 天覆盖不了一次月度结算周期 |
| `D-9` | 主库写入方式 | **维持现状**（同步事务） | 主库在途行必须与状态行**同事务可见**，不能引入异步丢失窗口 |
| `D-10` | 记录目录推导 | 由主库路径 **确定性推导** | 公开函数签名不变 ⇒ 不新增配置参数 ⇒ 调用方零改动 |
| `D-11` | **v1.1 目录布局**（使用者裁定 2026-11-23） | 复核 **`db/review_record_jsonl/<链路>/<日期>/<方向闭环>.jsonl`**；广播 **`db/broadcast_transaction_db/<链路>/<月份>/trades.sqlite3`**（**全部方向闭环同库**）。**「链路」= `<network>/<chain_id>` 两级**（如 `robinhood/4663`），详见 §3.2 | 复核侧要**按闭环单独读**⇒ 必须拆文件；广播侧要**按币种跨闭环合计**⇒ 必须同库 |

> **`D-4` 是本次唯一一处「否决原始设想」的地方**，也是最要紧的一处 —— 见 §3.4。

### 2.4 三个决定性发现（决定了方案形态）

| # | 发现 | 对方案的含义 |
|---|---|---|
| **F-1** | **主库零套利/广播存量**（相关表 0 行） | 剥离是**纯前向**的，**零数据迁移**、零回填、无历史兼容负担 |
| **F-2** | **复核记录不增长**（每代全量替换） | 复核侧的痛点**不是磁盘**，而是**历史不可追溯**；⇒ JSONL 应定位为**审计流**，不是「省空间」 |
| **F-3** | **复核记录被门禁链高频读取**（完整性 / 新鲜度 / 容量 / 利润 / `BC-1`） | **当前代必须留在主库**；剥离的只能是「历史代」 |

> **F-2 值得特别强调。** 原始设想是「复核记录数据量极大 ⇒ 落 JSONL 解压主库」。
> 实测证明**主库里的复核数据只有 102 KB**，8.01 GiB 的主库另有其因（池子 / 快照 / 候选边等）。
> **所以剥离复核记录不是为了省空间，而是为了「留住每一代」** ——
> 方向是把「当前代物化视图」+「逐代审计流」拆开，而不是把复核数据「搬走」。

## 三、目标架构：三层权威

### 3.1 权威分层

| 层 | 载体 | 权威性 | 可丢 | 参与判定 |
|---|---|---|---|---|
| **L1 主库** | `local_store_4663.sqlite3` | **状态权威**：当前代物化视图 + 状态行 + 幂等台账 | ❌ 不可丢 | ✅ **是** |
| **L2 月度库** | `broadcast_transaction_db/<链路>/<chain_id>/<YYYY-MM>/trades.sqlite3` | **已终结套利记录的唯一权威** | ❌ 不可丢 | ✅ 是（幂等 / 回执关联） |
| **L3 JSONL** | `review_record_jsonl/<链路>/<chain_id>/<YYYY-MM-DD>/<方向闭环>.jsonl` | **审计流**：逐代复核快照 | ✅ 可丢 | ❌ **永不** |

**判据一句话**：**「要拿它做决定」→ L1/L2；「要拿它证明做过什么」→ L3。**

### 3.2 目录结构（由主库路径确定性推导）

**v1.1 布局（使用者裁定，2026-11-23）**：两棵记录树**与主库同目录**；
复核侧**按方向闭环拆文件**，广播侧**按方向闭环不拆文件**（全部闭环同库）。

```text
<主库目录>/                              ← 即 flashloan/db/
├── local_store_4663.sqlite3             ← 主库（不动）
├── review_record_jsonl/                 ← 复核审计流
│   └── <network>/<chain_id>/
│       └── <YYYY-MM-DD>/                ← 按日期建文件夹
│           └── <方向闭环>.jsonl          ← 每个方向闭环一个文件
├── broadcast_transaction_db/            ← 广播（套利）交易记录
│   └── <network>/<chain_id>/
│       └── <YYYY-MM>/                    ← 按月份建文件夹
│           └── trades.sqlite3            ← 全部方向闭环同库
└── record_maintenance/                  ← 清理台账（永不清理）
```

推导规则：**主库路径所在的目录**（即 `flashloan/db/`）。
**不新增配置项、不新增公开参数** ⇒ 4 个读路径消费者**零改动**。

**「方向闭环」的文件名怎么来**：闭环键（`loop_key`）由三个代币地址拼成
（`anchor:y:z`），**含冒号** —— Windows 文件名不允许冒号。因此文件名 =
**安全化后的闭环键 + 原键的 SHA-256 前 12 位十六进制**：

- 安全化 = 只保留 `[A-Za-z0-9._-]`，其余字符换成 `_`，再截断到 64 字符；
- 摘要后缀 ⇒ **两个不同闭环绝不会落到同一个文件**；
- 同一闭环**永远**得到同一个文件名 ⇒ 可重复定位。

**广播侧为何不拆文件**：月度库要回答的是「这个月这个链赚了多少」，**按币种分组**的
合计必须在**同一个库**里算；拆成每闭环一个库会把「跨闭环求和」重新变成
N 次连接。闭环维度由 `loop_key` **列**承担，不靠文件分片。

### 3.3 复核侧写入时序（主库保持权威，JSONL 旁路）

```text
① 主库事务：DELETE 三表 → INSERT 当前代 → upsert 状态行 → COMMIT   ← 权威，仍同步
② 事务提交后 → 构造 JSONL 行（只序列化「这一代」的差异集）
③ try_send 到有界通道（容量 10000）→ 后台 tokio 任务追加写文件
④ 通道满 → 丢弃该行 + dropped 计数 +1（可在 read_review_status 读到）
```

要点：

- **JSONL 写在事务提交之后** —— 写失败**绝不回滚**主库，**绝不阻塞**主库提交；
- **JSONL 是逐代增量**，不是每代全量快照（否则第 24 代就要写 24 份全量 ⇒ 反而更大）；
- 每行自带 `reviewVersion` + `closedLoopVersion` + `materializedChecksum` ⇒ 可自证是哪一代；
- **JSONL 永远不参与准入判定** —— 门禁只读主库当前代（`D-3`）。

### 3.4 广播侧写入时序（**这是与原始设想差别最大的一处**）

原始设想是「套利记录全部搬到按月 SQLite，主库只留索引」。**本方案否决该形态。**
否决理由（**安全级别**，不是风格偏好）：

> 幂等判定读的是主库。索引行若因任何原因落后于月度库（写失败、进程崩溃在两步之间、
> 月度库被锁、清理任务误删），系统会**认为「这个 attempt 从没发生过」** ⇒
> **同一条机会会被再次广播** ⇒ **重复交易 = 资金损失**。
> 而「重复广播一条已终结的尝试」与「多写一条记录」相比，**风险量级完全不同**。

因此采用**有序两步归档 + 主库瘦身**（主库 → 月库 → 主库瘦身行）：

```text
① 尝试发起 → 主库 INSERT（manager_cow_execution_attempts，status=在途）   ← 幂等锚点
② 尝试终结（回执 / 证据 / terminal_at 落定）
③ 先 INSERT OR REPLACE 进【当月库】（terminated 形态，含完整列）
④ 确认月库写入成功后 → 主库把该 attempt 行「瘦身」
   （清空体积列，保留判定列 / 幂等锚点 / 盈亏原值，≈250 B）
⑤ 反向禁止：任何时刻不得「先删主库、后写月库」
```

**为什么这样更安全**：

| 崩溃点 | 结果 |
|---|---|
| ③ 之前崩溃 | 尝试留在主库（**在途**）⇒ 幂等锚点在 ⇒ 不会被重复广播 |
| ③ 成功、④ 之前崩溃 | **两处都有** ⇒ 幂等锚点仍在主库 ⇒ 安全；下次启动由**幂等对账**收敛（月库行覆盖主库行） |
| ④ 之后崩溃 | 主库瘦身行 + 月库完整行 ⇒ 幂等锚点**仍在** ⇒ 安全 ✅ |

**与原始设想的关键差别**：原始设想是「搬走 + 留索引」；本方案是
**「搬走 + 留瘦身行」** —— 瘦身行**不是索引**（不携带路径明细与回执原文），
只承担**「这条 attempt 存在过、别再来一遍」**这一个职责 ⇒
**重复广播风险 = 0**，同时主库增长受控（≈250 B/行而非整行）。

> **⚠️ 为什么不是「墓碑行」**：`status` 列的 CHECK 只允许
> `pending` / `success` / `failed` ⇒ 新增 `'archived'` **必须改主库 DDL** ⇒ **越界**；
> 新增一张墓碑表**同样越界**。⇒ 改为**瘦身**（**不动 `status`、不新增列、不新增表**）。
> 完整论证见 **§5.4**。

### 3.5 跨月查询（**逐库只读** · v1.1 落地口径）

月度库**沿用主库的表名与列结构**（`manager_cow_execution_attempts` 等）。
**原始设想**是用 SQLite 的 `ATTACH` 把历史月库挂到当前连接上一句 SQL 查完：

```sql
ATTACH DATABASE 'flashloan/db/broadcast_transaction_db/robinhood/4663/2026-10/trades.sqlite3' AS m202610;
SELECT signed_pnl_raw, signed_pnl_currency FROM trades WHERE ...;
UNION ALL
SELECT signed_pnl_raw, signed_pnl_currency FROM m202610.trades WHERE ...;
```

要点：

- `ATTACH` **由 `broadcast_manager` 内部完成**，**不暴露给调用方** ⇒ 公开 API 不变；
- 月度库**零新表零新列** ⇒ `manager_db` / 迁移 / `schema_policy.json` **全部不动**；
- `M-6` 守卫按**表名**匹配 ⇒ 沿用主库表名 ⇒ **自动被既有守卫覆盖**（§4.3）。
- **⚠️ 落地修正（v1.1）**：SQL 里**只能取原始行**，**禁止** `SUM(signed_pnl_raw)` ——
  `signed_pnl_raw` 是**带符号十六进制字符串**、且**多币种混存** ⇒ SQL 聚合会
  **差 16 个数量级**（按十进制解析）**且**跨币种求和无意义。
  **落地实现**：按 `signed_pnl_currency` **分组**（`GROUP BY` 只用于**取分组键**，
  **不聚合金额**），金额在 **Rust 侧用 `U256` 精确求和** ⇒ **逐位相等**。
  另：**落地实现改为「月库一个一个只读打开」** —— **绝不**把月库 `ATTACH` 到
  **主库连接**上（避免跨库句柄泄漏、避免主库连接被历史库拖住），
  也**绝不**跨库做 SQL 聚合。跨月结果在 **Rust 侧**合并。

### 3.6 精度口径（对齐 `D-6`）—— **含实测修正**

现网 DDL 实测：`signed_pnl_raw TEXT`、`signed_pnl_amount REAL`（**f64**）。
`REAL` 在 2^53 之外**必然丢精度** ⇒ 金额**不可用它做权威**。

**但「权威字段的格式」与原始设想不同 —— 本轮已实测钉死**（只读统计主网库
`manager_v4_reviews` 中 **14** 条带盈亏的行）：

| 实测项 | 读数 | 含义 |
|---|---|---|
| `signed_pnl_raw` 的实际形态 | `-0x2ee726109c1` | **带符号的十六进制**，**不是**十进制 |
| `raw` 为纯十进制数字的行数 | **0 / 14** | 原始设想里的 `"profit_wei": "1250000000000000"` **与现网格式不符** |
| `raw` 带 `-` 前缀、且与 `amount` 符号一致 | **14 / 14** | ✅ **符号由 raw 携带**（可安全做有符号聚合） |
| `amount` 与 `raw` 的换算 | **≈1e18**（**13/14** 精确为 1e18；余 1 行是 f64 除法舍入，非另一套定标） | `amount = raw ÷ 10^decimals` |
| `signed_pnl_currency` 分布 | WETH **4** / SPY **8** / TZ **2** | ⚠️ **多币种** ⇒ 跨币种求和**没有意义** |

> **⚠️ 原始设想的一处必须修正**：把 `signed_pnl_raw` 当作「U256 的十进制字符串」会
> **得到完全错误的数量级**（把 `-0x2ee726109c1` 当十进制解析 ⇒ 读成约 -3.2e10，
> 而真值是 -3.22e-06）。**正确做法**：JSONL 与月度库
> **原样保留 `signed_pnl_raw` 的十六进制字符串**（**逐字节无损**），
> 额外的十进制派生字段**只在实现了精确的 hex→十进制换算并有逐位测试时才允许出现**。

| 字段 | 类型 | 权威性 | 处置 |
|---|---|---|---|
| `signed_pnl_raw` | `TEXT`（**带符号十六进制**） | ✅ **唯一权威** | JSONL 与月库**逐字节原样保留** |
| `signed_pnl_amount` | `REAL`（f64） | ❌ 派生值 | 保留（兼容既有读路径），但**只作展示**；判正负用 `raw` |
| `signed_pnl_currency` | `TEXT` | ✅ 分组键 | 聚合**必须按币种分组**（§5.5） |
| 派生十进制字符串 | `String` | 派生 | **可选**；未实现精确换算前**一律不写** |

> JSONL 行内**只写字符串**：`"signedPnlRaw": "-0x2ee726109c1"`。
> **不写** `"profit_usd": 3.50`（JSON 数字 = f64）—— 只写 `"profitUsd": "3.50"`。

### 3.7 反压与丢弃（对齐 `D-7`）

两条通道**分级**，因为两类记录的**可丢性不同**：

| 通道 | 容量 | 满时策略 | 理由 |
|---|---:|---|---|
| **JSONL 复核审计流** | 10,000 | **`try_send` 失败即丢弃** + `dropped` 计数 +1 | 审计流丢了**不影响正确性**，只影响「可追溯性」；**绝不能因此卡住复核物化** |
| **月度套利库** | 1,000 | **`send().await` 背压**（等待而非丢弃） | 套利记录**是核心资产**，**不可丢**；背压只会让广播线程慢一点，**不会让记录消失** |

> **与原始建议的一处刻意分歧**：原始建议写「套利记录……可以阻塞几毫秒等待写入，
> **或者强制同步写一次**」。本方案选 **`send().await` 背压**，不选「强制同步写」。理由：
> 「强制同步写」= 在持锁 / 持事务上下文里做磁盘 IO ⇒ **把磁盘延迟传导进主引擎**；
> `send().await` = **在通道处等**，等待发生在**独立任务**里 ⇒ 主引擎只是「稍后拿到结果」，**不持任何锁**。
> 两者最终都不丢数据，但**后者不会把 IO 延迟叠到套利计算上**。

### 3.8 保留期与清理

| 对象 | 保留期 | 清理方式 | 注意事项 |
|---|---:|---|---|
| JSONL 复核审计流 | **30 天**（`D-8`） | **按日期文件夹整目录删除** | **绝不**逐行改写；整目录删除天然规避「文件尾损坏」 |
| 月度套利库 | **永久**（不做自动清理） | 人工 / 显式命令 | 套利是**财务凭据**；自动清理必须先有人工审批（`D-8` 的取舍点） |

清理任务**必须**：① 只删 `review_record_jsonl/` 子树里的**日期文件夹**；
② **绝不触碰** `broadcast_transaction_db/`；③ 记录每次删除的
**路径清单与字节数**（审计台账落在 `record_maintenance/`）。

> **JSONL 格式硬约束**：**一行一个 JSON 对象（JSONL）**，**严禁**写成 JSON 数组。
> 数组格式下，文件尾部一次写入中断 ⇒ **整个文件不可解析**；JSONL 下最多损失最后一行。

## 五、相容性论证

### 5.1 读路径看不出差别

四类消费者读的都是**主库当前代**：

- 复核侧：主库仍写当前代（`manager_v4_reviews` 仍每代全量替换）⇒ `read_review_snapshot` / `read_review_page` **读到的内容与今天完全一致**；
- 广播侧：主库仍写**在途**行与**瘦身后的归档行** ⇒ `read_broadcast_status` / `read_broadcast_snapshot_page` **结构一致**。

⇒ **没有任何一个既有公开函数需要改签名** ⇒ 消费者 crate **零改动**。

### 5.2 幂等与门禁不被削弱

| 机制 | 位置 | 剥离后是否仍然有效 |
|---|---|---|
| **写请求幂等台账** | `manager_write_requests`（`find_write_request` / `persist_submit_write`） | ✅ **完全不受影响**（不在剥离范围，48 行） |

### 5.3 崩溃一致性（有序两步）

| 崩溃点 | 主库状态 | 月库状态 | 后果 |
|---|---|---|---|
| 写月库**之前** | 完整在途/终结行 | 无 | ✅ 安全：记录仍在主库，重启后可重放归档 |
| 写月库**成功**、瘦身主库**之前** | 完整行 | 完整行 | ✅ 安全：**两份都在**；下次归档用 `INSERT OR REPLACE` 幂等收敛 |
| 瘦身主库**之后** | 瘦身行 | 完整行 | ✅ 安全：判定列仍在主库，幂等锚点健在 |

**因此「先写月库、后动主库」是唯一允许的顺序**，且必须由守卫钉死。

### 5.4 「瘦身归档」而不是「删除 + 墓碑」（**重要修正**）

初稿曾设想「归档后删除主库行 + 留一行墓碑」。**实测 DDL 后此路不通**：

```sql
status  TEXT NOT NULL CHECK (status IN ('pending','success','failed'))
```

- `status` 的 CHECK **不允许**新增 `'archived'` 值 ⇒ 要加就要**改主库 DDL** ⇒ **越界**；
- 新增一张墓碑表 ⇒ **同样越界**（主库不能加表）。

⇒ 改为**瘦身归档**：

| 类别 | 列 | 归档后 |
|---|---|---|
| **保留**（判定 / 幂等 / 对账所需） | `attempt_id` · `loop_key` · `network/chain_id/protocol/scope_key` · `status` · `status_reason` · `tx_hash` · `signed_pnl_raw` · `signed_pnl_currency/unit/source` · `created_at` · `terminal_at` · `updated_at`（改为归档时刻） | 原样 |
| **清空**（体积大、判定不需要） | `path_addresses_json` · `path_symbols_json` · `pool_ids_json` · `hop_sqrt_price_limits_json` · `receipt_json` · `evidence_json` | `'[]'` / `'{}'` |

效果：主库行从 **~2–3 KB** 降到 **~250 B**；**零 DDL 变更、零迁移、零 CHECK 冲突**；
`attempt_id` 仍在 ⇒ 幂等锚点在；`status` / `tx_hash` / `signed_pnl_raw` 仍在 ⇒
**运行时的「这个闭环广播过」证据不丢**。

> **已知后果（如实记录）**：`read_broadcast_snapshot_page` 返回的是主库行 ⇒
> **已归档的尝试在页面上不再显示路径明细与回执原文**（仍显示 attempt_id / loop_key / 状态 / tx_hash / 盈亏）。
> 取回完整原文需查月度库。若要在 UI 上补这个能力，需要**新增** `broadcast_manager::read_archived_attempt()`
> **并**在 `manager_api` / UI 侧接线 ⇒ **超出本次范围**，本次**不做**，列为可选后续（§七 `Q-4`）。

### 5.5 跨月聚合的正确姿势（三条硬规则）

**规则 1 · 绝不跨币种求和。**
实测 `signed_pnl_currency` 有 WETH / SPY / TZ 三种 ⇒ 「过去 3 个月的总利润」这个说法
**本身不成立**（不同币种不可加）。正确口径是
**按币种分组，每组一个精确合计**：`{ "WETH": "-0x…", "SPY": "0x…" }`。

**规则 2 · 禁止在 SQL 里做金额聚合。**
SQLite 的 `SUM()` 对 `TEXT` 会做**数值转换**（十六进制串会被直接解析成 0 或错误值）。

```sql
-- ❌ 禁止：精度与格式双重错误
SELECT SUM(signed_pnl_raw) FROM trades;
-- ✅ 允许：只做筛选与取行，聚合在 Rust 侧做
SELECT signed_pnl_raw, signed_pnl_currency FROM trades WHERE ...;
```

**规则 3 · 聚合在 Rust 侧用任意精度做。**
流程：**逐个只读打开**各月库（**不** `ATTACH` 到主库连接）→ 逐行取出 `signed_pnl_raw` → 解析为
`alloy_primitives::U256`（**工作区已有依赖，不新增 crate**）→ 按符号做有符号加法
→ 输出**十六进制字符串**（与存储格式一致，**不引入十进制换算的误差面**）。

> **落地修正（v1.1）**：`broadcast_manager` **不需要** `alloy-primitives` ——
> 聚合实现落在 `review_manager::records`（那里**已有** `alloy-primitives` 依赖），
> 广播侧**只调用** ⇒ `broadcast_manager/Cargo.toml` **零改动**。
