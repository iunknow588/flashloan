# D-143 闭环引用有向池：核实结论与三处未收口

> **本文档是一次核实的读数，不是方案。**
> 它回答用户提出的两个问题（闭环是否只引用有向池；内存大对象的池子数组是否也是有向池），
> 并把核实过程中暴露的缺口登记成任务。

## 0. 一句话结论

**「闭环引用的是有向池」在管理层成立，并已实盘验证**；
**「内存大对象里的池子数组也是有向池」不成立** —— 运行时内核仍装载基础池。

| # | 命题 | 判定 | 依据 |
|---|---|---|---|
| 1 | 闭环的**选池**（池 / 方向 / 序位 / 依据）走有向池 | ✅ 实盘 **522/522** | §1.2 |
| 2 | 闭环的**容量**（单 tick + 深度）与 tick 状态走有向池行 | ✅ 代码级 | §1.3 |
| 3 | 基础池 id 在闭环里的角色 | ✅ 只是**查找键**，不是引用对象 | §1.2 |
| 4 | **内存大对象**的池子数组是有向池 | ❌ **仍是基础池**，零方向信息 | §2.1 |
| 5 | 闭环层不再直读基础池表 | ⚠️ 剩 **1** 处（USDG 估值），且是**有意的取舍** | §2.2 |
| 6 | 管理层流水线会**自动**重建 | ❌ 运行时重建的是**遗留表** | §2.3 |

## 1. 核实：闭环确实只引用有向池

### 1.1 数据面

闭环跳表 `manager_v4_closed_loop_hops` 每一行都带**方向层的行标识**：

```text
directional_pool_id   = dpool:v1:robinhood:4663:core4:<base_pool_id>:1
hop_direction         = 1
directional_scope_key = core4
directional_pool_rank = 1
pool_selection_basis  = directional_pair_direction_rank:1
pool_id / base_pool_id = <基础池 id>   ← 基础池是方向池的子对象，不是引用对象
```

**读数（实盘，2026-11-25）**：跳 **522** 行，
`directional_pool_id` 解析到唯一方向行 **522/522**（`inv-4` I-7）；
`hop_direction` 与该行方向一致 **522/522**（`inv-3` I-12）；
跳的 `base_pool_id` 与方向行的 `base_pool_id` 一致 **522/522**。

### 1.2 代码面：基础池 id 只是查找键

`closed_loop_manager/src/lib.rs`：

```text
build_hop_candidates(...)                                     :2480
  └─ resolve_hop_directional_pool(index, scope, base_pool_id, token_in, token_out)
        ├─ index.rows_of_base(scope, base_pool_id)            ← 用基础池 id 找方向行
        ├─ 选 input_token == token_in 的那一行（= 方向）        :2420
        └─ 返回 HopPool { directional_pool_id, direction, rank }

  └─ 主序（position == 0）解析失败 ⇒ InvalidStoredTopology（拓扑错误，直接中止）
  └─ 备用层：直接来自方向组的其余方向行（directional_{candidate|backup}_tier_rank:N）
  └─ order_hop_candidates_by_direction_rank(...)               :2560
        按方向层 pair_direction_rank 重排（纯置换，不改成员、不动门禁）
```

⇒ **基础池 id 的唯一用途是「到方向层里查一行」**。
跳真正携带的是方向行；`pool_id` / `base_pool_id` 两列只是为了保持基础池表的外键指向。

### 1.3 代码面：容量与 tick 状态全部来自方向行

```text
folded_path_capacity(...)        :2259
  └─ usable_tick_state(pool)     :2183
        pool.base.sqrt_price_x96 / liquidity / tick / fee / tick_spacing
        ↑ 全部取自方向行（base 子结构 = 投影进来的基础池事实）
  └─ pool.input_token_key_id() / output_token_key_id()   ← 由方向决定
     zero_for_one = pool.direction.zero_for_one()

folded_path_depth_capacity(...)  :2311
  └─ pool.base.depth_capacity_raw                        ← 同样取自方向行
```

⇒ 方向与容量**同出一行**，不可能错位。

## 2. 三处未收口（**核实中暴露的缺口**）

### 2.1 缺口 A：内存大对象的池子数组仍是**基础池**

用户口径：**「内存对象中的池子信息数组也是方向池子，不是基础池子」**。

**实测（不成立）**：`flashloan/rs-src/src/worker_pool.rs` 的 `V4PoolRegistry`

```text
sqlite_read::load_v4_exchange_pool_registry_rows()   sqlite_read.rs:74
  SELECT pool_id, token0, token1, pool_manager FROM v4_exchange_pools   ← 基础池表

V4PoolRegistry {
  pool_by_id: HashMap<String, PoolRegistryEntry>,   ← 键 = 基础池 id
  liquidity_by_id: HashMap<String, LiquidityRegistryEntry>,
  pool_ids_by_token: HashMap<String, HashSet<String>>,
}
PoolRegistryEntry { token0, token1, pool_manager }   ← 无方向、无容量、无序位
```

| 项 | 目标 | 现状 |
|---|---|---|
| 装载体 | `manager_v4_directional_exchange_pools` | `v4_exchange_pools` |
| 键 | `directional_pool_id` | 基础池 id |
| 行的内容 | 基础池事实 ＋ 方向 ＋ 容量 ＋ 序位 | 只有 `token0/token1/pool_manager` |

**为什么重要**：内核用它做路由测量（`pool_manager_for_selected_keys`、
`pool_ids_by_token`、零流动性剔除）。一条闭环的三跳**方向各不相同**，
而基础池 id 无法区分「同一基础池的高→低」与「低→高」两行 ——
方向只能靠代币序在运行时反推，这正是 `D-008` §3.3 说的「方向应该被物化出来的最强证据」。

**注**：`D-008` §3.1 的盘点表覆盖的是 **Rust 管理器 crate**，
**没有覆盖运行时内核（`rs-src`）的注册表** —— 这是盘点口径本身的缺口。

**登记**：→ `T-核.01`（新增模块 `M-13`）。

### 2.2 缺口 B：闭环层仍直读基础池表（**1 处，且是有意的取舍**）

```text
closed_loop_manager/src/lib.rs:1748  read_valuation_pool_states()
  ← FROM v4_exchange_pools_candidate_exchange / v4_exchange_pools_core4
  唯一消费者：usdg_valuation_for_token()  :2346  （USDG 估值 → 利润门禁的基准）
```

代码里已写明**为什么保留**（`:585` 起的注释）：

> 估值是**市场**属性而不是路由属性；把它收窄到方向层的合格子集，
> 会改变借款代币的 USDG 值，进而改变利润门禁 —— 所以它**故意**读基础池表的全集。

⇒ **这不是疏漏，是有意取舍**。但它带来一个**实测到的口径分裂**：

| 读数 | 值 |
|---|---|
| 估值读的 tick（基础池表 `updated_at`） | **2026-11-19** |
| 折叠读的 tick（方向行 `materialized_at`） | **2026-11-23** |
| 688 组可比行中 `sqrt_price_x96` 不同 | **314**（45.6 %） |
| 688 组可比行中 `tick` 不同 | **306**（44.5 %） |
| 522 跳在两张基础池表都查不到的 | **0**（覆盖完整） |

⇒ 代码注释里「估值与折叠**总是描述同一个快照**」这句话**已经不成立**。
它描述的是迁移 017 之前的状态；017 之后折叠读方向行、估值读基础池表，
两者**必然**是两个快照。

**修法不是收窄**（那会改利润门禁），而是**让估值读同一个快照**：
估值改读 `v4_exchange_pool_liquidity_snapshots`（方向层自身的投影源，
也是流动性 worker 刷新的**最新**一份），两者同源于同一张表 ⇒ 口径重新合一。

**登记**：→ `T-闭.02`。

### 2.3 缺口 C：管理层流水线**没有**接进运行时（**本轮最要紧的一条**）

实测（生产库，2026-11-25）：

| 表组 | 行数 | 最后更新 | 谁写的 |
|---|---:|---|---|
| `v4_closed_loops`（**遗留**） | **46** | 2026-11-25 **15:08 +08** | 运行时的 `v4_closed_loop_worker`（**Python** 遗留 builder） |
| `v4_closed_loop_hops`（**遗留**） | **138** | 同上 | 同上 |
| `manager_v4_closed_loops`（**管理器**） | **174** | 2026-11-25 **08:25 +08** | `closed_loop_manager`（Rust） |
| `manager_v4_closed_loop_hops`（**管理器**） | **522** | 同上 | 同上 |
| `manager_v4_closed_loop_optimizations`（**管理器**） | **472 → 503** | 2026-11-25 **18:14 +08** | 同上（本轮显式重建） |

**系统真正消费的是管理器表**（运行时内核 `load_manager_closed_loop_rows`、
复核层的方向交叉校验、广播层，全部读 `manager_v4_*`）。

**运行时维护链写的是遗留表**：`flashloan/src/dex/runtime/v4_maintenance_workers.py`
的 `run_closed_loop_build` 调 `core.db.builders.build_closed_loops_anchor`，
而该函数**只读写遗留表**（`dex_candidate_pool_recommendations` /
`market_observation_yz_pairs` / `v4_closed_loop*` / `v4_exchange_pools`）——
`builders.py` 里**没有一处** `manager_*` 表。

⇒ **后果**：迁移 017 落地后，运行时的维护 worker **永远不会**把新口径带进闭环；
上一轮「等运行时自动重建」的前提**不成立**。

**这也解释了 D-142 §9 的「重建不落地」**：不是重建慢，是**没有人在重建管理器闭环**。

**同时违反用户口径**：「python 侧没有自己的数据处理逻辑，仅仅使用内存对象中的实际值，
内存对象直接调用相关的管理工具（rust 实现）」——
`builders.build_all_anchor_data` 已经**正确地**委托给 Rust 内核
（`core.rs_bridge.build_v4_anchor_data`，并明确写「kernel 缺失是坏系统，
不是可以退回 Python 本地重建的模式」），
但 `run_closed_loop_build` 绕过它、直接调 Python 本地实现。

**登记**：→ `T-闭.02`（闭环层）与 `T-方.02`（方向层）。

## 5. 诚实边界

* §1 的判定来自**代码 + 实盘双向读数**，不是设计文档的复述。
* §2.1 的「为什么重要」是**推断**（方向在测量时按代币序反推），
**未**在本轮量化；量化归 `T-核.01`。
* §2.2 的「修法」（估值改读流动性快照表）是**建议**，**未实施**；
它会改变 USDG 估值口径 ⇒ 会改变利润门禁的读数 ⇒ 必须单独做 A/B 后再落地。
* §2.3 的事实部分（两张表组、最后更新时刻、写入方）**已实测**；
「谁应该重建」是**裁定**，归 `T-闭.02`。
* 本轮**未**触碰 `flashloan/src/core/db/builders.py`（并行施工保护），
因此 §2.3 的登记只落在**调用方**（运行时维护链）而不是被调用方。
