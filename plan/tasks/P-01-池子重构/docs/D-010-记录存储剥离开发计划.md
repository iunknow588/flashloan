### 3.1 `TASK-174`｜记录根目录解析与目录布局

**目标**：建立「主库路径 → 记录根目录」的**唯一确定性推导**，两个管理器共用。

**改动点**

| 文件 | 改动 |
|---|---|
| `review_manager/src/records.rs`（**新增**） | `pub fn store_directory_for(database_path: &Path) -> PathBuf`；`pub fn review_record_dir(...) -> Result<PathBuf, RecordError>`；`pub fn trade_record_dir(...) -> Result<PathBuf, RecordError>`；`pub fn maintenance_record_dir(...) -> PathBuf`；目录创建辅助 |
| `broadcast_manager` | **复用** `review_manager::records`（`broadcast_manager` 已依赖 `review-manager`，**不新增 crate、不复制实现**） |

**推导规则（定稿）**

```text
store_dir  = <主库路径>.parent()                       ← 主库**所在目录**
review_dir = store_dir / "review_record_jsonl"     / <链路> / <chain_id>
trade_dir  = store_dir / "broadcast_transaction_db" / <链路> / <chain_id>
maint_dir  = store_dir / "record_maintenance"
```

- 主库 `flashloan/db/local_store_4663.sqlite3` ⇒ 两棵记录树落在 `flashloan/db/` **之内**
  （`flashloan/db/review_record_jsonl/` 与 `flashloan/db/broadcast_transaction_db/`）
  ⇒ **一整个部署的历史只在一个目录里**，拷贝主库目录即带走全部记录；
- `parent()` 为空时**退化为当前目录**（`.`）并在启动日志打印实际解析结果；
- `<network>` 取现有 `network` 参数（现网为 `robinhood` / `mainnet` 等），`<chain_id>` 取现有 `chain_id` 参数
  ⇒ **不新增任何配置项**，**不新增任何公开函数参数**。

**验收 `AC-223`**

- [ ] 给定主库路径，解析结果与上表**逐字符一致**；
- [ ] `review_dir` / `trade_dir` 在首次写入时**自动创建**（`create_dir_all`）；
- [ ] 解析过程**不触碰主库**（不打开、不创建 `-wal`/`-shm`）；
- [ ] 单元测试覆盖：正常路径 · 单级父目录 · 无父目录（退化）· 含空格路径。

**函数签名（定稿 · 公开面就这四个）**

```rust
// review_manager/src/records.rs
/// The directory that holds the main store.  Pure: never touches the disk.
pub fn store_directory_for(database_path: &Path) -> PathBuf;

pub fn review_record_dir(database_path: &Path, network: &str, chain_id: i64) -> Result<PathBuf, RecordError>;
pub fn trade_record_dir(database_path: &Path, network: &str, chain_id: i64) -> Result<PathBuf, RecordError>;
pub fn maintenance_record_dir(database_path: &Path) -> PathBuf;
```

> **为什么 `review_record_dir` / `trade_record_dir` 返回 `Result`**：`<链路>` 会**变成目录名**，
> 而 `<链路>` 来自请求侧 ⇒ 必须先校验（**非空 / 非 `. ` ..` / 不含控制符与路径分隔符**），
> 否则一个 `../` 就能让调用方写到记录树之外。`chain_id <= 0` 同样拒绝。
> （纯函数**不会**失败的那个「记录根」推导因此保留为 `store_directory_for` —— 见 §2.1 · DD-3。）

**目录创建策略**

- **不在解析时创建**（解析是**纯函数**，便于单测）；
- 在**写任务首次落盘前**由写任务调用 `tokio::fs::create_dir_all`；
- 创建失败 ⇒ 写任务**记错误 + 计数**，**不崩主流程**；
- `create_dir_all` 是**幂等**的 ⇒ 重复调用无副作用。

**测试矩阵**

| # | 用例 | 期望 |
|---|---|---|
| 1 | `.../flashloan/db/local_store_4663.sqlite3` | 复核树 = `.../flashloan/db/review_record_jsonl`；广播树 = `.../flashloan/db/broadcast_transaction_db` |

### 3.2 `TASK-175`｜复核 JSONL 行模型与写入器

**目标**：定义复核审计流的**行格式**与**写入器**，一次实现、两端复用。

**行模型（schema `review_record.v1`）**

```json
{"schema":"review_record.v1","event":"upsert","observedAt":"2026-11-23T09:00:00Z","network":"robinhood","chainId":4663,"reviewVersion":25,"closedLoopVersion":17,"reviewChecksum":"0x…","loopKey":"…","reviewStatus":"…","reviewReason":"…","signedPnlRaw":"-0x2ee726109c1","signedPnlCurrency":"WETH","signedPnlUnit":"raw","signedPnlSource":"native_rust_ladder","pathSymbols":["A","B","C"],"poolIds":["0x…"],"capacityAnchorRaw":"…","capacityBindingPoolId":"0x…"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | 固定 `review_record.v1` ⇒ 未来改格式可识别 |
| `event` | ✅ | `upsert`（新增/变更）或 `removed`（本代消失） |
| `observedAt` | ✅ | **UTC** RFC3339（**不是**本地时区） |
| `reviewVersion` / `closedLoopVersion` / `reviewChecksum` | ✅ | **自证是哪一代**，可离线回放 |
| `loopKey` | ✅ | 复核身份键 |
| `signedPnlRaw` | ➖ | **原样十六进制字符串**；无盈亏时**省略**（不写 `null`） |
| `signedPnlCurrency` | ➖ | **多币种** ⇒ 聚合的分组键 |
| `pathSymbols` / `poolIds` | ➖ | 数组；**不写** `null`，无则省略 |

**写入器**

- 路径：`<store_dir>/review_record_jsonl/<链路>/<chain_id>/<YYYY-MM-DD>/<闭环>.jsonl`
  ⇒ **按日分片**（UTC）**且按方向闭环分文件**；
- 打开：`tokio::fs::OpenOptions::new().create(true).append(true)`；
- 写入：**一行一次 `write_all`**（含末尾 `\n`）⇒ **杜绝行内撕裂**；
- **强制 JSONL**：一行一个对象，**严禁** JSON 数组；

### 3.3 `TASK-176`｜JSONL 逐行增量与 `removed` 事件

**目标**：**只写变化**，不写全代快照。

**算法**

1. 在 `replace_review_rows` 的**事务内、`DELETE` 之前**读出旧行（`manager_v4_reviews` 当前 164 行，代价可忽略）；
2. 事务提交后，计算差异：
   - **新增 / 变更** ⇒ 产生 `upsert` 事件行；
   - **旧有新无** ⇒ 产生 `removed` 事件行（**必须**，否则审计流无法还原「这一代少了谁」）；
3. 若**整代 checksum 未变** ⇒ **一行都不写**（重复物化不产生审计噪声）；
4. 差异行 `try_send` 到通道（容量 **10,000**）。

**验收 `AC-225`**

- [ ] 同一代**连续物化两次** ⇒ JSONL **行数不增加**；
- [ ] 变更 1 条复核 ⇒ JSONL **只增加 1 条** `upsert`（不是全代重写）；
- [ ] 删除 1 条复核 ⇒ 增加 **1 条** `removed`，且含 `loopKey` 与 `reviewVersion`；
- [ ] 用 JSONL **可还原**任意一代的复核集合（逐 `reviewVersion` 回放验证）。

**差异算法（定稿）**

```rust
/// Compare the previous generation with the new one and produce the audit events.
pub fn diff_review_generations(
    previous: &[ReviewRowSnapshot],
    next: &[ReviewRowSnapshot],
    review_version: i64,
) -> Vec<ReviewRecordLine>;
```

1. **键**：`loop_key`（复核身份键）。若未来出现同键多行 ⇒ 改用
   `(loop_key, path_text)` 复合键，并在守卫中固定下来；
2. **比较字段**：`review_status` · `review_reason` · `signed_pnl_raw` ·
   `signed_pnl_currency/unit/source` · `path_symbols` · `pool_ids` ·
   `capacity_anchor_raw` · `capacity_binding_pool_id`；
3. **产出**：
   - 键只在 `next` ⇒ `upsert`；
   - 键只在 `previous` ⇒ `removed`；
   - 两边都有但**比较字段任一不同** ⇒ `upsert`（**不产出** `removed`）；
   - 两边都有且**完全相同** ⇒ **不产出任何行**；
4. **整代短路**：若新旧两代的 `materialized_checksum` **相同**
   ⇒ **一行都不产出**（**最外层**先判，省掉逐行比较）。

**「读旧行」放在哪里（关键）**

```text
① 开事务（IMMEDIATE）
② 【事务内】SELECT 旧行 → 快照到内存（164 行，代价可忽略）
③ DELETE 三表 → INSERT 当前代 → upsert 状态行
④ COMMIT                                        ← 权威落定
⑤ 【事务外】diff(旧快照, 新行) → try_send 到通道
```

> **为什么旧行必须在事务内读**：事务外的读会看到「已被别的事务删掉」或
> 「尚未提交」的中间态 ⇒ 差异集不准 ⇒ 审计流会描述一个**不存在的中间态**。
> **为什么 diff 在事务外算**：CPU 计算**不持有锁** ⇒ 不拖慢其它写者。

**测试矩阵**

| # | 用例 | 期望 |
|---|---|---|
| 1 | 同代物化 **2** 次 | JSONL **行数不增加**（checksum 短路） |
| 2 | 改 1 条的 `review_status` | 增加 **1** 条 `upsert`（**不是**全代） |
| 3 | 删 1 条 | 增加 **1** 条 `removed` |
| 4 | 改 1 条的 `signed_pnl_raw` | 增加 **1** 条 `upsert`，且 **raw 原样** |
| 5 | 一增一删同批 | 增加 **2** 条（1 upsert + 1 removed），**顺序稳定** |
| 6 | 全代为空 | 增加 **N** 条 `removed`（N = 旧行数） |
| 7 | **事务回滚** | JSONL **一行都不增加** |
| 8 | 旧行在**事务内**被读到 | 与事务外读到的**可能不同** ⇒ 测试须在**事务内**断言 |

### 3.4 `TASK-177`｜复核管理器接入与丢弃计数

**目标**：把写入器接进复核管理器，并让「丢了多少」**可见**。

**改动点**

| 位置 | 改动 |
|---|---|
| `review_manager/src/lib.rs` | ① `replace_review_rows` 提交后推流；② **新增** `pub fn read_review_record_health() -> ReviewRecordHealth` |
| `review_manager/src/records.rs` | 后台写任务（有界通道 + 独立写线程） |

```rust
pub struct ReviewRecordHealth {
    pub queued: usize,        // 当前排队待写的行数
    pub written: u64,        // 已成功落盘的行数
    pub dropped: u64,        // 因通道满而丢弃的行数  ← 可观测
    pub last_error: Option<String>,
}
```

**写入路径（硬性顺序）**

```text
① 主库事务（DELETE → INSERT → upsert 状态行）→ COMMIT      ← 权威，先提交
② 计算差异行
③ try_send(通道)  ├─ 成功 → 后台写线程落盘
                  └─ 失败（通道满）→ dropped += 1（**丢弃，不阻塞**）
```

- **JSONL 写在 COMMIT 之后** ⇒ 写失败**不回滚**主库；
- `try_send` **绝不阻塞** ⇒ 通道满时**丢弃 + 计数**，复核物化**不受影响**；
- 后台写任务跑在**独立线程 + 独立 current-thread runtime** ⇒
  **不要求调用方在 tokio runtime 内**（避免 `blocking_send` 在 runtime 内 panic，见 `R-9`）。

**验收 `AC-226`**

- [ ] `read_review_record_health()` **新增**且既有公开函数签名**一个都没改**；
- [ ] 通道满 ⇒ `dropped` 递增、**主库物化不阻塞**（用测量断言耗时上界）；
- [ ] 主库 COMMIT 失败 ⇒ **一行 JSONL 都不写**；
- [ ] JSONL 路径**不出现在任何门禁判据的读路径里**（源码级断言）。

**接入点（定稿 · 只碰两处）**

```rust
// review_manager/src/lib.rs —— materialize 路径
let transaction = connection.transaction_with_behavior(TransactionBehavior::Immediate)?;
let previous = read_review_rows_for_diff(&transaction, network, chain_id)?;  // ② 事务内读旧行

transaction.commit()?;                                                      // ④

let events = diff_review_generations(&previous, &desired_snapshot, result.review_version);

    if record_channel().try_send(event).is_err() {
        record_health().dropped.fetch_add(1, Ordering::Relaxed);
    }
}
```

> `replace_review_rows` 的**签名与内部 SQL 一字不改** ——
> 只在**调用方**多读一次旧行、多推一次事件。
> ⇒ **既有行为零变化**（回归可证）。

**写任务（后台线程 · 独立 runtime）**

```rust

    sender: tokio::sync::mpsc::Sender<ReviewRecordLine>,
    health: Arc<ReviewRecordHealth>,
}

    pub queued: AtomicUsize,
    pub written: AtomicU64,
    pub dropped: AtomicU64,
    pub write_errors: AtomicU64,
    pub last_error: Mutex<Option<String>>,

```

- 写任务跑在**独立 `std::thread`** + **独立 `current_thread` runtime**
  ⇒ **不要求调用方在 tokio runtime 内**（避免 `blocking_send` 在 runtime 内 panic，见 `R-9`）；
- **唯一消费者** ⇒ 写入**天然串行** ⇒ 文件**不会**交错；
- 进程退出时：`Drop` 里 **flush + 关句柄**（尽力而为，**不阻塞退出超过 1s**）。

**三级降级（反压 · 定稿）**

| 级 | 条件 | 动作 | 是否丢数据 |
|---|---|---|---|
| **1** | 通道**未满** | `try_send` 成功 | ❌ 不丢 |
| **2** | 通道**满** + **不在** tokio runtime 内 | `blocking_send`（**有界等待**） | ❌ 不丢（**可能阻塞调用线程**） |
| **3** | 通道**满** + **在** tokio runtime 内 | **单次同步兜底写**（当前线程直写文件） | ❌ 不丢（**不阻塞等待**） |

> **复核侧其实只会走到第 1 级**：复核 JSONL 是**可丢的审计流**，
> 所以本方案在**第 1 级失败时直接丢弃 + 计数**（**不升级到 2/3 级**）——
> 否则审计流会**反过来拖慢复核物化**。
> **第 2/3 级是给套利记录用的**（**不可丢**），见 §3.6。
> **一句话**：**可丢的流宁可丢，不可丢的流宁可等。**

| 5 | 进程正常退出 | 已入队数据**全部落盘**（flush 生效） |

### 3.5 `TASK-178`｜月度套利库（DDL 克隆 / roll-over）

**目标**：建立**与主库同构**的按月分库，**零手抄 schema**。

**改动点**

| 文件 | 改动 |
|---|---|
| `broadcast_manager/Cargo.toml` | 追加 `tokio = { workspace = true, features = ["fs","sync","time"] }`（当前**没有** tokio）；追加 `alloy-primitives.workspace = true`（跨月聚合用） |
| `broadcast_manager/src/records.rs`（**新增**） | 月库打开 / roll-over / DDL 克隆 / `ATTACH` |

**DDL 克隆（防漂移的关键）**

1. 从**主库**读 `SELECT sql FROM sqlite_master WHERE type='table' AND name IN ('manager_cow_execution_attempts','manager_broadcast_attempt_diagnostics')`；
2. 把 `CREATE TABLE ` 前缀改写为 `CREATE TABLE IF NOT EXISTS `，把 `CREATE INDEX ` 改写为 `CREATE INDEX IF NOT EXISTS`；
3. 在月库执行 ⇒ **月库 schema 与主库逐字符一致**（**不手抄、不新增表、不新增列**）。

**打开参数**

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 60000;
```

**Roll-over**

- 写入目标库 = **记录自身 `created_at` 的 UTC 月**（**发起月**，不是当前月）；
- 月份变化 ⇒ 对旧连接 `PRAGMA wal_checkpoint(TRUNCATE)` ⇒ `drop(conn)` ⇒ 打开新月库；
- **句柄切换必须安全**：旧连接 drop 之后**才**打开新库；
- 写入**全部由单一后台任务串行执行** ⇒ 月库**不会**出现并发写。

**验收 `AC-227`**

- [ ] 月库的 `sqlite_master.sql` **等于**主库对应表 SQL（逐字符比对）；
- [ ] 月库**零新表零新列**（`manager_db` / `schema_policy.json` **零 diff**）；
- [ ] 跨月归档 ⇒ 记录落在**发起月**的库，不是归档当月；
- [ ] roll-over 后旧库 `-wal` 被 checkpoint 且**文件句柄已释放**（可删除旧库文件即证）；
- [ ] `cargo build --offline --workspace` **exit 0**（**不引入新外部 crate**）。

**DDL 克隆算法（定稿 · 防漂移的关键）**

```rust
/// Read the live DDL from the main store and materialise it into the month store.
pub fn clone_schema_into(
    main: &Connection,
    month: &Connection,
    tables: &[&str],
) -> Result<(), BroadcastError>;
```

1. 从**主库**读 `SELECT name, sql FROM sqlite_master WHERE type='table' AND name IN (?)`；
2. 同样读 `type='index' AND tbl_name IN (?)`（索引**必须一起克隆**，否则跨月查询变慢）；
3. **改写规则**（唯一的改写点）：
   - `CREATE TABLE ` ⇒ `CREATE TABLE IF NOT EXISTS `
   - `CREATE TABLE IF NOT EXISTS ` ⇒ **原样**
   - `CREATE INDEX ` ⇒ `CREATE INDEX IF NOT EXISTS `
   - `CREATE UNIQUE INDEX ` ⇒ `CREATE UNIQUE INDEX IF NOT EXISTS`
   - **其余一律原样**（**不得**做任何其它改写）
4. 在月库**逐条执行** ⇒ 月库 schema **与主库逐字符一致**（除 `IF NOT EXISTS` 后缀）；
5. **主库缺表 ⇒ 直接报错**（**不得**跳过、**不得**自造表）。

> **为什么必须克隆、不能手抄**：手抄的 schema 会与主库**漂移**（主库加了列，月库没加）
> ⇒ 跨月查询与主库读数**不可比** ⇒ 财务账目对不上。
> **为什么不能改 `manager_db`**：迁移与 DDL **不在允许改动范围**内（用户明确要求主库信息维持不变）。

**月库打开参数**

```sql

PRAGMA foreign_keys = ON;
```

**Roll-over 状态机（定稿）**

```text

              │
              ▼
    ┌───────────────────────┐
    │ 当前句柄的月 == M ?   │──是──▶ 直接写
    └───────────┬───────────┘
                │否
                ▼

                ▼

                ▼

                ▼
             写 入
```

- **句柄切换必须安全**：旧连接 `drop` **之后**才打开新库（**禁止**两个句柄同时持有同一个文件）；
- 月归属 = **记录自身 `created_at` 的 UTC 月** ⇒ 跨月归档会**打开上个月的库**；

  ⇒ 直接解析即可；
- 解析失败 ⇒ **归档失败 + 计数**（**绝不**猜测月份）。

### 3.7 `TASK-180`｜跨月聚合与月归属判据

**目标**：支持「跨月查利润」，且**不跨币种、不丢精度**。

**改动点**：`broadcast_manager/src/records.rs` 新增

```rust

    -> Result<Vec<String>, BroadcastError>;              // ["2026_10", "2026_11"]
pub fn read_trade_archive_summary(database_path: &Path, network: &str, chain_id: i64)
    -> Result<TradeArchiveSummary, BroadcastError>;      // 按币种分组的精确合计
```

**聚合算法（三条硬规则，见技术方案 §5.5）**

1. **按币种分组** ⇒ `{ "WETH": "-0x…", "SPY": "0x…" }`，**绝不**给出一个跨币种的「总利润」；
2. **禁止 SQL `SUM()`** ⇒ 只在 SQL 里筛选 / 取行；
3. **Rust 侧任意精度** ⇒ `signed_pnl_raw` → `U256::from_str_radix(hex, 16)` → 按符号累加 → 输出**十六进制字符串**。

**`ATTACH` 纪律**

- `ATTACH` 只在**专用查询连接**上做（**不是**主库连接）⇒ 不污染主库连接状态；
- 用完立即 `DETACH`；
- 只读打开月库（`mode=ro`）⇒ **查询绝不写月库**。

**验收 `AC-229`**

- [ ] 跨 3 个月查询 ⇒ 结果**按币种分组**，与手工逐行累加**逐位相等**；
- [ ] 构造 **2^255** 量级的 `signed_pnl_raw` ⇒ 合计**逐位相等**（**不丢一位**）；
- [ ] `signed_pnl_currency` 不同的两行**不被加到一起**；
- [ ] 查询后**主库连接**未被 `ATTACH` 污染（连接状态断言）。

**API（定稿）**

```rust

    network: &str,
    chain_id: i64,

}
```

**聚合算法（定稿 · 三条硬规则）**

```rust

/// Add two signed magnitudes and render the result in the same signed hex form.

```

1. **按币种分组** ⇒ `signed_pnl_currency` 不同的行**绝不合并**
   （实测：WETH / SPY / TZ **三种**）；
2. **禁止在 SQL 里做金额聚合** ⇒ SQL 只做**筛选与取行**；
3. **Rust 侧任意精度** ⇒ `U256::from_str_radix(hex, 16)` + `checked_add` /
   `checked_sub` ⇒ 输出**带符号十六进制字符串**（**与存储格式一致**）。
