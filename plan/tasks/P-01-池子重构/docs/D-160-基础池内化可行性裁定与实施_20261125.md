# D-160 基础池内化：可行性裁定与实施

> **本文档回答一个裁定问题**：把基础池子数据直接做成方向池子的**内部对象**，
> 让外部拿不到裸基础池，从而「自然不会造成遗漏」——**这条路可行吗**。
>
> 依据：
> [`D-143 闭环引用有向池核实`](./D-143-闭环引用有向池核实与三处未收口_20261125.md)、
> [`D-008 内存对象与闭环引用链`](./D-008-内存对象与闭环引用链.md)、
> [`D-011 check_list`](./D-011-check_list_20261123.md)、
> [`D-014 未完成任务清单`](./D-014-未完成任务清单_20261123.md)。

---

## 0. 一句话结论

**可行，但成立的不是「封住基础池」，而是「封住裸基础池引用」。**

| # | 命题 | 判定 | 依据 |
|---|---|---|---|
| 1 | 方向池的身份已经是「基础池 ＋ 方向」，不可分割 | ✅ **已成立** | §1.1 |
| 2 | 基础池成为方向池的**私有内部对象**，外部拿不到对象本身 | ✅ **本轮落地** | §1.2 / §3.1 |
| 3 | 消费者**不可能**再持有「没有方向的基础池对象」 | ✅ **本轮落地**（编译期） | §2.1 |
| 4 | 序列化后的方向行**不含**嵌套的裸基础池对象 | ✅ **本轮落地**（序列化层） | §2.4 |
| 5 | 消费者**不可能**在 SQL 里引用裸基础池 | ❌ **封不住** ⇒ 靠审计 ＋ 守卫 | §2.3 |
| 6 | 基础池 id 本身可以隐藏 | ❌ **不该隐藏**（它是身份的一部分） | §3.1 |
| 7 | 链上事实（价格 / tick / 流动性）可以消失 | ❌ **它是基础池级的**，方向行里是**投影副本** | §3.2 |
| 8 | 基础池表可以删除 | ❌ **不能删**：池管理器要按基础池寻址链上状态 | §3.3 |

⇒ **裁定：采纳**，按 §5 的三步走；**第一步与第二步本轮已落地**，第三步登记为下一轮。

## 1. 现状：这件事已经完成了多少

### 1.1 标识层：**已经成立**（不需要再做）

`flashloan/tools/manager_contracts/src/ids.rs:274-328`：

```text
DirectionalPoolId = dpool:v1:{network}:{chain_id}:{scope_key}:{base_pool_id}:{direction}
                     └──────────── 身份不可分割 ────────────┘
访问器：base_pool_id() / direction() / scope_key()
FromStr 校验：direction 只能是 0 或 1；base 必须是 64 位 keccak
```

⇒ 外部拿到方向池 id，**拿不到「没有方向的基础池把手」**；
反过来，基础池 id 也推不出方向（同一基础池有**两个**方向行）。
**标识层无需改动**，这是「V4 池子 ＋ 方向值 ＝ 方向池子」最硬的一层。

### 1.2 契约对象层：**本轮从公开字段改成私有内部对象**

改动前：`flashloan/tools/manager_contracts/src/directional_pool.rs:185-186`

```rust
pub struct DirectionalPool {
    pub base: V4Pool,          // ← 任何 crate 都能把基础池整个拿走
    pub direction: PoolDirection,
    ..
}
```

改动后（**本轮落地**）：

```rust
pub struct DirectionalPool {
    base: V4Pool,             // ← 私有：外部拿不到基础池对象
    pub direction: PoolDirection,
    ..
}

// 只提供**标量**访问器，不提供 &V4Pool：
// base_pool_id() / pool_manager() / pool_key_json() / token0() / token1()
// token0_key_id() / token1_key_id() / fee() / tick_spacing() / hooks()
// sqrt_price_x96() / tick() / liquidity() / depth_capacity_raw()
```

**为什么不给一个返回 `&V4Pool` 的访问口**：那等于把封装原样打穿——
调用方一句 `let base = pool.base();` 就能把裸基础池存起来，
「外部无法访问」就只剩下一句注释。**标量访问器不带方向**这件事才是关键：
调用方能读到的每一个基础事实，**都只能从一个带方向的对象里读出来**。

**序列化边界也封住了**（`base` 标 `#[serde(flatten)]`）：
Rust 的私有字段**挡不住 serde** —— `#[derive(Serialize)]` 会把私有字段一并写出。
不处理的话方向池的 JSON 会是 `{ "base": { … }, "direction": 0, … }`，
那个 `"base"` 子对象对读者来说**就是一个裸基础池的把手** ⇒ 详见 §2.4。

### 1.3 内核层：**已经是私有结构**（另一个线程在处理，不在本轮范围）

`flashloan/rs-src/src/worker_pool.rs:251-281`：

```rust
struct BasePoolFacts { .. }                            // 模块私有类型
struct DirectionalPool { .., base: BasePoolFacts, .. }  // base 私有字段
struct V4PoolRegistry {
    directional_by_id: HashMap<String, DirectionalPool>, // 池数组 ＝ 方向池
    base_by_id: HashMap<String, BasePoolFacts>,          // 由方向行**派生**的索引
    ..
}
```

⇒ 内核的「内存大对象池数组是方向池」这条**已成立**（`D-159` 有实测读数）；
`base_by_id` 只是**派生索引**，不构成第二个数组，也不对外暴露。

### 1.4 存储层：**方向行是自足的**（已成立）

`manager_v4_directional_exchange_pools` 每一行携带：

```text
基础池静态事实 9 列：pool_manager / pool_key_json / token0 / token1
                     token0_key_id / token1_key_id / fee / tick_spacing / hooks
快照事实 4 列：      sqrt_price_x96 / tick / liquidity / depth_capacity_raw
方向事实 6 列：      direction / zero_for_one / input_capacity_raw
                     input_capacity_measured / pair_direction_rank / pool_status
```

⇒ 消费者**只读方向表**就能拿到全部事实，**不需要**再查基础池表。

## 2. 「内化」到底封住了什么

用户口径是「外部无法访问，自然不会造成遗漏」。这句话要拆成三种**遗漏**：

| 遗漏形态 | 真实含义 | 内化能否封住 | 现状 |
|---|---|---|---|
| **引用遗漏** | 消费者拿基础池 id 建了一个**没有方向**的闭环 / 跳 | ✅ 能 | 018 迁移把跳表 `pool_id` / `base_pool_id` **删掉**，`directional_pool_id` **NOT NULL** ⇒ 结构上写不出来 |
| **方向遗漏** | 同一基础池的两个方向行各自漂移 | ⚠️ 不能靠封装 | 已由方向层投影不变式覆盖（`compare_directional_pools` 的 I-9 比对 9 列基础事实，`D-011` §4） |
| **事实遗漏** | 方向行缺价格 / 流动性，被当成「测得为零」 | ⚠️ 不能靠封装 | 层内已用 `input_capacity_measured` 等「已测量」标记区分（`D-011` §4「未测量 ≠ 零」） |

### 2.1 引用遗漏：**从「约定」变成「编译错误」**

改动前，闭环层要写一行跳，得先决定「我到底持有一个基础池还是一个方向池」——
而这个决定是**开放式的**，写错编译器不会管。改动后：

```text
消费者想读基础事实 → 必须先拿到 DirectionalPool → 方向是它的固有属性
消费者想传一个基础池给别人 → 传不了（拿不到 &V4Pool）
消费者想把方向丢掉只留基础池 → 做不到（没有这样的构造）
```

### 2.2 一个**真实的遗漏案例**（本轮实测发现）

`flashloan/tools/pool_manager/src/baseline_audit.rs:681`（改动前）：

```sql
-- 闭环跳引用的基础池必须存在
AND NOT EXISTS (SELECT 1 FROM v4_exchange_pools_candidate_exchange p
                WHERE .. AND p.pool_id = h.pool_id)
```

⇒ **一个消费者在闭环跳表上按基础池 id 引用池子**——
而闭环跳表在 018 之后**已经没有 `pool_id` 这一列了** ⇒ 这条 SQL 会在实盘上直接
报 `no such column: h.pool_id`。

**这正是用户担心的「遗漏」**：靠约定时，一个消费者改了形状、另一个没跟上，
要等到运行时才炸。本轮已把它改成**方向层可解析性检查**（§5 第 ② 步）。

### 2.3 封不住的越狱通道：**SQL 与 Python**

**Rust 隐私只管编译期。** 三条通道能绕过它：

| 通道 | 事实 | 对策 |
|---|---|---|
| **SQL 字符串** | 任何消费者都能 `SELECT ... FROM v4_exchange_pools_core4`；类型系统管不到字符串 | ① 迁移的**结构约束**（列 NOT NULL / 删列）② **审计器**（引用可解析性）③ **架构守卫**（静态扫描消费 SQL） |
| **Python 扩展** | 内核导出的诊断负载里仍有 `basePoolId`（`worker_pool.rs:743`） | 归**内核线程**（内核一次性存储改造）负责；Python 侧只读内存对象的实际值，不做自己的数据处理 |
| **遗留表** | `v4_closed_loops` / `v4_closed_loop_hops`（Python 遗留写路径）仍是基础池形状 | 遗留写路径**已退出**维护流水线（`run_closed_loop_build` 不再回退）⇒ 登记为遗留下线项（§6） |

⇒ **结论**：「内化」是**必要但不充分**的一层。真正的防线是三层叠加：

```text
类型层（私有字段）── 结构层（NOT NULL / 删列）── 审计层（可解析性检查 ＋ 静态守卫）
```

### 2.4 序列化边界：嵌套的 `"base"` **也是一把把手**（本轮补上）

Rust 的**私有字段挡不住 serde**：`#[derive(Serialize)]` 会把私有字段**一并写出**。
不处理的话，方向池的 JSON 形状是：

```json
{ "base": { "basePoolId": "0x…", "token0": "0x…", … }, "direction": 0, … }
```

那个 `"base"` 子对象对读者来说**就是一个裸基础池的把手** ——
拿它就能重新按基础池 id 建闭环，正是本任务要消灭的形状。
（**当前无实际暴露**：`DirectionalPool` 今天**没有任何地方被序列化**；
但「靠没人调用」来保证边界，正是本任务要消灭的那种约定。）

⇒ 本轮把 `base` 标成 `#[serde(flatten)]`：**JSON 本身就是一行方向行**
（基础事实以**投影副本**的形式平铺，与数据库方向行的形状一致），
**没有子对象可拿** ⇒ 序列化边界与类型层边界**同形**。

守卫 `test_the_base_pool_is_an_internal_object_of_the_directional_pool` 现在**同时**断言：
① `base` **私有** ② 契约里**零** `&V4Pool` 出口 ③ `base` **被 flatten**（无嵌套基础池对象）。
契约内单测 `the_serialized_row_is_a_direction_row_and_carries_no_base_object`
断言序列化结果**没有 `"base"` 键**、基础事实平铺在行内、且**往返可重建**。

## 3. 封不住的三件事（诚实边界）

### 3.1 基础池 id **必须**可见

基础池 id 是**方向池身份的一部分**（`dpool:v1:...:{base}:{dir}`），也是：

- 幂等键与回执关联的锚；
- 两个方向行「同源」的判据（`by_base` 索引、投影不变式比对）；
- 审计追溯（从链上池追到某次广播）的唯一线索。

⇒ 隐藏它会**破坏可追溯性**，与「要么成功要么失败」的口径相悖。
**本轮的做法**：基础池 id 以**标量**形式从方向池读出（`base_pool_id()`），
但**没有任何 API 能单独持有一个基础池**。

### 3.2 链上事实是**基础池级**的，方向行里是**投影副本**

价格 / tick / 流动性随池变化，**与方向无关**：同一基础池的两个方向行携带同一份值。
这意味着：

- 方向行里的事实是**副本**，副本可能与源不同步 ⇒ 必须有「**单一写者 ＋ 投影不变式**」守护；
- 现状的写者是**方向层**（`directional_pool_manager` 从基础池表投影），
  不变式由 `compare_directional_pools` 的 I-9 检查（实盘读数：不一致 **0** 行）；
- **残留缺口（下一轮）**：复核层的**定价事实**仍按基础池 id 从快照表读
  （`review_manager` 的 `read_pool_parity_states`）⇒ 复核层仍「知道」基础池 id。
  改法见 §5 第 ③ 步。

### 3.3 基础池表**不能删**

池管理器必须按**基础池**寻址链上事实：PoolManager ＋ poolId 是合约级身份，
tick / bitmap 是基础池级索引，流动性快照按基础池 id 落库。

⇒ 正确的目标不是「消灭基础池」，而是「**基础池对外封闭**」：

```text
写者：池管理器（基础池级）──→ 方向层（投影）──→ 消费者（只读方向行）
```

## 4. 与用户既有口径的一致性

| 用户口径 | 本裁定下的落点 |
|---|---|
| 「闭环引用的是有向池」 | ✅ 闭环层**只留** `directional_pool_id` / `hop_direction` / `directional_scope_key`；基础池 id **只作为方向行的属性**出现 |
| 「内存对象中的池子信息数组也是方向池」 | ✅ 内核 `directional_by_id` 是唯一池数组；`base_by_id` 是派生索引 |
| 「新的系统闭环对象，只包含三个方向池子」 | ✅ 018 迁移把闭环体与跳表的**基础池列全部删掉** |
| 「要么成功，要么失败，没有降级处理」 | ✅ 018 **删列**而非「置空兼容」；跳表重建后 `directional_pool_id` **NOT NULL**；写不进去就直接失败 |
| 「固定费率 / 无 hook 的池子约定不被突破」 | ✅ 方向层不投影动态费率与带 hook 的池；本轮改动不触碰该判定 |

## 8. 一句话给使用者

> **可以做，而且已经做了大半**：方向池的身份本来就把方向焊死在身份里，
> 本轮把「基础池」从公开字段改成私有内部对象，闭环层与复核层全部改走访问器，
> 跳表在存储层删掉基础池列并把方向列设为必填。
>
> **但要清楚它封不住什么**：基础池 id 仍然是身份的一部分（要留），
> 价格与流动性天生是基础池级的事实（方向行里是投影副本），
> 池管理器仍要保留基础池级入口（它按基础池寻址链上数据）。
>
> **真正的防线是三层**：私有字段（编译期）＋ 存储约束（结构上写不出）＋
> 审计与守卫（SQL 绕过去时判红）。缺任何一层，「自然不会遗漏」都只是愿望。
