## 3. 决策依据（三条 · 全部可复算）

### 3.1 依据一：`rank` 现在是**活排序键**，不是旧排序的载体

**代码事实**（2026-11-25 当前工作区读数）：

| # | 位置 | 事实 | 角色 |
|---:|---|---|---|
| 1 | `candidate_edge_pool_manager/src/lib.rs:1381` | `rank: offset + 1` | **写入方** —— 由方向层排序结果派生的**组内稠密序号** |
| 2 | `candidate_edge_pool_manager/src/lib.rs:1386` | `selection_basis = SELECTION_BASIS_DIRECTIONAL_PAIR_DIRECTION_RANK` | 口径标签 |
| 3 | `candidate_edge_pool_manager/src/lib.rs:1183-1194` | `recommendations_from_ranking`：**先按方向层 rank 排序**（`left.1.cmp(&right.1).then_with(pool_id)`），再按 `MAX_RECOMMENDATIONS_PER_HOP` 截断 | **排序来源 ＝ 方向层** |
| 4 | `closed_loop_manager/src/lib.rs:1582` / `:1586` | `SELECT ... rank ... ORDER BY anchor_token_key_id, candidate_token_key_id, hop, rank` | **消费方 · 排序键** |
| 5 | `closed_loop_manager/src/lib.rs:1610` | `if recommendation.rank == 0 { return Err(InvalidStoredTopology(...)) }` | **消费方 · 有效性校验** |
| 6 | `closed_loop_manager/src/lib.rs:2749` | `recommendations.sort_by_key(|recommendation| recommendation.rank)` | **消费方 · 排序** |

⇒ **`rank` 的语义已从「旧排序（`liquidity_index` 代理）的序位」换成「方向层序位的派生组内序号」。**
⇒ 它**不再承载旧排序** ⇒ 删它**不是**「旧排序下线」的必要条件。

### 3.2 依据二：`depth_score` **不能**替代 `rank`

`depth_score` 是唯一「看起来像能替代」的列（两者都源自方向层序位），但**实测不可替代**：

| 读数（实盘 · 只读） | 值 | 含义 |
|---|---:|---|
| `rank` 在 PRIMARY KEY 里 | **true** | PK ＝ `network, chain_id, protocol, scope_key, anchor_token_key_id, candidate_token_key_id, hop, rank` |
| 组数（anchor × candidate × hop） | **216** | — |
| `rank` **稠密 1..N** 的组 | **216 / 216** | 无缺口、无并列 |
| `rank` 起点为 1 的组 | **216 / 216** | — |
| `rank = 0` 的行 | **0** | 闭环层的有效性校验**依赖**该列存在 |
| `depth_score IS NULL` 的行 | **0** | 但列定义是 `REAL`（**可空**） |
| `depth_score` **与 `rank` 相等**的行 | **0 / 340** | 两列**从不**相等 |
| `depth_score` 与 `rank` **排序不一致**的组 | **82 / 216** | ⇒ **`depth_score` 不是 `rank` 的替代排序键** |
| 方向层 `pair_direction_rank` **组内重复**的组 | **0** | 方向层自身无并列 |

**为什么不可替代（三条硬理由）**：

1. **唯一性**：PK 的最后一列是 `rank` ⇒ 它必须**组内唯一**。`depth_score` 是 `REAL`（SQLite 浮点，**不可**承担主键去重）且**可并列** ⇒ 不能顶替 PK 位置。
2. **稠密性**：`rank` 是 **1..N 稠密序号**（**216/216** 组）；`depth_score` 携带的是方向层**原值**，可带缺口 ⇒ 两者不是同一个量。
3. **排序等价性**：实测 **82/216** 组两者排序不一致 ⇒ 直接换列会**改变闭环的候选次序**。

> ⚠️ **诚实边界**：以上排序读数取自**活表**，而活表**尚未**被新生产者刷新
> （`selection_basis` 仍全为 `direction_single_tick_exact_output_then_tick_fee_pool_id` **340/340**，
> 最后写入 **2026-11-24 08:41:55 UTC** ＝ **16:41:55 +08**）⇒
> **活表的 `rank` / `depth_score` 仍是旧口径的值**。
> 因此「82/216 组排序不一致」证明的是**「今天这两列不等价」**；
> 而「新口径下 `rank` 仍是活排序键」是由 §3.1 的**代码事实**证明的（与是否已上线无关）。
> **两个依据相互独立，结论不依赖活表是否刷新。**

### 3.3 依据三：删除动作的**净收益为负**

| 成本 | 说明 |
|---|---|
| **必须重建表** | `rank` 在 PRIMARY KEY 里 ⇒ SQLite `ALTER TABLE DROP COLUMN` 直接报 `cannot drop PRIMARY KEY column` ⇒ 需「建新表 → 拷数据 → 换名 → 重建索引/触发器」 |
| **必须换掉闭环层的排序键** | 需改 `closed_loop_manager` 的 `ORDER BY` / `sort_by_key` / `rank == 0` 校验（**`M-4` 越界**） |
| **失去唯一性来源** | 新 PK 需要另一个**组内唯一**的列；`depth_score` 不满足（§3.2） |
| **不带来任何口径收益** | 删它**不会**让系统更接近「单一排序真相源」—— 真相源**已经是**方向层；`rank` 只是它的**投影** |

⇒ **裁定：保留。** 「删 `rank` 列」**不是**死代码清理，而是**拆除一条正在服役的排序契约**。
