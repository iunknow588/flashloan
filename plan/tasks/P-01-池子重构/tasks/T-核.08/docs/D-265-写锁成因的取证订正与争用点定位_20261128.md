## 2. ★ 订正一：那条计数**不是**整表扫描（实测 **0.47 s**）

探针：`plan/runtime_evidence/tools/probe_legacy_count_cost_20261128.py`（只读连接 ＋ 进度处理器 5 s 预算 ＋ `EXPLAIN QUERY PLAN`）。

```
语句      SELECT COUNT(*) FROM cow_execution_reviews WHERE network = ? AND chain_id = ?
计划      SEARCH cow_execution_reviews USING COVERING INDEX
          idx_cow_execution_reviews_scope_profit_source_created (network=? AND chain_id=?)
读数      count = 125,317     elapsed = 0.469 s     abortedByBudget = false
```

表上四个索引，其中 `idx_cow_execution_reviews_scope_profit_source_created` **就是为了不做整表读而建的** ——
`pool_manager/src/lib.rs:1004-1011` 的注释写得很清楚：

> 「Without an index that column is scanned for every aggregate, so the breakdown degenerates into a full table read.」

⇒ **18.01 GB 是那张表的体积，不是这条语句要读的量**：覆盖索引里只有索引项，**0.47 s** 读完。

⇒ **订正**：`B7` 的「一次计数按住写锁几分钟」**不成立**。真实代价是 **0.47 s 的写锁占用**（且只在 apply 分支里）。

## 3. ★ 订正二：复核发布的链上测量**不在**写事务里（代码自证）

`D-245` §11.6 写的是「链上测量被放进了写事务」。在**复核发布这条路径上**它不成立：

| 步骤 | 位置 | 是否在写事务内 |
|---|---|---|
| 链上测量（`route_pool_states_by_loop`，eth_call，timeout **20 s**） | `worker_pool.rs:2546` | **否**（在事务之前） |
| 证据装配（`build_route_evidence`） | `worker_pool.rs:2547` | 否 |
| 发布（`publish_review_loops` → `run_reviews_write`） | `worker_pool.rs:2584` → `review_publish.rs:637` | 事务在这里才**开**（`review_manager/src/lib.rs:896`） |

⇒ 写事务里只有「读目录 ＋ 写复核行」，**没有链上调用**。

## 4. ★ 落点与实施待办（**方案已定，代码未动**）

### 4.1 改法（写在文件与函数级，实施时按此改）

`flashloan/tools/review_manager/src/lib.rs`：

1. `delete_from_optional_manager_table` 改为**返回删除行数**（`execute()` 的返回值），不再是「删完就完」。
2. **apply 分支**（`clear_review_records_write`）改成：先删、再用**删除行数**当计数器，**不再调用** `prepare_clear_result`（那条路径里的三处 `COUNT(*)` 与 legacy 的整表计数全部消失）。

⇒ **写锁的持有时间不再包含任何计数**；计数口径**不变**（删除行数 ＝ 同一谓词下的 `COUNT(*)`）。

### 4.2 验收口径（实施时必须一起交付）

## 5. 方法学边界：**WAL 看不到那条长事务**

`read_wal_open_transaction_20261128.py` 在 **150 s** 内每 **50 ms** 采样一次 WAL（`probe_write_lock_holder_tables_20261128.py`）：

```
frames = 1012      openFrames = 0（每一次采样，最后一帧都是提交帧）
walRootPages: manager_review_library_state 29 · manager_v4_reviews 27 · kv_meta 16
              dex_candidate_pools 10 · dex_candidate_abnormal_pools 6
              manager_v4_review_diagnostics 5 · manager_write_requests 1
```

⇒ **打开的事务在 WAL 里从未可见**。原因不是「没有长事务」，而是 SQLite 在 WAL 模式下**在提交那一刻**才把页写进 WAL：
一个「开了很久、最后才写页」的事务，在 WAL 里只留下最后一瞬间。

⇒ **WAL 能回答「哪些表被写了」，回答不了「谁持锁持了多久」** —— 这是方法边界，不是读数缺陷。

## 6. ★ 定位：争用发生在 **Python 业务写层**，不在复核层

`plan/runtime_evidence/tools/probe_runtime_thread_duty_20261128.py`（py-spy 连续 **40** 次采样，间隔 **1.5 s**，共 **68.5 s**）：

| 线程 | 最内层帧 | 占空比 |
|---|---|---|
| `v4-maintenance-v4_pool_liquidity_worker` | **`_write_transaction (core\db\storage_business_io.py:53)`** | **100 %** |
| `dex-closed-loop-watchdog` | **同上** | **82.5 %** |
| `dex-opportunity-scanner` | **同上**（另 **17.5 %** 在 `submit_group`） | **80 %** |
| 其余维护槽 | `_run_one (v4_maintenance_workers.py:1230)`（**排队等进程内的写锁**） | 100 % |

`core/db/storage_business_io.py` 的写法是：

```python
_WRITE_BUSY_TIMEOUT_MS = 60000          # L23：等锁预算 60 s

@contextmanager
def _write_transaction(connection):      # L44
    connection.execute("BEGIN IMMEDIATE")   # L53：★ 三个线程 80–100 % 卡在这一行
```

⇒ **这三个线程不是在写，它们在排队等写锁**：`BEGIN IMMEDIATE` 在锁被占时**阻塞到 60 s 预算耗尽**。
其余维护槽卡在 `_run_one` 的 `with _sqlite_consumer_lock(...)` 上 —— 那是**进程内**的写锁，被上面那一个线程占着，于是**整条维护流水线排队**。

⇒ **写锁饱和的形状是「队列」而不是「一个长持有者」**：每个提交之后立刻有下一个写者接手，外部探针 8 s 内 **0 %** 空闲（`D-264` §2.3）。
