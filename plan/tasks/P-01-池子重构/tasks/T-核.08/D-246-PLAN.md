## 1. 缺陷（**生产在产 · 只读实测已复现**）

主库的写锁被**常年占住**，管理器与运行时的写接口整片 `503 database is locked`。

| 读数（2026-11-28 · 生产库只读） | 值 |
|---|---|
| 主库 | `flashloan/db/local_store_4663.sqlite3` **18.83 GiB**（WAL 8.35 MB） |
| 写锁探针（`busy_timeout=500 ms`，12 次 / 2 s） | **12 / 12 全锁**（每次约 0.62 s 即超时） |
| 写锁 ＋ 检查点对齐探针（90 次 / 1 s） | **89 / 90 锁**、**0** 次检查点 ⇒ **排除检查点阻塞** |
| 长预算探针（`busy_timeout=30 s`） | 一次等 **33 s** 仍超时、一次 **7.255 s** 才拿到 ⇒ 存在**长事务** |
| 运行时自身 | `closed-loop runtime state sync failed: database is locked`（`record_state_from_attempts` → `BEGIN IMMEDIATE`） |
| 复核刷新 | `reviewCycleClaim` → **503** `UPSTREAM_UNAVAILABLE` / `database is locked` / `retryable: true` |

**已证实的与未证实的（不得混写）**：

* **已证实**：写锁**几乎连续**被占；持锁方是**运行时的连续写流量**（12 条常驻闭环 worker 的状态转移，每条转移一次 `BEGIN IMMEDIATE`）**加上**管理器的级联整块重写；大对象表本身很小（`v4_exchange_pools` **2 550** 行、`manager_v4_directional_exchange_pools` **464**、`manager_v4_closed_loop_hops` **144**）⇒ **长事务不是「行多」造成的**。
* **未证实（只是推断）**：「测量与写入被放进同一段写事务」。本任务的第一步就是**把这件事测出来**，而不是先改它。

## 3. 目标状态（**可验收**）

1. **测量在写事务之外**：链上测量（RPC / 报价 / 容量探测）全部发生在**没有持有写锁**的时段；写事务里**只落结果**。
2. **一轮一次写事务**：一轮的状态写入**合并**成一次（或每闭环一次）**短**事务，而不是 N 次。
3. **忙等分级**：状态类写入用**短** busy timeout（快失败 ＋ 可重试），只有大对象整块重写才配 60 s。
4. **可观测**：写事务**次数**与**持有时长**进运行时状态（只加指标，不改判定）。

## 4. 步骤（**每步都有退出条件**）

| 步 | 做什么 | 退出条件 |
|---|---|---|
| **S1 取证** | 给写事务加**计数与持有时长**指标（`storage_business_io` 侧），并在运行时快照里读出 | 快照里能看到「每轮写事务次数 / 持有时长 p50 / p95 / 最长」 |
| **S2 定序** | 记录**测量开始/结束**与**写事务开始/结束**两个时间戳，判定测量是否落在写事务区间内 | 给出「测量落在写事务内」的**比例**（期望 **0**；非 0 则先改这一处） |
| **S3 外置** | 把落在写事务内的测量搬出去：先测量、再一次性落结果 | 测量区间与写事务区间**不重叠**（按 S2 的口径复测） |
| **S4 合并** | 一轮的状态写入合并成一次 `executemany` / `transaction` | 一轮的**写事务次数**从「数十次」降到「个位数」 |
| **S5 分级** | 状态类写入的 busy timeout 降到**秒级**，大对象重写保留 60 s | 状态写入失败时**快**失败并重试，而不是占着 60 s |
| **S6 回归** | 只跑 `M-13` 相关测试 ＋ 只读探针 | `M-13` 测试 **0 failed**；写锁探针读数入报告 |
| **S7 实盘** | 在产观察 3 个连续 ≥30 分钟窗口 | 写锁占用率下降、复核刷新 **503** 计数 **0**、代次**继续前进** |
