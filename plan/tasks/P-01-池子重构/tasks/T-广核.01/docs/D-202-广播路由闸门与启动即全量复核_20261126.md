## 1. 起点：一个**错**的结论，和它错在哪

我此前说「**一轮复核要跑约 49 分钟**」。用户指出「多复核工作线程并发，不可能需要这么长时间」——**用户是对的**。

**那个 49 分钟是什么**：我在 `manager_v4_reviews` 里取两条 `reviewed_at` 相减，量到 **48.1 min**
（**12:01 → 12:49**）。那是**停机窗口**，不是复核耗时 —— 库里这段时间**没有**复核在跑。

**库里根本没有「轮次」这个概念**：`manager_v4_reviews` 主键
`(network, chain_id, protocol, scope_key, loop_key)` ＝ **单槽**，永远 **174** 行；
`manager_v4_review_broadcast_requests` 同样**单槽**（每闭环 **1** 行）。
⇒ 用户口径「**任何一个闭环，第二次复核出现结果，必然覆盖前一次闭环的结果**，这样，每个闭环仅仅有一个当前的复核结果」
**是系统语义本身**，不是缺陷。

**稳态真实节奏**（append-only JSONL `flashloan/db/review_record_jsonl/robinhood/4663/2026-11-26/`）：
稳态每 5 分钟触达 **84** 个闭环（峰值 **143**）⇒ 174 闭环全覆盖实测 **13.6 / 13.9 / 25.8 min**；
单闭环重评间隔中位 **4.06 min**（p25 **2.32** / p75 **5.94** / p90 **23.08** / p99 **96.32**）。

**「看起来慢」的三个真因**（此前被误当成「复核慢」）：

| 真因 | 读数 |
|---|---|
| **停机窗口** | 11-25 **02:35 → 08:08** ＝ **333 min**；11-26 **08:29 → 09:33** ＝ **63 min**、**11:15 → 11:35** ＝ **20 min**、**12:01 → 12:49** ＝ **48 min** |
| **重启后爬坡** | 06:05 每 5 分钟仅 **24** 个闭环 ⇒ 08:00 才 **143** |
| **优先偏斜长尾** | **110/174** 闭环当日发布 **> 20** 次（最多 **150** 次）；p99 ＝ **96 min** |

**顺带作废一条旧推理**：`D-195` §3.4 的「一轮 ≈ **40 min**（48/174 条 / 11 min）」是**爬坡期抽样**，稳态快 **4–7** 倍。
原缺省 **5400 s** 陈旧窗口的**结论仍安全**（**90 min** > **26 min**），但真正该比的是
**单闭环重评间隔的尾部（p99 ≈ 96 min）**，不是轮次长度。

## 2. 一轮复核的真实耗时：**5.4 min**，以及它**卡在哪**

### 2.1 三个候选，按实测排除

#### 候选 A：复核线程不够并发 —— **不是**

`/api/status` ⇒ `dex_opportunity_scanner.closedLoop`：**`activeConcurrency = 16`、`concurrencyLimit = 16`**（第一代实例）。
来源：`closed_loop_state_machine.py:2647 CLOSED_LOOP_WORKER_DEFAULT = 16`；上限 `worker_pool.rs:845 CLOSED_LOOP_WORKER_CEILING = 256`；
`.env` **未覆盖** `DEX_CLOSED_LOOP_MAX_WORKERS`。

**★ 后续订正（22:05:01 起的新实例）**：算子把 `DEX_CLOSED_LOOP_MAX_WORKERS` 设为 **48**，
但 Python 侧 `max_workers_override()` 取 `min(CLOSED_LOOP_WORKER_CEILING = 32, 48) = **32**`
（`closed_loop_state_machine.py:2648 / :2680`）⇒ 实盘读数 **`concurrencyLimit = 32`**（**不是 48**）。
⇒ **Python 天花板 32 与 Rust 上限 256 的不对称**是**真的**（登记为 `D-199` §6 `R6`）。
**但提并发依然不是提速杠杆**：并发 **16 → 32（实测）** 后吞吐**不变**（≈ **34 次/分**）⇒ 瓶颈在**候选 B**。

**但并发不是瓶颈** —— 见候选 B。

#### 候选 B：链上读取被**单地址**限速 —— **是** ✅

`flashloan/rs-src/src/execution.rs:55`：

```rust
fn throttle_rpc_call(rpc_url: &str) {
    static LAST_CALL: Mutex<Option<HashMap<String, Instant>>> = Mutex::new(None);
    let interval = dex_rpc_min_interval_seconds();      // DEX_RPC_MIN_INTERVAL_SECONDS = 0.2
    let Ok(mut guard) = LAST_CALL.lock() else { return; };
    ...
    if wait > 0.0 { std::thread::sleep(...); }           // ← 持锁期间睡
    calls.insert(rpc_url.to_string(), Instant::now());
}
```

三点后果：

1. **按地址**限速 ⇒ 整个内核对**那一个** `rpcUrl` 的总速率 **≤ 1 / 0.2 = 5 次/秒**；
2. **持锁 sleep** ⇒ 所有复核线程在**同一把锁**上排队，**加线程只会多排队**；
3. 复核用的地址来自 Python 侧 `_probe_robinhood_family_rpc`（**第一个能通的地址**）⇒ 实际**几乎全部压在一个端点上**。

**算术自洽**：实测复核 **32 次/分** ＝ **0.53 次/秒**；若一次复核约 **9.4** 次链上读取 ⇒ **0.53 × 9.4 ≈ 5.0 次/秒**
＝ **限速上限**。⇒ **吞吐正好顶在限速上**，不是顶在并发上。

#### 候选 C：投递是串行的 —— **是** ✅

`py-spy record --pid <runtime> --duration 90 --rate 50`（**1105** 个采样）后按线程拆分：

| 线程 | 采样数 | 占比 | 叶子分布（前三） |
|---|---|---|---|
| `dex-opportunity-scanner` | **240** | **21.7%** | `realpath` **45**、`stat` **20**、`connect` **39** —— **240/240（100%）** 都在 `_enqueue_closed_loop_groups_from_payload` 里 |
| `v4-market-observation` | 344 | 31.1% | 路径解析 ＋ `stat` 为主 |
| `v4-candidate_yc_zc` | 107 | 9.7% | `realpath` ＋ `delete_rows`（写） |
| 合计「开连接 ＋ 解析路径 ＋ 路径 `stat`」 | **524** | **47.4%** | 其中真正执行 SQL 的只有 **59**（**5.3%**） |

⇒ **投递阶段完全串行**在扫描线程里，而它在实测的 90 s 窗口内**从未离开**这个阶段。

### 2.2 投递阶段为什么这么贵：数据库连接税

`flashloan/src/core/db/storage_business_io.py:66` 的 `query()`：**每次操作都重开一个连接**。

| 基准（18 GB 的 WAL 库，生产库在跑） | 读数 |
|---|---|
| `storage_business_io.query(1 行)` | **13.8 ms** |
| 原生 `sqlite3.connect` + `SELECT 1` | **0.22 ms**（**63×** 差） |
| `Path.resolve()`（**每次**操作要 **3** 次：`from_url` ／ `ensure_store` ／ `connect`） | **0.42–0.49 ms** |
| `db.ensure()` | **0.94 ms** |
| 新连接 **只** `sqlite3.connect` | **0.18 ms** |
| 新连接 ＋ `PRAGMA busy_timeout` | **0.23 ms** |
| 新连接 ＋ `PRAGMA synchronous=NORMAL` | **11.0 ms** |
| 新连接 ＋ `PRAGMA journal_mode=WAL` | **11.8 ms** |
| **已开**连接上的 `PRAGMA synchronous=NORMAL` | **0.007 ms** |

**关键**：两个 pragma 本身**几乎不要钱**（**0.007 ms**）；贵的是「**新连接第一次碰这个 18 GB 的 WAL 文件**」
（映射 WAL 索引 ＋ 读库头）。每个 PRAGMA 只是恰好成了第一个真正访问数据库的语句。

⇒ **修法方向**：**复用连接**（每线程一条），而不是调 PRAGMA。归 `M-10`，本轮**只测不改**。

## 3. 落地的改动

### 3.1 广播路由：组级标签不再**一票否决**（`M-7` ＋ `M-13`）

**旧**：`should_route_to_execution_queue` 要求 `payload.status == "profitable_amount_found"` ——
那是**组级**内核标签（按**组**聚合），而复核判的是**单条闭环**。⇒ 一条闭环的复核证明**到不了**执行队列。

**新**（`worker_pool.rs:4688`）：

```rust
fn route_reaches_the_execution_queue(payload: &Value) -> bool {
    payload.status == "profitable_amount_found" || review_authorized_broadcast(payload)
}
```

**没有**复核证明时**仍然**要组级标签（不是无条件放开）——单测
`a_route_without_the_review_proof_still_needs_the_kernel_label` 与
`a_review_authorized_route_reaches_the_queue_beneath_an_unprofitable_group_label` 各守一边。

### 3.2 启动等待置 0：修一个**「0 什么也没做」**的缺陷（`M-13`）

**旧**（`dex_opportunity_scanner_rust_mixin.py`）：

```python
batch_limit = max(1, int(new_groups_per_scan_override() or 16))   # ← 0 被当成「未设置」
```

**新**：

```python
per_scan_override = new_groups_per_scan_override()
resident_room = max(0, total_group_limit - worker_group_count)
if per_scan_override is not None and int(per_scan_override) <= 0:
    batch_limit = resident_room        # 0 ＝ 不等待 ＝ 一次全量入组
else:
    batch_limit = max(1, int(per_scan_override or 16))
    batch_limit = min(batch_limit, resident_room)
```

**缺省路径（`or 16`）一字未改** ⇒ 不设置该变量时行为**完全不变**。

### 3.3 部署参数（`plan/runtime_evidence/tools/`）

| 变量 | 旧 | 新 | 含义 |
|---|---|---|---|
| `DEX_CLOSED_LOOP_MAX_NEW_GROUPS_PER_SCAN` | **32** | **0** | **启动不等待**：一次扫描把**整个目录**投进复核池 |
| `DEX_CLOSED_LOOP_MAX_RESIDENT_GROUPS` | 256 | 256 | 常驻组上限（**174** 个闭环放得下） |
| `DEX_CLOSED_LOOP_MAX_WORKERS` | （缺省 **16**） | **32** | 复核并发；**★ 订正**：原写 **48**，但 Python 侧 `min(CLOSED_LOOP_WORKER_CEILING = 32, 48) = 32` ⇒ **生效值本来就是 32**（实盘 `concurrencyLimit = 32`）⇒ 部署值订正为**如实值**，**运行实例无需重启**；Rust 上限 **256**，`.env` 不覆盖 |

## 4. 「链上广播仍然是 0」：读数指向**具体闸门**

| 读数 | 值 |
|---|---|
| `manager_v4_review_broadcast_requests` | **0 行** |
| `manager_cow_execution_attempts` | **0 行** |
| `manager_v4_reviews` | `not_executable` **132** ／ `data_incomplete` **42** ／ **`completed` 0** |
| 理由码 | `runArbitrage returned ok=false` **131**（链上合约自己回退 `NoProfitableRoute`）／ `signed PnL is missing or incomplete` **24** ／ `ladder_not_measured:single_tick_capacity_below_min_probe` **2** ／ `not_reviewed_since:<t>` **17** |
| 正利润行 | **5** 行；其中 **2** 行有实测 **3/3** 跳限值 |
| 那 2 行 | USDG `0x5fc5360d…:0x000…0`：`pnl_raw = 0xc` ＝ **1.2e-05 USDG**，被 `state_transition_gate_failed:hop_1_failed:tick_range_changed` 挡；PFE `0x7066a64c…:0x5fc5360d…`：`pnl_raw = 0x690ae28b32` ＝ **4.5e-07 USDG**，被 `single_tick_capacity_below_min_probe` 挡 |

**闸门在按设计工作**：`execution.rs` 里，容量小于最小探测量 ⇒ **拒绝探测**（不浪费 gas 去探一个注定装不下的金额）；
经济性底线大于容量 ⇒ 同样拒绝。**这两条不是缺陷，是「这笔单子不值得做」的诚实表达。**

**必须如实说的话**：观测到的正利润是**灰尘级**（**1.2e-05** / **4.5e-07** USDG）。
即使把全部闸门放行、也真的签了单，**手续费与 gas 也会吃掉它**。
⇒ 「持续产生链上广播交易记录」这件事，**当前卡在市场侧，不在链路侧**；
链路上本轮**已经打通**（复核证明 → 执行队列 → 广播尝试），**只等一个真的赚钱的闭环**。
