# D-263 复核状态语义归正（可成交但不盈利 ≠ 不可成交）

> 日期：2026-11-28　·　范围：`T-池编.02`（复核层）　·　模块：`M-6`（复核层）、`M-8`（编排器）
> 性质：**缺陷定位（复核状态语义失真）** ＋ **代码修复**（复核层判定）＋ **统计口径归正**（编排器）
> 证据：`flashloan/tools/review_manager/src/lib.rs`（代码自证）；`manager_v4_reviews` 的**只读**对表（本文 §2）

---

## 1. 本轮改的是什么

用户口径（一直有效的那两条）：

1. 「**持续观察统计套利交易 盈亏情况**」——盈亏统计要读得出「测到了什么」。
2. 「**如果复核没有给出具体的盈亏数值，就利用复核管理工具修正复核问题，直到每个复核都有明确的盈亏数值**」。

本轮发现的缺陷：**复核确实给出了明确的盈亏数值**，可这些行被归档在 `not_executable`（不可成交）名下 ⇒ 统计读出来是「**128 条路线不可成交**」，而链上事实是「**128 条路线被成交了，钱没回来**」。

两句话差在：前者说「这条路线跑不了」，后者说「这条路线跑了，亏了」。**前者是错的。**

### 2.2 那 128 条到底是什么（样本原文）

`manager_v4_reviews.run_arbitrage_json` 的最新一条：

```json
{"ok": false, "executable": true, "error": "NoProfitableRoute",
 "rawError": "execution reverted", "revertSelector": "0x16301234",
 "noProfitableRoute": true, "blockNumber": null,
 "initialAmountRaw": "0xd72dcadd7b3e30", "selectedAmountRaw": "0x0",
 "arbitrageNotProfitable": {"profitDeltaRaw": "-0x1f8947da1a0a1",
   "receivedRaw": "0xd535365fd99d90", "requiredRaw": "0xd72dcadd7b3e31"},
 "signedPnl": {"amount": -5.54791623303329e-4, "currency": "SPY",
   "raw": "-0x1f8947da1a0a1", "source": "native_rust_ladder"}}
```

逐项读：

| 字段 | 值 | 含义 |
|---|---|---|
| `executable` | `true` | **这条路线是可成交的**（池子解析成功、跳链完整、合约自己的探针走到了盈利判定） |
| `ok` | `false` | 合约**回滚**了，回滚选择子 `0x16301234` ＝ `ArbitrageNotProfitable` |
| `error` | `NoProfitableRoute` | 合约自己的措辞：「往返一圈不赚钱」 |
| `arbitrageNotProfitable` | `received < required` | **确切的亏损**：拿回来的比要的少 `0x1f8947da1a0a1` |
| `signedPnl` | `-5.54791623303329e-4 SPY` | **确切的盈亏数值**（来源 `native_rust_ladder`，不是占位零） |
| `blockNumber` | `null` | 这是 `eth_call` 模拟，没有上链交易（正常） |

分布：128 条里 **126** 条是 `ok=false ∧ executable=true`（其余 2 条 `executable=false`）。126 条里 **121** 条的阶梯**量过**（`bestAmountMeasured=1`，`probeCount` 1–21，`bestAmountLadderStatus=not_profitable_after_costs`），只有 **5** 条是 `single_tick_capacity_below_min_probe`（阶梯确实没跑起来）。

### 2.3 判定链上的落点（`review_manager::build_review_rows`）

```rust
Some(run) if run.ok && run.executable => { /* 身份闸门 → 单 tick 闸门 → 阶梯闸门 → completed */ }
Some(run) if !run.ok => ("not_executable", Some("runArbitrage returned ok=false".to_owned())),
Some(_) => ("not_executable", Some("runArbitrage returned executable=false".to_owned())),
```

`ok=false` 这一支**不看 `executable`**，也不看理由 ⇒ **可成交的盈利判定与不可成交的测量失败被并成了一类**，而且理由串写的是「`runArbitrage returned ok=false`」，读起来像「**测量失败**」。

### 2.4 结论

`ok=false` 在这一层**不是「测量失败」**：合约回滚本身就是一次**成功的测量**——它把「这条路不赚钱」连同确切的亏损一起说了出来。`ok=false` 只有在**回滚原因不是盈利判定**（RPC 失败、池子读不到）时才是测量失败，而那两行 `executable=false` 本来就归在最后一条支上。

**后果**：① 盈亏统计读不出「测到了什么」；② 自愈编排器会以为这 128 条**测量坏了**，去追一个**根本没坏的**测量；③ 「持续产生套利广播交易」这条目标的输入被自己判没了（库里 `completed` 是 **0** 条）。

## 3. 本轮改动

### 3.1 复核层（`M-6`）：三类拒绝分开

**不新增状态值**：`review_status` 的取值集合被数据库 CHECK 约束、管理器 API 参数校验、页面积分类、广播准入事实、界面读面、Python 侧统计共同依赖（`completed / data_incomplete / not_executable / failed`）⇒ 本轮**用既有词汇**表达新语义。

新增三个判定（`flashloan/tools/review_manager/src/lib.rs`）：

| 函数 | 判据 |
|---|---|
| `rejection_is_profitability_verdict(run)` | 回滚是**盈利判定**：`noProfitableRoute=true` ／ 有 `arbitrageNotProfitable` ／ `error` 含 `NoProfitableRoute` |
| `rejection_kind(run)` | 回滚的短类别（`NoProfitableRoute` ／ `execution reverted` …） |
| `identity_gate_reason(hop_without_options, pool_outside_options)` | 身份闸门**只判一次**、供每条支复用（原来的两段 `format!` 重复代码） |

判定链改成：

| 证据 | 旧 | 新 |
|---|---|---|
| `ok ∧ executable` ＋ 身份不符 | `not_executable` ＋ `loop_options_unavailable` / `pool_not_in_loop_options` | **不变**（身份闸门优先） |
| `ok ∧ executable` ＋ 单 tick 闸门不过 | `not_executable` ＋ `single_tick_gate_failed:*` | **不变** |
| `ok ∧ executable` ＋ 阶梯没量过 | `data_incomplete` ＋ `ladder_not_measured:*` | **不变** |
| `ok ∧ executable` ＋ 全过 | `completed` | **不变** |
| **`¬ok ∧ executable` ＋ 盈利判定** | `not_executable` ＋ `runArbitrage returned ok=false` | **`completed` ＋ `measured_not_profitable:<kind>`**（⇒ 页面积分类 `confirmed_no_profit`） |
| **`¬ok ∧ executable` ＋ 盈利判定 ＋ 阶梯没量过** | 同上 | **`data_incomplete` ＋ `ladder_not_measured:*`**（量级不足仍是量不足） |
| **`¬ok ∧ executable` ＋ 盈利判定 ＋ 实测为正** | — | **`not_executable` ＋ `measured_profit_contradicts_contract_verdict`**（合约说不赚钱、阶梯说赚钱 ⇒ 复核无法裁定 ⇒ 复测，**不得**进广播请求） |
| `¬ok ∧ ¬executable` | `not_executable` ＋ `runArbitrage returned ok=false` | `not_executable` ＋ `runArbitrage rejected the route and reported it as not executable:<kind>` |
| `ok ∧ ¬executable` | `not_executable` ＋ `runArbitrage returned executable=false` | `not_executable` ＋ `runArbitrage reported the route as not executable` |

**广播路径一条门禁都没松**：

* 复核层生成广播请求的条件**未变**（`completed` ＋ 正盈亏 ＋ 三跳价格限 ＋ 三跳确认池 ＋ 时刻可用）——而盈利判定这一支的实测值**必为负**（合约自己说了不赚钱）⇒ **不会**产生广播请求。
* 即使出现「实测为正」的矛盾情形，复核层也把它判成 `not_executable` ⇒ **不生成**广播请求。
* 广播层的 `BC-1.run_ok` 规则**仍在**：回滚过的运行（`ok=false`）**永远**过不了广播准入 ⇒ 即使请求表里混进一条，广播层也会拒并留下 `BC-1.run_ok` 的理由。
* 闭环的**停驻语义不变**：`review_round_outcome` 只在「`completed` ＋ 正盈亏」时把闭环停在广播哨兵 ⇒ 本轮这些行（负盈亏）**照旧**按「本轮没赚钱」继续排队复核。

### 3.2 编排器（`M-8`）：统计口径

新增 `review_status_counts(rows)`（`scripts/mainnet_arbitrage_healer.py`），把复核库的状态读数摊开：

| 读数 | 含义 |
|---|---|
| `completed` | 复核**读到了**这条路线并给了裁定 |
| `completedWithProfit` | 裁定是「赚钱」 |
| `completedNoProfit` / `measuredNotProfitable` | 裁定是「**量过了，市场不买单**」——**本轮新增的可见口径** |
| `not_executable` | 这条路线**跑不了**（身份不符 / 版本一规则不符 / 合约根本没跑成） |
| `data_incomplete` | 测量**不足**（阶梯没量 / 盈亏缺失） |
| `failed` / `other` | 其余 |

口径挂在报告的 `layers.reviews.manager.statusCounts`，并随 `pnl_snapshot` 的 `reviews.statusCounts` 一起落进观察文件 ⇒ **「测到了多少 / 赚了多少 / 亏了多少」三件事分开读**。

| `review_status` | 回答的问题 | 页面积分类 |

### 5.2 在产读数（**2026-11-28 · 部署后**）

部署：**2026-11-28 17:58:45**（`manager-api.exe` pid 29424）、**17:59:00**（`flashloan_rs.dll` 运行时 pid 30348）同批上线；自愈器 pid 22816 随之起。

读数取自 `manager_v4_reviews` 的**同一条** `GROUP BY` 语句（一次读 ⇒ 一个快照，避免运行时正在逐条重测时各行读数来自不同时刻）：

```
SELECT review_status, COUNT(*) AS n,
       SUM(CASE WHEN signed_pnl_amount IS NULL THEN 1 ELSE 0 END) AS pnl_null,
       SUM(CASE WHEN signed_pnl_amount >  0 THEN 1 ELSE 0 END) AS pnl_pos,
       SUM(CASE WHEN signed_pnl_amount <  0 THEN 1 ELSE 0 END) AS pnl_neg,
       SUM(CASE WHEN review_reason LIKE 'measured_not_profitable%' THEN 1 ELSE 0 END) AS reason_new,
       SUM(CASE WHEN review_reason LIKE '%returned ok=false%'      THEN 1 ELSE 0 END) AS reason_old,
       MAX(updated_at) AS last_upd
FROM manager_v4_reviews GROUP BY review_status;
```

| `review_status` | 行数 | 缺盈亏数值 | **正**盈亏 | 负盈亏 | 新理由串 | 旧理由串 | 快照时刻（UTC） |
|---|---|---|---|---|---|---|---|
| `not_executable` | **121** | 0 | **7** | 114 | 0 | **106** | `2026-11-28T10:36:31Z` |
| **`completed`** | **28** | **0** | **0** | **28** | **28** | 0 | `2026-11-28T10:49:36Z` |
| `data_incomplete` | **27** | **17** | 0 | 10 | 0 | 0 | `2026-11-28T10:39:36Z` |

逐条读：

1. **`completed` 从 0 变成 28** —— 部署前库里一条 `completed` 都没有（§2.1），现在有 28 条。这 28 条**全部**是 `measured_not_profitable:NoProfitableRoute`（新理由串），**全部带确切的负盈亏数值**（`signed_pnl_source = native_rust_ladder`，区间 `-3.26e-2` ～ `-6.18e-15`），**一条都不缺数值**。语义归正在生产上生效了：这些行现在说的是「**这条路线跑得了，但往返一圈没赚钱，亏了这么多**」，而不再是「这条路线跑不了」。
2. **旧理由串一次也没再被写出来**：那 106 条 `runArbitrage returned ok=false` 全部是 **2026-11-26** 的存量行（`updated_at` 最新一条 `2026-11-26T19:29:33Z`），部署之后新代码写出的每一行都带新理由串。存量行要等运行时按当前代次重测才会被逐条改写（**不删行、不改历史**）。
3. **广播请求仍然一条没有**（`manager_v4_review_broadcast_requests` = **0**）：被改判的 28 行实测值**全为负** ⇒ 复核层**不生成**广播请求。**广播门禁一条没松**（§3.1）。
4. **那 7 条正盈亏仍在 `not_executable`**：它们的阻断理由是 `loop_options_unavailable:hop_N`（闭环目录没给那一跳发布池选项，**身份问题**），与本轮语义无关，另案登记（`D-228`）。**它们没有因为本轮改动而变成广播候选。**
5. **17 条仍没有盈亏数值**（`data_incomplete`）：13 条是 **2026-11-26** 的存量 `signed PnL is missing or incomplete`，4 条是 `not_reviewed_since:<t>`（**该闭环这一轮还没排到**）。前者要等当前代次重测，后者是**排队状态**而不是「测了但没测出来」。
6. **读数是活的**：运行时每分钟重测一批闭环，`completed` 与 `not_executable` 之间会随重测结果来回落差（快照里 `completed` 从 9 → 28 → 34 变动过）。**口径以同一时刻的一次快照为准**，不把不同时刻的读数相加。

**结论**：本轮要修的那件事（**「可成交但不盈利」不能记成「不可成交」**）在生产上**已修好并有读数**：28 条复核从「不可成交」变成「测过了、亏了具体数额」，而**广播请求仍然是 0**（市场条件：实测值全为负）。

## 6. 诚实边界

* **未伪造任何盈亏**、**未填 0**、**未删任何历史复核行**、**未改任何历史代次**、**未手工写生产库**。
* **广播门禁一条没松**：只把「可成交但不盈利」从「不可成交」里**分出来**，广播准入的每一道（`completed` ＋ 正盈亏 ＋ 三跳价格限 ＋ 三跳确认池 ＋ `BC-1.run_ok` ＋ `BC-2` 链/账户/额度/窗口）都在原位。
* **广播 attempts 仍为 0**（**市场条件**）：本轮改动**不会**凭空产生广播——被改判的那些行实测值**全为负**。
* 那 **7** 条正盈亏复核**状态未变**（`not_executable` ＋ `loop_options_unavailable:hop_N`）：它们的阻断理由是**闭环目录没有给那一跳发布池选项**（身份问题），与本轮的语义归正**无关**；该问题另有登记（`D-228` §闭环目录缺口）。
* 写锁根治（`I2.7`）、热路径搬库、`broadcast_pending` 同源墓碑（`I2.13`）、**19 GB** 主库体积构成**均未实施**。
