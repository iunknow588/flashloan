# D-262 广播策略改为正向盈利直发（无新鲜度门禁）

> 日期：2026-11-28　·　范围：`T-池编.02`（复核/广播/自愈级联）　·　模块：`M-8`（复核层）、`M-7`（广播层）、`M-13`（运行时发布层）
> 性质：**用户口径改写**（广播策略）＋**缺陷定位（新鲜度门禁量的不是「年龄」）**＋**代码修复**（三层）
> 证据：`flashloan/tools/broadcast_manager/src/admission.rs`、`flashloan/tools/review_manager/src/lib.rs`、`flashloan/rs-src/src/worker_pool.rs`（代码自证）；`manager_v4_reviews` 与 `manager_v4_closed_loop_runtime_state` 的**只读**对表（本文 §2.3）

---


## 1. 用户口径（本轮改的是什么）

1. 「**新的广播交易策略是只要有正向盈利预期，就直接发出广播交易的指令，没有新鲜度的概念了，因为它是直接执行的。**」
2. 「**首先新鲜度不应该是门禁，不应该使用。其次，即使有新鲜度，这个位置也不应该过时，它为什么会过时呢？从复核结束到广播开始，这一段时间怎么会过时呢?**」

本文答第一问：**删掉新鲜度门禁**（三层均已改）。
答第二问：**旧门禁根本没有在量「测量有多旧」——它量的是另一个时刻**，所以它在两个方向上都会判错（§2）。

## 2. 旧门禁到底量了什么（三层落点 ＋ 它的真实含义）

### 2.1 三层落点

| 层 | 代码 | 旧判据 | 不通过时的话 |
|---|---|---|---|
| 复核层（生成广播请求） | `review_manager::review_is_current_for_automatic_broadcast` | 测量时刻 `≥` 本轮开始时刻；无轮次时刻则 `>` 库里已发布的复核 | 不生成广播请求（表里永远没有 `generated` 行） |
| 广播层（准入） | `broadcast_manager::AdmissionRule::ReviewFresh`（`BC-1.review_fresh`） | **当前时刻 `<` 闭环的下一次复核时刻** | 「the loop was scheduled at X, so its review is no longer the current measurement of the loop」/「the loop publishes no review time point」 |
| 运行时（直发） | `worker_pool::wake_broadcast_with_review_proof` | **当前时刻 `<` 闭环的下一次复核时刻** | 「the closed loop was scheduled at X, so this request is no longer the current measurement of the loop」/「the closed loop publishes no review time point」 |

### 2.2 广播与复核之间那段时间：它不可能过时（用户问题的直接答案）

运行时的复核线程是**一次连续动作**，不是「测量完」和「广播」两个独立阶段：

```
一次复核轮次（worker 的一次迭代）
  → 链上测量（runArbitrage）。所有链上读取在这一步里完成
  → 复核发布（review_publish_block）→ 写入广播请求（一行）
  → 唤醒（wake_broadcast_with_review_proof）→ 读回刚发布的请求
  → 签名（一次 eth_sendRawTransaction）
  → 链上的回执收到之前，由广播确认线程取回
```

「复核结束到广播开始」是**同一个线程的一次迭代内**，里面没有任何一个时刻比较参与。
旧门禁却在这里参与了一个时刻比较——而且比的是**闭环的下一次复核时刻**，不是测量的时刻。

### 2.3 它在两个方向上都会判错（定位结论）

| 方向 | 旧门禁的行为 | 后果 |
|---|---|---|
| 误判「旧」 | 闭环的复核时刻已经过去（**这是闭环到期待测的常态**）→ `now ≥ scheduled` → 拒播 | **刚测完的复核被判为「不是当前测量」** |
| 误判「新」 | 闭环停在广播哨兵（2035-05-05）→ `now < scheduled` 恒成立 | **两天前的复核也算「新鲜」** |
| 当时在产的 7 条正利润复核 | 它们的闭环**已经离开目录**（`manager_v4_closed_loop_runtime_state` 里 `next_review_at = null`、`runtime_status = null`） | 广播层与运行时以「闭环没有复核时刻」拒播，复核层以「不晚于库里已发布的复核」拒发 —— **与「新鲜度」无关** |

**结论：旧门禁不是「太严」，而是「问错了」。** 它用「闭环到期了没」回答「这个利润还是不是现在的」，而现在问的是「这个利润测过没过」。

## 3. 本轮改动（三层 ＋ 编排器）

### 3.1 复核层：删掉「当前轮次」判据

* `review_is_current_for_automatic_broadcast(reviewed_at, round_started_at, published_reviewed_at)` → **`review_stamp_is_usable(reviewed_at)`**：只剩两个判据——时刻**可读**且**不在未来**（未来时刻 ≠ 时钟不一致，不是测量）。
* 下游的 `read_loop_review_moments` / `LoopReviewMoments` / `build_review_rows` 的 `loop_moments` 参数整条删除（它们只服务于被删的判据）。
* 请求的生成条件不变：`review_status == "completed"` ＋ `signed_pnl.amount > 0` ＋ 三跳价格限齐全 ＋ 三跳确认池齐全 ＋ 时刻可用。

### 3.2 广播层：`BC-1.review_fresh` → `BC-1.review_clock_consistent`

* 规则码 `BC-1.review_fresh` 作废：新码只表达「时刻可读且不在未来」。
* 判据重写：取消了 `now < loop_scheduled_at` 这个比较；微距许可偏移仍然拒绝（**不是年龄门禁**）。
* `AdmissionDecision` 新增描述字段 `loop_scheduled_at`：闭环的下一次复核时刻**随决策记录**，但**不再拒绝发送**（审计轨迹里看得到它，但它不再是一道门）。
* 新增用例：**未来时刻**仍被拒（`BC-1.review_clock_consistent`）。

### 3.3 运行时直发路径

* 删掉了 `loop_review_moment` 的拒绝分支（「闭环没有复核时刻」与「闭环已到时刻」两个拒绝）。
* `loop_review_moment` 保留为**描述字段**：它的值随结果进入 `loopScheduledAt`，用作「闭环下次何时被测」的说明。
* 保留的拒绝（与新鲜度无关）：`run_ok` / `run_executable` / `review_status=completed` / 正盈利 / 三条价格限 / **路线必须交易复核确认的池**。

### 3.4 编排器：不再把广播策略写成「只播新鲜的」

* 策略标签：`fresh_positive_review_only` → **`positive_profit_direct`**（`audit_broadcast` 与 supervisor 日志两处）。
* `automaticBroadcastCandidates` 从硬编码的 **0** 改为**真实读数**：带可执行判元的正利润复核数（与 `historicalPositiveReviewsInWindow` 同源）。
* `transaction_production_status` 的原因词一律去掉「fresh」：`fresh_reviews_have_no_executable_positive_pnl` → `reviews_have_no_executable_positive_pnl`。

### 3.5 编排器：运行时忙不再饿死级联（同轮一并修复）

supervisor 的循环里有一个 `busy → continue`：运行时在忙（复核轮次占着 HTTP 线程）时，**整个自愈轮次被跳过**，包括不需要运行时空闲的三个管理写入：

| 被跳过的写入 | 是否需要运行时 | 作用 |
|---|---|---|
| `release_abandoned_review_claims` | **不需要**（写闭环库） | 归还失主的占用，让它们重新到期 |
| `advance_review_clocks` | **不需要**（写闭环库） | 推进复核时钟，让下一轮开始 |
| `walk_review_queue` | **不需要**（读闭环库） | 刷新到期队列，从队头重走 |

**实测（上一轮）**：新自愈器接管后 journal 里**只有** `runtime_adopted`(1) ＋ `runtime_busy`(7)，**没有一个 `healing_cycle`**；旧会话 2 小时里也只有 **4** 个复核轮次 ＋ **22** 个 `runtime_busy`。

**修复**：新增 `run_management_writes()` 与 `busy_management_cycle()`，**忙的分支也跑这三个写入**（日志事件 `management_cycle`）；需要运行时的部分（`converge_reviews` / `fill_missing_reviews` / 复核重测 / tick 重测 / 代次重测）仍然等待。

### 3.6 编排器：忙看门狗改为看「库有没有动」，不再只看「有没有回答」

上一节的忙分支只解决了「不饿死写入」，但**忙到 30 分钟就会被重启**：`RUNTIME_BUSY_RESTART_SECONDS = 1800` 之后，watchdog 把一个一直忙的运行时判成「卡死」并重启它。

**实测（上一轮）**：`supervisor_20261128T075250Z.jsonl` 里从 `07:53:58Z` 到 `08:25:58Z` **连续 32 分钟**都是 `runtime_busy` ⇒ `08:26:35Z` `runtime_restarted` ⇒ **正在测量的那一轮被丢掉**。

这与该判据自己的注释相反：

> 「A runtime that is busy measuring a review round answers late, and restarting it would throw the whole round away. … the caller keeps it and only restarts a runtime that stays unresponsive **far beyond a review round**.」

**问题**：在生产里，一轮复核**比 30 分钟更长**（48 条闭环、12 个常驻 worker、每轮每闭环一次链上测量），所以「30 分钟没回答」根本不代表卡死。

**修复**：看门狗改为看**库有没有动**——

| 量 | 来源 | 含义 |
|---|---|---|
| `review_progress_marker()` | 管理器发布的每条闭环 `lastReviewedAt` 的最大值 | **运行时还在测量**（读的是管理器，不是被测的运行时，代价极低） |

* 库在动 ⇒ 运行时在测量 ⇒ 忙窗口**重新计时**，不重启；
* 库不动 **且** 一直不回答 ⇒ 才是真的卡死 ⇒ 才重启；
* `runtime_busy` 事件带上 `reviewProgressAt`，日志里看得到运行时到底动没动。

顺带修掉一个潜在死循环：`--max-samples` 的计数原本只在完整自愈轮次里 +1，运行时一直忙时**永远到不了上限**；现在忙轮次也计入样本。


### 3.7 编排器：报告里剩下的「新鲜度」措辞也一并归正

广播门禁删掉之后，编排器的报告里还留着几处与新口径**矛盾**的措辞 —— 它们**不影响发送**，但会让人以为「新鲜度」还在起作用：

| 位置 | 旧措辞 | 改后 |
|---|---|---|
| 报告头的 `successCriteria` | `continuousFreshReviews` ／ `broadcastOnlyFromFreshProfitableReview` | `continuousCurrentReviews` ／ **`broadcastOnlyFromProfitableReview`** |
| `fill_missing_reviews()` 的 `policy` 串 | 「only **fresh** positive review may trigger broadcast」 | 「**a positive profitable review triggers a broadcast as it is**」 |
| 复核层的**本轮覆盖**判据 | `review_freshness_by_loop()` ／ `currentLoopFreshness` ／ `reviewFreshnessBasis` ／ `reviewNotCurrentLoops` ／ `basis = loop_review_time_point` | `review_coverage_by_loop()` ／ `currentLoopCoverage` ／ `reviewCoverageBasis` ／ `loopsWithoutCurrentMeasurement` ／ `basis = loop_review_round` |

**这个判据本身不是门禁**，它回答的是「**这一轮有没有测到这条闭环**」（本轮覆盖），不是「这个利润有多旧」：它**不量年龄**、**不读任何间隔**，只比闭环自己的两个时刻（复核时刻 ＋ 本轮开始时刻）；它**只喂**生产态读数与稳定性判据（`productionHealthy`），**不进任何广播判断**（三层广播路径里已经没有任何一处读它）。改名的原因是：旧名字会让读数看起来像一道还在生效的「新鲜度窗口」。

## 4. 改之后仍然拒绝广播的门禁（一条不少）

| 层 | 门禁 | 说明 |
|---|---|---|
| 复核层 | `review_status == "completed"` | 复核本身必须完成 |
| 复核层 | `signed_pnl.amount > 0` | 正向盈利预期 |
| 复核层 | 三跳价格限齐全 ＋ 三跳确认池齐全 | 没有它们就没有可发送的交易 |
| 广播层 `BC-1` | `evidence_complete` / `review_completed` / `run_ok` / `run_executable` / `pnl_measured` / `pnl_positive` / `price_limits_complete` | 未测量 ≠ 0；不可执行 ≠ 可执行 |
| 广播层 `BC-1` | **`review_clock_consistent`（新）** | 只拒绝**未来时刻**（时钟不一致），不再拒绝「旧」的复核 |
| 广播层 `BC-2` | `chain_matches` / `account_matches` / `amount_within_limit` / `within_window` | 链、账户、额度上限、交易窗口 |
| 运行时 | 路线必须交易复核确认的池 | 发送的始终是复核证明过的那个方案 |
| 闭环生命周期 | 交易后停在广播哨兵，等回执终态才释放 | 防止同一个机会被反复广播 |
