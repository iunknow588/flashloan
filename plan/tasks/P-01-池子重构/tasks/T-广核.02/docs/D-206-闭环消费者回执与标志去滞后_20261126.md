## 2. **订正上一轮的两个错判**（重要）

上一轮（`D-203` §2）把根因写成「消费者在目录写完的**同一刻**就重建了」并据此定下修法。**这一条是错的**，本节用读数更正。

### 2.1 错判一：`last_rebuilt_at` **不是**消费者的重建时刻

**上一轮的读数**：`manager_v4_closed_loops.updated_at` ＝ `manager_v4_closed_loop_runtime_state.last_rebuilt_at` ＝ **14:44:52.830271100Z**（174 行全同一刻）⇒ 「两个时刻完全相等 ⇒ 消费者没有欠任何重建」。

**更正**：这两个时刻相等，是因为它们**都是生产者自己写的**。

| 读数 | 值 |
|---|---|
| 写入路径 | `closed_loop_manager/src/lib.rs:4281 replace_closed_loop_rows` → `desired.runtime_states` → `lib.rs:3571 last_rebuilt_at: chrono::Utc::now()` ⇒ **与目录行同一事务、同一 `now`** |
| 实测（**23:41**） | `manager_v4_closed_loop_runtime_state.last_rebuilt_at` 的**唯一**取值 ＝ **15:34:27.741556900Z** ＝ `manager_v4_closed_loops.updated_at` ＝ `library_state.generated_at` ⇒ **三者恒等** |

⇒ `last_rebuilt_at` 是**生产者写入目录的时刻**，不是消费者重建的时刻。
**消费者真正重建的时刻**是它**第一次用新代次复核**的那一刻：

| 读数（**23:41**） | 值 |
|---|---|
| 目录换代（写入代次 **44**） | **15:34:27.741556900Z**（＝ **23:34:27** CST） |
| 第一条**代次 44** 的复核行 | **15:38:55.542163700Z**（＝ **23:38:55** CST） |
| ⇒ 消费者落后目录 | **4 min 28 s**（**不是 0**） |

### 2.2 错判二：按「`last_rebuilt_at` ≥ 目录写入时刻」清标志是**同义反复**

两者**恒等**（§2.1）⇒ 该判据**恒为真** ⇒ 等价于「**目录一写完就清标志**」。
那会在消费者**还没追上**（落后 **4 min 28 s**）时就放行 ⇒ **把哨兵拆掉**，违反 `D-204` 的 `D1`。
⇒ **该修法作废**，改用 §3 的**代次回执**。

### 2.3 真正的「消费者已重建」凭据：**复核行携带的实测代次**

| 环节 | 位置 | 事实 |
|---|---|---|
| 消费者的目录 | `rs-src/src/worker_pool.rs:1474-1496` | worker pool 把闭环目录**载入内存**（`data.closed_loops`），**连同它的代次**一起读（`sqlite_read::load_manager_closed_loop_generation`） |
| 代次随复核走 | `rs-src/src/review_publish.rs:846-849 measured_generation` | 每条复核证据携带**测量时目录的代次**（`closed_loop_version` + `materialized_checksum`） |
| 代次落库 | `review_manager/src/lib.rs:3152-3154` | 复核行 `manager_v4_reviews.closed_loop_version/checksum` ＝ **实测代次**（不是盘上当前代次） |
| 实测 | **23:41** | 复核行按代次分裂：**代次 43 共 115 行**（末条 15:37:06）／**代次 44 共 48 行**（首条 15:38:55）⇒ **「消费者持有了哪一代」是可直接读的事实** |

⇒ **「消费者已重建」＝ 已存在带当前代次的复核行**。这个事实**已经持久化**，**不需要新表、不需要新列**。

## 3. 最终修法：**消费者回执**（标志的所有者负责清，消费者负责说）

### 3.1 语义（改完之后）

| 标志 | 含义（改后） | 谁清 |
|---|---|---|
| `consumers_need_rebuild = 1` | 目录换代了，而**消费者还没针对当前代次重建** | **消费者**（通过所有者的 API 回执） |
| `consumers_need_rebuild = 0` | 消费者**确实**已针对当前代次重建 | — |

### 3.2 三处改动

| # | 改动 | 文件 | 要点 |
|---|---|---|---|
| 1 | **清标志的依据换成「消费者对当前代次的回执」** | `flashloan/tools/closed_loop_manager/src/lib.rs` | 新增 `acknowledge_consumers_rebuilt(...)`（**所有者**暴露的 API）＋ `acknowledge_consumers_rebuilt_on_connection(...)`；**删除**原 `clear_consumers_need_rebuild(...)` 与它的调用点（`materialize_on_connection` 里那条「下一次物化恰好没变化就清」的分支） |
| 2 | **消费者在发布时回执** | `flashloan/rs-src/src/review_publish.rs` | `publish_review_loops(...)` 发布成功后，用**实测目录的代次**调所有者的回执 API（`acknowledge_the_rebuilt_consumers`） |
| 3 | **护栏：回执只在「实测代次 ＝ 盘上当前代次」时生效** | 同 1 | SQL 的 `WHERE` 含 `closed_loop_version = ?`（＋可选 `materialized_checksum = ?`）⇒ **过期回执清不掉任何东西** |

### 3.3 为什么这样**不是**拆哨兵

| 场景 | 允许的行为 | 实测/单测依据 |
|---|---|---|
| 目录换代，消费者**还没**追上 | 标志保持 **1** ⇒ RuntimeCore **继续拒收** | 回执的 `WHERE` 要求代次相等 ⇒ 消费者的旧代次回执**清不掉**（单测 `an_acknowledgement_of_another_generation_clears_nothing` / `an_acknowledgement_of_a_generation_the_library_left_clears_nothing`） |
| 消费者**确实**追上（用当前代次复核并发布） | 标志清 **0** ⇒ RuntimeCore 恢复发布 | 回执命中 ⇒ `UPDATE` 命中 1 行（单测 `an_acknowledgement_of_the_current_generation_clears_the_flag`） |
| 回执**失败** | 标志保持 **1**（不猜、不降级） | 回执失败只打印日志，**不改**复核结果（`review_publish.rs` 的 `acknowledge_the_rebuilt_consumers`） |

**没有**改 `runtime_core.rs`、**没有**改 `composite_manager` 的 issue 判定、**没有**硬编码 0、**没有**删列。
