### 2.5 `state` 实测是 **`partial`**（不是 `ready`）—— **原因是广播未授权**

`/api/status` → `chain_runtime.runtimeCore` 实测（2026-11-24 18:36）：

| 字段 | 读数 |
|---|---|
| `state` | **`partial`** |
| `snapshotAvailable` | `true` |
| `generation` | **67**（持续递增） |
| `lastError` | **空** |
| `lastRefreshAt` | `2026-11-24T10:36:28` |

Rust 侧 `state` 的判定（`flashloan/rs-src/src/runtime_core.rs:697-711`）：

```rust
} else if state.snapshot.is_some() {
    if state.snapshot.as_ref().is_some_and(|s| s.readiness.chain_complete) {
        "ready"
    } else {
        "partial"     // ← 快照**存在**，但 chain_complete = false
    }
}
```

⇒ `partial` 的含义是「**快照已建立并被保留**，但**链路未完成**」——
**不是**「快照被拒绝」（那会是 `error`，且 `lastError` 非空）。

`chain_complete` 的构成（`runtime_core.rs:2405-2411`）要求 **8 个组件全部 enabled**：

| 组件 | 实测 |
|---|---|
| token libraries（4 个） | ✅ |
| `poolScope` | ✅ `true` |
| `candidateEdge` | ✅ `true` |
| `candidateExchange` | ✅ `true` |
| `closedLoop` | ✅ `true` |
| `review` | ✅ `true` |
| **`broadcast`** | ❌ **`false`**（`ROBINHOOD_MAINNET_ALLOW_OFFICIAL_V4_ARB_BROADCAST` 未开启） |

⇒ **`broadcast` 是唯一未启用的组件** ⇒ `chain_complete` **恒 false**
⇒ `state` **恒 `partial`** ⇒ 验收项 C3 写的「`state=ready`」**在广播未授权期间不可能满足**。

> **这是「测量口径」问题，不是缺陷**：C3 想验的是「**快照被接受**」，
> 而「快照被接受」的真信号是 **`snapshotAvailable=true` ＋ `generation>=1` ＋ `lastError` 为空**
> —— 三者实测**全部满足**。
> `state=ready` **额外**要求**广播也开着**，那是**广播门禁**的维度，
> **不属于**「快照是否被接受」。
> ⇒ **建议（需人工裁决）**：C3 的判定条件改为
> 「`snapshotAvailable=true` **且** `generation>=1` **且** `lastError` 为空」
> （**不**要求 `state=ready`），或**显式**记「`state=partial` 源于 broadcast 未授权」为**已知豁免**。

## 3. 剩余的 2 条一致性误判：**跨作用域比较**

### 3.1 现象

`/api/dex/overview` 的 `versions.consistencyIssues` 恒为 **2 条**：

```
candidate_exchange.pool_scope_checksum expected=sha256:2bea9bb4… actual=sha256:ae6b14ac…
closed_loop.pool_scope_checksum      expected=sha256:ae6b14ac… actual=sha256:2bea9bb4…
```

⇒ `versionsConsistent = false`。

### 3.2 根因：**两个作用域，本就不该相等**

实测各库状态行的 `scope_key` 与 `pool_scope_checksum`：

| 库状态表 | `scope_key` | `pool_scope_checksum` |
|---|---|---|
| `manager_dex_candidate_library_state` | `core4` | `sha256:ae6b14ac…` |
| `manager_v4_closed_loop_library_state` | `core4` | `sha256:ae6b14ac…` |
| `manager_review_library_state` | `core4` | `sha256:ae6b14ac…` |
| `manager_market_observation_library_state` | **`candidate_exchange`** | **`sha256:2bea9bb4…`** |
| `manager_v4_directional_pool_library_state` | `core4` | `sha256:ae6b14ac…` |
| `manager_v4_directional_pool_library_state` | **`candidate_exchange`** | **`sha256:2bea9bb4…`** |

⇒ **`pool_scope_checksum` 标识的是「池作用域的物化身份」**，**不是全局唯一值**：
`core4` 作用域与 `candidate_exchange` 作用域**各有各的**校验和。

代码侧同名常量印证（`flashloan/tools/candidate_exchange_pool_manager/src/lib.rs:11-12`）：

```rust
const CANDIDATE_SCOPE_KEY: &str = "core4";
const EXCHANGE_SCOPE_KEY: &str = "candidate_exchange";
```

⇒ **候选交换层工作在 `candidate_exchange` 作用域**，而**候选边 / 闭环 / 复核工作在 `core4` 作用域**。

### 3.3 缺陷位置：**同一处检查的「陈旧副本」在 `overview.rs`**

关键事实：**内核里有**两套**各自独立的一致性检查**，它们对同一个问题的**结论相反**：

| 检查路径 | 位置 | `closed_loop.pool_scope_checksum` 的比法 | 实测结果 |
|---|---|---|---|
| **pipeline status**（`lib.rs`） | `flashloan/tools/composite_manager/src/lib.rs:1721-1731` | 比 **`candidate_edge`**（`core4` 作用域） | ✅ **通过**（`upstreamAssessment.consistent = true`，`issues = []`） |
| **overview versions**（`overview.rs`） | `flashloan/tools/composite_manager/src/overview.rs:1195-1236` | 比 **`candidate_exchange`**（`candidate_exchange` 作用域） | ❌ **恒不相等** ⇒ 2 条假阳性 |

`lib.rs:1721-1731` **已经带修复注释**，把道理写得很清楚：

```rust
// The closed loop lives in the `core4` scope, so its pool-scope checksum must be
// compared against the checksum owned by the `core4` pool-scope configuration.
// `candidate_exchange` intentionally carries the `candidate_exchange` scope
// checksum, which is derived from a different pool table and a different
// selection mode, so comparing against it can never succeed and would pin the
// assessment to a permanent false positive.
check_option_value(
    "closed_loop",
    "poolScopeChecksum",
    snapshot.candidate_edge.pool_scope_checksum.as_deref(),
    snapshot.closed_loop.pool_scope_checksum.as_deref(),
    &mut issues,
);
```

⇒ **`overview.rs` 里留着这份修复之前的副本** ⇒ 同一件事被**判了两次**，
一次对、一次错 ⇒ **`/api/dex/overview` 的 `versions.consistencyIssues` 恒报 2 条**，
而 **`pipelineStatus.upstreamAssessment` 恒报一致**。

### 3.3.1 两条假阳性的**逐条来源**

`push_checksum_issue(field, left, right)` 输出的格式是 `expected={left} actual={right}`
（`flashloan/tools/composite_manager/src/overview.rs:1299-1310`）。

| issue 字段 | `left`（= expected） | `right`（= actual） | 对应源码行 |
|---|---|---|---|
| `candidate_exchange.pool_scope_checksum` | `exchange.status.pool_scope_checksum` = `2bea9bb4…`（`candidate_exchange` 作用域） | `candidate.status.pool_scope_checksum` = `ae6b14ac…`（`core4` 作用域） | `overview.rs:1227-1230` |
| `closed_loop.pool_scope_checksum` | `closed_loop.status.pool_scope_checksum` = `ae6b14ac…`（`core4`） | `candidate.status.pool_scope_checksum` = `2bea9bb4…`（**`candidate_exchange`**） | `overview.rs:1233-1236` |

> **第 2 条的 `right` 为什么是 `2bea9bb4…`**：**已一行行核对完毕**（2026-11-24 修复时）。
>
> `candidate.status.pool_scope_checksum` 的**取数链路**是：
> `overview.rs:347` `read_candidate_snapshot(...)`
> → `candidate_edge_pool_manager::read_candidate_snapshot_on_connection()`
> （`flashloan/tools/candidate_edge_pool_manager/src/lib.rs:2175`）
> → `read_candidate_status_on_connection()`（同文件 `:2077`）
> → SQL `SELECT … pool_scope_checksum … FROM manager_dex_candidate_library_state
>   WHERE network=?1 AND chain_id=?2 AND protocol=?3 AND scope_key=?4`，
>   而 `scope_key` 传的是该文件的 `const SCOPE_KEY: &str = "core4"`（同文件 `:12`）。
>
> ⇒ **`candidate.status.pool_scope_checksum` 恒等于 `core4` 作用域的校验和**
> （实测 `sha256:ae6b14ac…`），**永远不可能**是 `2bea9bb4…`。
>
> ⇒ 因此 §3.3.1 表格里第 2 条的 `right` 值 **不是** `candidate.status` 取得的，
> 而是**当时那条比较的 `left`/`right` 顺序**在记录时被**读反**了：
> 那条比较是 `closed_loop`(core4, `ae6b14ac…`) vs `candidate`(core4, `ae6b14ac…`)
> —— **两侧本就相等**，**本不应**报 issue。
>
> ⇒ **结论订正**：§3.3.1 的第 2 条**不是**一条独立缺陷，
> 而是**第 1 条**（`candidate_exchange` 跨作用域比较）的**同源重复**：
> **同一份 `candidate_exchange` 作用域校验和**（`2bea9bb4…`）被**两次**拿去和 `core4` 比。
> ⇒ **缺陷只有 1 处**：`overview.rs` 拿 `exchange` 作用域的校验和去比 `core4` 作用域。

### 3.4 为什么**现在**才暴露

`pool_scope_checksum` 在**旧代次**下曾相等（或两处都为空 ⇒ `push_checksum_issue` 跳过），
所以这条误判**长期潜伏**；直到**复核代次发布**、各层 `pool_scope_checksum` **各自被真实写入**，
两个作用域**各自的**校验和才第一次同时出现在对比里 ⇒ 误判显形。

> **推论（可复算）**：`versionsConsistent = false` **不是**「复核代次没发布」的成因
> —— 复核代次**已经发布**了（§2）。它**不会**阻塞发布（发布门禁在 `review_publish.rs`，
> 不看 `overview.rs` 的一致性 issue 列表），但它**会让 `overview` 一直报「不一致」**，
> ⇒ 需要**独立修**，且**修在 `composite_manager`（`M-8` 编排层）**。
>
> **实证**：同一时刻两个口径**同时**可读 ——
> `pipelineStatus.upstreamAssessment` = **`consistent: true` / `issues: []`**（`lib.rs` 口径，已修）
> vs `versions.consistencyIssues` = **2 条**（`overview.rs` 口径，陈旧副本）
> ⇒ **不是数据不一致，是检查逻辑重复且其中一份过期**。
