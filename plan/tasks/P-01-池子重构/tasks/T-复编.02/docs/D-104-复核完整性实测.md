## 2. 为什么「复核代次发布」是整组验收项的**单点阻塞**

这不是推测，是**实测出来的因果链**：

```text
闭环目录（Manager 发布）        closed_loop_version = 19   checksum = sha256:6927d8d6…
复核库（Manager 发布）          closed_loop_version = 14   checksum = sha256:ed2534ae…
                    │
                    ▼
RuntimeCore 刷新快照 → **拒绝**（mixed manager snapshot）：
  [ {"component":"closed_loop","field":"consumersNeedRebuild","expected":"false","actual":"true"}
  , {"component":"review","field":"closedLoopVersion","expected":"19","actual":"14"}
  , {"component":"review","field":"closedLoopChecksum","expected":"sha256:6927d8d6…","actual":"sha256:ed2534ae…"} ]
                    │
                    ▼
RuntimeCore 快照：generation = 0、snapshotAvailable = false
                    │
                    ▼
⇒ C1（上游一致）/ C2（consumers_need_rebuild 自然清除）/ C3（runtime_core 快照被接受）
   **三者同源**：都卡在「复核库还停在旧代次」。
```

**读法（2026-11-24 实测订正）**：三项**同源但不同步**。
`consumers_need_rebuild` **不由复核发布清除** —— 它归**闭环管理器自己的自愈路径**
（`review_publish.rs` 模块头原文：“It does not clear `consumers_need_rebuild`.
That flag belongs to the closed-loop Manager's own self-healing path.”）。
复核代次发布只解开 **C1 / C3**；**C2** 要由**闭环管理器用同一校验和再物化一次**来清除。
在此之前，这三项**不是**「复核失败」，而是「**上游还没更新**」。

### 2.1 `consumers_need_rebuild` 的**自然清除**（**已实测**）

| 步 | 动作 | 读数 |
|---|---|---|
| 0 | 清除前 | `closed_loop_version = 19`、`materialized_checksum = sha256:6927d8d6…`、`loop_count = 174`、`hop_count = 522`、**`consumers_need_rebuild = 1`** |
| 1 | **dry-run**（`composite-manager materialize-arbitrage`，**不写**） | `closedLoopVersion = 19`、`loopCount = 174`、`hopCount = 522`、**`changedRows = 0`**、**`consumersNeedRebuild = false`**、校验和与库内**逐字段相等** ⇒ **重跑不会回退目录** |
| 2 | **`--apply`**（闭环管理器**自己的**物化路径；**未手写该标志**） | `applied = true`、`changedRows = 0`、`closedLoopVersion = 19`、`loopCount = 174`、`hop_count = 522` |
| 3 | 清除后 | **`consumers_need_rebuild = 0`**、`closed_loop_version = 19`、校验和**未变**（`sha256:6927d8d6…`）、`loop_count = 174`、`hop_count = 522` |
| 4 | RuntimeCore 的拒绝项 | `closed_loop.consumersNeedRebuild` **从拒绝项中消失**；只剩 `review.closedLoopVersion 19≠14` 与 `review.closedLoopChecksum` 两项 ⇒ **等复核代次发布** |

> **为什么「同校验和再物化」是**清除**而不是**改写**：`closed_loop_manager` 的
> `materialize_impl` 在 `checksum_changed == false` 时**不替换行**，
> 只调用 `clear_consumers_need_rebuild()` ⇒ 目录行**一字未动**，
> 被清的是**标志**，不是数据。

> **⚠️ 实测到的真实隐患（如实登记）**：`flashloan/tools/target/release/composite-manager.exe`
> 是 **08:05** 的**旧构建**（**不含** `T-方闭.01` 的备用池接线修复）⇒ 它的 dry-run
> 给出 **168 闭环 / 504 跳 / 校验和 sha256:19168935…**（= v18）⇒
> **若用它 `--apply`，会把目录从 174 回退到 168**。
> 目录内**只有 debug 构建（12:12）与源码一致**（dry-run 逐字段相等）。
> ⇒ **本任务的实测一律用 debug 构建**；release 构建与源码**不同步**这件事
> **不在本任务范围**（属部署产物），**如实登记**在此，不代为修复。

### 2.2 复核代次为什么迟迟不发（**实测根因**）

| 事实 | 读数 |
|---|---|
| 闭环目录发布的方向组数 | **174**（每组 1 个闭环 ⇒ 需要 **174** 个常驻 worker） |
| **overview** 给出的方向组数 | **174**（与目录**完全覆盖**，缺口 0） |
| **扫描器 payload** 给出的方向组数 | **104**（**与目录缺 74** ⇒ 见 §2.3） |
| 修复前的常驻 worker 上限 | **16**（且内联硬顶 32） |
| ⇒ 没有 worker 的闭环数 | **158** |

`covers_catalog()` 要求**证据条数 == 目录条数 == 174**。
158 个闭环永远拿不到证据 ⇒ `review_publish_block` 永远返回
`coverage_incomplete` ⇒ **复核代次永不发布** ⇒ 上面那条因果链**永远断在这里**。

**修法**（`M-8` 编排层，**门禁一字未动**）：
把「常驻组上限」与「并发上限」拆开，删掉扫描器里内联的那份
「默认 16 / 硬顶 32」复制品，改调**共享**的 `resolve_resident_group_limit()`。
详见 `D-047` `1.3。

### 2.3 第二层根因：**方向组全集**缺 74 组（**死锁**）

> §2.2 放开的是**容量**。容量放开后常驻上限不再是 16，
> 但**方向组全集本身**仍缺 74 组 ⇒ 那 74 个闭环**连第一个 worker 都拿不到**。

| 事实 | 读数 |
|---|---|
| 闭环目录发布的**方向组**数 | **174** |
| 扫描器 payload 的 **route** 数 / **方向组**数 | **104** / **104**（与常驻 worker 组集合**完全相同**，双向差 0） |
| 两者**交集** | **100** 组 |
| **目录有、扫描器没有 route** 的组 | **74** |
| **扫描器有、目录没有** 的组 | **4**（`spy¦coin¦usdg`、`spy¦eth¦meta`、`spy¦meta¦eth`、`spy¦usdg¦coin`） |

> **口径**：按**方向组**（`anchor¦Y¦Z`）统计；按**物理闭合键**（地址有序三元组）
> 统计同源（扫描器 104 / 目录 174 / 交集 100 / 扫描器独有 4 / 目录独有 74）。

**死锁形状**：组只有在扫描器产出 route 时才成为常驻 worker，
而扫描器只产出**已经持有 worker** 的组的 route ⇒ 74 个目录组永远拿不到第一个 worker
⇒ 永远拿不到复核证据 ⇒ `covers_catalog()`（证据条数 == 目录条数 == 174）永不成立。

**为什么是「不一致」而不是「设计」**：**手动复核路径**
（`_refresh_native_closed_loop_group_locked`）**早已优先用 manager 闭环视图**，
其注释原文即为
“Mainnet refresh prefers the RuntimeCore manager overview so loop libraries that are
not yet in the static observation snapshot can still be submitted.”
⇒ **自动扫描路径漏了这一步** ⇒ 同一份目录，两条路径给出**不同的方向组全集**。

**修法**（`M-8`，**门禁一字未动**）：`_submit_native_closed_loop_groups()` 先收扫描
payload 的组（**原行为不变**），再取 **manager 闭环视图**并**只补齐缺失的组**；
新增 `_native_chain_runtime()` 让**后台扫描线程**（无 Flask app context）
也能拿到 RuntimeCore 绑定。详见 `D-047§ §1.3.1。

**多出来的 4 组为什么不破坏门禁**：它们**不在已发布闭环目录内** ⇒ 内核
`apply_closed_loop_identity()` 找不到对应 identity ⇒ 只写
`closedLoopIdentityStatus = "mismatch"`、**不写** `closedLoopKey`
⇒ **不产出复核证据** ⇒ 证据条数仍为 **174**（= 目录条数）。

### 2.4 第三层根因：闭环身份的「**池子那一半**」对不上（**25 条闭环**）

> §2.3 补齐了**方向组全集**，但**组齐了 ≠ 身份齐了**。
> 内核的闭环身份有**两半**：**有序地址路径**＋**逐跳发布的有向池**。
> 两半都对上，身份才成立；缺哪一半，内核都**不写** §closedLoopKey§。

**实测口径**（**只读**，离线复现**生产函数** §_route_task_config§）：
把「路由给每一跳定价的池」与「闭环管理器发布的逐跳池」**逐跳**比对。
证据脚本：§plan/runtime_evidence/tools/_probe_identity_replication.py§（修复前）
与 §plan/runtime_evidence/tools/_probe_identity_after_fix.py§（修复后）。

| 事实 | 读数 |
|---|---|
| 闭环目录发布的闭环数 | **174** |
| **身份成立**（路由定价的池 ∋ 发布的池，三跳全中） | **149 / 174** |
| ⇒ **身份不成立** | **25** |
| 25 条的失配位置 | **全部是第 2 跳（bridge）**，形态统一为 §[真, 假, 真]§ |
| 25 条的路由池组来源 | **全部来自扫描 payload 的「观测池组」**；走**候选面回落**的 **74** 条**全部成立** |
| 修复后（同函数、同库、同目录） | **174 / 174** |

**内核的契约原文**（§flashloan/rs-src/src/worker_pool.rs::apply_closed_loop_identity§）：

> The route prices **every candidate pool** of every hop, while the Manager
> publishes the **one pool it selected** for each hop and keeps the rest as
> backups.

⇒ 内核假定**路由给每一跳定价全部候选池**；但 Python 侧
§_route_task_config()§ **优先**用**市场观测的池组**（每跳 1 个池），
**候选面**只作**回落** ⇒ 观测选的池与管理器发布的池不同时，
路由**根本没定价**管理器发布的那个池 ⇒ 内核判**池失配** ⇒
不写 §closedLoopKey§、不发布 §singleTickCapacityRaw§ ⇒
阶梯以 §single_tick_capacity_unavailable§ 被挡 ⇒ **不产出复核证据**
⇒ 证据条数**封顶 149** < 目录条数 **174** ⇒ §covers_catalog()§
**永不成立**。

**实盘读数佐证**（§cow_execution_reviews§，运行时自己写的复核记录）：
§payload_json.loopKey§ **就是**内核发布的闭环键（Python 侧取自
§evidence.loopKey§）⇒ **带 loopKey 的行 = 有身份的闭环 = 产出了证据**。
2026-11-24 17:0x–17:3x 的运行里：**带 loopKey 的行 90 条 / 不带 193 条**，
且**带 loopKey 的行 90 / 90 全部在目录内**（目录外组不产证据，符合预期）。
带 loopKey 的行 §bestAmountSelectionBasis = native_rust_ladder_no_profitable_size_measured§
（阶梯真的跑了）；不带 loopKey 的行 §blocked_reasons§ 含
§chain review failed: single_tick_capacity_unavailable§（**没有容量，阶梯根本没起步**）。

**修法**（§M-8§ 编排层，**门禁一字未改**）：
§_route_task_config()§ 改为**观测池组与候选面池组取并集**
（按 PoolKey 身份去重），不再「优先观测、回落候选」。
**没有新增任何 Python 侧的数据处理** —— 候选面**本来就是 Python 侧已经读到的**，
这次只是**不再把它丢掉**。
详见 §D-047§ §1.3.2。

### 2.5 第四层（**测量口径**层）：`C5` 的「假失配」与它的正确算法

**现象**：`C5`（I-15 方向层一致性）首次实测为 **NOT MET**：

> `closedLoopDirectionalPoolChecksum = sha256:84cf7aef…`
> `directionalLayerPoolChecksum     = sha256:f6836f97…` ⇒ 不相等

**根因**：**这是采集器的口径错误，不是系统缺陷。**
闭环层记录的 `directional_pool_checksum` **不是**任何单个方向 scope 的
`materialized_checksum`，而是 Rust `directional_layer_identity()`
（`flashloan/tools/closed_loop_manager/src/lib.rs:848`）对**全部**方向 scope
求的**复合身份**：

```text
payload  = "candidate_exchange:2:sha256:f6836f97…|core4:2:sha256:5a609caf…"
identity = "sha256:" + sha256(payload)  =  sha256:84cf7aef…
```

**实测复算**（`probe_t401_live_state_20261124.py identity`）：
复算值 `sha256:84cf7aef56554c5e140522b989e43701a911bc6ab03d061135df3d1b6b42f9cf`
与闭环层库中记录的**逐字相等** ⇒ **方向层与闭环层其实完全一致**。

**修法**（**只改测量工具，不改系统**）：
`plan/runtime_evidence/tools/collect_t401_review_integrity_20261124.py` 改为按
`directional_layer_identity()` 的**同一条规则**复算复合身份，再与闭环层记录比对；
同时把**每个 scope 的** `scopeKey / version / checksum` 与**复合 payload**
一并写进观测，便于复核。修后 `C5` = **MET**。

> **教训**：**比对前必须先确认「被比对的量是什么」。**
> 方向层有 `candidate_exchange` 与 `core4` **两个 scope**，
> 拿复合身份去和单 scope 比 ⇒ **必然失配**，且失配**看起来像上游陈旧**。

### 2.6 第五层：**发布层把金额证据丢在了链路之外**（`A1` / `A2` / `A8` 的真根因）

**现象**：复核代次发布之后，`A1`（缺字段 = 0）、`A2`（金额状态 = `measured`）、
`A8`（只读 healer 一致）**同时** NOT MET，且读数整齐得可疑：

```text
reviews = 174 | complete = 0 | incomplete = 174 | measured = 0 | missing = 174
healer: missing = 174 | ladderIncomplete = 174 | confirmed = 0
```

**根因（**逐字**核对发布出来的记录）**：

| 环节 | 事实 |
|---|---|
| 内核**产出** | `flashloan/rs-src/src/execution.rs:2422-2445` 在**预览 payload 顶层**写 `bestAmountMissing` / `bestAmountMeasured` / `bestAmount` / `bestAmountConfirmed`（阶梯在 `attempts`，`execution.rs:2398`） |
| 发布层**转发** | `flashloan/rs-src/src/review_publish.rs::static_preview()`（`654` 行）**只抄 8 个字段**：`source` / `measuredAt` / `status` / `routeSymbols` / `routeAddresses` / `selectedAmountRaw` / `selectedProfitRaw` / `attemptedCount` |
| ⇒ 实测库里的样子 | `manager_v4_reviews.static_preview_json` 的键**正好就是那 8 个** —— **没有 `bestAmountCalculation`**；`run_arbitrage_json` 里也没有 `attempts` / `bestAmount*`（`raw` 只带 `route.runArbitrage` 的非保留键） |

⇒ **测量做了，没带出来。** 采集器读 `static_preview_json.bestAmountCalculation` ⇒
**174 行全部 `amount_state=missing`**；只读 healer 同样只认这个块 ⇒ `missing=174`。

**系统自己早就知道这件事** —— `scripts/mainnet_arbitrage_healer.py::kernel_best_amount_calculation()`
的文档字符串原文写着：

> The block used to be dropped on the way into the Manager evidence: only
> ``staticPreview`` and ``runArbitrage`` were forwarded, so every Manager row lost
> the measured amount and the healer reported ``best_amount_missing`` for loops the
> kernel had already measured. The measurement therefore has to be carried across
> explicitly.

healer 只在**它自己**的物化路径上做了补偿（`live_review_evidence()` 里补
`preview["bestAmountCalculation"]`），**Rust 原生发布链路**没有补偿 ⇒
主网实盘走的**正是后者** ⇒ 每一条复核都像「从未测量过交易金额」。

**修法**（**改产品，不改口径**）：`M-6` 内 `flashloan/rs-src/src/review_publish.rs`
的 `static_preview()` **增加** `bestAmountCalculation`：

| 字段 | 来源 |
|---|---|
| `bestAmount` / `bestAmountRaw` / `bestAmountConfirmed` / `bestAmountMissing` / `bestAmountMeasured` / `bestAmountSelectionBasis` / `bestAmountZeroReason` | 内核**原样**带出（不解释、不改口径） |
| `method` / `requestedAmount` / `requestedSymbol` / `probeCount` | 发布层补的**载体信息** |
| `probeRecords[]` | 内核 `attempts` **逐档**带出：每档同时给**原始量**（`amountRaw` / `profitRaw`）与**人单位量**（`amount` / `borrowAmount` / `requestedAmount` / `profit` / `profitAmount`，按借款代币 decimals 换算），并保留 `ok` / `profitable` / `status` / `error` / `revertData` / `routeIndex` |

**没改什么**：发布门禁（覆盖全集 / 上游代际 / 幂等键）**一字未动**；
金额口径**未放宽**（「测得为零」仍是「测得的零」，**不是**「缺失」）；
方向池与固定费率约定不变；广播门禁不变。
