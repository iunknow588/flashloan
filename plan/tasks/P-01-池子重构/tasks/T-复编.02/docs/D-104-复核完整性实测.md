## 2. 为什么「复核代次发布」是整组验收项的**单点阻塞**

这不是推测，是**实测出来的因果链**：

```text
闭环目录（Manager 发布）        closed_loop_version = 19   checksum = sha256:6927d8d6…
复核库（Manager 发布）          closed_loop_version = 14   checksum = sha256:ed2534ae…
                    │
                    ▼
RuntimeCore 刷新快照 → **拒绝**（mixed manager snapshot）：
  [ {"component":"closed_loop","field":"consumersNeedRebuild","expected":"false","actual":"true"}
  , {"component":"review","field":"closedLoopVersion","expected":"19","actual":"14"}
  , {"component":"review","field":"closedLoopChecksum","expected":"sha256:6927d8d6…","actual":"sha256:ed2534ae…"} ]
                    │
                    ▼
RuntimeCore 快照：generation = 0、snapshotAvailable = false
                    │
                    ▼
⇒ C1（上游一致）/ C2（consumers_need_rebuild 自然清除）/ C3（runtime_core 快照被接受）
   **三者同源**：都卡在「复核库还停在旧代次」。
```

**读法（2026-11-24 实测订正）**：三项**同源但不同步**。
`consumers_need_rebuild` **不由复核发布清除** —— 它归**闭环管理器自己的自愈路径**
（`review_publish.rs` 模块头原文：“It does not clear `consumers_need_rebuild`.
That flag belongs to the closed-loop Manager's own self-healing path.”）。
复核代次发布只解开 **C1 / C3**；**C2** 要由**闭环管理器用同一校验和再物化一次**来清除。
在此之前，这三项**不是**「复核失败」，而是「**上游还没更新**」。

### 2.1 `consumers_need_rebuild` 的**自然清除**（**已实测**）

| 步 | 动作 | 读数 |
|---|---|---|
| 0 | 清除前 | `closed_loop_version = 19`、`materialized_checksum = sha256:6927d8d6…`、`loop_count = 174`、`hop_count = 522`、**`consumers_need_rebuild = 1`** |
| 1 | **dry-run**（`composite-manager materialize-arbitrage`，**不写**） | `closedLoopVersion = 19`、`loopCount = 174`、`hopCount = 522`、**`changedRows = 0`**、**`consumersNeedRebuild = false`**、校验和与库内**逐字段相等** ⇒ **重跑不会回退目录** |
| 2 | **`--apply`**（闭环管理器**自己的**物化路径；**未手写该标志**） | `applied = true`、`changedRows = 0`、`closedLoopVersion = 19`、`loopCount = 174`、`hop_count = 522` |
| 3 | 清除后 | **`consumers_need_rebuild = 0`**、`closed_loop_version = 19`、校验和**未变**（`sha256:6927d8d6…`）、`loop_count = 174`、`hop_count = 522` |
| 4 | RuntimeCore 的拒绝项 | `closed_loop.consumersNeedRebuild` **从拒绝项中消失**；只剩 `review.closedLoopVersion 19≠14` 与 `review.closedLoopChecksum` 两项 ⇒ **等复核代次发布** |

> **为什么「同校验和再物化」是**清除**而不是**改写**：`closed_loop_manager` 的
> `materialize_impl` 在 `checksum_changed == false` 时**不替换行**，
> 只调用 `clear_consumers_need_rebuild()` ⇒ 目录行**一字未动**，
> 被清的是**标志**，不是数据。

> **⚠️ 实测到的真实隐患（如实登记）**：`flashloan/tools/target/release/composite-manager.exe`
> 是 **08:05** 的**旧构建**（**不含** `T-方闭.01` 的备用池接线修复）⇒ 它的 dry-run
> 给出 **168 闭环 / 504 跳 / 校验和 sha256:19168935…**（= v18）⇒
> **若用它 `--apply`，会把目录从 174 回退到 168**。
> 目录内**只有 debug 构建（12:12）与源码一致**（dry-run 逐字段相等）。
> ⇒ **本任务的实测一律用 debug 构建**；release 构建与源码**不同步**这件事
> **不在本任务范围**（属部署产物），**如实登记**在此，不代为修复。

### 2.2 复核代次为什么迟迟不发（**实测根因**）

| 事实 | 读数 |
|---|---|
| 闭环目录发布的方向组数 | **174**（每组 1 个闭环 ⇒ 需要 **174** 个常驻 worker） |
| **overview** 给出的方向组数 | **174**（与目录**完全覆盖**，缺口 0） |
| **扫描器 payload** 给出的方向组数 | **104**（**与目录缺 74** ⇒ 见 §2.3） |
| 修复前的常驻 worker 上限 | **16**（且内联硬顶 32） |
| ⇒ 没有 worker 的闭环数 | **158** |

`covers_catalog()` 要求**证据条数 == 目录条数 == 174**。
158 个闭环永远拿不到证据 ⇒ `review_publish_block` 永远返回
`coverage_incomplete` ⇒ **复核代次永不发布** ⇒ 上面那条因果链**永远断在这里**。

**修法**（`M-8` 编排层，**门禁一字未动**）：
把「常驻组上限」与「并发上限」拆开，删掉扫描器里内联的那份
「默认 16 / 硬顶 32」复制品，改调**共享**的 `resolve_resident_group_limit()`。
详见 `D-047` `1.3。

### 2.3 第二层根因：**方向组全集**缺 74 组（**死锁**）

> §2.2 放开的是**容量**。容量放开后常驻上限不再是 16，
> 但**方向组全集本身**仍缺 74 组 ⇒ 那 74 个闭环**连第一个 worker 都拿不到**。

| 事实 | 读数 |
|---|---|
| 闭环目录发布的**方向组**数 | **174** |
| 扫描器 payload 的 **route** 数 / **方向组**数 | **104** / **104**（与常驻 worker 组集合**完全相同**，双向差 0） |
| 两者**交集** | **100** 组 |
| **目录有、扫描器没有 route** 的组 | **74** |
| **扫描器有、目录没有** 的组 | **4**（`spy¦coin¦usdg`、`spy¦eth¦meta`、`spy¦meta¦eth`、`spy¦usdg¦coin`） |

> **口径**：按**方向组**（`anchor¦Y¦Z`）统计；按**物理闭合键**（地址有序三元组）
> 统计同源（扫描器 104 / 目录 174 / 交集 100 / 扫描器独有 4 / 目录独有 74）。

**死锁形状**：组只有在扫描器产出 route 时才成为常驻 worker，
而扫描器只产出**已经持有 worker** 的组的 route ⇒ 74 个目录组永远拿不到第一个 worker
⇒ 永远拿不到复核证据 ⇒ `covers_catalog()`（证据条数 == 目录条数 == 174）永不成立。

**为什么是「不一致」而不是「设计」**：**手动复核路径**
（`_refresh_native_closed_loop_group_locked`）**早已优先用 manager 闭环视图**，
其注释原文即为
“Mainnet refresh prefers the RuntimeCore manager overview so loop libraries that are
not yet in the static observation snapshot can still be submitted.”
⇒ **自动扫描路径漏了这一步** ⇒ 同一份目录，两条路径给出**不同的方向组全集**。

**修法**（`M-8`，**门禁一字未动**）：`_submit_native_closed_loop_groups()` 先收扫描
payload 的组（**原行为不变**），再取 **manager 闭环视图**并**只补齐缺失的组**；
新增 `_native_chain_runtime()` 让**后台扫描线程**（无 Flask app context）
也能拿到 RuntimeCore 绑定。详见 `D-047§ §1.3.1。

**多出来的 4 组为什么不破坏门禁**：它们**不在已发布闭环目录内** ⇒ 内核
`apply_closed_loop_identity()` 找不到对应 identity ⇒ 只写
`closedLoopIdentityStatus = "mismatch"`、**不写** `closedLoopKey`
⇒ **不产出复核证据** ⇒ 证据条数仍为 **174**（= 目录条数）。
