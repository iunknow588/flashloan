## 3. 读数二：「旧价格」的确切来源

**不是**复核读了旧价，**也不是**链上返回了旧价，而是**离线扫描读了库里存的价格**：

1. 池只有在**作用域内**（active）才会被刷新。
2. 被排除出 active 作用域的池（`invalid` / `blocked`）**永远不刷新**，库里留着**最后一次**读到的价 ——
   那个价可以是 **11 天前**的。
3. 「扫全表」的分析（离线扫描）把陈旧价与活池的价混在一起乘，于是**造出**了并不存在的套利。

**合约本身不受影响**：复核走链上 `runArbitrage`，价格永远是当下的。
所以「旧价格」只污染**离线分析**，不污染**运行时判定**。

## 6. 顺手修掉的**两处**缺陷

### 6.1 状态语义：把「没利润」写成了「广播丢了」

**缺陷**：运行时每轮复核之后无条件调用 `release_broadcast_pending_loop`，只要没有广播尝试就把闭环的
`status_reason` 覆盖成 `the broadcast never became an attempt` ——
**哪怕该轮根本没有利润、根本不存在广播**。
生产库实测：**8 条闭环有 7 条**挂着这条误导性理由。

**修法**：

1. `closed_loop_manager` 新增 `read_runtime_status_on_connection` / `read_runtime_status`（读 `runtime_status`）。
2. `worker_pool.rs` 的 `release_broadcast_pending_loop` 加**状态闸门**：**只有**
   `runtime_status == broadcast_pending` 才写；否则原样返回「这个闭环不在广播哨兵上」。
   （`release` 的职责本来就是「把**等回执**的闭环放回复核队列」，对**不在等回执**的闭环没有发言权。）

**回归**：新增 `a_loop_that_is_not_parked_at_the_broadcast_sentinel_keeps_its_reason`。

### 6.2 写锁**不等** ⇒ 手工复核请求被丢掉

**缺陷**：`closed_loop_manager::open_connection` 打开连接时**没有设忙等待**（`busy_timeout`），
SQLite 的默认是 **0** ⇒ 锁被别的写者占着时，**第一次尝试就失败**：`database is locked`。

**实盘**：手工复核请求（`POST /v1/closed-loops/review-request`，`waitSeconds = 0`）返回
**503** `closed loop storage error: database is locked` —— 复核**根本没开始**，
而原因只是一把锁。

**修法**：`open_connection` 对**可写**连接统一设 **60 s** 忙等待（与仓里已有的两处写法一致）。

**回归**：新增 `a_writer_waits_for_the_lock_instead_of_failing_at_once`（持锁者不放手时，
第二个写者**在等**而不是立刻失败；放手后拿到锁）。

**上线后的实盘读数**：同一个请求 ⇒ **200**、`applied = true`；
闭环从 `cooldown / measured_without_profit` 变成 **`ready_for_review` / `review_required`**，
`next_review_at` ＝ **请求那一刻**（**19:01:28**）⇒ 运行时**8 秒后**就测了这条闭环
（**19:01:36**），轮末回到 `cooldown`、`next_review_at` ＝ **19:02:59**（＝轮末 **19:01:59** ＋ **60 s**）
⇒ **手工复核把复核启动时间设成了当前时间**，复核结束**重新计时**（用户口径）。
