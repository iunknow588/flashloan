## 1. 「旧数据」的真身：不是旧价格，是**写回被整批拒绝**

### 1.1 先把两件事分开

* **复核读到的价格**：每次都是链上现读，**没有**「旧价格」进复核这一步。
* **库里那一行**：它记的是「**最后一次成功写回**」的快照。写回失败，这一行就一直停在旧时刻。

写数（`flashloan/db/local_store_4663.sqlite3`，只读）在 02:05Z 时读到的就是这样：

| 读数 | 值 |
|---|---|
| `MAX(manager_v4_reviews.reviewed_at)` | `2026-11-27T02:02:06Z` |
| 10 条当前闭环里带 `last_reviewed_at` 的 | **1** 条 |
| 其余 9 条 | `last_reviewed_at=NULL`、`next_review_at=NULL`、`review_required=1` |
| `manager_v4_reviews` 总行数 | 176（= 10 当前 ＋ **166** 已退场闭环） |

### 1.2 真根因：编排器把**已退场闭环**的复核一并提交，Manager **整批拒绝**

编排器每轮做两件事：先 `converge_reviews`（成功），再 `fill_current_loop_reviews`（实时复核 10 条闭环、
`candidateCount=10`、`evidenceCount=10`，**复核本身全部成功**），然后把证据**物化**回 Manager 库。
物化这一次**失败**了 —— journal `supervisor_20261127T015646Z.jsonl`（`healing_cycle` · `02:04:57Z`）里
`fill_current_loop_reviews → materialization.response`：

```json
{"ok": false, "status": 400,
 "error": {"code": "INVALID_REQUEST",
           "message": "review evidence references unknown loop
                        0xff080c8ce2e5feadaca0da81314ae59d232d4afd:0x0000…0000:0x117cc…"}}
```

物化提交的证据是 **157 块**（10 条新的 ＋ 147 条存量）。存量里带着那 **166** 条**已退场闭环**的旧复核，
而 Review Manager 的 `validate_evidence_membership`（`review_manager/src/lib.rs:2478`）规定：

> 证据必须**逐字**点名 Manager 发布过的闭环；点不到就是 `UnknownClosedLoop`。

校验是**整批**的 —— 一条对不上，**整次写入全部作废**：复核行没写、闭环的复核计时也没重启。
于是「库里那一行」永远停在上一轮的旧时刻，看上去就是「旧数据」。

**这不是价格问题，是写入被拒的问题。**

### 1.3 修法：只提交**当前目录**的闭环

`scripts/mainnet_arbitrage_healer.py` 的 `merge_with_stored_evidence` 原来把库里的复核**全部**带上，
现在只带**当前闭环目录仍然发布**的那些，退场的按计数上报（`retiredReviewCount`），不再悄悄混进去：

```python
published = {row["loop_key"].strip().lower() for row in manager_loop_rows(manager_api)}
for item in stored:
    if published and loop_key.lower() not in published:
        retired += 1
        continue
```

Review Manager 那侧的**严格校验保留不动**（点错闭环仍然必须整体失败 —— 那是身份完整性，不是噪声）。

## 2. 复核计时重启：**生产读数**

修好之后（10:52Z 起），10 条闭环全部拿到自己的钟：

| 读数 | 值 |
|---|---|
| 带 `last_reviewed_at` 的闭环 | **10 / 10** |
| `next_review_at` | **= `last_reviewed_at` + 600 s**（逐条核对一致） |
| `review_required` | **0**（不再等复核） |

说明它们是**逐条被重新测量**的，不是同一份快照被复制了 10 遍。

## 3. 复核记录：时间入档、按该时刻选文件、固定北京时区

### 3.1 改前：记录行里**没有**复核时刻

`records.rs` 的 `ReviewRecordLine` 只有 `observedAt`（**写入**时刻），没有「复核**发生**的时刻」。
两个后果：

1. **文件归桶用的是写入时刻**，不是测量时刻 ⇒ 记录和文件对不上；
2. `same_audit_state` **不比较时间** ⇒ 一次**内容相同**的重新测量**根本不产生记录行** ⇒
   「这条复核是什么时候测的」在记录里查不到。

### 3.2 改后

| 改动 | 落点 |
|---|---|
| `ReviewRowSnapshot` 新增 `reviewed_at`（**测量时刻**），并进入 `same_audit_state` | `records.rs` |
| `ReviewRecordLine` 新增 `reviewedAt`（写入时按北京时渲染，带 `+08:00` 偏移） | `records.rs` |
| 文件归桶改用**测量时刻**：`line_hour` 先读 `reviewedAt`，再回落 `observedAt` | `records.rs` |
| 保留期清理的「今天」改为北京时，与日期目录同一把尺子 | `records.rs` |
| 链上区块时间读入即转北京时（`read_block_timestamps`） | `pool_manager/src/pool_roles.rs` |

**时区是固定偏移（UTC+8），不是机器时区**：文件命名和记录里的时刻在任何机器上读出来都是同一小时。
记录自带偏移 ⇒ 文件名可以直接从记录本身读回来。

### 3.3 「本机时间 vs 服务器时间」的落点

复核的测量时刻由**这台机器**给出（运行时 `measured_at = chrono::Utc::now()`），
链上时间只在 `pool-manager` 读区块时被取用，取用即转北京时。
复核链路上**没有**任何一处用链上区块时间当复核时刻。

* 10 条闭环当前**全部** `not_executable`（`runArbitrage returned ok=false`，费后现货乘积为负）⇒
  **广播请求仍是 0 行**，「持续产生链上广播交易记录」**未达成**；
  缺口在**上游没有正收益复核**，不在广播准入，本轮**没有放宽任何门禁**。
* 运行时在本轮多次处于 `busy`（readiness 超时），编排器按既定规则**跳过修复轮**；
  复核因此主要由运行时自己的发布路径完成，而不是编排器的物化路径。
* 「已退场闭环的复核」现在**不再被提交**，但那 **166** 行**仍留在库里**（它们是历史，不是价格）；
  是否清理是另一件事（D-222 缺陷 D）。
