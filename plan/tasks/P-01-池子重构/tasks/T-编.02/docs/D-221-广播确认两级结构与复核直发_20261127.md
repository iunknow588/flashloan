## 0. 用户口径（本轮起点）

> 「**复核正收益，直接广播，这个过程还需要再次复核广播么**，是否需要优化这个流程呢，
> 否则浪费交易时机。」
>
> 「就是复核工作线程发现正收益，直接发出广播交易指令，然后把相关的响应数据留在广播确认线程来完成。」
>
> 「**广播确认主线程的任务要注意调整，需要动态等待广播消息，启动广播确认工作线程。**
> 广播确认工作线程再确定时 重发还是直接解析结果存储数据记录。」

> 「复核线程的广播包括广播消息的签名确认，这是一个完整的过程。消息确认以及解析交给广播确认线程，
> 确认的是**广播交易的结果**，不是广播消息的签名。……当出现错误需要重试的时候，可以再次发送消息，
> 并签名确认，这也是其正常的工作内容，只是**首次发消息的功能在复核线程中实现**，减少时间的损耗。」

这四条口径落成了三件事：

| # | 口径 | 落点 | 状态 |
|---|---|---|:---:|
| U1 | 复核正收益 ⇒ **状态机直接切换**，中间**不再复核、不再审计拦截** | `worker_pool.rs` · `broadcast_from_review()` | ✅ |
| U2 | **首次发送（含签名）在复核线程**完成；回执解析与失败重发在**广播确认线程** | `worker_pool.rs` · `run_confirmation_task()` | ✅ |
| U3 | 广播确认**主线程动态等待消息**，**按消息启动工作线程**；工作线程再判定「重发」还是「解析落库」 | `broadcast_manager/src/runtime.rs` · `BroadcastSupervisor::start` | ✅ |

**框架不变**：仍然是「确认广播线程 ＋ 主线程 ＋ 工作线程」三段。变的只是**名字**与**分工**：
旧「广播线程」改名**广播确认线程**，内部由**主线程**（等消息、起工作线程）与**工作线程**（干活）组成。

## 1. 裁定一改判：「复核线程不广播」→「复核线程直发 ＋ 确认线程异步」

### 1.1 改的是什么

| | 改前 | 改后 |
|---|---|---|
| 复核线程 | 复核出正收益 ⇒ **入队**，把活交给广播线程 | 复核出正收益 ⇒ **就地签名、就地发送**，随即把**确认项**入队 |
| 广播线程 | 签名 ＋ 发送 ＋ **等回执** ＋ 解析 | 改名**广播确认线程**：只管**回执**（链上交易结果） |
| 状态机 | 复核正收益 ⇒ 待广播 ⇒ 广播线程复核一遍 ⇒ 广播 | 复核正收益 ⇒ **已广播**（直接切换） |
| 二次复核 | **有**（浪费一个交易时机） | **无** |

### 1.2 为什么签名留在复核线程

签名是**发消息**的一部分，而发消息是**首次**动作。把它留在复核线程里，
链上交易能在复核判定的**同一个瞬间**发出去；确认线程接手的是**已经发出的交易**，
它要回答的是「链上这笔交易的结果是什么」，而不是「这条消息要不要发」。

确认线程**仍然碰签名**，但只在**重发**的时候：链上**拒收**（没有产生交易）时，
重新发消息、重新签名，是它正常的工作内容。

### 1.3 三态判定（确认线程的工作线程做）

| 链上的事实 | 判定 | 动作 |
|---|---|---|
| 交易**被接受**（有 txHash），链上**未回执** | 事实成立，**沉默不是判决** | 轮询回执（**120 s** 上限，**2 s** 间隔） |
| 交易**被接受**，链上**已回执** `status=1` | 成功 | 解析回执 ⇒ **同一 attempt 行改写为终态** |
| 交易**被接受**，链上**已回执** `status=0` | 链上**挖出但回滚** | 判决就是判决 ⇒ **不再重发**，落终态 `failed` |
| 交易**被拒收**（无 txHash） | 没上链 ⇒ **没有可确认的东西** | **重发**（新签名、新交易），最多 **3** 次 |

常量：`BROADCAST_CONFIRMATION_MAX_SENDS = 3`、`BROADCAST_CONFIRMATION_TIMEOUT_SECONDS = 120`、
`BROADCAST_CONFIRMATION_INTERVAL_SECONDS = 2`（`rs-src/src/worker_pool.rs`）。

### 1.4 pending 与终态

| 状态 | 含义 | 何时写 |
|---|---|---|
| `pending` | **已发出、未确认** | 复核线程直发之后**立刻**落记录 |
| `success` | 链上回执 `status=1` | 确认线程拿到回执 |
| `failed` | 链上回执 `status=0`（挖出但回滚）或重发耗尽 | 确认线程 |

`pending` 的 attempt **不能**被当作终态去结算
（`validate_finalization_input` 拒绝 `a pending attempt cannot be finalized`），
`terminal_at` 在 `pending` 时是 `None`。

## 2. 广播确认主线程：动态等待，按消息起工作线程

`flashloan/tools/broadcast_manager/src/runtime.rs` · `BroadcastSupervisor::start`：

```
主线程  {prefix}-main
  └─ 在队列上动态等待（condvar）
       └─ 每来一条消息 ⇒ spawn 一个工作线程 {prefix}-worker-N
            ├─ skip 判定
            ├─ handler（复核线程 ⇒ run_execution_task；确认项 ⇒ run_confirmation_task）
            └─ complete(key)
```

| # | 设计点 | 为什么 |
|---|---|---|
| D1 | 主线程**只等消息**，不干活 | 一条消息等 120 s 回执，**不该**堵住另一条消息 |
| D2 | **按消息起工作线程**，并发上限 `worker_count`（clamp 1..8） | 交易数 ⇒ 线程数，两条交易互不等待 |
| D3 | 队列键用 `task_key`：**请求**按 group 覆盖（一闭环一当前复核），**确认项**按交易唯一 | 确认项彼此**不覆盖** |
| D4 | 线程前缀 `rust-broadcast-manager-exec` ⇒ `rust-broadcast-confirmation` | 名实相符 |

读数：`cargo test -p broadcast-manager` ⇒ **42 passed / 0 failed**
（新增 2 个：`task_key` 语义、主线程按消息起工作线程）。

## 3. 本轮修掉的复核层回归：金额阶梯闸门**曾经失效**

### 3.1 症状

`cargo test --workspace`（tools 全量）里 `manager-api` **174 passed / 1 failed**：
`tests::a_review_without_a_measured_ladder_is_data_incomplete` ——
断言 `completed_count == 0`，实测 **1**。

### 3.2 根因

上一轮把「市场移动」从**闸门**改成**证据**（`transition_blocked` 几乎恒为 `None`），
而金额阶梯的 `data_incomplete` 闸门**被挂在** `(None, Some(_))` 这个分支上：

```rust
(None, Some(_)) if !ladder_measured(&static_preview) => ("data_incomplete", ...),
```

分支的前提（`Some(_)`）不再成立 ⇒ **阶梯闸门成了死代码**：
一条**从未被金额阶梯探测过**的路由，**只要 `runArbitrage` 报 ok ＋ 可执行**，
就会被记成 `completed`（＝可以发广播）。

### 3.3 修法

把阶梯闸门从**市场移动分支**里拿出来，做成**独立的一支**：

```rust
(_, _) if !ladder_measured(&static_preview) => ("data_incomplete", ...),
```

语义变得和**它本来要问的问题**一致：
「这条路由**有没有被金额阶梯真正探测过**」与「市场动没动」**互不相干**。

### 4.2 旧价格的**两个**入口，逐一封堵

**入口一：复核管理器的链上读回落（系统内）**

`flashloan/tools/review_manager/src/lib.rs` · `read_current_pool_states()`：

```rust
if let Ok(states) = read_live_pool_parity_states(...  /* 链上，同一批次、钉在一个区块 */ ) {
    return into_map(states);
}
read_pool_parity_states(...)   /* ← 回落：库里的存储快照 */
```

这是系统内**唯一**能让陈旧读数进入复核的路径，而且它**不是无声的**：
`read_live_pool_parity_states`（`pool_manager/src/parity_state.rs`）对**读失败的池**
**保留整条存储测量**（`sqrt_price_x96` / `tick` / `liquidity` **连同** `liquidity_read_at` 一起保留），
于是复核的**陈旧池态闸门**看得出「这条读数不是当前区块」，**拒掉这一跳**，
而不是拿旧价算出一个假盈利。

⇒ **旧价格 ⇒ 复核拒绝**，永远不会变成一条广播请求。

**入口二：离线扫描脚本读库里的存储快照（本轮 +1266 ppm 的真正来源）**

`plan/runtime_evidence/logs/t401_runtime_sup/v4_cycle_scan_20261127.json`（**库读**，非链上）：

| 项 | 读数 |
|---|---|
| `poolCount` / `orderedPairCount` / `cycleCount` | **365** / **66** / **60** |
| `profitableCycleCount`（**库读**） | **12** |
| `profitableAnchoredCycleCount` | **0** |
| 「最优环」`ETH→PFE→CRCL` 第一跳 `pool_status` | **`invalid` / `fee_not_fixed_candidate_range`** |
| 「最优环」第一跳 `liquidity_read_at` | **2026-11-17T20:13:27Z**（**10 天前**） |
| 「最优环」第二、三跳 `liquidity_read_at` | 2026-11-26T17:59Z（**约 1 天前**） |

离线扫描**没有闸门**，所以它把一条**10 天前、且状态已经是 `invalid`** 的存储读数

### 4.4 「复核是旧记录，广播之前发现过期、重新复核」这条

是的，而且**已经是这样**：复核行带 `closed_loop_version` / `checksum` / `reviewed_at`；
广播闸门**先**校验复核行的版本与新鲜度，过期直接**拒绝并要求重新复核**
（`stale_closed_loop_version_is_rejected_without_writes`、
`stale_positive_review_never_generates_automatic_broadcast_request`）。
`REVIEW_STALE_AFTER_SECONDS`（默认 **5400 s**）之外还有一轮**按秒**的陈旧扫描
（`mark_stale_reviews`）把超时闭环标成 `not_reviewed_since:<ts>`。

## 5. 主网实测：**2 条闭环的复核拿不出盈亏数值**（用户第 3 步）

### 5.1 症状

当前核心库 **10** 条闭环的复核结果：

| 复核状态 | 条数 | 说明 |
|---|---:|---|
| `not_executable` | **8** | `runArbitrage returned ok=false`，**带明确负盈亏** |
| `data_incomplete` | **2** | `signed PnL is missing or incomplete`，**没有盈亏数值** |
| `completed`（可广播） | **0** | — |

### 5.2 根因：`SwapNotResolved()` ≠ 「不盈利」

两条 `data_incomplete` 的 `run_arbitrage_json`：

```json
{"error": "execution reverted", "ok": false, "executable": false,
 "revertData": "0xb20c2204", "revertSelector": "0xb20c2204", "signedPnl": null}
```

选择器解码（keccak-256 前 4 字节）：

| 选择器 | 错误 | 有参数吗 |
|---|---|---|
| `0x16301234` | `ArbitrageNotProfitable(uint256 received, uint256 required)` | **有** ⇒ 能解出**精确的亏损** |
| `0xb20c2204` | **`SwapNotResolved()`** | **没有** ⇒ 解不出任何数字 |

那 8 条 `not_executable` 之所以**有**负盈亏，正是因为它们拿到的是
`0x16301234` ＋ 两个参数（`received` / `required`），差值就是费后亏损。

而这 2 条拿到的是 **`SwapNotResolved()`**：**合约没能解析出这笔 swap**。
这不是「不赚钱」，而是**路由本身跑不通** —— 它**永远拿不到**盈亏数值，
因为链上根本没成交。

### 5.3 定位到具体的方向池

把 10 条闭环逐跳对齐 `manager_v4_directional_exchange_pools`：

| 闭环 | hop1 | hop2 | hop3 | 复核 |
|---|---|---|---|---|
| `ETH → NVDA → MU → ETH` | `0x71f9660f` | `0x7b1c4469` | **`0x0fef17ec`** | **data_incomplete** |
| `ETH → SPY → MU → ETH` | `0x509c6c68` | `0xcc2a903a` | **`0x0fef17ec`** | **data_incomplete** |
| `ETH → MU → NVDA → ETH` | **`0x0fef17ec`**（方向 1） | `0x7b1c4469` | `0x71f9660f` | not_executable（有亏损值） |
| 其余 7 条 | 都不含 `0x0fef17ec` | | | not_executable（有亏损值） |

⇒ 同一个池 `0x0fef17ec…`（**MU ⇄ ETH**）：
**方向 1（ETH→MU）能跑**，**方向 0（MU→ETH）解析不出来**。
两条出问题的闭环**都**用到它的方向 0。

⇒ 这是一个**方向性池缺陷**，落在用户第 2 步：
「如果代币有效，就检查池子，如果池子无效，可以使用**池子工具修复池子的有效性**」。

### 5.4 诊断口径的缺口（本轮发现，未修）

复核管理器**已经**有 `swap_not_resolved` 这个诊断类型
（`review_manager/src/lib.rs` · `ReviewDiagnosticType::SwapNotResolved`），
但生产库里这两条闭环挂的是 **通用** 诊断：

| diagnostic_type | diagnostic_code | message |
|---|---|---|
| `evidence_missing` | `EvidenceMissing` | `signed PnL is missing or incomplete` |
| `evidence_missing` | `measured_signed_pnl_missing` | `the route was not priced, so it carries no measured signed profit` |

⇒ 编排器看到的是「证据缺失」，**看不出是哪个池解析不出来**，也就**无从修**。
**下一步**：让 `SwapNotResolved` 走选择器 → 诊断类型的分类，并带上 `hop_index` 与 `pool_id`。
