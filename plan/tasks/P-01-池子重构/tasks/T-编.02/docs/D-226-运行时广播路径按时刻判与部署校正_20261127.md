## 1. 读数一：运行时广播路径还在用 **age 窗口**（第四处）

### 1.1 旧判据长什么样

`flashloan/rs-src/src/worker_pool.rs::wake_broadcast_with_review_proof`
（**运行时**把复核发布的请求变成广播消息的那一步）：

``text
const MAX_BROADCAST_REQUEST_AGE_SECONDS: i64 = 120;
let age = (Utc::now() - reviewed_at).num_seconds();
if age > MAX_BROADCAST_REQUEST_AGE_SECONDS { 拒绝："the published request is {age}s old" }
`@

这一处的 **age** 算的是「**测量时刻**到现在有多久」——和 `D-225` 里已经改掉的三处
（stale sweep ／ 物化广播请求 ／ 广播准入）**是同一个量**。
也就是说：**同一个错误在核心库里还有第四个落点**，而这一处正好在**正收益复核
变成广播消息**的门口。

| 层 | 位置 | 改前判据 | 改后判据 |

同一个请求，两层用两把尺子量；准入放行、运行时拒绝，或反过来。

## 2. 修法：运行时也**只比时刻**

`flashloan/rs-src/src/worker_pool.rs`

``text
now <  闭环的复核时间点  ⇒ 放行（这条复核还是闭环的当前测量）
now >= 闭环的复核时间点  ⇒ 拒绝（闭环已经往后走了：轮结束了，请求是上一轮的）
闭环没有复核时间点      ⇒ 拒绝（证不出来 ⇒ 不发；失败即闭锁）
future skew > 30 s      ⇒ 拒绝（两个钟对不上，不是测量）
`@

* **删掉** `MAX_BROADCAST_REQUEST_AGE_SECONDS`（120 s 的 age 窗口）与其判定。
* 复核时间点从**闭环管理器**读（`closed_loop_manager::read_review_queue` ⇒ `due_at`），
  **不重建任何间隔**；间隔已经在设置时刻的辅助函数里折进这个时刻了。
* **哨兵不特殊**：`2036-06-06`（正在复核）与 `2035-05-05`（正在广播）都在**未来**，
  于是 `now < 时刻` 成立 ⇒ 放行。**忙碌不是过期**。
* `reviewAgeSeconds` 仍作为**观测值**写在结果里（它是读数，不是判据）。

## 3. 读数二：运行时**到底加载哪一个 Rust 产物**（部署读数订正）

> **本节订正本文上一稿的结论。** 上一稿写「运行时加载的是 site-packages 的
> `09:54` 旧件，`22:42` 那件 DLL 没有人用」——**这个结论是错的**，
> 事实恰好相反。下面是**实测**，不是推断。

### 3.1 加载顺序：工作区自建件**优先**

`flashloan/src/core/rust_extension.py::load_rust_extension` 的候选顺序是：

1. 环境变量 `FLASHLOAN_RS_EXTENSION_PATH`；
2. **工作区自建件** `flashloan/rs-src/target/release/flashloan_rs.dll`（再 `.pyd` / `.so`）；
3. 都加载不了才回落 `importlib.import_module("flashloan_rs")`（＝ site-packages）。

文档第一行就写着「**Load the worktree-owned Rust extension before any installed fallback.**」

### 3.2 实测：运行时进程里映射的那个模块

工具：读运行时的**进程模块表**（不是猜路径）。

| # | 读数 | 值 |
|---|---|---|
| M1 | 运行时 PID | **18004**（**22:56:14** 启动，`flashloan/app_runtime/run.py --port 5000`） |
| M2 | 该进程映射的 Rust 模块 | **`flashloan_rs.dll`** |
| M3 | M2 的**真实路径** | **`E:\2026OPC大赛\flashLoan\flashloan\rs-src\target\release\flashloan_rs.dll`** |

⇒ 运行时加载的**就是**工作区那件 **22:42** 的 DLL，**不是** site-packages 的旧件。

### 3.3 订正后的「上线」账

判据：**构件的编译时刻** 与 **它含进去的源码的写入时刻** 比大小
（cargo 凭 mtime 决定重编 ⇒ 源码更早 ⇒ 已被编进）。

| 落点 | 源码写入时刻 | 编进哪个构件 | 构件时刻 | 上一轮上线了吗？ |
|---|---|---|---|:---:|
| 编排器（Python）陈旧判定 | 22:xx | 编排器进程 | **22:56** 重启 | ✅ |
| `review_manager` stale sweep（Rust） | **22:11** | 工作区 DLL ＋ `manager-api.exe` | 22:42 ／ 22:53 | ✅ |
| `broadcast_manager` 准入 `loop_scheduled_at`（Rust） | **21:52 – 21:53** | 同上 | 22:42 ／ 22:53 | ✅ |
| 运行时广播路径（Rust，`worker_pool.rs`） | **23:29**（本轮才写） | 工作区 DLL | **22:42 早于它 ⇒ 没编进去** | ❌ |

**结论要改写**：

* 上一稿说「Rust 侧的三处改动在观察窗口里一次都没有被真正执行过」——**错**。
  上一轮的三处 Rust 改动**已经上线**（22:42 的 DLL ＋ 22:53 的 manager-api）。
  `D-225` 的实盘读数**同时**包含 Python 与 Rust 两边的改动，原先的归因**只算 Python 一边**，偏窄。
* 真正没上线的只有**一处**：本轮 `worker_pool.rs` 的时刻口径。
  原因是**顺序**，不是部署事故：**旧 DLL 已经在跑**，源码改动是在那之后才写的
  （23:29 > 22:42）⇒ 必须**重建 + 重启**才生效。

## 5. 读数四：一张表缺失就让**整轮自愈**中断

`supervisor_20261127T120525Z.jsonl` 的第 11 个采样：

``text

同一个文件里，代币表就是按 `table_names(db)` **先查存在再读**的（`HEALER` 既有约定），
