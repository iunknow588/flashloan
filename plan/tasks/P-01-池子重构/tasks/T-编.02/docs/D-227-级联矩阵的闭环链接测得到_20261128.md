### 1.2 为什么测不了（**两处**独立的错）

| # | 错 | 事实（实测） |
|---|---|---|
| E1 | **字段名对不上** | 管理器发布的闭环行里**没有** `poolIds` / `pool_ids`；它发布的是 **`directionalPoolIds`**，而每跳的池另有**跳行**（`hops[]`，含 `directionalPoolId` ＋ `directionalScopeKey`） |
| E2 | **池 ID 的格式不同** | 闭环侧发的是**组合 ID**：`dpool:v1:<网络>:<链>:<作用域>:<池键>:<名次>`；候选作用域侧发的是**裸池键**（`0x…`）。两者**直接比较永远不相等** |

E2 是关键：**即使把跳行接上**，不规范化格式的话，每一跳都会被判成「不在候选作用域内」——
于是「闭环的池不在作用域内」这条**假缺陷**会一直响。

### 1.3 实测：真相其实是**好的**

只读核对（管理 API 的跳行 ＋ 生产库的候选池表）：

| 读数 | 值 |
|---|---|
| 闭环 ／ 跳行 | **8** 条闭环 ／ **24** 条跳行（每条闭环 **3** 跳） |
| 跳的**原始池键**落在当前候选作用域池集（**26** 个）内 | **24 / 24** |
| 跳的**作用域分布** | `core4` **16** 跳 ＋ `candidate_exchange` **8** 跳 |
| 缺跳的闭环 | **0** |

⇒ 闭环层**本来就健康**；坏的是**量它的尺子**。
