# D-222 ｜加载模式的落点、候选数据保留与「复核后重新计时」（`T-编.02` · `2026-11-27`）

> **本文只记实测读数**。生产库全程只读：`mode=ro` ＋ `PRAGMA query_only=ON`。
> 库：`flashloan/db/local_store_4663.sqlite3`（robinhood / 4663）。

## 0. 用户口径（本轮起点）

> 「**修改启动的资金池的启动方式，不应该去影响池子信息**，股票代币测试代币的相关数据应该都还在库里面，
> 只是没有用到，**不应该清空候选池子数据**吧，毕竟下次修改资金池启动模式，这些闭环以及池子数据。
> 应该都还会用到，而且当前也**没有清空候选池的入口**。
> 请**分析当前的处理有没有一些细节上的处理缺陷**。」
>
> 「**复核过后，闭环的再次复核计时时间应该重新开始计时，不是一直维持不变。**」

这两条口径拆成两件事：

| # | 口径 | 落点 | 状态 |
|---|---|---|:---:|
| U1 | 改**加载模式**不得动**池子/代币/候选池**的存量数据；被排除的行只是「不用」，不是「删掉」 | `pool_manager` · `candidate_edge_pool_manager` · `closed_loop_manager` | 读数确认 + 缺陷定位 |
| U2 | 复核完成后，闭环的**再次复核计时重新开始** | `closed_loop_manager` · `review_manager` · `mainnet_arbitrage_healer.py` | ✅ 已落地 |

## 1. 结论一：存量数据**没有**被清空

「资金池启动方式」= **池 scope 的加载模式**（`tokenLoadMode`）。它只写进一张表：

```
pool_scope_config
  core4             library_keys_json=["core"]   filter_mode=edge_any   last_rebuilt_at=2026-11-26T19:29:48Z
  candidate_exchange library_keys_json=["core"]   filter_mode=both_end  last_rebuilt_at=2026-11-26T19:29:48Z
```

改模式走的是 `POST /v1/pools/scopes/rebuild|repair`（请求体 `tokenLoadMode`），
重建时只重写 **scope 表本身**（`pool_manager/src/scope.rs:1433` 的 `DELETE FROM {scope.pool_table}`），
**master 池表与代币目录一律不动**。生产库读数：

| 表 | 行数 | 结论 |
|---|---:|---|
| `v4_exchange_pools`（master，模式的**源**） | **2550** | 完整保留 |
| `v4_exchange_pools_core4`（scope） | 415 | 派生视图，随模式收窄 |
| `v4_exchange_pools_candidate_exchange`（scope） | 429 | 派生视图 |
| `token_core` / `token_stocks` / `token_extension` / `token_test` | 4 / 194 / 162 / 1 | **完整保留** |
| `chain_tokens` | 4619 | 完整保留 |
| `manager_dex_candidate_pools` | 26 行（13 个池 × 2 方向） | 在库 |
| `manager_dex_candidate_pool_recommendations` | 52 | 在库 |
| `manager_dex_candidate_anchor_tokens` | 18 | 在库 |
| `dex_candidate_pools`（legacy） | 74 | 在库 |
| `manager_dex_candidate_abnormal_pools` | 804（legacy 1005） | 在库 |

**清空入口确实不存在**：manager-api 的写入口只有 `POST /v1/reviews/clear` 与 `POST /v1/broadcasts/clear`
（`manager_api/src/lib.rs:276,284`），候选池、候选边、闭环目录**都没有 clear 接口**。
所以「清空候选池」这件事在当前系统里**只能由重建隐式发生**，没有人工路径。

## 2. 结论二：处理确实有细节缺陷（逐条带读数）

### 缺陷 A：加载模式只落到**资金代币锚集合**，没有落到闭环的**候选代币**

| | 事实 | 位置 |
|---|---|---|
| 模式决定的 | scope 的**锚集合**（`TokenLoadMode::fund_token_library_keys`） | `pool_manager/src/scope.rs:60` |
| 闭环读的 | `manager_dex_candidate_anchor_tokens`（**只按 `scope_key='core4'` 过滤，不看模式**） | `closed_loop_manager/src/lib.rs:1443` |
| 候选边写锚点的 | **硬编码** `FUND_TOKEN_LIBRARY_KEYS = ["core","stocks","test"]` | `candidate_edge_pool_manager/src/lib.rs:40` |

读数：模式是 `core`，但 `manager_dex_candidate_anchor_tokens` 的 18 行里**有 9 行的 `anchor_library_key='stocks'`**
（SPY/GLXY/GOOGL/SPCX/META/NVDA/CRCL/MSTR/MU 被登记成**资金代币**），
10 条闭环也全是 `ETH→股票→股票→ETH`。
⇒ 「只加载核心库」在**闭环层没有落地**：候选边管理器不读 scope 的策略，自己决定谁是资金代币。

### 缺陷 B：`candidate_exchange` scope 对模式**完全免疫**（中间跳不受模式约束）

`materialize_raw_pool` 的两个分支：

```rust
match filter_mode {
    "edge_any" => { /* 要求至少一端是锚 */ }
    "both_end" => {}      // ← 空实现：只看「两端是否被准入」
}
```

而「被准入」来自 `token_library_catalog` 视图的 `admission_status='admitted'`（core 4 + stocks 194 + test 1 + extension 2），
**与模式无关**。⇒ `core` 模式下，中间跳（Y→Z）的 `extension↔stocks` 66 条、`extension↔extension` 349 条池照样留在 scope 表里，
而闭环的中间跳正是从这张表取（`directional_scope_key='candidate_exchange'`）。

### 缺陷 C：派生层是「**删 + 重建**」，不是「过滤」

| 层 | 写法 | 位置 |
|---|---|---|
| 候选边 | 对 7 张候选表按 `scope_key` 整表 `DELETE` 再 `INSERT` | `candidate_edge_pool_manager/src/lib.rs:1706` |
| 闭环目录 | 对 5 张闭环表整表 `DELETE` 再 `INSERT` | `closed_loop_manager/src/lib.rs:4287` |

⇒ 收窄模式时，被排除池子的候选行与闭环行是**物理消失**的。用户的心智模型（数据还在、只是不用）在这里不成立；
这些行只能从 master 池表**重算**出来（可再生，但不是「留库不用」）。

### 缺陷 D：闭环目录与复核目录**口径不一致**

`manager_v4_closed_loops` = **10** 条（当前目录），`manager_v4_reviews` = **176** 行，
其中 **166 行是已退场闭环的孤儿复核**（2026-11-26T19:07–19:11Z）。
复核行按 `loop_key` 覆盖写（第二次复核覆盖第一次，符合口径），但**退场闭环的复核行永远留着**——
这是「复核数据太多、无法分析」的直接来源。

### 缺陷 E：复核计时**无处安放**（本轮已修）

改前 `manager_v4_closed_loop_runtime_state` 的列是：
`runtime_status / status_reason / review_generation / review_required / last_rebuilt_at / updated_at`。

* **没有** `last_reviewed_at` / `next_review_at` ⇒ 没有「这条闭环的下次复核时刻」；
* `review_required` **只写不读**（全仓无读点，materialize 时恒写 `true`）⇒ 是个死标志；
* 闭环重建会**整表替换** runtime_state ⇒ 即使加了计时字段也会被重建冲掉；
* 复核时刻只落在 `manager_v4_reviews.reviewed_at`，陈旧扫描（`mark_stale_reviews`）按它重新计时——
  但前提是**新复核真的发生**。改前编排器只给「没有复核」的闭环做复核，
  于是闭环的复核时刻**冻结在第一次复核**，看起来就是「一直维持不变」。

## 3. 本轮改动：复核后**重新计时**

### 3.1 模型

计时属于**闭环**，不属于复核行；每次测量**重启**这个计时。

```
last_reviewed_at = 本次测量时刻
next_review_at  = last_reviewed_at + REVIEW_INTERVAL（默认 600 s，可用 CLOSED_LOOP_REVIEW_INTERVAL_SECONDS 覆盖）
review_required = 0（已复核）/ 1（过期或从未复核）
```

### 3.2 落点

| 文件 | 改动 |
|---|---|
| `manager_db/migrations/20261127_019_review_schedule_schema.sql` | 新增：`manager_v4_closed_loop_runtime_state` 加 `last_reviewed_at` / `next_review_at` |
| `manager_db/src/migrate.rs` | 注册迁移 019（`LATEST_MIGRATION_ID` 前移） |
| `closed_loop_manager/src/lib.rs` | ① 运行时状态行带出两个时刻；② 闭环重建**沿用**存活闭环的计时（不再清零）；③ 新增 `record_review_schedule_on_connection` / `mark_review_required_on_connection` / `next_review_moment` / `review_interval_seconds` |
| `review_manager/src/lib.rs` | ① 复核落库后**重启**闭环计时（与复核行同一事务）；② 陈旧扫描标记过期时置 `review_required=1`、清空 `next_review_at` |
| `scripts/mainnet_arbitrage_healer.py` | 编排器按闭环**自己发布的** `nextReviewAt` 判断是否到期复核；没有发布时回退到「复核行新鲜度」 |

### 3.3 为什么计时放在闭环这一层

闭环目录由 closed-loop Manager 拥有，复核由 review Manager 拥有。
计时是**闭环的属性**（这条闭环多久要重新测一次），所以写入走闭环管理器的公开入口，
复核管理器只是调用方——两层都不越界，计时也随闭环重建**被带过去而不是被冲掉**。

## 5. 遗留

* **缺陷 A/B** 需要一次跨层改动：候选边管理器改读 scope 的 `library_keys_json`，`both_end` 改为按模式准入。
  改完核心库模式的闭环会从「股票三角」变成「核心代币三角」（master 表里两端都是核心代币的池有 **310** 条），
  闭环数会再降一档——这正是「核心库模式便于确定问题」的本意，但会改变当前在跑的生产目录，
  需要单独一轮变更窗口。
* **缺陷 D**（孤儿复核行）需要给复核层加「退场闭环」的清理口径，或按小时文件归档后只保留当期。
* **缺陷 C** 若要满足「被排除的行留在库里只是不用」，需要给派生层引入 scope/代际维度，
  而不是整表替换——这是一次存储层语义变更。
