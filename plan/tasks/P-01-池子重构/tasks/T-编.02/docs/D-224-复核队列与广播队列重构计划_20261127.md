## 0. 用户口径（本轮起点）

> 「在闭环的状态机里面，每个闭环它在广播成功以后都会启动一个时钟，就是下一次复核需要等待时间间隔，
> 一旦这个时间间隔变成 0 了，就要开始启动下一轮复核。」（**已落地**，见 §1.3）
>
> 「闭环对象包括复核开始时间点，复核主线程检测闭环是否到达该闭环的开始启动时间，
> 然后决定是否启动闭环工作线程。这样不要让每个闭环保存一个定时器，只要保留一个复核启动时间点就行了。」
>
> 「闭环对象有一个重置复核起始时间的辅助函数，如果是正常闭环复核广播流程的结束，需要重新开始，
> 就把当前的时间加上复核间隔时间，作为闭环的复核启动时间。如果是手动复核，
> 就把当前时间设置为闭环的复核启动时间。」（**已落地**，见 §1.4）
>
> 「复核主线程，主要是检测一下当前时间是否超过了闭环的复核时间点，由此来决定是否启动该闭环的复核流程。
> 这样也可以控制在系统启动的时候让不同的闭环对象启动时间设为的稍微有差异时间点，
> 从而不会在一秒内超出系统的 RPC 访问频率。」（**已落地**，见 §1.5）
>
> 「**闭环复核队列，当前是否支持按照复核时间排序的功能**，这样，复核主线程只需要保证复核到
> 第一个无需复核的闭环元素，后面就不需要检测了，避免无效的循环检测。」
>
> 「**是不是应该使用 BTreeSet 来处理复核数据？** 复核完成的闭环对象放在广播队列中
> （预期收益为正数的话），或者**重新插入复核队列**（如果预期收益为负数的话）。」
>
> 「**系统可以使用一个队列**，当一个闭环正在复核或者正在等待广播消息确认的时候，
> 把它的复核时间设置为一个**无限远的数值或者 2100 年**，因为这个数值在 100 年之后，
> 等价于永远不会到达。这样，**不需要处理多个队列**，只要保持**一个队列**，
> 加上**闭环状态**就可以完成任务。」（**第四轮修正**：闭环级**只留一个队列**，
> 排序键**只有** `next_review_at`，「正在复核」与「等回执」用**远期哨兵**表示）

| # | 口径 | 落点 | 状态 |

## 1. 现状盘点：逐条回答用户的问题

### 1.1 「复核队列现在按复核时间排序了吗？」

**排了，但排的不是主线程要的那个东西。**

现在只有一个查询：`read_due_review_loops`（`closed_loop_manager/src/lib.rs:4959`）：

```sql
SELECT loop_key, runtime_status, next_review_at, review_cycle_started_at
  FROM manager_v4_closed_loop_runtime_state
 WHERE ... AND runtime_status IN ('ready_for_review', 'cooldown')
   AND (next_review_at IS NULL OR julianday(next_review_at) <= julianday(?5))
 ORDER BY julianday(next_review_at) ASC, loop_key ASC
```

**排序键就是 `next_review_at`**（调度时刻）—— 与用户要的口径**一致**。
但这条 SQL 是**每次调用现算**的：

| 性质 | 现状 | 用户要的口径 |
|---|---|---|
| 排序 | ✅ `ORDER BY julianday(next_review_at)` | 同 |
| **过滤与截断** | ❌ 过滤**在 SQL 里**，主线程拿到的是**已经过滤完**的列表 | 主线程**自己**看到第一个未到点就停 |
| 主线程每轮成本 | **O(作用域内闭环总条数)** | **O(到期条数)** |
| 常驻结构 | ❌ 无（每次查询重建） | ✅ 常驻 |
| 索引 | ❌ `next_review_at` 上无索引 | —— |

### 1.2 「复核主线程只需要检测到第一个无需复核的闭环元素，后面就不需要检测」

**现在做不到，而且不是「差一点」，是方向不同。**

现状：SQL 先把没到点的**滤掉**，主线程拿到的是「已经全部到期」的列表，
主线程**没有**机会看到「第一个未到点的元素」—— 它已经被 SQL 扔掉了。
主线程要判断「还有没有要处理的」，只能靠 `dueCount` 与 `waitingCount` 这两个**数**，
拿不到「下一个什么时候到期」。

主线程真正需要的是**一个有序的、含未到期元素的集合**：

```text
取第一个元素
  ├─ 未到期 ⇒ 后面必然都未到期 ⇒ 本轮结束（不再看）
  └─ 到期   ⇒ 弹出、认领、交给复核工作线程，继续取下一个
```

这正是 `BTreeSet` 能给的：**前缀截断**。

### 1.3 每闭环的定时器

**已经删掉了。**

改前每闭环有一个倒计时器（`review_wait_seconds` 列 ＋ 每闭环一个 timer）；
改后只留一个**调度时刻** `next_review_at`，等待时长在**读取时派生**
（`seconds_until_moment` / `seconds_since_moment`）。
迁移 `20261127_020_closed_loop_review_clock.sql` 把列换成 `review_cycle_started_at`。

### 1.4 重置辅助函数

**已经落地**，只有一个写点：

```rust
pub enum ReviewStartReset { AfterRound, Manual }
pub fn reset_review_start_on_connection(..., reset: ReviewStartReset, ..)
```

| 模式 | `next_review_at` | 状态 |
|---|---|---|
| `AfterRound` | `now + 复核间隔` | `cooldown` |
| `Manual` | `now`（**立刻到期**） | `ready_for_review` |

### 1.5 启动错峰

**已经落地**：新目录的第 *i* 条闭环，调度时刻 = `now + i × CLOSED_LOOP_REVIEW_START_SPACING_SECONDS`
（默认 **2 s**）。错峰写在**库里**（`next_review_at`），所以进程重启后错位**不丢**。

### 1.6 「复核完成的闭环对象放广播队列 / 回插复核队列」现在在哪？

**现在没有「内存对象」这一层**，闭环在运行时是**库里的行**，不是对象。
现状的「分流」是这样的：

```text
复核工作线程
  ├─ 复核完成（有 signed PnL）
  │    ├─ 盈亏 > 0 且新鲜且三跳齐备 ─▶ 物化**广播请求行**（manager_v4_review_broadcast_requests）
  │    │                                  └─▶ 提交侧读它 → 进广播执行队列
  │    └─ 盈亏 ≤ 0 或条件不满足 ─▶ **什么也不做**（下一轮由库里的时刻决定）
  └─ 复核失败 ─▶ 物化**诊断行**（manager_v4_review_diagnostics）
```

也就是说：**「分流」现在落在数据库的行上**，不在内存队列上；
「回插复核队列」现在等价于「**不写广播请求行**」——
下一次复核由 `advance_review_clocks_on_connection` 把这条闭环重新转成 `ready_for_review`。

**★ 第四轮修正**：这段「分流」在目标形态里**不再分两处** ——
闭环级**只有一个**队列，复核完成时**覆盖那一条记录**：
正收益 ⇒ 状态 `broadcast_pending` ＋ 调度时刻 = **哨兵** ＋ 广播任务入队；
负/缺值/失败 ⇒ 状态 `cooldown` ＋ 调度时刻 = `now + 间隔`。
详见 §2.5。

### 1.7 缺口清单

| # | 缺口 | 后果 | 归属 |
|---|---|---|---|
| G1 | 复核队列**每次现算**，无常驻结构 | 主线程每轮成本 ∝ 作用域闭环总条数 | 本计划 |
| G2 | 过滤在 SQL 里，主线程**看不到**「下一个何时到期」 | 主线程只能靠计数判断，**无法前缀截断** | 本计划 |
| G3 | `next_review_at` **无索引** | 作用域大了以后 SQL 自己就慢 | 本计划 |
| G4 | 「到期」在两处各算一遍（`advance_review_clocks` 与 `read_due_review_loops`） | 两处口径必须永远一致，否则有窗口 | 本计划 |
| G5 | 广播请求行**物化**在复核管理器里，**不是**复核线程直接 enqueue | 「复核正收益 ⇒ 直接广播」在**编排器**路径成立，在**运行时**路径要绕一圈 | 本计划 |
| G6 | 内存侧**没有**「同一闭环只有一条当前结果」的约束 | 靠库的主键兜底；内存队列落地后必须**自己**保证 | 本计划 |

## 2. 目标设计：闭环级**一个**队列

### 2.1 一个队列，一个排序键

用户口径（第四轮修正）：

> 「**系统可以使用一个队列**，当一个闭环正在复核或者正在等待广播消息确认的时候，
> 把它的复核时间设置为一个**无限远的数值或者 2100 年**，因为这个数值在 100 年之后，
> 等价于永远不会到达。这样，**不需要处理多个队列**，只要保持**一个队列**，
> 加上**闭环状态**就可以完成任务。」

**采纳。** 闭环级的队列**只留一个**，排序键**只有**一个：`next_review_at`。

队列的语义收敛成一句话：

```text
这条闭环下一次该由复核主线程动手的时刻
```

| 闭环的处境 | 调度时刻 | 状态 |
|---|---|---|
| 欠一次测量（到期） | 真实时刻（≤ now） | `ready_for_review` |
| 刚被处理完，时钟在跑 | `now + 复核间隔` | `cooldown` |
| **正在复核** | ✅ | **复核哨兵**（2036-06-06） | `review_pending` |
| **正收益已广播，等回执** | ✅ | **广播哨兵**（2035-05-05） | `broadcast_pending`（**新**，已迁移） |

一条闭环**永远只有一条队列记录**。复核完成时**覆盖**那一条，不是新增一条 ——
这就是「**第二次复核出现结果，必然覆盖前一次闭环的结果，每个闭环仅仅有一个当前的复核结果**」。

### 2.2 数据结构

```rust
/// 复核队列：常驻内存的有序集合。
///
/// 排序键是**调度时刻**（`next_review_at`），不是闭环键。
/// 主线程只看**第一个**元素。
pub struct ReviewQueue {
    /// (到期秒, loop_key) 的有序集合。
    ///
    /// 同一个 `loop_key` 在集合里**最多一条**：重排时先删旧条目再插新条目。
    order: BTreeSet<(i64, String)>,
    /// 每条闭环的载荷：调度时刻、状态、已等了多久。
    slots: HashMap<String, ReviewSlot>,
}
```

**为什么是 `BTreeSet` 而不是 `BinaryHeap`：**

| | `BTreeSet` | `BinaryHeap` |
|---|---|---|
| 取「最小的未到期元素」 | ✅ `first()` | ❌ 只能取最大 |
| 删掉任意一条 | ✅ `remove` | ❌ 只能删顶 |
| 「这条闭环改了时刻」 | ✅ 删旧 ＋ 插新 | ❌ 堆不支持中间修改 |
| 前缀截断 | ✅ 天然支持 | ❌ 不支持 |

广播**任务**队列现在用的就是 `BinaryHeap`（`broadcast_manager/src/runtime.rs` 的
`ExecutionPriority`），那是**对的** —— 它要的是「优先级最高的先发」，
不是「时间最早的先发」。**两个队列的排序语义不同，所以用不同的结构**，这不是不一致。

### 2.3 哨兵：没有「下一次」的时刻 —— **两个**

用户口径（第五轮修正）：

> 「**那直接定义两个哨兵吧，不要用一个了，无法区分。**
> 正在复核 ⇒ 哨兵（**2036-6-6-6**）⇒ `review_pending`；
> 正收益已广播，等回执 ⇒ 哨兵（**2035-5-5-5**）⇒ `broadcast_pending`」

**采纳。** 一个哨兵**分不出**两种「忙」，所以定义**两个**：

```rust
/// 哨兵一：这条闭环**正在复核**。
///
/// 它排在所有真实时刻**之后**，所以前缀截断天然跳过它。
/// 它是**具体时刻**而不是 NULL：NULL 已经占用为
/// 「从未测量 ⇒ 立即到期」。
pub const REVIEW_PENDING_SENTINEL_AT: &str = "2036-06-06T06:06:00+00:00";
pub const REVIEW_PENDING_SENTINEL_EPOCH: i64 = 2_096_345_160;

/// 哨兵二：这条闭环**已广播，等回执**。
pub const BROADCAST_PENDING_SENTINEL_AT: &str = "2035-05-05T05:05:00+00:00";
pub const BROADCAST_PENDING_SENTINEL_EPOCH: i64 = 2_061_954_300;
```

| 哨兵 | 时刻 | epoch 秒 | 落在 i32 内？ | 闭环状态 |
|---|---|---|---|---|
| 复核哨兵 | `2036-06-06T06:06:00+00:00` | 2 096 345 160 | ✅（离 i32 上限 51 138 487 s） | `review_pending` |
| 广播哨兵 | `2035-05-05T05:05:00+00:00` | 2 061 954 300 | ✅（离 i32 上限 85 529 347 s） | `broadcast_pending` |

**为什么是 2035/2036 而不是 2100**：2100 的 epoch 秒 = **4 102 444 800**，
超 `i32` 上限（2 147 483 647）。用户定的 2035-05-05 与 2036-06-06 两个时刻
**都在 i32 以内**，所以连「用 i32 数秒」的老读者也不会溢出。

**为什么不能用 NULL**：现有语义是
`next_review_at IS NULL` ⇒ **从未测量 ⇒ 立即到期**
（`read_due_review_loops` 的 `next_review_at IS NULL OR julianday(next_review_at) <= julianday(?5)`）。
NULL 已经被占用，**不能**拿来表示「不排期」⇒ 必须用另一个**具体时刻**。

**为什么必须是两个**：队列项**本身**就要能区分「在复核」与「等回执」——
两个哨兵**互不相同**，所以队列项的排序键就能分辨，不必回头读状态列。

哨兵的**四条硬规矩**：

| # | 规矩 | 落点 | 为什么 |
|---|---|---|---|
| K1 | **显式排除**，不能只靠「它很远」 | SQL：`AND next_review_at NOT IN (:s1,:s2)`；内存：`is_sentinel` | 现在靠 `julianday <= julianday(now)` 排除是**巧合式**的；日历/时区出 bug 时会**一次性放飞全部闭环** |
| K2 | 加一条测试：**哨兵永不到期** | 单测 `a_sentinel_is_never_due` | 同上 |
| K3 | 哨兵只用来**排序**，不用来**查账** | `review_cycle_started_at` 保留 | 看门狗要能发现「认领了 5 分钟还没结束」的闭环；哨兵把时刻抹掉了，起始时刻**不能**一起抹掉 |
| K4 | 用 `i64` | 内存队列与快照字段 | 哨兵 epoch ≈ 2.1e9 本身仍在 i32 内；但**排序键**用 `i64::MAX`，且「哨兵 − now」的差值 ≈ 1.1e9 只在 `i64` 里语义正确 ⇒ 队列键一律 `i64` |

**★ 第五轮修正（关键）**：哨兵**在库里是一个日期，在内存队列里不是**。

* 库里存**日期**（人看的标记）：运维在库里一眼看出「这条闭环停在哪个哨兵上」。
* 内存队列里哨兵的**排序键**用 `i64::MAX` ⇒ **日期不参与排序**。

为什么必须解耦：哨兵时刻一旦**变成过去**（系统时钟被改、或者哨兵本身过期），
它会排到所有真实时刻**前面**，前缀截断**立刻失效** ⇒ 主线程**静默停摆**。
把「标记」与「排序键」分开之后，哨兵**永远不会**参与到期判定，
也**永远不会**破坏前缀截断。

**哨兵与「到期」的关系**（三条，任何一条都不能破）：

```text
库里： next_review_at = 哨兵日期        （标记，人看的）
内存： due_epoch      = i64::MAX       （排序键，永不过期）
判定： is_sentinel ⇒ 永不到期
```

### 2.4 主线程的前缀截断

```rust
fn dispatch_due(&mut self, now: i64) -> Vec<LoopKey> {
    let mut dispatched = Vec::new();
    while let Some((due, key)) = self.order.first().copied() {
        if due > now {
            // 第一个没到期 ⇒ 后面的都没到期（集合有序）⇒ 本轮到此为止。
            break;
        }
        // 哨兵项在库里是日期，在队列里是 i64::MAX ⇒ 永远排在最后。
        self.order.remove(&(due, key.clone()));
        self.slots.remove(&key);
        dispatched.push(key);
    }
    dispatched
}
```

成本：**O(到期条数)**，与作用域闭环总条数**无关**。

### 2.5 复核完成时的**覆盖**（不是新增）

| 复核结果 | 闭环队列里的动作 | 广播任务队列 |
|---|---|---|
| 盈亏 **> 0** 且新鲜且三跳齐备 | **覆盖**：状态 `broadcast_pending` ＋ 调度时刻 = **广播哨兵** | **入队**（首次发送 ＋ 签名在复核线程） |
| 盈亏 **≤ 0**（含 `not_executable`） | **覆盖**：状态 `cooldown` ＋ 调度时刻 = `now + 间隔` | 不入队 |
| 缺值（`data_incomplete`） | **覆盖**：状态 `cooldown` ＋ 调度时刻 = `now + 间隔` ＋ 写诊断 | 不入队 |
| 失败（`failed`） | **覆盖**：状态 `cooldown` ＋ 调度时刻 = `now + 间隔` ＋ 写诊断 | 不入队 |

广播回执**终态**（成功 / 失败 / 重发耗尽）时：
闭环队列**覆盖**为 状态 `cooldown` ＋ 调度时刻 = `now + 间隔`。

**一条闭环同时只在一个队列里**；广播任务队列里装的是**消息**，不是闭环。

### 2.6 广播**任务**队列另算

用户说的「一个队列」指的是**闭环级**的队列。广播侧还有一个队列
（`ExecutionQueue`，装的是**广播消息**：raw tx、签名、nonce、重发次数、回执轮询），
它与闭环队列**不是一回事**：

| | 闭环队列 | 广播任务队列 |
|---|---|---|
| 单位 | 一条**闭环** | 一条**广播消息** |
| 排序 | **调度时刻** | **优先级** |
| 生命周期 | 一条闭环**一条**记录 | 一条闭环先后产生**多条** |

### 2.7 状态 ↔ 队列对照

| 闭环状态 | 在闭环队列里？ | 调度时刻 | 下一动 |
|:---|:---:|---|---|
| `ready_for_review` | ✅ | ≤ now（或 NULL） | 主线程认领 → 复核工作线程 |
| `cooldown` | ✅ | `now + 间隔` | 到点后同上 |
| `review_pending` | ✅ | **复核哨兵** | 复核工作线程 |
| `broadcast_pending` | ✅ | **广播哨兵** | 广播确认线程 |
| `retired` | ❌ | —— | —— |

### 2.8 队列是**派生索引**，库是**真相来源**

内存队列**不取代** `manager_v4_closed_loop_runtime_state`：

```text
库（真相）  ──装载──▶  内存队列（索引）  ──驱动──▶  工作线程
   ▲                        │
   └────── 回写状态与时刻 ◀───┘
```

装载时机：

| 时机 | 动作 |
|---|---|
| 进程启动 | 全量装载作用域内闭环（一次读） |
| 目录**代次**变化（闭环集合变了） | **重建**整个队列 |
| 单条闭环的调度时刻变了 | 就地改（删旧条目 ＋ 插新条目） |

**重建是幂等的**：队列内容可以随时从库里重算出来，所以它**不需要**成为持久化负担。
## 3. 线程职责边界

| 线程 | 负责 | **不**负责 |
|---|---|---|
| **复核主线程** | 维护复核队列；前缀截断；认领到期闭环；把认领成功的交给复核工作线程 | 不测量、不发广播 |
| **复核工作线程** | 链上现读；出具 signed PnL；**正收益 ⇒ 直接发广播指令**（含签名）；**负收益 ⇒ 回插复核队列** | 不等回执、不解析链上结果 |
| **广播确认主线程** | 动态等待广播消息；每条消息起一个确认工作线程 | 不签名、不解析 |
| **广播确认工作线程** | 解析**链上回执** ⇒ 落库；出错时**重发**（重发也重新签名） | 不做复核 |

**签名 vs 确认是两件事**：*广播消息的签名*在复核线程（首次发消息），
*广播交易的确认*在广播确认线程。

## 6. 风险与回滚

| # | 风险 | 处置 |
|---|---|---|
| R1 | 内存队列与库**不一致**（有人改了库里的时刻） | 队列是**派生索引**：任何写库路径都要**回写队列**；S3 的重建提供兜底 |
| R2 | 进程重启丢队列 ⇒ 漏复核 | 启动时**全量装载**（S3），装载失败 ⇒ **不放行**复核主线程 |
| R3 | 前缀截断写错 ⇒ **漏**该复核的闭环 | 单测 A2/A3/A9；S0 的逐键对照 |
| R4 | 正收益不进复核队列 ⇒ 广播**失败**后没人再测它 | 广播确认线程在**终态**（成功/失败/重发耗尽）时把闭环**重新排进**复核队列 |
| R5 | 目录代次变化时队列漏重建 | 队列记录自己装载的**代次**；代次不一致 ⇒ **重建**而不是继续用 |
| R6 | 闭包数量激增 ⇒ 队列变大 | 队列只装**作用域内**闭环；`retired` 不装 |
| R7 | **哨兵**被误当成「到期」 | 显式排除（K1）＋ 单测（A12）；不靠「它很远」 |
| R8 | 哨兵**抹掉**了「卡住」的线索 | 保留 `review_cycle_started_at`；必要时再加广播起始时刻（K3） |
| R9 | `i32` **溢出** | 2100 的 epoch 秒用 `i64`（K4） |
| R10 | 词表**加值**要重建表 | SQLite 的 CHECK 约束要重建表；迁移必须**保留全部旧行** |

**回滚**：内存队列是**派生**的，回滚只需关掉它，
系统立刻回到「每次现算 SQL」的行为，**不需要数据迁移**。

## 7. 诚实边界

* **本文是计划**：§4 的 **S5 / S5a（运行时广播路径）还没落地**。
  已落地：§1.3（时间点代替定时器）、§1.4（重置辅助函数）、§1.5（启动错峰）、
  §1.6/§2.5 的**覆盖**语义、`ReviewQueue`（§2.2）、**两个哨兵**（§2.3）、
  S1（索引）、S2/S3（队列与装载）、S4a（`broadcast_pending`）、S6（同口径）、S7（端点观测）。
* **队列还没有常驻**：现在是**每次读库现算** `ReviewQueue`（`read_review_queue`），
  排序与前缀截断的**结构**已经到位，但**没有**常驻实例，
  所以「一轮扫描只读到期条数」这一条（S4）**还没有**真正吃到。
* 广播侧目前**只有** `manager_v4_review_broadcast_requests` 里的**行**，
  没有「复核线程 ⇒ 广播队列」这条**直接**的内存通路（G5）；S5 才补上。
* 「持续产生链上广播交易记录」**仍未达成**：当前目录 10 条闭环的复核**全部** `not_executable`，
  广播请求行数 **0**。本计划**不改变**任何门禁 —— 它只改**调度**与**路由**，
  不放宽盈利口径。
* **第四轮修正**（用户口径「系统可以使用一个队列……把复核时间设置为一个无限远的数值或者 2100 年」）：
  闭环级**只留一个队列**，`next_review_at` 是**唯一**的排序键；
  「正在复核」与「等回执」两条用**远期哨兵**表示；
  哨兵**显式排除**、只用来**排序**不抹掉起始时刻、时间值用 `i64`；
  广播**任务**队列（装的是消息，不是闭环）**另算**。
* **第五轮修正**（用户口径「直接定义两个哨兵，不要用一个了，无法区分」）：
  两个哨兵分别是 **2036-06-06T06:06:00+00:00**（`review_pending`）与
  **2035-05-05T05:05:00+00:00**（`broadcast_pending`），**都在 i32 以内**；
  库里存**日期**（人看的标记），内存队列里排序键用 `i64::MAX`（**日期不参与排序**），
  所以哨兵**永远不会**到期，也**永远不会**破坏前缀截断。
* 队列落地的**前提**是市场那边先有正收益复核；
  没有正收益时，队列照样每 60 s 转一圈，但**永远不会**产生广播 ——
  这是**市场条件**，不是队列缺陷。
