# 任务管理系统说明（System Spec）

> **本文件是 `plan/` 目录的受控总纲。** 任何任务、模板、清单的增删改，**先读本文件**。
> 版本：**v1.0**　最后更新：**2026-11-24**

---

## 0. 一句话

**任务编号是纯 ID；功能关联只按模块编号表达；回归范围由改动模块集合决定；每个任务有自己的独立目录。**

**两级结构**：**一级任务**（方案 / 计划）**统一归档**；**二级任务**（具体执行项）**独立开启、独立闭合、独立完善**。

```
│   │       │   ├── README.md
│   │       │   ├── PLAN.md
│   │       │   ├── SCOPE_GUARD.md
│   │       │   ├── checklist.md
│   │       │   └── docs/                ← 【技术文案】该任务自己的技术说明
│   │       │       └── README.md
│   │       ├── T-4.01/ ...
│   │       └── ...
│   ├── P-02-xxx/ ...
│   └── ...
├── (无独立方案区)                ← 专题设计文档已下沉到 `tasks/P-01-池子重构/docs/`
├── runtime_evidence/             ← 【证据区】运行时证据与校验脚本

```

### 1.1 三条分区规则

| 区 | 路径 | 放什么 | 禁止放什么 |
|---|---|---|---|
| **模板区** | `plan/template/` | 模板文件、模板使用说明 | **任何具体任务** |
| **任务区** | `plan/tasks/` | **一级任务**目录 `P-nn-标题/`（内含二级任务 `tasks/T-nn/`） | 模板文件、跨任务混排文档 |
| **归档区** | `plan/archive/` | **受控**。已闭合任务 ＋ 权威冻结快照 | 未闭合任务、临时产物、大文件 |
| **临时通道** | `plan/back/` | **非受控**。中间态产物、运行时日志、**大体积**副本 | 已闭合任务、权威快照 |

> **模板与任务编码计划放在不同子目录** —— 模板区只增不改（除模板本身升版），
> 任务区随任务生命周期增删。两者**互不引用**。

### 1.2 归档区（`plan/archive/`）是**受控文档**

| 项 | 规则 |
|---|---|
| **性质** | 归档区**不是垃圾桶**，是**受控文档区**。归档件**同样受版本、命名、索引约束** |
| **索引** | [`plan/archive/README.md`](./archive/README.md) 是归档区**唯一索引**，登记每件归档的编号 / 标题 / 归档日期 / 来源 / 原路径 / 摘要 |
| **命名** | 已闭合任务统一为 `任务归档_T-nn_标题_YYYYMMDD.md`（任务目录四文件**整体**打包为**单个 md**，保留内部小节） |
| **冻结** | 归档件**内容不可再改**。更正一律写**新版本**（`..._v2.md`），旧版**保留** |
| **可追溯** | 每件归档**必须**能追溯到：来源任务编号、原路径、闭合判据、归档日期 |
| **反向引用** | 归档件**不反向引用**在办任务目录；需要时只引**专题清单 §6 已闭合任务表** |
| **清理** | 归档区**不做**批量删除。确需清理 ⇒ 先在索引里登记**删除批次**再执行 |

### 1.2b 临时通道（`plan/back/`）**不是受控区**

| 项 | 规则 |
|---|---|
| **性质** | **临时通道**。**可能丢失**，丢失**不心疼** |
| **放什么** | 中间态产物、运行时观测日志、一次性报告、**大体积数据库副本**（GB 级） |
| **索引** | **无**。清理**不需要**登记 |
| **禁止** | 已闭合任务的归档件、权威冻结快照 —— 那些进 `plan/archive/` |
| **体积判据** | **大文件默认进本区** —— 归档区只放**小而贵**的文档 |

> **一句话**：**`archive/` 是仓库，`back/` 是过道。**
> 过道里的东西丢了不心疼；仓库里的东西丢了要赔。

### 1.3 两级任务结构（**一级统一归档 · 二级独立闭合**）

| 级 | 形式 | 目录 | 闭合粒度 | 归档时机 |
|---|---|---|---|---|
| **一级任务** | `P-nn-标题` | `plan/tasks/P-nn-标题/` | **整体**（全部二级闭合 ＋ 一级特有项闭合） | **整体归档**，进 `plan/archive/` |
| **二级任务** | `T-<模块>.<序>` | `plan/tasks/P-nn-标题/tasks/T-<模块>.<序>/` | **单个**（自己的五部分全闭合） | **立即**移出 `tasks/`，进 `plan/archive/` |

**规则**：

1. **一级任务是「容器 + 边界」** —— 它声明**整体目标**、**总改动范围**、**模块级波次**，
   并把工作**拆成**若干**互相独立**的二级任务。
2. **二级任务是「执行单元」** —— 每个二级任务有**自己**的
   `PLAN.md` / `SCOPE_GUARD.md` / `checklist.md` / `README.md`，
   **自己的**回归范围（= **自己的**改动模块集合），**不依赖**其它二级任务的验收。
3. **二级任务闭合即归档** —— 闭合一个就打包进 `plan/archive/`，**立即**从
   一级任务的 `tasks/` 下移除。这样「`tasks/` 里还剩什么」永远等于
   「一级任务还剩什么没做」。
4. **一级任务统一归档** —— 当其**全部**二级任务都已归档、且一级自身验收项全闭合时，
   **整个一级任务目录**打包进 `plan/archive/`。
5. **一级任务不在 `plan/tasks/` 顶层** —— 它**只**在 `plan/tasks/` 下作为**一级目录**存在；
   `plan/tasks/` 顶层**只放一级任务目录**，不放散落的二级任务。
6. **功能关联只按模块表达** —— 一级与二级、二级与二级之间，**一律不写任务号依赖**。

> **为什么两级**：方案（池子重构）本身**不产出可闭合的代码**，
> 它的价值在于**边界**与**分解**。把「边界」放一级、把「执行」放二级，
> 于是：**一级只归档一次**，**二级各自独立闭合**，互不拖累。

### 1.4 技术文案区（`docs/`）—— **每个任务自己的**

> **任务目录可以包含独立的 `docs/` 目录，介绍具体的技术文案。**

| 项 | 规则 |
|---|---|
| **位置** | **每个**任务目录（**一级与二级都有**）都有**自己的** `docs/` |
| **内容** | **该任务自己的**技术说明：设计推导、背景分析、口径定义、读数记录 |
| **独立性** | **与其它任务不共享** —— 别的任务的技术文案**不复制**到这里，需要时只**链接**到权威出处 |
| **不参与回归** | `docs/` 是**说明性文档**，**不含**可执行验收项 ⇒ **不参与**回归范围判定 |
| **口径唯一** | 同一口径在 `docs/` 与 `PLAN.md` 中**不得矛盾** |
| **冻结** | 任务闭合后 `docs/` 随任务**整体归档**（打包进归档件 §⑤） |

### 1.5 归档区对两级任务的命名

| 级 | 归档件命名 |
|---|---|
| 一级 | `方案归档_P-nn-标题_YYYYMMDD.md` |
| 二级 | `任务归档_T-nn_标题_YYYYMMDD.md` |

> 二级归档件**必须**标注其**所属一级任务**（`P-nn-标题`），
> 以便从归档件反查回一级任务树。

## 2. 编号体系

| 种类 | 形式 | 例 | 说明 |
|---|---|---|---|
| **一级任务编号** | `P-nn-标题` | `P-01-池子重构` | **纯 ID** ＋ 目录名里的**可读标题**。方案 / 计划级 |
| **任务编号（二级）** | `T-nn` | `T-3.01` | **纯 ID**。唯一标识，**不表达任何功能关联** |
| **验收编号** | `AC-nn` | `AC-3.01` | **纯 ID**。与任务编号一一对应 |
| **模块编号** | `M-n` | `M-3` | **大模块**。功能归属的唯一表达 |
| **子模块编号** | `M-n.k` | `M-3.2` | 大模块下的子模块 |
| **波次编号** | `W-n` | `W-2` | 模块级执行波次（用于排期，**不是**依赖） |

### 2.1 硬性纪律（违反即不合规）

1. **编号只做 ID**：文档中**不得**出现「`T-3.01` 依赖 `T-4.01`」「`T-6.01` 阻塞 `T-7.02`」这类表述。
2. **依赖只按模块写**：需要别的任务先完成时，只写**模块级前置**
   （例如「前置模块：`M-3`」），**不写任务号**。
3. **功能关联只按模块写**：两个任务「相关」的唯一合法表达是
   「**改动模块集合相交**」。
4. **编号不回收**：任务闭合后，其编号**永久不再使用**，下一个新任务取下一个可用号。
5. **两级各自独立编号空间**：`P-nn` 与 `T-nn` **互不占用**。
   `P-01` 不占用 `T-3.01`；`T-3.01` 不占用 `P-01`。
6. **二级任务**编号**在全树内唯一**（跨一级任务也不重复）——
   便于「只看编号就知道改哪一块」，且归档件可唯一定位。

## 3. 回归范围规则（**最关键**）

> **控制修改测试范围的核心机制。**

### 3.1 规则

1. 一个任务的**回归范围 = 该任务改动模块集合**。
2. **未改动模块一律不跑测试**。
3. **不得**以「有新任务」「功能没变」「保险起见」为由跑全量。
4. 回归命令**逐模块**写死在 `SCOPE_GUARD.md` ＋ `README.md` ＋ `PLAN.md`，
   **可逐条复制执行**。

### 3.2 为什么这样定（历史教训）

旧制把任务号当依赖链，导致：

- 每次新任务都要重跑**从未改动**的模块 ⇒ 大量无效工时；
- 「大数据备份」这类**无阶段性修正**的数据反复备份 ⇒ 无意义的磁盘占用；
- 生产库**授权**被反复要求 ⇒ 授权与实际改动脱钩。

新制把**关联收敛到模块编号**，把**测试范围收敛到改动集合**，
把**授权收敛到真正写库的模块**。

### 3.3 范围变更的处理

若施工中发现必须触碰**不在**改动模块集合内的模块：

1. **先扩范围**：在 `PLAN.md` §1.1 与 `SCOPE_GUARD.md` 增列该模块；
2. **再施工**：并记录扩范围原因；
3. **后重跑**：**只**跑扩范围后模块的测试，**不**回头跑全部。

## 4. 任务生命周期

| 阶段 | 目录 | 动作 |
|---|---|---|
| **立项（一级）** | `plan/tasks/P-nn-标题/` | 按 `plan/template/` 生成 4 个文件 ＋ 建 `tasks/` 子目录 |
| **立项（二级）** | `plan/tasks/P-nn-标题/tasks/T-nn/` | 按 `plan/template/` 生成 4 个文件 ＋ 登记进一级 README |
| **施工中** | 同上 | 逐条勾选 `checklist.md`；扩范围须先登记 |
| **闭合（二级）** | 同上 | 全部勾选 + 回归全绿 + 证据入 `plan/runtime_evidence/` |
| **闭合（一级）** | 同上 | 全部二级已归档 ＋ 一级自身验收项全闭合 |
| **归档** | `plan/archive/` | ① 打包任务目录（四文件 ＋ `docs/`）为**单个 md**（`任务归档_T-nn_标题_YYYYMMDD.md`）<br>② 放入 `plan/archive/`<br>③ 在 `plan/archive/README.md` **索引**登记一行<br>④ 在一级任务 README 的二级清单标记「✅ 已闭合 · 已归档」<br>⑤ **删除** `plan/tasks/<一级>/tasks/T-nn/` 原目录 |

### 4.1 闭合判据（全部满足才算闭合）

- [ ] `checklist.md` 中**全部** `- [ ]` 变为 `- [x]`
- [ ] `SCOPE_GUARD.md` 的**全部**回归命令**全绿**
- [ ] 每条已勾选项都有**可复算的实测读数**（**不得**用零冒充未测量）
- [ ] **未放宽**任何既有门禁（金额 / 容量 / 利润口径 / 幂等键 / 回执关联 / 阈值）
- [ ] **未**触碰改动模块集合以外的模块（或已按 §3.3 扩范围并重跑）

### 4.2 归档操作步骤（**任务完成 ⇒ 必须移出 `plan/tasks/`**）

> **规则**：任务完成后**不得**继续留在 `plan/tasks/`。
> `plan/tasks/` **只放未闭合任务** —— 这样「目录里有什么」永远等于「还有什么没做」。

```powershell
# 1. 打包（四文件合一，保留内部小节结构）
$TASK="T-10.03"; $TITLE="标题"; $DATE="20261124"
#    拼接 PLAN.md + SCOPE_GUARD.md + checklist.md + README.md + docs/
#    → plan/archive/任务归档_${TASK}_${TITLE}_${DATE}.md

# 2. 在归档索引登记（plan/archive/README.md）
# 3. 在一级任务 README 的二级清单标记已归档
# 4. 删除原任务目录（打包件已在归档区，且索引已登记 ⇒ 可安全删）
Remove-Item -Recurse "plan/tasks/<一级>/tasks/$TASK"
```

**归档件内部结构（打包后保留四个小节标题）**：

```markdown
# `T-nn`｜标题 · 任务归档（**已闭合**）

> **归档元信息**：编号 / 验收 / 归档日期 / 闭合判据 / 原路径

## ① 任务说明 ＋ ② 开发计划
（原 `PLAN.md` 全文）

## ③ 修改范围守护
（原 `SCOPE_GUARD.md` 全文）

## ④ 测试目标 check list
（原 `checklist.md` 全文）

## ⑤ 独立技术文案（docs/）
（原 `docs/` 内各文件全文，逐文件嵌入）

## 导航
（原 `README.md` 全文）
```

**归档后自检**：
- [ ] `plan/tasks/<一级>/tasks/T-nn/` **已删除**
- [ ] `plan/archive/任务归档_T-nn_*.md` **已存在**且内容完整
- [ ] `plan/archive/README.md` 索引**已登记**该行
- [ ] 一级任务 README 的**二级清单**已标记该子项「✅ 已闭合 · 已归档」
- [ ] 归档件**内容未再改动**（更正走新版本）

### 4.3 一级任务归档（**全部二级闭合后**）

```powershell
python plan/runtime_evidence/tools/archive_task_20261124.py P-01-池子重构
```

一级归档件 = **一级自身五部分** ＋ **一级 `docs/` 技术文案** ＋ **全部二级归档件清单**（含各自路径）。
工具会把它放进 **`plan/archive/`** 并在 **`plan/archive/README.md`** 登记。
**二级归档件本体不合并进一级件** —— 保持「一级看全局、二级看细节」。

**归档后自检**：
- [ ] `plan/tasks/P-nn-标题/` **整个目录已删除**
- [ ] `plan/archive/方案归档_P-nn-标题_*.md` **已存在**
- [ ] 一级归档件内含**完整二级归档件清单**
- [ ] `plan/archive/README.md` 索引**已登记**该行
- [ ] **全部**二级任务**各自**已登记归档索引

## 5. 新建任务的标准流程

### 5.1 新建**一级任务**（方案 / 计划级）

1. 读 `plan/README.md`（本文件）与 `plan/template/README.md`；
2. 取**下一个可用**一级编号 `P-nn`（见 §7），建目录 `plan/tasks/P-nn-标题/`；
3. 复制模板：`TASK_TEMPLATE.md`→`PLAN.md`、`SCOPE_GUARD_TEMPLATE.md`→`SCOPE_GUARD.md`、
   `CHECKLIST_TEMPLATE.md`→`checklist.md`；
4. 建 `tasks/` 子目录（放二级任务）；
5. 一级 `PLAN.md` 写**整体目标 / 总边界 / 模块级波次 / 二级分解表**；
6. 一级 `checklist.md` **只放一级特有**的验收项（跨二级的一致性、总回归、整体读数）。

### 5.2 新建**二级任务**（执行级）

1. 读 `plan/README.md`（本文件）与 `plan/template/README.md`；
2. 确定**主改动模块 `M-n`**（一个任务只服务一个模块），查
   [`plan/TASK_REGISTRY.md`](./TASK_REGISTRY.md) §4.2 取该模块的**下一个可用**编号
   `T-<模块>.<序>`（**不同模块各自独立，互不消耗**），验收编号 `AC-<模块>.<序>`；
3. 复制 `plan/template/` 的 3 个模板文件到 `plan/tasks/<一级>/tasks/T-<模块>.<序>/`：
   - `TASK_TEMPLATE.md` → `PLAN.md`
   - `CHECKLIST_TEMPLATE.md` → `checklist.md`
   - `SCOPE_GUARD_TEMPLATE.md` → `SCOPE_GUARD.md`
4. 按 `plan/template/README.md` 的字段填写规则**填满**占位符；
   在 **`plan/TASK_REGISTRY.md` §4.2 登记一行**（编号册即时生效）；
5. 新建 `plan/tasks/<一级>/tasks/T-<模块>.<序>/README.md`（导航）；
6. 在**一级任务** README 的**二级清单**登记一行；
7. 在专题清单（`plan/tasks/P-01-池子重构/docs/未完成任务清单_20261123.md`）**登记一行**；
8. **不要**修改其它任务的目录 —— **二级任务之间不耦合**。

## 6. 固定部分（每个任务必备）

| 顺序 | 部分 | 载体文件 | 必备内容 |
|---:|---|---|---|
| **1** | **任务说明** | `PLAN.md` §1 | 编号 / 标题 / 优先级 / 波次 / 前置模块 / 授权 / 验收项计数 |
| **2** | **开发计划** | `PLAN.md` §2–§4 | 执行步骤 / 纪律 / 完成定义 / 归档动作 |
| **3** | **修改范围守护** | `SCOPE_GUARD.md` | 改动模块集合 / 逐模块回归命令 / 触碰边界 / 范围变更流程 |
| **4** | **测试目标 check list** | `checklist.md` | 逐条验收框，每条带判定依据 |
| **5** | **编号逻辑** | `PLAN.md` §1.0 | **本任务自己的**编号声明：作用域（模块内 / 跨模块）／编号所依据的模块／模块内序号／同号段其它任务 |

| **6** | **技术文案**（可选） | `docs/README.md` | **该任务自己的**技术说明（设计推导 / 口径定义 / 读数） |

> **一级任务同样用这五部分**。差别只在：
> 一级的 `checklist.md` **只放一级特有**项；
> 二级的 `checklist.md` 放**该二级任务自己**的全部验收项。
> **`docs/` 是两级的公共第六部分**（技术文案区），**不参与**回归判定。

> **五部分是固定模板**，新增任务**直接按模板生成**，不另起格式。

> **§1.0 编号逻辑是硬性要求**：每个任务**必须自己**声明「编号是模块内还是跨模块、
> 按哪个模块编号」。读者**不看编号册**也能定位这个编号属于哪个号段。
> 一级任务的 `P-nn` 是**跨模块、不按模块分组**的容器编号，例外只此一处。
