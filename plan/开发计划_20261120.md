## 3. 架构约束

### 3.1 内存对象处理约束（MIO-1..MIO-8）

- **MIO-1** SQLite 只在初始化/持久化/审计时读写；review/depth 处理循环不得逐条 SQL 查询业务状态。
- **MIO-2** 全局内存上下文持有池、闭环和运行时快照；运行期计算只消费该上下文。
- **MIO-3** token decimals 是内存上下文的一部分，金额缩放必须使用对应 token 的精度。
- **MIO-4** WSS/监控器更新内存快照；状态版本和新鲜度必须随计算证据传播。
- **MIO-5** Review Manager 通过 Rust 内核/管理接口消费业务状态，不由 Python 另建权威路径。
- **MIO-6** Python 只消费内核发布的金额、利润、路线和状态，**不重算、不拼接闭环身份**。
- **MIO-7** Rust 内核发布有符号利润及 `signedPnl.amount`，包含 raw 值、币种/精度、来源和测量状态；测得零与未测量严格区分。
- **MIO-8** 每条链使用独立 SQLite、chain ID、RPC、权限和内存状态，禁止跨链读取或写入。
- **MIO-9** 记录读取由 **Rust Manager 拥有**：复核 / 广播 / 闭环目录 / 闭环身份的读取走 Manager 接口；**Python 侧不得直查 manager 拥有的表**，**不得**把记录缓存为内存对象当权威；Manager 未发布的读数**如实显示为未测量**，**不得**由 Python 代为推导。

### 3.2 闭环身份与路径匹配

> **闭环身份 = 资金锚点 + 方向池子。**

**系统设计中不存在"旋转"这一概念。** 闭环的业务身份由两件事共同确定：**资金代币（锚点）** 与**有方向的池子序列**。中间代币不一定是某条路由的资金代币，因此一条以中间代币为起点的路径是**另一个闭环**，有自己的身份、容量、池集合、估值与阈值。

由此得到的约束是**设计约束**，而不是行为约束：

- 代码里**不存在**闭环旋转查找、旋转归一化、旋转 alias merge、canonical rotation 这一类能力。任何层（Rust 内核、Python 运行时、脚本层）都**不得定义、不得调用、不得导入**这类能力。
- 闭环关键字 = 资金锚点 + 方向池子，即 Manager 发布的**完整有序路径**；匹配一律**精确匹配**。
- 精确匹配失败时**不借用**任何其他闭环的 loop key、pool IDs、capacity、USDG valuation 或 threshold，并 fail-closed 返回可定位的 identity mismatch。
- 因为"旋转后的路径是否命中"在系统中**不存在可观测行为**，所以**不得**把它写成验收项、指标或测试断言；那类检查项是**假问题**，应当删除而不是改写。

**同一资金锚点下可以有多条方向闭环，它们各自独立。** 例如 `X-Y-Z-X` 与 `X-Z-Y-X` 共享锚点 `X`，但方向池子不同，因此是**两条闭环**，各自拥有独立的 loop key、池集合、折叠容量、绑定池、阈值与运行时状态行（实证见 `plan/back/已完成任务归档索引_20261120_v10.29.md` 与 `plan/runtime_evidence/reports/task150_pool_set_verification_20261121.json`）。**一个锚点 ≠ 一条闭环**；不得把同锚点的多条方向闭环聚合为一条，也不得把一条拆成多条。

**观测层不是闭环身份层。** `market_observation` 层的 `group_key = anchor|direction_key`（现更名 `edge_group_key`）是按**池边（X-Y 入口边）**的**观测分组**，用于收集该边的桥接池；闭环身份在 Manager 发布层与 Rust 内核目录层。二者**不得**混淆。

**没有例外，没有"仅限状态表"的例外命名空间**。运行时状态行与 Manager 闭环身份使用同一套精确匹配契约：

| 命名空间 | 键 | 规则 |
|---|---|---|
| **Manager 闭环身份** | `loop_key` / `pool_ids` / `single_tick_capacity_*` / `borrow_token_usdg_value_*` / `cross_tick_*` / review→loop 归属 | 只精确匹配；不借用其他闭环的任何字段 |
| **运行时状态行** | `v4_closed_loop_runtime_state.loop_key` | 与 Manager 闭环身份**同一套精确匹配**；不承载 capacity / pool / USDG / threshold，不决定 review 归属 |

**实现落点**：Rust 闭环目录与身份匹配层（`flashloan/rs-src/src/closed_loop_identity.rs`、`worker_pool.rs`）、Python 运行时状态机（`flashloan/src/dex/runtime/closed_loop_state_machine.py`）与 Rust 复核管理器（`flashloan/tools/review_manager/src/lib.rs`）及其守卫测试。**不在** healer、Python 复核或脚本层做路径规整；Python 侧只消费内核权威结果。

**关闭条件**：系统内不存在任何旋转能力（源码级守卫可证），全部闭环身份与状态键按资金锚点 + 方向池子精确匹配，且**实盘证据齐备**（仅通过单元测试不构成关闭依据）。

### 3.3 级联与计算边界

- 处理顺序固定为代币→池→闭环→复核→广播；某层失败只关闭该层执行路径并继续诊断，不删除候选项或越级放行。
- 关键 token 字段优先由代币管理器修复；只有无法修复的关键字段才允许删除，且必须清理所有依赖引用。池代币精度以 token admission 为权威。
- 闭环身份匹配遵循 §3.2 的资金锚点 + 方向池子契约；缺少精确身份时按未解决依赖处理，**不得猜测或复用其他闭环的容量与估值**。
- Rust 负责单 tick 起始量、跨 tick 最佳金额、容量和利润。跨 tick 使用真实闭环输入/输出和既有 double/halve 搜索，不执行 tick 遍历；**单 tick 初值为 0 时不得启动跨 tick**。
- 未测量的金额或利润必须**缺值并附责任原因**；不能用默认零、历史估算或 SQL 回填伪装测量。
- 广播前检查正利润、具体金额、链/账户/nonce/gas/目标/快照/授权和幂等性。**无明确授权不得真实提交。**

### 3.3.0 写库分类学：**基础框架库** vs **动态记录**（**绑定性**）

> **使用者指示（2026-11-21）**：*"基础框架库要实盘写入，动态记录可以不写。"*

本计划中一切"写生产库"的表述必须归入**下面两类之一**。**把两者混为一谈是错误**；
尤其**不得**把"基础框架库写入"挂到"需单独授权"的闸门下。

| 类别 | 内容 | 性质 | 处置规则 |
|---|---|---|---|
| **基础框架库**（baseline framework） | DDL / migration / 表结构 / 列 / 约束 / 索引 / 视图 | 结构性、版本化、**幂等**、**保数据**（不重写业务行）、与链上实时状态无关 | **验证通过 ⇒ 必须实盘写入目标生产库**（该链的 DB）。**不需额外授权。** |
| **动态记录**（dynamic records） | review / depth / ladder / PnL / closed loop / broadcast attempt 等测量与运行记录 | 每次运行都变；受"**实测零 ≠ 未测**"、"**不历史回填**"、"**需当前链状态**"约束 | **可以不写**；要写时按 §7 的授权流程走 |

**判定口径**：一次写入若**不改变任何测量值、只让结构与代码对齐**，就是**基础框架库**；
若**写入的是某时刻的测量结果**，就是**动态记录**。

### 3.3.1 ETH 与 WETH 是两个独立资金锚点（**不做特殊处理，不做互相转换**）

**结论先行：ETH（`address(0)`）与 WETH（`0x0bd7…ad73`）在本系统里就是两个不同的资金锚点，各自成环。ETH 锚点的闭环用 ETH 结算，WETH 锚点的闭环用 WETH 结算。两者之间不做任何包装/解包转换，也不做特殊处理。**

- **它们是两个闭环，不是一个闭环的两种形态**：闭环身份 = **资金锚点 + 方向池子**（§3.2）。锚点地址本身就在闭环键里 —— `loop_key = "{anchor_address}:{y_address}:{z_address}"`（`flashloan/tools/closed_loop_manager/src/lib.rs` 约 2390 行）。锚点是 ETH 的闭环与锚点是 WETH 的闭环**键值不同**，是两条独立闭环，各自拥有独立的 loop key、池集合、容量、阈值与运行时状态行。**不合并、不互转。**
- **不需要“原生 vs 包装”的特殊分支**：`address(0)` 在本系统里就是一个**普通地址**。`normalize_address()`（`flashloan/tools/manager_contracts/src/ids.rs` 约 272 行）只做小写 + 长度 + 十六进制校验，**对 `address(0)` 无任何特判**；已有单测 `native_zero_address_is_valid_and_distinct_from_weth`（同文件约 323 行）断言 `address(0)` 的 `currency_key()` 与 WETH **不相等**。**保持现状即可 —— 不要引入 `isNative` / `isAddressZero` 分支去“特殊处理”原生 ETH。**
- **结算跟随锚点，不跟随路径中间段**：闭环的借出与偿还都以**锚点代币**计（内核注释：*"The borrow token is the anchor token: it is the token the loop spends first and receives last, so its USDG value is what values the profit."*，`flashloan/tools/closed_loop_manager/src/lib.rs` 约 2188–2193 行）。因此 ETH 锚点闭环自始至终以 ETH 结算，WETH 锚点闭环自始至终以 WETH 结算。
- **路径中经过 WETH 池不构成转换**：池的**币种**是池自身的属性。ETH 锚点闭环**可以**经过一个 WETH 池（该段用 WETH 计价），反之亦然；这只是路径的一段的计价币种，**不等于把锚点资产换成另一种**。实测（主网 chain 4663，164 条闭环）：ETH 锚点 **26** 条、WETH 锚点 **6** 条，**键完全分离**；其中 ETH 锚点有 4 条路径含 WETH 池、WETH 锚点有 4 条路径含 `address(0)` 池 —— 两类共存且互不影响。
- **禁止的动作（不是“浪费”，是语义错误）**：把 ETH 转成 WETH、或把 WETH 转成 ETH。任一方向都会**改变闭环锚点**，使借出币种与偿还币种不再同一个锚点 —— 这在语义上就不是同一个闭环了，且要付出两次 ERC-20 `transfer` + `approve` 的 gas。
- **与现有资产边界的关系**：两者是**两个独立的 Currency**，各自拥有独立的 USDG 估值（实测 ETH `2461669444` / WETH `1804537685`，均为 18 小数）。**不得**把两者当作同一资产（属“不同估值”而非“同值”）。
- **实现落点**：`flashloan/rs-src/src/execution.rs` —— `route_currency()`（约 517 行，读 `currency0`/`currency1`）与 `build_v4_flash_executor_request()`（约 529 行）。该函数已**按锚点自然成立**，无需为原生 ETH 增加分支：它要求 `first_input == token` 且 `third_output == token`（约 604–610 行），请求体只带**一个** `token` 字段与 `finalToken`（约 626–630 行）—— 借出与偿还用**同一个锚点代币**，中间 hop 的池币种由各自 `currency0`/`currency1` 决定。**要求：不得引入任何把锚点资产换成另一种的转换路径。**
- **证据口径**：本规则不以单元测试通过即算完成；需在对应任务中以**实盘请求的 `token` 字段等于该闭环锚点地址**（ETH 锚点闭环即 `address(0)`，WETH 锚点闭环即 WETH 地址）可被独立核验、且请求体中**不存在**跨锚点转换动作时才能关闭。


### 3.4 `pool_depth_audit` 分类口径（已变更，随代码归档）

“坏读数（TVL 超上限）”与“薄池（TVL 低于下限）”是**两个不同分类**，不可混同：

| 情形 | 判定 | 报告字段 |
|---|---|---|
| TVL 读数超过 `MAX_POOL_TVL_USD`（1e9）且 `estimated_tvl_usd` 无效 | **读数无效**，不计入薄池 | `staleTvlReadingPoolCount` |
| TVL 读数有效但低于 `MIN_POOL_TVL_USD`（1e5） | **池确实薄** | `thinPoolIdCount` |
| TVL 读数有效且充足 | 合格 | `adequatePoolIdCount` |

超过 TVL 上限的读数**不**再使 `classification` 变成 `pool_reading_invalid`，也**不**触发 `remeasure_pool_depth` 修复路径。旧口径已随 `scripts/tests/test_mainnet_arbitrage_healer.py` 同步更新并归档。

## 8.1 ETH 与 WETH 的协议分析与实测证据（绑定性，不归档）

> 本节是 **绑定性规则**（见 §3.3.1）的依据与证据，**不是某一轮的工作日志**，因此**保留在活动文档中**。
> 第 51 轮的完整读数见 `plan/back/已完成任务归档_20261121_第51轮_TASK145估值单位与覆盖核验.md`。

### 8.1.1 ETH 与 WETH 是两个独立 Currency（实测）

| 符号 | 地址 | token_kind | decimals | 锚点闭环数 | USDG 估值 |
|---|---|---|---:|---:|---:|
| **ETH** | `0x0000…0000` | `native` | 18 | **26** | **2461669444** |
| **WETH** | `0x0bd7…ad73` | `wrapped_native` | 18 | **6** | **1804537685** |

两者地址不同、估值不同、**闭环键不同**（`loop_key` 以锚点地址开头）。**不得当作同一资产**（属“不同估值”而非“同值”）。
单测 `native_zero_address_is_valid_and_distinct_from_weth`（`flashloan/tools/manager_contracts/src/ids.rs` 约 323 行）已把这一点钉死。

### 8.1.2 结算对象是**资金锚点**，不是 `signed_pnl_currency`

内核 `flashloan/tools/closed_loop_manager/src/lib.rs`（约 2188-2193 行）注释：

> *"The borrow token is the anchor token: it is the token the loop spends first and receives last,
> so its USDG value is what values the profit."*

即 **结算与估值对象 = 锚点代币**（路径 `path[0] == path[-1] == anchor`，实测 **164/164** 命中）。
锚点是 ETH 的闭环用 ETH 结算，锚点是 WETH 的闭环用 WETH 结算 —— 由此**自然得出**无需互相转换。

### 8.1.3 单位契约（已验证，主网 44/44）

| 量 | 契约 |
|---|---|
| `signed_pnl_raw` | 借款代币 **raw 单位**的带符号十六进制整数；`signed_pnl_amount = raw / 10^decimals`，`decimals` 取自 **token library**（不是 review 行字段） |
| `ladderRow.amountRaw` | 同一 raw 单位（**288** 行探针，**0** 不一致） |
| `borrowPrincipal` | borrow token 的 **human 单位** |
| `usdgIdentity` | `10^usdg_decimals` raw USDG（USDG decimals = 6 → **1000000**），**不依赖 USDG/USDG 池**（**36/36** 环闭命中） |
| `fee` | Uniswap V4 **1e-6 刻度**（fee=500 → 0.05%，由 `flashloan/tools/pool_manager/src/depth.rs` 的 `fee_complement = 1_000_000 - fee_pips` 反证）；**绝不混入 PnL** |
| `gas` | V4 quoter 返回 **两个独立 word**（`decode_v4_quote_words`）；gas **不进入 PnL 单位**，链上 gas 门禁是独立裁决 |

### 8.1.4 覆盖缺口的 fail-closed（已实盘生效）

TZ 无 USDG 路径 → 不发布估值（**缺值，不是零**）→ 内核 `cross_tick_inputs_unavailable`。
这证明了“缺价格 → fail-closed”这一条路径**真实生效**，而不是缺陷。

### 8.1.5 V4 的 `Currency` 与原生资产（协议核对）

- V4 用统一的 `Currency` 同时表示原生资产与 ERC-20：原生 ETH 的代表是 `address(0)`，WETH 是**普通 ERC-20**，在 V4 眼中与 `address(0)` 是**两个不同的 Currency**（`CurrencyLibrary.isAddressZero()` 用于识别）。
- 原生 ETH 的结算不需要 ERC-20 `transferFrom`：`settle{value: amount}(address(0))` 通过 `msg.value` 结算。
- 对 `address(0)` 调用 `transfer` / `approve` 会回滚 —— 这正是**不把两者混为一谈**的协议层理由。
- **但这不意味着本系统需要为原生 ETH 写特殊分支**：本系统不直接调用 PoolManager 的 `take`/`settle`，而是构造对**外部 V4 闪贷执行器合约**的请求
  （`build_v4_flash_executor_request`，`flashloan/rs-src/src/execution.rs` 约 529 行；`route_currency()` 约 517 行读 `currency0`/`currency1`）。
  请求体只带**一个** `token` 字段与 `finalToken`（约 626–630 行），并且已强制 `first_input == token && third_output == token`（约 604–610 行）。
  **锚点是什么，偿还的就是什么 —— 现有代码已经如此，不需要也不应该新增 `isNative` 分支。**

### 8.1.6 对一个外部常见说法的核对

> 常见说法：“V4 里借入原生 ETH 后可以直接套利，不需要强制转换成 WETH。”

**判定：说法本身基本成立，但用错了框架 —— 它把 ETH 与 WETH 当成了“同一资产的两种形态”，而实际上它们在本系统里是两个独立资金锚点、两个独立闭环。**

- **成立的部分**：V4 协议层确实把原生 ETH（`address(0)`）与 WETH 当作两个不同的 `Currency`；用原生 ETH 结算不需要 `transferFrom`；对 `address(0)` 调 `transfer`/`approve` 会回滚。
- **需要校正的部分**：
  1. **“V4 重新引入原生 ETH 支持”的口径需要精确**：对 V4 而言成立（V3 也支持原生 ETH，`ETH/WETH` 池是典型）；但 V4 的贡献是**统一的 `Currency` 形态**（相对“池对里只有 ERC-20”的形态），不是从零新增原生支持。
  2. **“Router 自动包装/解包”是路由层行为，不是 PoolManager 自身行为** —— 本项目**不做**这种转换，因此该行为与本项目无关。
  3. **“原生结算完全独立、更简单”不够精确**：V4 `PoolManager._settle` 的注释明确要求原生结算**仍先 `sync`**，以避免 DoS 向量。但这是**协议层的调用顺序**，不是本项目需要特殊处理的分支。
  4. **最关键的一点**：本项目的问题**不是**“要不要把 ETH 换成 WETH”，而是**“这个闭环的锚点是哪一个”**。ETH 锚点闭环与 WETH 锚点闭环是两条不同的闭环，各自用各自锚点的资产结算。**把两个锚点合并或互相转换，才是错误。**

### 8.1.7 本项目的落实结论

- ETH 锚点闭环 → 以 ETH 结算；WETH 锚点闭环 → 以 WETH 结算。**不做任何包装/解包中转。**
- 请求构建层：**一个闭环一个 `token` 字段**，值 = 该闭环锚点地址；ETH 锚点闭环即 `address(0)`，WETH 锚点闭环即 WETH 地址。
- **不新增** `isNative` / `isAddressZero` 之类“原生特殊处理”分支 —— `address(0)` 在本系统里就是普通地址。
- 与 §3.3.1 是同一体的两面：**规则**说明必须做什么，**保证**说明为什么现在就已经满足。

### 9.5 全局停止条件（任一命中即停止广播并归档）

- 缺 amount / PnL、快照陈旧、闭环身份不唯一、签名授权不足、重复提交或 receipt 无法关联。
- 无完整正利润且无用户明确授权。
- 任何跨链读取/写入，或跨链状态污染。
- 用历史深度/业务数据回填，或用默认零/估值掩盖缺陷。
- 处理顺序固定为 **代币 → 池 → 闭环 → 复核 → 广播**；某层失败只关闭该层执行路径并继续诊断，**不删除候选项、不越级放行**。
