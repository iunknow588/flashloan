## 3. W2｜TASK-150：闭环身份第二维度可独立复核（P0，代码）

> **为什么这是唯一真正的 P0 代码缺口**：闭环身份 = **资金锚点 + 方向池子**。但当前实现中**只有地址路径这一半真正参与判定**，"方向池子"这一半是**哑保险**。
> 守卫要求：**不得**改变现有身份语义（身份仍以有序地址路径为键），**不得**合并同锚点方向闭环，**不得**引入任何旋转能力，**不得**加任何兜底/默认池集合。

### 3.1 缺口事实（已核实）

`flashloan/rs-src/src/worker_pool.rs:2824-2841` 的 `apply_closed_loop_identity`：

```rust
let route_pool_ids = route_config
    .get("routePoolIds")
    .or_else(|| route_config.get("poolIds"))
    .and_then(Value::as_array)
    .map(...);
if route_pool_ids.as_ref().is_some_and(|pool_ids| pool_ids != &identity.pool_ids) {
    // -> manager_closed_loop_pool_identity_mismatch, fail-closed
}
```

**问题**：`routePoolIds` / 顶层 `poolIds` 在真实 review 配置中**不存在**：

| 核验点 | 读数 |
|---|---|
| 主网 44 条 review payload 中提及 `routePoolIds` | **0** |
| 主网 44 条 review payload 中提及顶层 `poolIds` | **0** |
| `poolIds` 实际出现位置 | `quote.candidate_pools` / `quote.route.hopCandidates`（**嵌套**，非顶层键） |
| Manager 侧 `manager_v4_reviews.pool_ids_json` | 44/44 非空（**权威数据存在**） |

→ `route_pool_ids` 恒为 `None` → `is_some_and(...)` 恒假 → **池集合比对分支永不触发**。

**分两层判读**：
- **结果层面：正确。** 闭环身份确实由有序地址路径唯一决定；池集合本就是路径的确定性函数，比对与否不改变判定结果（164/164 容量 > 0、44/44 review 池集合与 Manager 一致，均无偏差）。
- **保障层面：哑。** 该分支无法独立发现「地址路径正确但池集合被篡改/错配」的缺陷 —— 而这正是"方向池子"作为身份第二维度的**全部意义**。

### 3.2 施工步骤（已核实的精确落点）

> **关键发现（源码核实）**：`routePoolIds` 之所以恒为 `None`，是因为 **review 配置的字段白名单里根本没有它** —— 不是一个"忘了填值"的偶发问题，而是**结构性缺失**。
> 这决定了施工必须**同时**改 3 个位置，缺一不可。

#### 落点 A｜Rust 内核：从任务配置派生有序池 ID 并注入 `routePoolIds`

**为什么必须在 Rust 侧算**：MIO-6 规定 Python 只消费内核发布的金额/利润/路线/状态，**不重算**。池 ID 是闭环身份的组成部分，**不得**由 Python 计算。

**已有能力（可直接复用，无需新建）**：
- `flashloan/rs-src/src/pool_index.rs:85` 的 `pub fn pool_id(key: &V4PoolKey) -> Result<String, String>` —— 从池键（currency0/currency1/fee/tickSpacing/hooks）算出规范池 ID，内部经 `shared_pool_key` 做地址归一。
- `worker_pool.rs:1673-1687` 已有**完全相同的用法**（逐个 `pool_index::pool_id(&pool_key)` + `to_ascii_lowercase()` + 按序 push），可直接作为实现范式。

**施工**：在 `worker_pool.rs` 的 review 配置处理路径上，用 `entryKeys` / `bridgeKeys` / `exitKeys`（这三段是**该路由实际使用的池键**，按跳有序）依次计算 `pool_id`，拼成**有序** `routePoolIds`，写入 `route_config["routePoolIds"]`。

- 顺序语义：**entry → bridge → exit**，与 Manager `pool_ids_json` 的有序逐跳对齐。
- 归一：`pool_id` 内部已做地址归一，额外 `to_ascii_lowercase()`（与既有范式一致）。
- **不得**去重、**不得**重排（方向池子有方向）。
- 若某段池键无法算出 `pool_id`（`pool_id` 返回 `Err`）→ **不写** `routePoolIds`，并让身份校验走"显式缺失"路径（见步骤 C），**不得**填默认值。

#### 落点 B｜Rust 内核：把 `routePoolIds` 加入配置字段白名单

**当前障碍（`worker_pool.rs:2925-2944`）**：review 循环用 `let mut route_config = config.clone();` 后，**从一个显式白名单**把 `route` 上的字段拷进 `route_config`：

```
token, routeSymbols, routeAddresses, entryKeys, entryDirections,
bridgeKeys, bridgeDirections, exitKeys, exitDirections,
initialAmountRaw, minProfitRaw, minProbeAmountRaw, maxProbeAmountRaw,
singleTickCapacityRaw, singleTickCapacityBasis, singleTickCapacityBindingPoolId,
maxProbeAttempts, searchMode
```

`routePoolIds` **不在白名单**。因此即使上游填了它，也**到不了** `apply_closed_loop_identity` 读的那份 `route_config`。

**施工**：把 `routePoolIds` 加入该白名单（与 `routeAddresses` 同级）。

> **注意**：`route_config` 是 `config.clone()` + 白名单覆盖，所以只要白名单带上 `routePoolIds`，**内核自己算出的值**会在这一步落到 `route_config` 上，再被 `apply_closed_loop_identity` 读到。**Python 侧不需要、也不应该**计算或填写 `routePoolIds`。

#### 落点 C｜Rust 内核：缺失时显式，禁止"哑通过"

**当前行为（`worker_pool.rs:2824-2841`）**：

```rust
let route_pool_ids = route_config.get("routePoolIds")
    .or_else(|| route_config.get("poolIds"))
    .and_then(Value::as_array)
    .map(...);
if route_pool_ids.as_ref().is_some_and(|pool_ids| pool_ids != &identity.pool_ids) {
    // -> manager_closed_loop_pool_identity_mismatch, fail-closed
}
```

两个问题：
1. `route_pool_ids == None` → `is_some_and(...)` 恒假 → **校验分支永不触发**（哑保险）。
2. 更糟：即使跳过校验，后续仍写 `closedLoopIdentityStatus = "matched"` —— **宣称身份已完整匹配**，而实际只验证了地址路径这一半。

**施工**：
- **一致**（`routePoolIds` 存在且逐项等于 `identity.pool_ids`）→ 保持 `closedLoopIdentityStatus = "matched"`，并新增显式字段记录池集合校验状态（如 `closedLoopPoolIdentityStatus = "verified"`）。
- **不一致** → 现有 `manager_closed_loop_pool_identity_mismatch` + `repairTarget = "closed_loop_manager"` + **fail-closed**（不写 `closedLoopKey` / `singleTickCapacityRaw`）。**分支逻辑基本已正确，只需让输入非空。**
- **缺失** → **不得**写 `"matched"`。推荐写 `closedLoopPoolIdentityStatus = "unverifiable"`，并把 `closedLoopIdentityStatus` 置为**可区分**的非完整匹配值（如 `"matched_address_only"`），让下游能分辨"完整匹配"与"仅地址匹配"。
  > 备选方案：缺失即 fail-closed。二者**任选其一**，但**必须显式**，且**不得**引入兜底池集合 / 默认池 / 空集合默认值来"通过"校验。

#### 落点 D｜Python 桥接层：只做透传，不计算

- `flashloan/src/dex/runtime/rust_closed_loop.py:3510` 的 `_route_task_config` 是 review 配置的构建点。它已产出 `entryKeys` / `bridgeKeys` / `exitKeys`（完整池键对象），**并已明确声明自己是"纯消费者"，不产出任何交易数字**。
- **本次不改 Python**：池 ID 由**内核**从池键派生（落点 A），Python 无需也**不应**新增池 ID 计算路径。
- **需要核对的点**：`_route_task_config` 返回的 dict 里**没有** `routePoolIds` —— 这是**正确**的。内核在 `route_config` 层面自行派生。

**要求**：缺失时**不得**宣称身份已完整匹配。二选一（推荐前者）：
