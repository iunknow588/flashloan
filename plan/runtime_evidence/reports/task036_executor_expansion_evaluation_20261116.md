## 4. 三个扩容方案的对比

### 方案 A｜拆分 Executor

**形态**：Executor 只保留「闪电贷 + 结算 + 利润门禁」入口；把逐跳 `amountOutMinimum` 编码
移到独立合约（或 library），由它返回编码后的 hop payload 与 pool id；Executor 接收已编码
calldata 并在使用前校验。

- **字节压力**：属于**替换**而非新增，逐跳编码代码离开 Executor，从而腾出余量；
  但 Executor 仍需校验收到的 payload，净节省小于编码器原始体积。
- **信任模型**：外部编码器是**不可信输入**。Executor 必须独立重算，
  或至少用「route id → payload hash」做哈希绑定，否则恶意编码器可替换成更差的路线。
- **运维成本**：**高**。两个部署地址要进每条链的 `chain.json`；部署有先后顺序
  （编码器必须先于 Executor 存在）；payload 格式需版本化。
- **结论**：安全模型最强，但运维改动最大。当前路线级下限已经提供了硬性结算下界，
  且批次路径默认关闭，**不足以支撑这样的结构性改动**。

### 方案 B｜链下预编译 + calldata 拼接（推荐）

**形态**：在链下编译好逐跳 payload（Rust 侧本来就产出精确的 PoolManager `swap` calldata），
作为**尾随 calldata** 附加进请求；Executor 读取尾部字节并透传给 PoolManager。

- **字节压力**：**最小**。尾部 calldata 读取 + 透传只是少量代码。
  实测的"逐跳下限"变体正好落在 24,576 字节、余量 0，因此**必须**在计入当前
  24,551 字节的 `executorRequest` 工作后**重新实测**。
- **信任模型**：**链上不新增信任假设** —— Executor 仍自行判定结算下界。
  但必须承认：Uniswap V4 的原生 `swap` **没有** `amountOutMinimum` 参数，
  只有 `sqrtPriceLimitX96`，所以 Executor **无法在链上独立验证每一跳是否遵守了逐跳下限**。
  逐跳保护完全依赖链下构建器的正确性。
- **运维成本**：**最低**。无需新部署。需与 Solidity 约定严格且版本化的 payload 格式。
- **结论**：**推荐**。逐跳决策仍留在已复核的 Rust 路径内，链下构建器只是格式化步骤而非新的决策点。

### 方案 C｜`delegatecall` 辅助库

**形态**：把逐跳编码与校验移入已部署的 library，用 `delegatecall` 在 Executor 存储上下文中执行。

- **字节压力**：`delegatecall` + library 地址是**净增**字节，对 25 字节余量**必然放不下**，
  除非先移除其它代码。
- **信任模型**：**三者中最弱**。`delegatecall` 让 library 以 Executor 的完整存储权限运行，
  恶意或有缺陷的 library 可破坏余额与授权；Executor 至少要 pin library 地址并校验 code hash。
- **运维成本**：中。需部署 library 并 pin 地址，library 重新部署时地址需同步更新。
- **结论**：**拒绝**。预算契合度最差、信任模型最弱。仅当 B 被证明不足且 A 被否决时才重新考虑。

## 5. 推荐路径的前置条件

1. **在干净分支上重新实测部署字节码**。24,576 这个数字早于当前 24,551 字节的
   `executorRequest` 工作，不可复用。
2. **先在测试网验证**。测试网 Executor 尚有 148 字节余量。
3. **规范 payload 格式及其版本字节**，并让 Executor 对未知版本直接拒绝。
4. **明确逐跳保护的性质**：是"链下已验证"（advisory）还是"链上可强制"（enforceable）。
   由于 V4 原生 swap 无 `amountOutMinimum`，**链上强制逐跳下限只有方案 A 能做到**。
5. **保持 `executorBatchEnabled=false`**，直到 parity 闸门产出真实复核行，
   且路线级下界在测试网得到验证。
