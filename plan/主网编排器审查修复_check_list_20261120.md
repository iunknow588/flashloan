### 0.0 写库分类学：**基础框架库** vs **动态记录**（**绑定性规则**）

> **使用者指示（2026-11-21）**：*"基础框架库要实盘写入，动态记录可以不写。"*

任何"写生产库"的验收项必须归入**下面两类之一**。**混为一谈是错误**；尤其**不得**
把"基础框架库写入"当作"需单独授权"的动态记录动作。

| 类别 | 内容 | 性质 | 处置 |
|---|---|---|---|
| **基础框架库** | DDL / migration / 表结构 / 列 / 约束 / 索引 / 视图 | 结构性、版本化、**幂等**、**保数据**、与链上实时状态无关 | **验证通过 ⇒ 必须实盘写入目标生产库**；**不需额外授权** |
| **动态记录** | review / depth / ladder / PnL / closed loop / broadcast attempt | 每次运行都变；受"实测零 ≠ 未测"、"不历史回填"、"需当前链状态"约束 | **可以不写**；要写则走 §2 授权流程 |

**判定口径**：不改变任何测量值、只让结构与代码对齐 ⇒ **基础框架库**；
写入某时刻的测量结果 ⇒ **动态记录**。

### 0.1 排序原则（绑定性）

1. **功能完善优先**：离线可实施的功能性验收项**排在 §1**。
2. **耗时/需授权的测试靠后**：实盘广播、**动态记录**写库授权、长窗口**排在 §2**。
   **基础框架库写入不在此列** —— 它在 §1 就地完成（结构对齐，不取任何读数）。
3. **性能优化最后**：性能验收项**排在 §3**，且**不得**改变任何金额/容量/利润口径，**不得**放宽任何门禁。

**§1 全部闭合 = 系统功能完整**；**§2 全部闭合 = 实盘读数完整**；**§3 = 性能达标**。三者**互不替代**。

- [ ] stale WSS、版本漂移、重复提交、错误激增或实际亏损触发对应广播准入关闭，同时保留诊断/修复通道。

## 3. 性能优化验收（**排在全部功能性工作之后**）

> **当前判定**：§1 的功能性验收已清空，故性能优化**可以启动**。
> 但优化**不得**改变任何金额/容量/利润口径，**不得**放宽任何门禁。

- [ ] 建立性能基线（每条链的 review 耗时、广播准备耗时、DB 写入耗时），**先测量再优化**。
- [ ] 定位热点后**逐项**优化，每项优化**单独**附回归证据，**不得**与功能改动混在同一批次。
- [ ] 优化后**重跑全部回归**（见开发计划 §9.2 基线），**不得**以"功能没变"为由跳过。
- [ ] **测量值零 ≠ 未测量**：性能基线缺失的项按**未测量**记录，**不得**用默认零冒充。

## 4. 总体停止条件

- [ ] 机器证据包含 TASK/AC、代码版本、chain ID、DB 绝对路径、schema/checksum、工具版本、时间范围和原始计数。
- [ ] Python 全量单测、Rust 内核、Manager workspace、架构守卫及相关回归在当前 `scripts/` 根目录布局下通过；**跳过和警告逐项说明**。
- [ ] 无历史深度/业务数据回灌；无用默认零或估值掩盖缺陷；**无未授权真实广播**。
- [ ] 缺 amount/PnL、陈旧快照、身份不唯一、签名授权不足、重复提交或 receipt 无法关联时**停止广播**。

## 5. 归档门槛

- 关闭任一任务前，先把当前机器证据与人工摘要存入 `back/`，再从活动清单移除该任务，并在此清单删除对应验收项。
- 归档记录须含：任务号与验收号、代码版本、证据文件路径、chain ID、DB 路径与 checksum、执行时间、结论与残留风险。
- **编号永久不复用**；归档后不得再以同一编号新开任务。
- 实现完成但缺端到端证据的任务**保持开放**，只归档其已验证子项，并在归档记录中写明未覆盖部分。
- **离线演练只能归档"离线侧已验证"的子项**，实盘读数未取到的部分**必须保持开放**并写明未覆盖范围。
