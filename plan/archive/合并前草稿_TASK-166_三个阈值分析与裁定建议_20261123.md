> **为什么阈值只管中间跳？**（详见 §9）
> 第 1/3 跳**本来就用对了**方向敏感排序（`exact_directional_output` → tick → fee → pool_id）；
> 中间跳是**唯一用错的那个**，且**不是"忘了排序"，而是"结构上无法做方向敏感排序"** ——
> 它的取池用 `canonical_pair_key` 把 `(Y,Z)` 折叠成**无序对**，
> 方向在**取池那一刻就被丢掉了**，剩下的排序键只能是方向无关的 `liquidity_index`。
> ⇒ **只有中间跳的选池口径在变** ⇒ 只有它需要阈值。

> **新方案既然有方向，`direction` 列还需要吗？**（详见 §10）
> **需要** —— 但它**不是新造的链上事实**，而是「**区分同一池两个方向投影的钥匙**」。
> 方向在老方案里**一直存在**（`token0`/`token1` 的地址序），只是**没有任何一层把它持久化**，
> 闭环层只能靠**字符串拼接 + 重建时反推**去"借"它（缺陷 3）。
> 同一个池的两个方向，`directional_output` / `tick_rank`（取反）/ `input_capacity_raw`（取不同的列）
> **三者都不同** ⇒ 没有 `direction` 维度，这两行**无处安放**。

## 1. 三个阈值各自的**具体含义**

### 1.1 `_MID_CHANGE_RATE_` —— 中间跳选池变化率（**波及面**）

**它问的问题**：把中间跳的排序口径从 `liquidity_index` 改成方向价格质量
（`directional_output` → tick 序 → fee → pool_id），**有多少个选池决策被换掉了**？

**为什么它是第一道门**：中间跳是**三跳里唯一换口径的**（两侧跳口径不变）。
如果换池率很高，说明原排序在新旧口径下分歧巨大 —— 那么「口径不一致」这个缺陷
（`01 §2.4 缺陷 1`）不仅真实存在，而且**比预想严重**，此时应当**先回 `01 §4.1` 重审主序**，
而不是硬着头皮往下做 `TASK-167`。

**关键：这个阈值有**三种**可能的口径，实测报告同时给了三个数。**必须先定死用哪一个**：

| 口径 | 定义 | 实测 | 含义 |
|---|---|---|---|
| **Δ2 换宇宙**（脚本当前采用） | 新口径在**目标池宇宙**（core4 基础池表）里选出的池 ≠ 旧 `yz.optimal_pool_id` | **82 / 1420 = 5.77 %** | 最终**会不会落到不同的池**（真正的结果口径） |
| Δ1 同宇宙 | 新口径在**同一池宇宙**内仅改排序，取到的池 ≠ 旧的 | **114 / 1420 = 8.03 %** | 纯**排序**造成的分歧 |
| **并集** | Δ1 或 Δ2 任一改变 | **128 / 1420 = 9.01 %** | 最保守的"波及面" |

**建议采用 Δ2（换宇宙）为主判据，Δ1 与并集作为辅助读数**，
理由：Δ2 是**最终结果口径** —— 它直接回答「闭环最终会落到哪个池」。
建议值取 **10 %** 的另一层考虑是：**给并集口径留出余量**
（并集 9.01 % 仍低于 10 % ⇒ 两个口径都不命中 ⇒ **结论不会因口径选择而翻转**，这是稳健的）。

**推论（重要）**：当前实测 5.77 % < 10 % ⇒ **不得进入 P1 的禁令不触发** ⇒
`TASK-167` 可以开工 —— **前提是**另外两个阈值也写死（§3）。

### 1.2 `_LOOP_NET_RATE_` —— 闭环数净变化率（**产出损失**）

**它问的问题**：新口径下的闭环**目录**比旧口径少了多少？

**注意它的符号约定**（`03 §2.1` 阈值表第 2 行）：
阈值写作 `< -_LOOP_NET_RATE_ %`（**净减少**），即触发条件是
`closedLoopNetRate < -LOOP_NET_RATE`，其中
`closedLoopNetRate = (newLoopCount - oldLoopCount) / oldLoopCount`（脚本 `:2504`）。

**为什么它是第二道门**：闭环数减少 = **能套利的组合变少了**。这是**业务产出**的直接损失，
比「换池」本身更严重。命中时不仅要走查，还要**逐条**给出**容量口径**层面的解释
（是新口径算出的容量更严、还是真的没有这条闭环了）。

**建议值 5 %** 的依据：当前实测 **168 → 168，净 0 %**（保留 164 / 新增 4 / 消失 4）。
净 0 % 看起来「完美」，但它**掩盖了结构变化**：有 **4 条消失 + 4 条新增**，
且 **164 条保留闭环中有 26 条中间池换了**。因此：

- 阈值**不能只看净数**（净 0 % 会让任何阈值都不命中，等于门禁形同虚设）；
- 建议 **5 %**：净减少 5 %（即 168 → 约 160）即触发走查。
  按实测，**净减少 1 条闭环 = 0.60 %**，所以 5 % ≈ **8 条**闭环 —— 这个量级足以
  触发逐条解释，又不至于被日常波动误触发。

> **建议补充**：把阈值从「净变化率」升级为「**净变化率** + **消失数**」**双触发**。
> 实测消失 4 条 = 2.38 %。若只看净数，**「消失 10 条 + 新增 10 条」的净 0 %**
> 会**完全绕过**这道门 —— 而实际产能已经掉了 6 %。这是本阈值目前最大的漏洞。

### 1.3 `_PROFIT_DROP_` —— 受影响闭环的有效利润中位数跌幅（**经济代价**）

**它问的问题**：在**受影响**（中间池换了）的闭环上，新口径算出的**有效利润**
比旧口径掉了多少（以**中位数**衡量）？

**为什么它是第三道门、也是最重的一道**：容量变了还能靠调参弥补，**利润变了**才是真的伤。
并且它命中时要求「**核对是否触及利润门禁**」—— 即 `BC-1` 的**正向利润确认**。

**⚠️ 本阈值当前处于「无法测量」状态，必须先解决测量问题**：

| 项 | 实测（2026-11-23） |
|---|---|
| 旧利润 · 实测为正 | **0** |
| 旧利润 · 实测为零 | **0** |
| 旧利润 · 实测为负 | **14**（`runArbitrage returned executable=false`） |
| 旧利润 · **未测量** | **154** |
| **新利润** | **未测量**（只读波次不可算：需要**执行器**跑新池路径） |

**后果**：**154 条闭环连旧利润都没有**（占 168 的 91.7 %）。
中位数在「154 个未测量 + 14 个负」上的取值是**无意义的** —— 它既不是中位负值，
也不是中位正值，而是**主要由缺失值决定**。脚本因此把 `profitDrop` 记为 **`n/a`**。

**建议值 20 %** 的依据：
- 中位数比均值**抗离群**，适合「多数闭环是否受影响」的问题；
- 20 % 的利润跌幅，对套利业务是**显著但非致命**的量级 —— 低于 20 % 视为正常波动，
  高于 20 % 说明新口径选出的池**系统性更差**；
- **刻意不放宽**：项目一贯口径是「门禁一条不放宽」（`README §0`）。
  若取 30 % 或 50 %，等于给「利润腰斩」开口子。

**但必须补上测量前置**（§4）：在 `_PROFIT_DROP_` **能被真正触发之前**，
本阈值只是**一个写在纸上的数**。

## 2. 为什么不能三个阈值用同一个数 / 不能取整

- **三者的**量纲**不同**：`_MID_CHANGE_RATE_` 是**选池决策**的改变比例（分母 1420 三元组）；
  `_LOOP_NET_RATE_` 是**闭环目录**的净变化（分母 168）；`_PROFIT_DROP_` 是**金额**的跌幅（分母中位数）。
  混用会导致「用闭环口径去卡中间跳」这类无意义的比较。
- **基数差 8.5 倍**（1420 vs 168）：同样写「10 %」，中间跳触发线是 142 条三元组，
  闭环触发线是 17 条闭环。**不是同一个意思**。
- **不应取整成 5/10/20 这样的"顺口数"**却不做实测支撑：本次三个阈值**全部有实测锚点**
  （5.77 % / 0.00 % / 未测量），建议值与实测值的关系是明确的（不命中 / 不命中 / 待补测）。

## 3. 建议值的**逐条**推导

### `_MID_CHANGE_RATE_ = 10`

| 依据 | 说明 |
|---|---|
| 实测锚点 | Δ2 = 5.77 %，Δ1 = 8.03 %，并集 = 9.01 % |
| 余量 | 10 % 比并集实测（9.01 %）高约 1 个百分点 ⇒ **三个口径都不命中** |
| 对称性 | 变化率是**双向**的（换更差的池 / 换更好的池），故用**单向**阈值时需留余量；单侧 5 % 会把「并集 9 %」误判为命中 |
| 不放宽 | 若取 15 %，则并集口径下**未来**的常规波动（换池本来就有随机性）会反复误触发 |

### `_LOOP_NET_RATE_ = 5`

| 依据 | 说明 |
|---|---|
| 实测锚点 | 净 **0 %**（168 → 168）；消失 **4** / 新增 **4** |
| 分辨率 | 5 % ≈ **8 条**闭环（168 × 5 %）；实测净 0 % ⇒ 不命中 |
| 反误触 | 日常重物化的闭环增删是**个位数**量级，5 % 足以吸收噪声 |
| 反漏触 | 净减 8 条（产能掉 5 %）已足够触发**逐条**解释，成本可接受 |
| **补强** | 建议**同时**设「**消失数 ≥ 5 条**（≈3 %）」为独立触发条件（§1.2） |

### `_PROFIT_DROP_ = 20`

| 依据 | 说明 |
|---|---|
| 实测锚点 | **无有效锚点**（旧利润 154 未测量 / 新利润未测量）⇒ **须补测后复核** |
| 统计口径 | **中位数**（抗离群），且只在**受影响闭环**（实测 26 条）上计算 —— 样本量小，中位数比均值更稳 |
| 业务量级 | 套利利润跌 20 % 属显著但可挽回；跌 50 % 属结构性伤害 |
| 不放宽 | 门禁不放宽是项目既有纪律 ⇒ 不取 30 %/50 % |

## 6. **发现的一处**口径不一致（需一并订正）

`check_list_20261123.md:256`（T-S-4）与 `未完成任务清单_20261123.md:492`（S-3）写的是：

> 「**510** 对 / **1420** 三元组，变化 **82**（同宇宙 **15** / 换宇宙 **14**）」

但报告 JSON 实测为：

| 项 | 文档写法 | JSON 实测 |
|---|---|---|
| 变化（同宇宙） | **15** | **114**（`changedSameUniverseTriples`） |
| 变化（换宇宙） | **14** | **82**（`changedTargetUniverseTriples`） |

**成因**：文档里的 **15 / 14** 是**「对」（pairs，510）** 的计数，
而 **82 / 114** 是**「三元组」（triples，1420）** 的计数。
两者是**不同分母**，文档把 pairs 的数写在了 triples 的句子里 ⇒ **口径混写**。

**建议**：把该句改为
「510 对 / 1420 三元组；**三元组**口径变化 **128 / 1420 = 9.01 %**（Δ2 换宇宙 **82 / 1420 = 5.77 %**，
Δ1 同宇宙 **114 / 1420 = 8.03 %**）；pairs 口径 Δ2 **14 / 510**、Δ1 **15 / 510**」。

## 9. 附加分析：为什么**只有中间跳**的排序需要改？第 1、3 跳为什么不用改？

> 本节回答一个设计上的核心疑问：**阈值只针对中间跳，是否意味着第一、三跳"没有排序问题"？**
> 答案：**不是没有排序问题，而是它们已经用对了排序；中间跳是唯一用错的那个。**

### 9.1 事实核对：三跳的选池口径

| 跳 | 选池代码 | 排序键 | 方向敏感？ |
|---|---|---|---|
| 第 1 跳（锚点→Y） | `candidate_edge_pool_manager/src/lib.rs:1230` `recommend_direction` | `exact_directional_output` ↓ → tick 序 ↓ → fee ↑ → pool_id ↑ | **是** |
| 第 2 跳（Y→Z） | `candidate_exchange_pool_manager/src/lib.rs:1159` `pool_score` | `liquidity_index` ↓ → pool_id ↑ | **否** |
| 第 3 跳（Z→锚点） | `candidate_edge_pool_manager/src/lib.rs:1230` `recommend_direction` | `exact_directional_output` ↓ → tick 序 ↓ → fee ↑ → pool_id ↑ | **是** |

第 1/3 跳的排序是**方向敏感**的：它按 `token_in` 分流计算 `exact_directional_output`
（`:1249`）与 `tick_ordering_rank`（`:1244`），同一批池在两个方向上被排成**相反**的顺序
（`01 §3.2` 引 `tick_ordering_rank` 注释："两个方向因此将同一批池排成相反的顺序"）。

### 9.2 核心原因：**中间跳的选池数据模型里，根本没有"方向"这个维度**

这是最本质的原因，**不是**"中间跳碰巧忘了排序"，而是**它的数据模型表达能力不够**。

看中间跳的取池代码（`candidate_exchange_pool_manager/src/lib.rs:1034-1045`）：

```rust
for token_x in tokens {
    for token_y in tokens {
        let direction_key = format!("{token_x}->{token_y}");   // ← 方向只存在于「标签」
        let pair_key = canonical_pair_key(token_x, token_y);    // ← 取池却按「无序对」取
        let matched = active_by_pair.get(&pair_key)...          // ← 拿到的池列表与方向无关
        let optimal_pool_id = pool_ids.first().cloned();        // ← 于是排序也必然与方向无关
```

**关键在 `canonical_pair_key`（`:1151-1157`）**：它把 `(Y, Z)` 折叠成**无序**的
`min:max`。于是：

- `active_by_pair` 这个池列表，**对 `Y->Z` 和 `Z->Y` 是同一个列表**（`:1040-1041`）；
- 这个列表的排序键 `pool_score = liquidity_index`（`:1159-1163`）是
  **方向对称的标量**（V4 的 `L` 不区分方向）⇒ **同一个列表在两个方向上排序结果必然相同**；
- 所以 `direction_key`（`Y->Z` / `Z->Y`）**只是一个标签**，
  **背后的池和顺序对两个方向是同一份**。

**一句话**：中间跳**在结构上无法做方向敏感排序** —— 它的排序对象里没有方向信息。
它不是"选错了排序键"，而是**"排序键只能是方向无关的，因为取池时方向就被丢掉了"**。

### 9.3 为什么 `liquidity_index` 在这里特别糟糕

因为它是**方向对称**的量：`L` 是集中流动性的总标量，**不携带深度信息**。
仓库自己在深度质量门禁里已经明文否定它（`pool_manager/src/lib.rs:1394-1399`）：

> "The liquidity index is `L / 1e18` ... carries no information about depth: measured
> against the true reserve TVL its rank correlation is only ~0.09. Filtering on it
> removed genuinely deep pools."

与真实储备 TVL 的秩相关仅 **0.09** ⇒ **近乎随机**。
⇒ 中间跳实际选出的是「**流动性数值大但价格最差**」的池，
而两侧跳选的是「**方向价格最好**」的池。**三跳用三把尺子量同一件事。**

### 9.4 三层的**职责差异**是为什么会分叉出两种口径的历史原因

链路是严格分层的（`01 §2.1`）：

```text
token_libraries → pool_scope → candidate_edge → candidate_exchange → closed_loop → review → broadcast
```

| 层 | 职责 | 与方向的关系 |
|---|---|---|
| 候选边 `candidate_edge` | **锚点 ↔ 候选代币**：为锚点的每条边找最优池 | `direction_key` = `A>B`（**一种格式**） |
| 市场观察 `candidate_exchange` | **中间交换池的观察**：记录"某个锚点下 Y→Z 有哪些池" | `direction_key` = `A->B`（**另一种格式**） |

`candidate_exchange` 的定位是**观察/记录**（"观察到的池有哪些、最优是哪个"），
`candidate_edge` 的定位是**推荐/择优**（"这条边该用哪个池"）。

**观察层只需要回答"有没有池"，不需要回答"这个方向上哪个池最好"** ——
所以它退化成了 `liquidity_index` 排序 + 一个 `direction_key` 标签。
**这个设计在"观察"语义下是自洽的**（记录一个不敏感于方向的排序，省一半计算）；
**但闭环层复用它来选池时，它就变成了"选池口径不一致"的来源**。

⇒ **根因是「观察层与择优层复用了一张表」**：闭环层需要的语义（方向敏感择优）
比 `candidate_exchange` 提供的语义（方向无关观察）**更强**。

### 9.5 为什么重构能一次性解决三跳（而不只是"修中间跳"）

方向表的**主键是 `(pool, direction)`**，方向成为**第一等维度**后：

1. **中间跳不再是特例** —— 它和两侧跳读**同一张方向表**的同一列，
   "三跳口径一致"不再靠"两边改对了、中间还没改"来维持，而是**结构上无法不一致**。
2. **方向成为主键的一部分 ⇒ 排序天然方向敏感** —— 同一批池在两个方向上有两行、两套序位，
   不再需要 `canonical_pair_key` 把方向丢掉。
3. **两侧跳的行为必须保持不变** —— 这是 `TASK-166` 影子比对的**核心验证点**：
   新口径下第 1/3 跳选中的池必须与现状**逐条相同**。

   > **⚠️ 实测证据的准确边界（如实记录）**：当前报告**只测了中间跳**，
   > 两侧跳的选池**没有被单独比对**。可间接印证的是：
   > 保留闭环 **164** 条中，**仅 26** 条的中间池发生变更
   > （`retainedWithChangedMiddlePoolCount = 26`），
   > 其余 **138** 条**中间池未变**；容量差值为零的恰为 **142** 条、
   > 负 **18** / 正 **4** —— 与"26 条受影响"同量级。
   > 而**两侧跳的池 ID** 在 `retained` 列表中**未被记录**
   > （字段仅 `anchorTokenKeyId` / `loopKey` / `tokenY` / `tokenZ`），
   > 因此**"两侧跳选池逐条未变"目前是设计推断，不是已实测结论**。
   > ⇒ 见 §9.6 的建议：**这条推断应升级为一条可执行的断言**。

### 9.6 对三个阈值的直接影响（本节的结论）

**`_MID_CHANGE_RATE_` 只针对中间跳，是因为只有中间跳的选池口径在变。**
两侧跳口径不变 ⇒ 其闭环归属、利润、容量**均不变** ⇒ 不需要为它们设阈值。

但**这带来一个重要的推论**：

> 若日后有人**改动两侧跳的排序口径**，本阈值体系**不会自动捕获**。
> 因为 `_MID_CHANGE_RATE_` 只测中间跳。
> ⇒ **建议**：在 `TASK-168`（闭环层切换）的验收里，
> 增加一条**两侧跳等价性断言**（第 1/3 跳选中的池**逐条**与现状相同）。
> 这不是放宽门禁，而是把"两侧跳不变"这件事**显式地、可执行地**钉住
> —— 否则"两侧跳不变"目前只是**设计意图**，没有**自动守卫**。
> （`check_list §1.3.6` 已有"逐个闭环核对"的等价性验收，应确认其覆盖第 1/3 跳的**选池**，
> 而不仅是闭环的**容量/利润**相等。）

## 10. 附加分析：新方案既然有方向，**`direction` 这个参数还需要吗**？

> 问题：最初的池子信息**没有方向**，新的池子方案**有方向** ——
> 那 `direction` 这一列是不是"为了新方案而新造出来的参数"？还需要吗？

### 10.1 先澄清一个前提：**老方案并非"没有方向"，而是"方向不承载信息"**

老方案里方向是**存在的**，但只以**三种弱表达**存在（`01 §2.2`）：

| # | 表达 | 位置 | 缺陷 |
|---|---|---|---|
| (a) | **物理方向**（池自身 token 顺序） | `pool_manager/src/scope.rs:1117-1127` | `token0`=低地址、`token1`=高地址 —— **事实层已有方向，但从未被存储** |
| (b) | **逻辑方向键**（代币对+字符串） | `candidate_edge:996`、`candidate_exchange:1039` | `A>B` 与 `A->B` **两种格式**，靠拼接字符串对齐 |
| (c) | **运行时反推** | `closed_loop_manager:1906` `resolve_hop_direction` | 方向**每次重建时重算**，反推失败即**硬失败** |

⇒ **老方案不是"无方向"，而是"方向没有被物化"**：
方向藏在 `token0/token1` 的地址序里（事实层），
但**闭环层存不下它**，只能在重建时**反推** —— 这正是缺陷 3
（`01 §2.4`："方向在闭环构建期反推，错一步即硬失败"）。

### 10.2 那么 `direction` 列是不是**冗余**的？—— 不是

关键区分：

| 概念 | 是否冗余 |
|---|---|
| **`direction` 作为「池的身份标签」** | **冗余** —— 它是 `f(token0, token1)` 的**纯函数**（`02 §2.2`："恒成立，不存在需要判定的分叉"），确实可推导 |
| **`direction` 作为「行的主键维度」** | **不冗余** —— 它是**承载方向相关量**的索引维度 |

**为什么必须是主键维度**：因为一个池在两个方向上的**量是不一样的**。
看投影代码（`compare_directional_pool_projection_20261123.py:1106-1143`）：

```python
for direction in (0, 1):
    token_in  = direction_input_token(pool, direction)      # ← 方向决定输入代币
    token_out = direction_output_token(pool, direction)
    output   = exact_directional_output(state, token_in, catalog)  # ← 方向改变价格质量
    rank     = tick_ordering_rank(state, token_in)                  # ← 方向改变 tick 序（取反）
    capacity = snapshot["single_tick_max_token1_raw" if direction == 0
                        else "single_tick_max_token0_raw"]           # ← 方向改变容量上限
```

**同一批池，在两个方向上：**
- `directional_output`（价格质量）**不同**；
- `tick_rank` **相反**（`candidate_edge_pool_manager:1330-1333`：`token_in==token0` 取 `tick`，
  `token_in==token1` 取 `tick.checked_neg()`；注释明写"两个方向因此将同一批池排成**相反的顺序**"）；
- `input_capacity_raw` **取不同的列**（方向 0 取 `single_tick_max_token1_raw`，方向 1 取 `..._token0_raw`）。

**实测印证**：方向 0 的 `directional_output` **86 行中 3 行未测量**，
方向 1 **86 行全部测量** —— **同一批池，两个方向的测量完备性都不同**（`step4_directional_output`）。
若没有 `direction` 维度，这两行**无处安放**。

### 10.3 决定性证据：I-3 的两行投影不变量

实测报告 `step3_two_row_projection` 验证了**每个可用池恰好两行**，
且**两行的"共享字段"逐字节相同**（`invariantI3Holds = True`，`sharedFieldMismatches = []`）。

脚本的判定逻辑（`:1594-1610`）把字段分成两类：

```python
for field in ("pair_key_id", "fee", "tick_spacing", "tick",
               "sqrt_price_x96", "liquidity", "pool_status"):
    if entries[0][field] != entries[1][field]:   # ← 这七个字段必须相同
        field_mismatches.append(...)
```

**共享字段**（两方向相同）：`pair_key_id` / `fee` / `tick_spacing` / `tick` / `sqrt_price_x96` /
`liquidity` / `pool_status` —— 这些是**池的固定事实**，与方向无关。

**方向相关字段**（两方向不同）：`input_token_key_id` / `output_token_key_id` / `zero_for_one` /
`directional_output` / `input_capacity_raw` / `pair_direction_rank`。

⇒ **`direction` 不是"给池加了一个新属性"，而是"把同一个池的两种投影区分开的那把钥匙"。**
两行共享事实行，**只在方向相关量上分叉**。没有 `direction`，这两行无法共存于一张表。

### 10.4 它真正解决的四件事（每件都是老方案做不到的）

| # | 解决的问题 | 老方案为何做不到 | `direction` 的作用 |
|---|---|---|---|
| **1** | **中间跳做方向敏感排序** | `canonical_pair_key` 把 `(Y,Z)` 折叠成无序对，方向在**取池时**就没了（§9.2） | 方向进主键 ⇒ 排序天然方向敏感 ⇒ **中间跳不再是特例** |
| **2** | **方向不用反推** | 闭环层重建时 `resolve_hop_direction` 反推，**错一步即硬失败**（缺陷 3） | 方向**随行存储** ⇒ 从"反推"降级为"读取"（`02 §4.3` 阶段 2） |
| **3** | **闭环跳表存下方向** | 闭环表**只存逻辑代币对**，不存方向 | `hop_direction` 列 + `directional_pool_id` 引用（`02 §4.1`） |
| **4** | **消除字符串拼接对齐** | `A>B` 与 `A->B` 两种格式，靠 `format!` 拼接对齐（缺陷 2） | 结构化 `direction` 列成为**权威字段**（`02 §5.1`） |

### 10.5 那"老方案没有方向"这个说法，在**哪个意义上**成立？

在**「闭环层存不下方向」**这个意义上成立 —— 这正是缺陷 3。
但**基础池层一直有方向**（`token0`/`token1` 的地址序），
而且**两侧跳一直在做方向敏感排序**（`recommend_direction` 按 `token_in` 分流）。

⇒ **老方案的真实状态是**：
**方向在事实层存在、在两侧跳的排序里生效，但没有任何一层把它持久化下来**，
闭环层只能靠字符串拼接 + 重建时反推来"借"这个信息。
新方案做的不是**发明**方向，而是**把既有事实物化下来**。

### 10.6 一个可以讨论的简化点：`direction` 本身可推导，是否该存？

严格说，`direction` 由 `token0`/`token1` 地址序**唯一确定**（`02 §2.2`），
且 DDL 的 `CHECK (direction IN (0,1))` 也保证不会分叉。
**理论上可以做成生成列**（SQLite 支持 `GENERATED ALWAYS AS ... STORED`），
或干脆由 `zero_for_one` 替代（`direction=0 ↔ zero_for_one=false`）。

**但当前设计保留为普通列是合理的**，理由：

1. **主键需要它**：SQLite **明确禁止**生成列参与 `PRIMARY KEY` —— 实测确认：`STORED` 与 `VIRTUAL` 两种生成列建主键均报 ``generated columns cannot be part of the PRIMARY KEY``（SQLite 3.45.3）；
   而 `PRIMARY KEY (network, chain_id, protocol, scope_key, base_pool_id, direction)`
   （`02 §3.1`）**恰恰需要 `direction` 在主键里** ⇒ 它必须是**存储列**。
2. **它是"读出来的权威字段"**：闭环层、候选边层都要**按方向取行**，
   让它们都去现场推导一次，既多一处代码，又多一个可能推导错的点。
3. **与既有纪律一致**：本项目的方向一贯是「**存下来，而不是每次反推**」
   （缺陷 3 的整改目标就是"方向在写入时就应该是存在的"）。

> **一句话答案**：**需要**。
> 但它的性质要说清楚 —— **它不是一个"新的链上事实"，而是一把
> 「区分同一池的两个方向投影」的钥匙 + 一个「让方向敏感排序成为可能」的索引维度**。
> 方向**从来不是被发明的**，只是**第一次被存下来了**。
