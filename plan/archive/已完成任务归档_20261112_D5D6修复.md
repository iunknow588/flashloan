## 1. 批次背景

D4（容量感知双向阶梯）落地后，代码侧已具备"按实测容量确定阶梯起点"的能力。
但 W6 副本演练暴露了一个更靠上游的事实：

> **容量数据从未到达尺寸计算路径。**

D4 的起点依赖 `cap_raw`，而 `cap_raw` 来自 `_liquidity_cap_raw()`，
后者读取的是 `dex_candidate_pools.balances_json` —— **候选表**，不是快照表。
`depth --apply` 填满了快照表，却从未触碰候选表。

两个缺陷叠加后，**D4 的容量感知起点仍会走回退分支**，
即"每次仍从 1.0 token 起步"的老问题原封不动地保留。

## 2. 缺陷 D5（P0）——`depth --apply` 只写快照表

### 根因

```text
refresh_depth()
  └─ write_depth_snapshot()
       └─ UPDATE v4_exchange_pool_liquidity_snapshots   ← 只写这一张表

dex_candidate_pools 的唯一写入者：
  upsert_eligible_pool_rows()
    └─ 仅由 refresh_pair() / refresh_key() 触发
       └─ refresh_depth() 从不调用  ← 断链点
```

### 为什么致命

尺寸计算路径真正读取的是**候选表**：

- `core/db/builders.py:688`、`:823`
  → `"balances": _json_loads(pool.get("balances_json"))`
- `dex_quote_evidence_size.py:172` `_liquidity_cap_raw()`
  → `_pool_borrow_side_amount()` → `balances["token0"|"token1"]`

快照表填得再满，对这条链路**零影响**。

### 副本库实测（修复前）

```text
snapshot balances 非空            = 94 / 4669
dex_candidate_pools balances 非空 = 0  / 47
有实测快照的候选池                = 47 / 47
```

⇒ 纯属**传播缺失**，不是**采集缺失**。

### 修法

新增 `flashloan/tools/pool_manager/src/lib.rs::propagate_balances_to_candidate_pools()`：

- 在 `refresh_depth()` 的 `options.apply` 分支中调用
- 以**相关子查询**把快照载荷 UPDATE 进 `dex_candidate_pools.balances_json`
- **无实测快照的行保持原样**（缺失测量必须保持缺失，**不得伪造为零**）
- 输出新增字段 `candidateBalancesPropagated`

## 3. 缺陷 D6（P0，潜伏）——候选表 `balances_json` 写的是 token 地址

### 根因

`upsert_eligible_pool_rows` 原写：

```rust
"token0": pool.token0,
"token1": pool.token1,
```

而 `pool.token0` / `pool.token1` 来自 `SELECT e.token0 ... FROM v4_exchange_pools`
—— 这是 **token 地址**（`0x...`），不是数量。

### 为什么致命

```text
_pool_borrow_side_amount()
  └─ _positive_decimal_or_none(balances["token0"])
       └─ _decimal()
            └─ Decimal("0x0868...") → InvalidOperation
               → ValueError("invalid decimal amount")   ← 抛异常，不是返回 None
```

而 `rust_closed_loop.py:3509` 调用 `_liquidity_cap_raw()` **无 try/except**，
`_route_task_config` 调用侧也无局部处理器
⇒ **未捕获异常中断复核循环**。

### 潜伏原因

修复前候选表 `balances_json` 恒为 `{}`，这条异常路径**从未被触发**。
D5 修好传播后 D6 **必然暴露** ⇒ 两者**必须同批修复**，
单独修 D5 反而会把"静默回退"升级为"运行时崩溃"。

### 修法

- `token0` / `token1` 改用**实测快照数量**
- 地址身份保留在显式键 `token0Address` / `token1Address`
- 无实测快照时写 `Value::Null` ⇒ 消费端安全退化到 `None` 回退分支
