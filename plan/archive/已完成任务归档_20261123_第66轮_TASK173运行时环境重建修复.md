## 一、缺陷机制（**实测钉死**，比初判更精确）

初判只说「Windows 上 `SetEnvironmentVariableW(name, "")` 等于删除」。
本轮把**「损失在哪里」**也钉死了 —— 这一点决定了守卫该怎么写。

| 环节 | 实测 |
|---|---|
| 宿主注入 | `GIT_CONFIG_COUNT=10` + `GIT_CONFIG_KEY_0..9` / `GIT_CONFIG_VALUE_0..9`，其中 `GIT_CONFIG_VALUE_0` 与 `GIT_CONFIG_VALUE_5` 为**空值**（经 .NET `GetEnvironmentVariables('Process')` 复核：**key 存在**、值长度 **0**）；此时 `git config --list` **rc=0** |
| `os.environ.clear()` | 把**进程环境块**整体清空 |
| `os.environ.update(original_env)` | 逐键写回；对**空值**变量，`SetEnvironmentVariableW(name, "")` 等于**删除** ⇒ 空值变量**从环境块里消失** |
| **关键点** | `os.environ` **仍然报得出**该变量（值 `""`）—— **损失在 Python 侧完全不可见**；只有**子进程**看得见，因为它继承的是**进程环境块** |
| 子进程实测 | 同一台机器上：清空前子进程**看得到** `GIT_CONFIG_VALUE_0`；`clear()+update()` 之后**看不到** ⇒ `git` 以 **128** 退出（`error: missing config value GIT_CONFIG_VALUE_0`） |

⇒ **判据**：损失**不在** `os.environ`，**在**环境块 ⇒ **回归守卫必须从子进程观察**；
   只断言 `os.environ` 会得到一条**空洞**的断言（改前改后都是 `""`）。

**可观察后果**：之后任何 **Python 子进程调用 `git`** 都会以 **128** 退出：
`error: missing config value GIT_CONFIG_VALUE_0` / `fatal: unable to parse command-line config`。

### 2.1 守卫的形状（为什么必须是「子进程 → 孙进程」）

守卫探针跑在**子进程**里，因为**空值环境变量无法在当前进程内构造**
（Windows 上 `os.environ[k]=""` 会**删除**该变量）。
子进程用**显式环境块**启动 ⇒ 该变量在子进程的环境块里**存在且为空**；
子进程跑完 `_runtime_environment()` 后再起**孙进程**（**不指定**环境块 ⇒ 继承子进程的环境块）⇒
孙进程里 `sys.argv[1] in os.environ` 为真 ⟺ **该变量仍在环境块里**。

```
pytest 进程
  └─ 子进程（显式 env：含空值变量）
       ├─ with run_module._runtime_environment(): pass
       └─ 孙进程（继承子进程环境块）→ 断言变量仍在
```

**探针已修一处**：上一轮引入的探针字符串里有**一行重复**的
`sys.exit(0 if survived else 1)`（死代码，第一行即退出）⇒ 本轮删除。
