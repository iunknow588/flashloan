### 读取器的口径

`_read_valuations_from_db()` **只**返回 `verdict='route_found' AND usdg_amount_raw IS NOT NULL` 的行：

* `no_route` 是**真负面**，不携带价值；
* `api_error` / `api_unavailable` 是**未知**，不携带价值；
* 两者都只是"缺席"，**绝不写 0**。

因此一个绑定侧代币没有估值的池会落入 `unmeasured`，而**不会**被当成"价值为零"。

`_read_depth_rows_from_db()` **只**返回 `capacity_raw IS NOT NULL` 的池：
"没有容量行"= 未测量，与"测量为 0"是不同陈述。

## 二、本轮发现并修复的两个缺陷

### 缺陷 1：基础资产估值报告**无法落库** ⇒ 42 个池被误判"未测量"

`read_valuation_report()` 原本只接受两种包络：带 `report` 键的完整批次报告，或本身就是完整批次报告。
但**基础资产探针**（ETH / WETH / USDC）产出的是**只含 `tokens` 的偏包络**
（顶层为 `source` / `observedAt` / `sources`，没有 `report`），落库时报 `missing field 'source'`。

后果：

* 基础资产估值**从未进入持久化估值库**；
* 分带工具从库里读估值时，**ETH 侧找不到估值**；
* **42 个以 ETH 为绑定侧的池全部落入"未测量"**（`binding token has no USDG valuation`），
  恰好复现了交接说明预期中的"ETH 估值缺口"。

**修法**：`read_valuation_report()` 在既非完整批次、也非 `report` 包裹时，若文档含 `tokens` 列表，
则按 token 行重建批次报告——`source` / `observed_at` / `protocols` 取自 token 行本身；
计数器（`requested_count` / `route_found_count` / `no_route_count` / `unknown_count`）**由行重算**，
**不信任**可能描述了不同总体的外层信封。

这条路径与 `ValuationBatchReport::from_tokens()` 同源，
因此"探针报告"与"库中读回的证据"在门禁眼里**无法区分**，也就不会做出不同裁决。

### 缺陷 2：持久化估值库的**基础资产从未被落库**

即使修好读取器，基础资产估值报告本身也从未落过库——上一轮只落了 194 只股票代币的报告。
本轮补做：

```
token-manager land-valuations --database <副本> \
  --valuation-report logs/plan/runtime_evidence/reports/val2_base_asset_usdg_valuation_20261112T135110.json --apply
=> {"written":3,"valued":3,"unvaluable":0,"unknown":0}
```

库中估值行 **194 → 197**，其中 `route_found` **159 → 162**（新增 ETH / WETH / USDC）。

### 3) 确定性复现

三个分档子报告（carryable / dust / unmeasured）同样**逐字段一致**。

### 4) 与旧基线（25 / 69 / 0）的差异归因

数据库路径给出 **26 / 68 / 0**，旧报告路径给出 **25 / 69 / 0**，差异**恰好 1 个池**：

| 池 | 旧（13:46 dry-run 报告） | 新（15:32 库内快照） | 结论 |
|---|---|---|---|
| `0xedaf5b20d883a50a01411912f1977077d3d94b01f6e5996f6cd14aaecc1a2a35` | `capacityToken0Raw=1647747756641` → 深度 0.003368 USDG → dust | `capacityToken0Raw=61124088476116541` → 深度 124.970494 USDG → carryable | **链上流动性在两次测量之间变化**（约 37 倍） |

* 该池的 **USDG 估值完全相同**（`2044537553`），**唯一变化的是深度快照**。
* 库内快照由 `pool-manager depth --apply` 于 **15:32** 写入，**比**旧 dry-run 报告（**13:46**）**更新**。
* 全量对比：**94 池中 74 个池的 `bindingCapacityRaw` 不同**（市场波动），
  **但只有 1 个池跨越 10 USDG 门槛** ⇒ 阈值判定对实测波动不敏感，分带逻辑本身稳定。
* **旧报告路径仍可复现原始 25/69/0**（实测 `--depth-report` + `--valuation-report` 输出完全一致），
  证明本轮重构**行为等价**，差异**全部来自数据新鲜度**，不是来自代码。
