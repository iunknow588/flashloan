## 3. 关键发现：ladder 不是线性链，而是**分支** double/halve 搜索

这是本轮最重要的实测结论，也是初版采集器判错的根因。

内核 `official_v4_best_amount`（`flashloan/rs-src/src/execution.rs`）执行的是**分支搜索**，
不是一条线性链：

- 先探测**自己推导出的起始量**（`derive_initial_amount_raw`：容量 ×
  `ladderStartCapacityFraction`，默认 0.5，并夹取到容量）；
- 首探测成功 → `bounded_double` 向上翻倍（利润变好才继续），
  变差则 `bounded_half` 向下；
- 首探测 revert → 先**向下**折半搜，再**向上**翻倍搜，两者按探测预算交织。

因此"每相邻两行必须是 double 或 half"这个判据**本身就不成立**：
在分支点会出现 `other`，那是内核合法的换向。

实测（8 行 ladder）：

```
0xd5ca3088c29b93  ← 起始量（内核自推导）
0x6ae51844614dc9  ← 折半
0x35728c2230a6e4  ← 折半
0x1ab94611185372  ← 折半
0xd5ca3088c29b9   ← 折半（触及 floor）
0x6ae51844614dc   ← 向上分支（×2 回溯）
0x38d7ea4c68000   ← floor 夹取（0x38d7ea4c68000 = 1e15 = 0.001 @18dp）
0x1ab946111853726 ← 继续翻倍
```

### 3.1 正确的判据：double/half **闭包**可达性

改用**传递闭包**判据后，**44/44** 条 ladder 的**每一个**观测尺寸
都落在起始量的 double/half 闭包内：

| 观测 | 读数 |
|---|---|
| 带 ladder 的 review | **44 / 44** |
| `everySizeIsReachableFromTheStart` | **true**（44/44） |
| `everyLadderUsesDoubleOrHalf` | **true**（44/44） |
| 呈线性 double/halve 链的 ladder | **3**（单行：只探测了起始量） |
| `allLadderSizesWithinCapacity` | **true**（44/44） |
| ladder 最小值分布 | `0x38d7ea4c68000`（=1e15，floor）**41** 条；单行 ladder **3** 条 |
| `clamped_to_floor` 步数 | 3 行 ladder 各 1 次（floor 夹取是内核 `bounded_half` 的合法行为） |

### 5.1 关于 DB 摘要的一次跨轮变化（据实说明）

第 50 轮复采时，该文件的摘要变为 `79e67bf26add304372eb3f28f42ec29871b14a75b451dacb204ef9f797c2229f`。
经核验：

- 变化时刻为 **2026-11-21 04:50:26 本地时间**，早于第 50 轮采集；
- 同一时刻本环境内**运行中的应用运行时**写入了
  `flashloan/src/runtime/parameters/execution.json`
  （`last_success_at=2026-11-20T20:50:26+00:00`，即一次例行运行时心跳，
  **不是** review 写入）；
- **review 数据本身逐条未变**：44 条 review 的 `signed_pnl_raw` / `signed_pnl_amount` /
  `reviewed_at` / `review_status` / `review_reason` / `bestAmount` / 容量锚
  与第 50 轮快照**零差异**；`manager_review_library_state` 的全部计数、
  版本与 checksum 亦**完全一致**。

即：摘要变化是 **WAL 落盘/页重排**造成的**文件字节**变化，**不是**业务数据变化。
两轮报告各自记录的摘要都是**其采集时点**的真实读数。
