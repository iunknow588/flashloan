## 1. FIX-R23-01｜TASK-128 / GAP-C：`resolve_token` 单币种定点修复

**根因**：`healing_actions()` 的代币分支只有 `repair_tokens`（批量
`materialize-libraries`）。批量路径重写全部四库，无法告诉运营方**究竟是哪个符号**
被修复，还把已经正确的行一并改写。

**修复**：

| 新符号 | 职责 |
|---|---|
| `token_defects()` | 逐符号定位五类缺陷：`missing_decimals` / `missing_symbol` / `funding_address_mismatch` / `counterfeit_admission` / `stock_provenance_invalid` |
| `resolve_token_targets()` | 只把**可按符号解析**的缺陷送往 `POST /v1/tokens/resolve` |
| `repair_resolve_token()` | 逐符号调用并统计 `resolvedCount` / `failedCount` / `blockedCount` |
| `audit_tokens()` | 新增 `defects` / `defectCount` / `defectKinds` / `resolvableTargets` / `unresolvableDefectCount` |

**一个关键的设计判断**：**假币准入不能按符号修复**。假币地址本身就是错的，
解析它的符号只会返回同一个假币。因此假币与无符号 token 被标记为 `blocked`
并回落批量路径（批量路径负责撤销错误准入），而不是被静默跳过或假装修好。

**关联**：`TASK-128` / `AC-192`

## 2. FIX-R23-02｜TASK-129 / GAP-D：池异常分离 + 全范围贯通矩阵

**根因**：`healing_actions()` 未区分「池子无容量」与「池子读数异常」，
两者修复路径不同却共用一个 `pool_depth_insufficient` 状态；且缺少 §7.0.5 要求的
贯通矩阵，任一环节为空集会被沉默掩盖。

**修复（分类按池 id，按真实读数判定）**：

| 情形 | 判定 | 分类 | 修复路径 |
|---|---|---|---|
| TVL 高于上限 / 缺失 | 读数不可信 | `pool_reading_invalid` | `remeasure_pool_depth` → `pool-manager depth` |
| TVL 在带内但低于下限 | 市场事实：池真的浅 | `pool_depth_insufficient` | `replace_shallow_pool` → `refresh-key` |
| 两者兼有 | 两者皆有 | `pool_depth_insufficient` | `replace_shallow_pool_and_remeasure_depth` |

**贯通矩阵**（`cascade_matrix()`，§7.0.5 的 F→C→P→L）：

```text
资金代币集合 F（官方地址唯一、decimals/symbol 完整）
   ∪ 候选代币集合 C（USDG 门禁通过、估值新鲜）
        ↓ 配对
   候选池 P（固定费率 0<fee<=30000、非动态、hook=0、深度已确认）
        ↓ 三跳组合
   闭环 L（恰好 3 hops、hop 全命中 P、pool_scope_checksum ∈ core4）
```

**主网只读实测**（本轮新增可见性）：

```text
MATRIX funding valid=5/5 counterfeit=0 | candidateTokens admitted=199 symbols=199
       | pools distinct=858 | loops total=106 threeHops=106 hopsInScope=260/318
```

> **新发现**：**58 个闭环 hop 引用了候选集外的池**（`260/318`）。
> 这个缺口此前在编排器报告里**完全不可见**——它既不体现在池层计数里，
> 也不体现在闭环层的 `valid` 里。贯通矩阵把它显式呈现出来。

**关联**：`TASK-129` / `AC-193`

```text

    positive_reviews > 0

    blockers == []
    missingValue == 0
```

`stableWindows=N/3` 与 `stable=`。

## 4. FIX-R23-04｜TASK-131：链无关性证明

**证明的两部分**：

1. **同一代码路径**：`activate_scope()` 只注入 `NETWORK` / `SCOPE` / `CHAIN_ID`；
   链 id 在源码中仅出现于 `KNOWN_SCOPES` / `CHAIN_DATABASES` / `REGISTRIES` /
   `database_for_chain()` 四处**配置**位置，业务逻辑零硬编码。
2. **数据隔离**：所有查询带 `network=? AND chain_id=?` 过滤，
   `assert_chain_database()` 拒绝他链文件。

**固化为 5 条可执行回归用例**：

| 用例 | 锁定的不变量 |
|---|---|
| `test_the_orchestrator_supports_both_chains_through_one_path` | 两条链走同一 `activate_scope` 路径 |
| `test_each_chain_resolves_to_its_own_database_file` | 每链解析到自己的数据库文件 |
| `test_the_chain_database_guard_refuses_the_other_chains_file` | 守卫拒绝他链文件 |
| `test_a_report_never_contains_another_chains_rows` | 同一库含两链数据时报告只含当前链 |
| `test_the_cascade_matrix_is_chain_scoped` | 矩阵只统计当前链 |

**关联**：`TASK-131` / `AC-197`
