## 1. 已修复缺陷

### FIX-R22-01 编排器源码语法错误（critical）

`pool_depth_replacement_report` 的 `return {` 语句在一次行区间拼接中被吞掉，
剩余字典字面量成为游离表达式，模块 **import 即失败**。

- 修复：重新插入 `return {`，并补回被吞掉的 `status` 与 `reason` 返回键。
- 关联：`TASK-127` / `AC-190` `AC-191`

### FIX-R22-02 Manager 复核库的 best-amount 证据完全不可见（critical）

这是本轮**最具生产影响**的一项。

- **根因**：`manager_v4_reviews` **根本没有 `payload_json` 列**——它把最优交易金额
  证据放在 `static_preview_json` / `run_arbitrage_json`。而 `best_amount_state`
  只读 `payload_json`，于是**每一条 Manager 复核都被判成 `best_amount_missing`**，
  复核层永远不满足"每个复核都有明确盈亏数值"，广播永远不会发生。
- **放大因素**：同一文件还存在 5 份常量块、3 份 `best_amount_state` 与
  `best_amount_failure_reason`、2 份 `materialize_reviews`，后定义者把正确实现
  整段遮蔽。
- **修复**：新增 `review_payloads` 与 `_best_amount_calculation` /
  `_live_onchain_evidence` / `_probe_rows` 三个解析辅助函数，统一从三种载体解析；
  `best_amount_state` 与 `best_amount_audit` 改走同一路径；删除全部重复定义。
- 关联：`TASK-127` / `AC-190` `AC-193` `AC-197`

### FIX-R22-03 Manager 复核缺失原因被抹平（major）

`audit_reviews` 与 `review_evidence` 直接读 legacy 专有列
`selected_profit_missing_reason`；Manager 复核把原因写在 `review_status` /
`review_reason`。真实上游失败原因被丢弃，运营侧只能看到 `evidence_missing`。

- 修复：两处统一改用已兼容两种来源的 `review_missing_reason(row)`。
- 关联：`TASK-127` / `AC-193` `AC-194`

### FIX-R22-04 pool-manager 能力探测是死代码，且会崩溃编排器（major）

- **死代码**：`pool_manager_command_support` 从未被调用 → 部署旧二进制时
  深度刷新静默空跑，而报告看起来健康。
- **崩溃**：即使被调用，它只捕获 `FileNotFoundError` / `TimeoutExpired`，
  截断或架构不符的二进制抛 `OSError` 会让整个编排器崩溃。
- **键缺失**：缺失二进制分支不返回 `complete`，调用方读到 `None` 而非 `False`。
- **修复**：接入 `audit_pools` 并经 `build_report` 贯穿 `tools` 参数
  （check / repair / watch 三条路径全覆盖）；补捕获 `OSError`；所有分支统一
  返回 `complete` 布尔键。**能力不完整现在会真实阻断池层，而不是静默空跑。**
- 关联：`TASK-129` / `AC-195` `AC-196`

### FIX-R22-05 测试文件 7 个同名重复方法（major）

6 份完全相同的 `api_post` 用例 + 2 份完全相同的 `token_audit` 用例。
Python 只保留最后一份 → 等于 6 个用例从未真正执行，掩盖真实回归。

- 修复：删除重复定义，保留唯一实现。
- 关联：`TASK-127` / `AC-190`

### FIX-R22-06 测试文件语法错误与 INSERT 列数错误（critical）

`try` 块结构被破坏导致整个测试文件无法解析；修正后仍有一处 INSERT
提供值数量与列数不符。

- 关联：`TASK-127` / `AC-190`

### FIX-R22-07 pnl_snapshot 日志行含畸形表达式（minor）

`f"state={() .get('production') if False else ...}"` 是被破坏的 f-string 表达式，
遗留恒假分支与非法属性访问写法。

- 修复：改写为 `(snapshot.get('production') or {}).get('state')`。
- 关联：`TASK-130` / `AC-199`

### FIX-R22-08 broadcast 修复门禁与计划 INV-5 不一致（minor）

失败用例并非实现错误，而是用例没有表达计划约束：**INV-5 规定广播只在正净收益
复核上触发**，而用例构造的复核统计缺少 `positive` 键。

- 修复：补齐 `positive` 统计，并新增两条用例锁定：
  - **INV-4**：复核层不健全 → 不得修广播；
  - **INV-5**：无正净收益 → 不得修广播。
- 关联：`TASK-127` / `AC-190` `AC-198`

## 3. 每链 SQLite 隔离（前提条件）

| 链 | chain_id | 文件 | 字节数（修复前后一致） |

编排器通过 `assert_chain_database(db, chain_id)` 强制该前提：只接受**已注册的本链文件**，
legacy `local_store.sqlite3` 与其它链的文件一律拒绝。编排器本身与链无关——
它只按 `NETWORK` / `CHAIN_ID` 过滤全部查询，因此换链只需换配置。

> 附带观察：主网库 `cow_execution_reviews` 中存在 4 条 `robinhood-testnet` 行与 1 条
> `bnb` 行（历史写入残留）。由于全部查询都带 `network=? AND chain_id=?` 过滤，
> **不会**污染主网结论；本轮不做清理，以免触碰生产库。
