# Robinhood 主网自愈编排器开发计划 v10.16（2026-11-18）

## 1. 目标与完成定义

交付一套链无关的自愈处理机制：当生产库前置依赖满足时自动解除限制，按代币、池、闭环、复核、广播的顺序处理问题；每条复核都有明确盈亏值；只有有效正利润经过 Rust 计算且所有安全门禁通过时才提交广播；之后持续统计已确认交易的盈亏。

本计划有两个不同的完成定义：

1. **实现完成**：代码、测试、迁移、双链一致性及各层修复闭环全部通过。
2. **生产稳定**：连续 3 个观测窗口，每个窗口至少 30 分钟，`blockers=[]`、`missingValue=0`、`positive>0`，并且广播记录和链上回执可对应。只有第二项通过后，才可以宣称主网稳定产生套利广播交易。

## 2. 固定架构边界

### 2.1 权威数据与方向

- Rust 全局内核对象必须存在；不存在即系统错误，不允许 Python 伪造或重建它。
- 管理对象持有权威业务数据。Rust 内核对象调用管理对象并维护运行期对象；Python 只消费 Rust 内核对象公开的信息用于 UI 展示、配置展示和操作转发。
- 初始化从对应链 SQLite 读取基础架构；运行期 WSS 更新只修改内存对象。计算与修复以该内存对象为事实源，结果经队列交给所属管理器并持久化到对应链 SQLite。
- SQLite 文件按链隔离，例如 Robinhood 主网 `local_store_4663.sqlite3`、测试网 `local_store_46630.sqlite3`。不得跨链共用可变状态或把一条链的地址、权限、观察数据写入另一条链。
- 深度和实时池状态由内存对象更新，禁止将 SQL 查询/写入当作深度计算路径。SQL 仅承担初始化、持久化、审计和只读核查。

### 2.2 最佳交易量与收益口径

- 最佳交易量与盈亏模拟统一由 Rust 内核计算。Python 不计算、不折算、不拼装 `initialAmountRaw`、容量或利润。
- 复核管理调用闭环管理；闭环管理调用全局 Rust 内核对象。`loopKey` 是内存对象身份，不是闭环业务结构体中的冗余字段。
- 单 tick 算法负责算出跨 tick 通用梯形的初始输入量，不是后续搜索的限制条件。单 tick 初始最佳量为 0 时不启动跨 tick；否则以该值作为既有加倍/减半算法的初始量，不递归调用，不使用固定 `1`。
- 跨 tick 版本使用闭环真实输入/输出做链下探测，不在本版本加入 tick 遍历模拟。深度容量只作为安全搜索上限，不得把单 tick 容量误作跨 tick 上限。
- 最佳量为 0 且 Rust 明确测得利润为 0，是完整测量；零大于负数。未执行/未测得才是缺值，严禁将未测量占位值归一成零。
- 闭环收益依赖 USDG 估值时，必须有对应代币的有效精度和可用兑换池状态。USDG 本身不能用 USDG/USDG 自价；对 USDG 借款锚需定义可审计的计价/成本路径，否则标记估值缺口而非伪造价格。

### 2.3 级联自愈

1. **代币层**：缺少名称/符号/精度等信息先由代币管理器补齐并复核。只有关键字段无法修复时才删除；删除要同步失效/清理闭环及其他依赖引用。非关键显示字段不能触发删除。
2. **池层**：池代币从核心、股票、测试三库及三库代币的直接兑换扩展库取得。通过准入约束保证池代币都有精度，池管理器不得另造“缺精度池代币”问题。池状态、池身份、方向、费率、深度或有效性异常由池管理器修复。
3. **闭环层**：使用管理库定义和 Rust 内存对象计算闭环、单 tick 起始量、跨 tick 容量及可执行性。缺边、脏身份或容量覆盖缺失应回到实际责任层修复。
4. **复核层**：复核管理调用闭环管理，以同一内存状态计算交易量和盈亏。每条复核必须输出具体带符号的利润数值、币种/精度、计算依据、测量状态和所选金额。零利润为值；缺值需定位 `runArbitrage`/预览数据链路并修复。
5. **广播层**：利润大于零且安全门禁通过后提交；广播失败交由广播管理器按错误类型修复并重试。不得因利润缺失、未知或零利润广播。外部副作用需要授权；生产限流、nonce、余额、gas、目标合约、链 ID、快照新鲜度均须满足。

准入控制由前置依赖判定器决定：依赖全部解决并且本层回归通过后自动解除对应限制，不得永久禁用生产库，也不得越过未解决门禁强制放开。修复失败只关闭当前层的执行路径，不删除候选数据；每次重试必须幂等并记录原因、影响和回滚点。

## 3. 算法方案与已知根因

### 3.1 当前版本算法

输入为闭环三跳和内存中的池状态。Rust 对每个 hop 按 pool token 顺序确定方向，折叠单 tick 物理容量得 `M_single` 作为通用最佳量梯形的初始输入；零值立即结束。跨 tick 使用此前的加倍/减半算法，根据合约真实输入/输出评估候选，并受 `Capacity_depth` 上限约束。跨 tick 不重新计算单 tick，不遍历 tick，也不递归。

每个候选必须在同一快照/区块标识下完成三跳实际输出、费用和利润核算。收益统一按借款 token 的原始精度存储，显示层可另作换算但不得改变 Rust 的判决。任何容量、估值或池状态不完整均 fail-closed，并指向正确的代币/池/闭环修复目标。

### 3.2 本轮定位到的核心代码缺陷

- `token_library_catalog` 在实际库中是 view。闭环管理器曾只认 `sqlite_master.type='table'`，导致精度与 USDG 身份均读取为空，所有估值缺失。修复应接受 table/view 并增加真实 schema 形态回归测试。
- USDG 借款锚不能通过自兑换对自身估值。应在业务语义上显式处理稳定币计价单位，而非依赖不存在的 USDG/USDG 池。
- 旧 healer 对缺失 Manager hop 表直接查询导致 SQLite 错误；当 Manager 与 legacy 复核行共存时需按路线归一身份去重，并优先保留包含有效利润值的记录。
- Python 中不得复建容量或交易量。Rust 是金额计算的唯一权威，Python 只转发必要的环境信息和消费结果。

## 4. 阶段路线与退出门禁

### 阶段 A：实现与回归（立即）

修复 Rust 读取 table/view、USDG 锚点定价、金额零值语义、双算法种子衔接和审计合并；补齐单元、属性/边界和链无关测试。退出：Rust/Python/tools 测试全绿；架构守卫确认 Python 没有最佳量计算；无 SQL 深度路径。

### 阶段 B：测试网闭环验证

用独立测试网 SQLite 按完整级联执行代币→池→闭环→复核→广播准备；验证多轮 WSS 更新只更改内存对象、处理队列持久化结果、每条复核都有利润值（含有效零），且零或负利润不广播。修正后的测试网闭环阻塞为：AMZN 在 stocks 主库已 admitted，extension candidate-only 是合法重叠；候选边仅有一个不同 token，M4 无法生成 Y-Z 方向。core4 只有 1 个 active pool，36 个 raw pool 中 35 个未满足 scope 准入；本轮只读 RPC 深度刷新因 endpoint DNS 解析失败。先修复并验证 RPC/WSS，再由池管理器读取当前状态并 dry-run 分类；按正式候选关系形成第二个有效 token 后逐层重建。不得手工写 admission、放宽池门槛或回灌历史 loops/depth。退出：同一功能代码通过测试网，Manager loopCount>0 且版本/checksum 闭合。

### 阶段 C：主网修复与准入解除

先只读核查 SQLite schema、迁移、行数、校验和、闭环与估值覆盖；再执行明确列出的 manager migration 和闭环物化。不能从历史备份恢复深度或覆盖错误。逐层按依赖状态自动放行，只有对应前置项解决才解除限制。重新运行复核，按类别统计缺值、0、负、正值；逐个修复缺失证据原因。退出：所有 active review 都有可审计盈亏值，阻塞数为 0，且各自使用 Rust 计算的金额。

### 阶段 D：受控广播与错误自愈

先 dry-run 确认广播 payload、nonce、gas、账户、路由和阈值，再在已授权窗口内提交。仅正利润进入队列。广播失败按错误码交给广播管理器修复；记录每次错误、重试、交易哈希和回执。退出：失败可分类、重试幂等、没有绕过门禁。

### 阶段 E：稳定运行与统计

连续观察至少 3×30 分钟窗口；每窗记录候选数、有效闭环数、review 完成/缺值/0/负/正、广播成功/失败、已确认盈亏、RPC/WSS 新鲜度。只有 `blockers=[]`、`missingValue=0` 且正利润样本 `positive>0` 才满足稳定判据。发生回退、状态陈旧或重复广播时自动关闭对应广播准入并保留修复通道。

## 5. 近期交付与依赖

| 顺序 | 交付 | 依赖/退出 |
|---|---|---|
| 1 | table/view schema 回归及 USDG 计价覆盖 | 确认管理库 view 契约；无 USDG 自价 |
| 2 | Rust 单 tick 初始量 + 原加倍/减半跨 tick 算法 | Rust 内存对象与深度容量有效 |

| 4 | 测试网 candidate-only 审核、有效池刷新和 Manager 闭环恢复 | 代币管理器正式准入、池管理器当前状态 dry-run/apply、loopCount>0 |

依赖顺序不得倒置。生产库限制不能长期冻结，但只能由依赖状态自动解除；处理链必须继续运行诊断和修复，不以“停用生产库”作为终态。

## 6. 测试、变更与数据保护

- 每次 Rust 改动运行 `cargo test --offline --lib`；Manager 改动运行对应 crate 测试；Python 改动运行定向测试后再跑 `flashloan/app_runtime/tests/unit`。
- DB schema 变更只通过有编号迁移执行；迁移前验证链、绝对路径、当前版本、备份可读和预期列差异。每条链分别迁移、分别回读。
- 重物化前先只读检查基线，保存证据。闭环数据由 Manager 从当前权威库构建；严禁回填历史深度。
- 生产写入和真实交易都需授权窗口、操作清单、幂等键、日志和回滚方案；代码测试通过不等于生产可广播。
- 报告区分静态事实、当前数据库事实、链上/运行时观测和分析推断。证据过期或缺字段按未知处理。
