## 三、两个口径决策（写在这里，避免后轮误判）

### 3.1 为什么 `--rehearse` 必须在影子副本上跑

主网库是 **WAL 模式**且 **8.6 GB**。**以读写方式打开**会在关闭时 checkpoint、**必然改动主文件**
> ⇒ 校验值**不可能**保持一致。因此：

- 主库**始终只读打开**（`mode=ro` **+** `PRAGMA query_only = ON`，双保险）；
- `--rehearse` 一律在**临时目录的影子副本**上进行；
- 影子库复制 `manager_v4_closed_loops`（**168** 行）+ `manager_v4_closed_loop_hops`（**504** 行），
  按 02 §4.1 的 DDL 补上 **5** 个方向列并填**合成方向值** ⇒ 回滚**非空洞**（否则测的是空转）。

### 3.2 授权拒绝**复用**既有错误码

`authority_denied` 是**概念名**；实现复用 `ErrorCode::TokenAuthorityWriteDenied`。

## 四、已知遗留（如实记录，不隐瞒）

| 项 | 说明 |
|---|---|
| 现象 | 主库同目录出现 `local_store_4663.sqlite3-wal`（**0** 字节）与 `-shm`（**32768** 字节） |
| 成因 | SQLite **以只读方式打开** WAL 库时会**自建**这两个运行时文件（**任何**进程打开库都会生成） |
| 数据 | **不携带任何库数据**；wal 保持 **0** 字节 |
| 判据 | 因此把「不得写库」收紧为「**不得产生 WAL 内容**」，并把同目录文件变化**如实写进报告**（`siblingNote`） |
| 处置 | **不手工删除**（`Remove-Item` 被策略拦截，且这两个文件由 SQLite 自身管理） |
| 进程核对（**v2.4 补记 · 订正上一版的错误结论**） | ⚠️ `manager-api`（PID 14648，2026-11-22 15:37 启动）**确实持有**该库；且**本仓库自身的 pytest 全量在运行期间会写入它**（库文件 mtime 在套件运行期反复推进，**size 始终不变** ⇒ 页内改写 / checkpoint）⇒ 主网库是**活的生产库，有并发写者** |
| 由此得出的判据改写 | `T-I-8` 改写为**可归因**形式：① **结构证明**（唯一连接 `mode=ro` + `PRAGMA query_only = ON`，全部写入落影子副本）；② **内容证明**（主库 `-wal` **始终 0 字节** ⇒ 未贡献任何 WAL 帧）；③ **归因证据**（`LibraryWatcher` **0.25 s** 采样主库与 `-wal` 的 size / mtime **变化时间线**）；④ **字节比对降级为观测**（不再作唯一判据，因活库有**并发写者**） |
| **演练脚本的三处报告缺陷（本轮实测发现 · 已修）** | ① `libraryWatch` **被算出却在写报告时被丢弃**（`main()` 的拷贝清单漏了它）—— 文档里写着的「归因证据」在证据文件里**并不存在**；② watcher **把采样时间戳算进比较** ⇒ 每次采样都被记成一次「变化」（实测 **316** 采样 → **317** 条噪声事件，报告膨胀到数百 KB）；③ `liveLibraryQuiescent` 把「只读打开 WAL 库时 SQLite **自建** `-wal`/`-shm`」**误判为外部写者** ⇒ 演练明明没写库却报 `false`；④ 顺带修掉 `render_markdown` 一处**多参数 `append`** 的既有缺陷（此前因 ① 而**从未被执行到**） |
