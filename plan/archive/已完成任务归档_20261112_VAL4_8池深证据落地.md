## 1. `VAL-4-8` — 池深证据落地（✅）

### 1.1 起点

`flashloan/tools/pool_manager/src/usdg_depth.rs` 与
`flashloan/tools/token_manager/src/usdg_evidence.rs` 在上一轮已经写好，
包括：估值报告解析、容量→USDG 换算、表定义、写入、token manager 读取、
以及 `pool-manager depth --usdg-valuation-report <PATH>` 的 CLI 接线。
但**从未运行过、从未验证过、从未归档**，清单里仍是 ⏳。

本轮不假设它正确，而是把它当作一次代码审查 + 实测任务。

### 1.2 缺陷 1：`u128` 深度溢出 → SQLite 静默存成 `REAL`

**机理**：`depth_usdg_raw` 的 Rust 类型是 `u128`，但建表语句写的是
`depth_usdg_raw INTEGER NOT NULL`（SQLite 有符号 64 位）。写入端用
`u128::to_string()` 传参，SQLite 的 INTEGER 亲和性在值超出 `i64::MAX`
时**无法完成整数转换**，于是把该行**存成 `REAL` 浮点**。

**实测复现**（Python `sqlite3`）：

```
INSERT INTO t (d) VALUES ('18446744073709551629')
  → 读回 1.8446744073709564e+19，typeof(d) = 'real'
```

而 token manager 的读取端是 `row.get::<_, i64>(1)?` —— 对一个 `REAL`
会直接**类型错误**，整批读取失败。

**可达性**：`depth_usdg_raw = capacity_raw × valuation / 10^decimals`。
18 位小数代币、1000 USDG 估值时，1e12 tokens 的容量即产生 `1e21` 的深度，
**远超 `i64::MAX`（9.22e18）**。这不是理论边界。

**修法**（`flashloan/tools/pool_manager/src/usdg_depth.rs`）：

1. 新增 `MAX_USDG_DEPTH_RAW: u128 = i64::MAX as u128`；
2. `capacity_to_usdg_depth()` 在返回前做范围校验，超出即返回 `None`
   —— **"不测量" ≠ "测量为 0"**，这条口径在本次修复中被完整保留；
3. `write_usdg_depth_observations()` 对每条观测二次校验地址与范围，
   不合格直接跳过；
4. `token_manager::read_measured_depths()` 增加占位符过滤（见缺陷 2）。

**回归**：
- `a_depth_that_cannot_fit_an_integer_stays_unmeasured`
- `a_depth_beyond_the_integer_range_is_not_written`
- `a_stored_depth_is_readable_as_an_integer`

### 1.3 缺陷 2：零地址占位符生成伪深度行

**机理**：`manager_dex_candidate_pools` 实测 **114 行中有 50 行的 `token0`
是零地址** `0x000...000`。它是"未知池边"的占位符，不是代币。
但 `chain_tokens` 表里**零地址确实存在**（6353 行中的一行）且
`token_decimals = 18`。

两个条件叠加的后果：一旦零地址进入估值报告，`pool-manager` 就会为它写出一行
**指向不存在代币**的深度证据；`token_manager` 读取后
`extension_depth_usdg_raw["0x000...0"]` 成为非空值，
经济门禁会把它当作一个**真实中间跳**参与判定。

**修法**：新增 `is_depth_bearing_token()`，语义为"空串与原生零地址都不是代币"，
在**写入端**（`pool_manager::usdg_depth`）与**读取端**
（`token_manager::usdg_evidence`）**双重拒绝**。
零地址常量 `ZERO_TOKEN_ADDRESS` 两端各自定义、语义一致。

**回归**：
- `the_placeholder_address_carries_no_depth_evidence`
- `a_placeholder_address_never_becomes_a_row`
- `the_placeholder_address_is_not_a_measured_hop`
- `the_placeholder_address_is_rejected`

### 1.4 缺陷 3：`depth --apply` 不自建 schema（顺序依赖的失败）

**机理**：`write_depth_snapshot()` 写入 `capacity_token0_raw` /
`capacity_token1_raw` / `capacity_binding_raw` 等 **7 个列**，
但 `refresh_depth()` **从不调用** `ensure_depth_schema()`。
生产库 `v4_exchange_pool_liquidity_snapshots` 实测**没有**这些列，
因此 `depth --apply` 直接失败：

```
pool-manager error: no such column: capacity_token0_raw
```

**为何此前没暴露**：`scripts/mainnet_arbitrage_healer.py` 的修复顺序里
先跑 `ensure-depth-schema` 再跑 `depth`，所以**守护器路径被掩盖**；
但 `depth` 在 CLI usage 里是独立子命令，单独调用即失败。
这类"顺序依赖的失败"正是 silent no-op 的温床：换一个调用方就炸。

**修法**：

1. 把列检查/添加逻辑抽成连接级 `add_depth_capacity_columns(&Connection)`
   —— 幂等（先查 `pragma_table_info` 再 `ALTER TABLE ADD COLUMN`）；
2. `refresh_depth()` 在 `--apply` 时**先自建 schema 再测量**；
3. `ensure-depth-schema` 子命令复用同一函数，行为不变；
4. 新增返回字段 `depthColumnsAdded`，使自愈行为**可观测**（而不是静默）。

**回归**：`val4_8_the_depth_refresh_adds_the_missing_capacity_columns`
（含幂等二次调用断言 + 9 列存在性断言）。

### 1.5 口径说明：为什么落独立证据表

`check_list` 中"决定是否落入 `manager` 代币元数据层"一项，本轮定案：
**落独立证据表 `token_usdg_depth_measurements`，不落 `manager` 代币元数据层**。

理由：该表回答的是"**某个池能承载多少 USDG**"，与代币元数据
（symbol / decimals / source）不同源、不同生命周期、不同刷新节奏。
估值刷新不应触碰池观测，池刷新也不应凭空造出估值。
独立存储让两个测量在"估值 × 容量"这一处显式相遇，
且 `token_manager` 可以**只读**打开它。

## 7. 教训

1. **"代码写了"不等于"任务完成"**。`VAL-4-8` 的代码规模不小、结构也清晰，
   但它从未被运行过；一旦真正跑起来，三个缺陷立刻全部暴露。
   **清单里的 ⏳ 与代码里的 ✅ 必须靠实测对齐，而不是靠代码审查对齐。**
2. **静默失真比崩溃危险**。缺陷 1 不会让程序崩溃，它只会让一个深度值变成
   `1.8446744073709564e+19` 这样的浮点数，安静地写进证据表；
   缺陷 2 不会让程序报错，它只会让一个不存在的代币获得一条深度记录。
   这两个都属于"看起来跑成功了"的那一类。
3. **顺序依赖的失败会被上游掩盖**。缺陷 3 只在绕过守护器直接调用 CLI 时出现，
   因为守护器恰好按正确顺序调用。**一个工具的正确用法不应该靠另一个工具
   来保证**，因此 `depth --apply` 自己补齐了 schema，并把补齐行为暴露成
   `depthColumnsAdded` 字段。
