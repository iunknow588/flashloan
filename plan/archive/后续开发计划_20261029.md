# Robinhood V4 后续开发计划（2026-10-29）

> 本计划依据 `plan/待完成任务清单_20261029.md` 制定，是当前轮次的执行入口。历史完成记录仍以 `plan/back/` 为准；本计划不改变 SQLite、`latest.json`、runtime evidence 或生产进程状态。

## 1. 当前目标

围绕 Robinhood V4 测试网 46630，完成以下闭环：

```text
scanner-main
  -> review-supervisor / review-worker
  -> review cycle 持久化与 lease 回收
  -> executionQueue
  -> broadcast-supervisor / broadcast-worker
  -> broadcast result / receipt evidence
  -> success、failed 或 isolation 落库
```

最终验收目标为：

1. 代码层面具备独立 supervisor、bounded worker、cycle lease、CAS 回收和结构化错误处置能力。
2. `executionQueue` 是唯一广播入口，review worker 不得直接广播或重发 raw transaction。
3. 46630 在用户明确确认维护窗口后，能够持续产生可复核的 scan、review、broadcast 和 success/failed evidence。
4. 2/4/8 worker 观测能够证明无重复领取、无重复广播、无单路阻塞、无 supervisor 级联退出。
5. readiness 仍保持 fail-closed；在 chain-test evidence 不完整时，不启动真实广播。

## 3. 优先级与执行顺序

### 阶段 A：调度主线收敛（P0，先于生产恢复）

目标：把现有代码中的 supervisor、worker、状态机和持久化契约收敛为可运行、可审计的闭环。

#### A1. review-supervisor 生产接线

范围：`closed_loop_supervisor.py`、`closed_loop_consumer.py`、review queue、scanner 接入点。

工作项：

1. 明确 supervisor 的启动、停止、异常捕获和重启边界；单个 review worker 异常只能结束当前 cycle。
2. 使用统一 canonical key：`anchor|sorted(bridge_a,bridge_b)`，以 `generation + CAS` 防止重复 claim。
3. 补齐 bounded queue 满载时的 backpressure 记录，禁止 scanner 无限等待。
4. 将 `review_cycle_id`、`claimed_at`、`heartbeat_at`、`lease_until`、`finished_at`、`persisted_at` 作为完整生命周期写入 runtime state 或专用 cycle 表。
5. lease 过期只能回收对应 loop；回收必须生成审计记录，并可进入 `offchain_estimate` 或 isolation。

验收：

- 一个 loop 卡在 `preflight_running` 时，其他 loop 仍能 claim、完成和落库。
- worker 抛出异常、RPC timeout、结果回写失败时，supervisor 仍继续消费后续任务。
- stale lease 回收不会清理其他 loop，也不会造成第三次/第四次 claim。

#### A2. broadcast-supervisor 与 executionQueue 收敛

范围：Rust `worker_pool.rs`、`execution.rs`、`rust_closed_loop.py`、broadcast bridge。

工作项：

1. review 结果只能生成 `execution_queued`，广播只能由 broadcast-supervisor 消费 `executionQueue`。
2. 广播 worker 一次只领取一个 execution task，并完成一次 raw transaction 广播及只读确认查询。
3. 禁止 worker 自己生成新 nonce、调整 gas、重新签名或替换 raw transaction。
4. 广播失败必须完整透传 `rawError/errorKey/errorCode/errorName/disposition/revertData/revertSelector/revertReason/rpcMethod/broadcastChannel/submitted/txHash/receipt`。
5. 区分：
   - 无 `tx_hash`：`submission_rejected_before_acceptance`；
   - 有 `tx_hash` 且 receipt status=0：`execution_reverted_onchain`；
   - 结果未知：先 `VERIFY_CHAIN_STATE`，不能直接判定失败或重复提交。
6. persistence writer 的失败只影响当前结果落库，并产生 `persist_failed`，不得阻塞其他 loop。

验收：

- 所有广播路径都能证明经过 `executionQueue`。
- 广播错误在 Rust、worker payload、Python attempt、SQLite summary 和页面层字段一致。
- `requires_live_quoter` 只能作为报价证据门禁，不能覆盖真实广播失败原因。

#### A3. 真实 queue metrics 与运行状态

必须暴露并持久化以下指标：

```text

running
completed
failed
isolated
skipped

```

要求：

- 若 native status 没有真实来源，明确标记为 unavailable，不得用静态 0 伪造运行 evidence。
- metrics 至少按 review queue、execution queue 和观察窗口分别统计。
- status poll 不得改变 claim 或重复触发执行。

## 6.1 数据正确性补充项（M2-5）

状态：工程实现与闭环定向回归已完成；旧记录不重写，新记录按新契约落库。

目标状态契约：

5. 页面同时显示：

   - 每条自动执行/复核结论是否只基于数值可用的分支。

修复顺序：

2. Python：`_signed_native_profit_value()` 接受合约确认的 signed 零值和负值；`_native_worker_evidence()` 新增 `numericValuesUnavailable/quoteUnavailable` 状态与 conclusion 文案。

5. 定向测试覆盖：
   - `previewBestPoolDetailed unavailable` 且无限值 => `quote_unavailable`，不显示 signed 数额；
   - `arbitrageNotProfitable` => 输出负数或零；

## 6.2 链上复核失败原因缺失（M2-6）

状态：工程实现与闭环定向回归已完成；旧记录不重写，新记录按新契约落库。

现象：`/dex/submissions?chain_id=46630&market_id=dex-arbitrage-46630-uniswap-v4&protocols=uniswap_v4&dex_strategy=closed_loop_routes` 中，“链上复核失败”记录的错误原因为空，不符合“失败必须有可读原因”的设计要求。

根因链路：

1. native `previewBestPoolDetailed unavailable` 被 Rust 归为 `not_profitable_after_costs`，Python `_native_worker_evidence` 又把它归为 `route_unprofitable`，而不是 `review_failed/quote_unavailable`。
2. `reasonText` 优先读取 `evidence.blockers`；但 compact summary/存储链路未保证把 `blockers/errorStack/error/blocked_reasons` 一并保留，导致该列显示 `-`。
3. review failed 行没有强制“失败原因字段非空”的契约，也没有在页面提供最底层的 `unknown_reason` 回退文案。

目标状态契约：

1. 任何 review failed 记录都必须非空展示原因，至少包含：
   - `reviewFailureKind`：`preview_unavailable`、`quoter_revert`、`rpc_transport_error`、`contract_revert`、`unknown_review_failure`；
   - `reviewFailureReasons`：可读字符串列表；
   - `reviewFailureDetail`：原始错误、revertData、rpcMethod、attempt 等；
   - `errorKey/errorCode/disposition` 按错误矩阵补齐。
2. `previewBestPool unavailable`、`previewBestPoolDetailed unavailable`、`numericValuesUnavailable=true` 明确归为链上复核失败/报价不可用，不再归为 `confirmed_no_profit`。
3. 即使没有可解码 revert，也显示“链上复核未完成：previewBestPoolDetailed unavailable，无具体 revert 数据”，不能留空。
4. 页面失败原因列改为增强回退：
   - `evidence.blockers` / `blocked_reasons` / `reason` / `error` / `errorStack` 任一存在即合并展示；
   - 全部缺失时展示 `reviewFailureKind + evidence.status`，绝不输出 `-`。
5. storage/summary 链路保留 `blockers`、`errorStack`、`errorDetail`、`failureReason` 等字段。

修复顺序：

1. Rust：区分 `NoProfitableRoute` 与 preview unavailable，后者输出 `status=quote_unavailable/review_failed`。
2. Python：`_native_worker_evidence()` 增加 `reviewFailureKind/reviewFailureReasons/reviewFailureDetail`，并把 unavailable 状态改为 review failed。
3. attempt 构造：`blocked_reasons/error/errorDetail/errorKey/errorCode/failureReason` 必须非空；`auto_execute.reason` 同步改为 `review_failed:quote_unavailable`。
4. 后端 `_review_row_kind()` 显式识别 `quote_unavailable/review_failed`；`_row_failure_reason_text()` 加强字段来源。
5. 页面 JS：`reasonText()` 增加失败原因回退逻辑，并补充 `quote_unavailable`、`previewBestPool unavailable` 文案。
6. 定向测试：
   - preview unavailable 构造 attempt 时 `blockers/error/blocked_reasons/failureReason` 非空；
   - `_row_failure_reason_text()` 返回非空；
   - compact summary 保留错误字段；
   - review failed 端点返回的每条记录失败原因为非空；
   - 页面 fixture 验证只有 `blocked_reasons/error` 时也能显示。

验收：

- `review-failed` 页面不再出现空失败原因行。
- `previewBestPoolDetailed unavailable` 不再计入“路线不可盈利”或 `confirmed_no_profit`。
- 错误矩阵、审计、页面显示使用统一的 `errorKey/errorCode/errorName/disposition`。
- 修复只影响新记录与展示层回退；不手工修改历史 SQLite/evidence。

## 6.3 复核消费停顿与自恢复（M2-7）

状态：工程实现与闭环定向回归已完成；watchdog 已接入 scanner，受控重启后需采集新窗口证据。

现象：持续扫描两轮后再次卡顿，`/dex/submissions` 页面既没有成功复核记录，也没有复核失败记录，说明 review 消费链路没有持续产出，不符合“常驻 supervisor 持续消费”的设计要求。

允许的停顿与不允许的停顿：

- 没有新 route、没有可领取任务时，只允许显示 `queued=0/running=0/completed 与 failed 不增长`，不能误报故障。
- 一旦队列中有 `queued/running` 任务，或两轮扫描后仍无任何 completed/failed 新增，必须给出明确证据，不能停留在静默空窗。
- `running` 任务必须持续心跳；超过 lease 上限后应回收该 loop 并审计，不能让 worker 占用槽位但不再产出。

目标状态契约：

1. review-supervisor、resident worker、广播 worker 都必须有可观测的 `heartbeat_at/last_loop_at/queued/running/completed/failed/skipped/isolation`。
2. 每个扫描窗口结束时必须记录：
   - scanner 投递任务数；
   - review queue depth、claimed、running、completed、failed、skipped；
   - 每轮是否有 review attempt 落库；
   - supervisor 线程是否仍存活、最近心跳是否过期；
   - 最近一次异常与隔离记录。
3. 若 `review_stall_seconds`（建议默认 60s）内 supervisor 没有 `claimed/completed/failed` 变化，且 queue 非空或超过两轮无 stamped review，自动触发：
   - 写入 `review_stall` 审计；
   - 尝试创建新的 supervisor；
   - 无法恢复时保留只读状态并生成告警，绝不用静态 0 冒充运行中。
4. supervisor 的 `_loop` 即使单次异常也必须继续循环；线程退出必须能被 watchdog 发现并重新拉起。
5. queue 里从未消费的任务不能无限滞留：超龄 queued 任务应重新入队或标记 `review_stall`，不能长期显示 `queued` 却无人消费。
6. 页面和 status API 必须把“无新任务”和“有任务但无人消费”区分开；后者必须显示红色/告警状态并给出原因。

修复顺序：

1. `ReviewSupervisor` 增加 heartbeat、last_progress_at、stall 检测和线程存活看护。
2. `ReviewSupervisor.status()` 增加 `heartbeatAgeSeconds`、`lastProgressAt`、`queuedAgeSeconds`、`stallDetected`。
3. scanner 或 watchdog 在每轮扫描后检查 supervisor progress；发现停顿则记录 `review_stall` 并尝试重启 supervisor。
4. review queue 增加超龄 queued 任务审计；Rust native 模式同样透传真实的 `reviewQueue.queued/running/completed/failed`，不提供字段时明确标记不可用。
5. 页面/API 增加“复核消费停止”告警，而不是只显示空列表。
6. 定向测试覆盖：
   - worker 异常后 supervisor 继续消费；
   - supervisor 线程退出后 watchdog 能检测并拉起；
   - queue 有任务但 supervisor 未消费时记录 `review_stall`；
   - 无任务时 status 显示 idle 而非故障；
   - 连续多轮扫描后 completed/failed 有更新或明确输出“无新任务”。

验收：

- 持续扫描多轮后，页面/status 永远有“成功复核、失败复核或明确未触发/idle”之一，不存在无任何复核记录且无说明的空窗。
- 卡顿发生后存在 `review_stall` 审计、supervisor 重启或隔离记录；不能只是线程静默消失。
- 不再以“进程存在”等同于“持续消费”，status 必须同时展示 heartbeat 和消费进度。

## 6.4 复核后广播终态缺失的状态机修复（M2-8）
现象：持续扫描运行 30 分钟后，`v4_closed_loop_runtime_state` 中存在大量 `preflight_done`、`execution_pending/submitted`，但没有对应的广播成功或广播失败结果；`executionQueue.recent` 为空时闭环停留在“已复核但无终态”的悬挂状态。

目标状态契约：
1. 每个成功复核闭环最终必须出现 `execution_success`、`execution_failed` 或 `execution_failed(last_error=broadcast_result_missing)`，不得长期停留在 `execution_pending/submitted` 且无广播结果。
2. 复核与广播都允许失败，但不能没有终态；缺失结果超过阈值后由 watchdog/consumer 批量回收为失败终态并写入隔离审计。
3. `runtimeStateSummary` 暴露 `states/total/missingBroadcast/terminalExecution`，提交记录 API 暴露 `loopStateSummary`，页面显示“闭环终态”和“缺失广播终态”指标。
4. scanner watchdog 在每一轮扫描后调用 `recover_stuck_execution_loops()`，把超时未返回广播结果的执行中任务关闭为终态，防止再次空窗。
5. 主网广播开关仍保持关闭；只有 testnet 46630 连续 30 分钟同时满足 review terminal + broadcast terminal（success/failed）持续产出，并且用户明确授权后，才受控打开主网只读开发/测试开关；主网广播写入始终关闭。

验收：
- `/dex/submissions` 无“成功复核后无广播终态”的长期悬挂；要么存在广播成功/失败记录，要么状态机自动生成 `broadcast_result_missing` 失败终态。
- `loopStateSummary` 可观测且 `missingBroadcast` 随时间收敛；watchdog `stuckExecutionRecovered` 有真实计数。
- 主网 4663/BNB 保持只读，不写入广播；M10-1 门禁写入本计划，不实际打开写开关。

## 6.5 SQLite 状态机对象化重构（M2-9）

### 6.5.1 现状分析

当前 `v4_closed_loop_runtime_state` 是闭环状态的唯一事实源，状态常量仍是 Python 字符串，状态转移、租约回收和超时恢复是模块级函数；`ReviewSupervisor.status()` 只是只读快照。这不是“每个闭环对象自持状态 ENUM 与转换方法”的模型，容易造成状态机逻辑散落、跨 loop 误改和状态契约不收敛。

### 6.5.2 目标模型

1. 新增 `LoopState`（`enum.Enum`/`StrEnum`）定义全部合法状态：
   `preflight_running`、`preflight_done`、`preflight_failed`、`execution_pending`、`execution_submitted`、`execution_success`、`execution_failed`、`isolated` 等；同时区分 `terminal` 与 `non_terminal`。
2. 新增 `ClosedLoop` 领域对象，每个闭环一个实例，唯一标识为 `(network, chain_id, protocol, market_id, loop_key)`，字段包括 `router`、`generation`、`claimed_at/heartbeat_at/lease_until`、`last_error`、`last_transition_at` 等。
3. 新增 `ClosedLoopStateMachine` 类，将状态转换、CAS claim/complete、lease heartbeat、stale 回收、`broadcast_result_missing` 超时回收和 `runtime_state_summary` 收敛为对象方法：
   - `closed_loop.transition(to_state, **evidence)`：校验转换合法并写回 SQLite；
   - `closed_loop.claim(...)` / `closed_loop.heartbeat(...)` / `closed_loop.complete(...)`：只操作自己这一行；
   - `machine.recover_stuck_execution_loops(...)` / `machine.fail_stuck_execution_loops(...)`：批量回收无广播终态的执行中闭环；
   - `machine.runtime_state_summary(...)`：返回 `states/total/missingBroadcast/terminalExecution`。
4. 保留 SQLite 持久化、owner/CAS、lease/heartbeat 和进程重启恢复；纯内存对象只在进程内作为读写入口，不替代 SQLite。
5. 状态转换表集中管理，支持 `can_transition(from_state, to_state)` 与白名单测试；终态转换必须满足“成功复核后存在广播成功或广播失败终态”的业务约束。

### 6.5.3 可行重构步骤

1. 新增 `LoopState` ENUM、状态转换表和单元测试（只改内部常量，不建表、不改运行数据）。

3. 将 `closed_loop_state_machine.py`、`closed_loop_consumer.py`、`closed_loop_supervisor.py` 改为调用对象层；保留旧函数名作为兼容薄胶水。

## 6.6 Rust 执行组件与 Python 编排/状态组件职责收敛（M2-10）

### 6.6.1 目标术语

不再把 Rust 组件称为“Native 模式”或“native 工作模式”。当前系统默认架构是：

```text
Rust 执行组件：
  常驻 per-group worker、链上 preview/assertion、金额阶梯、
  executionQueue、广播与回执解析（flashloan_rs）
Python 编排/状态组件：
  supervisor/watchdog、SQLite 状态机、attempt/review 落库、
  页面/API、审计与错误处置
```

`rust_execution_component_enabled()` 是 Rust 执行组件可用性检查；`native_closed_loop_enabled()`、`rust_native_closed_loop` 等旧名称只保留为兼容别名/兼容字段，不作为产品层模式概念。

### 6.6.2 本轮改动

1. 新增 `rust_execution_component_enabled()`；旧 `native_closed_loop_enabled()` 改为兼容别名。
2. scanner/status 新增 `execution_backend` 与 `executionBackend`，取值 `rust` 或 `python`；保留旧 `engine`/`fallback_only` 字段供兼容。
3. `DEX_CLOSED_LOOP_SUPERVISOR_ENABLED` 默认改为 `1`，Rust 执行组件下 watchdog 默认常驻；显式 `0` 仍可用于测试禁用。
4. 导入与类型层面同步：`__all__`、维护 worker、测试夹具继续兼容旧函数名。
5. 本地正式运行 `.env` 保持显式 `DEX_CLOSED_LOOP_SUPERVISOR_ENABLED=true`，与默认值一致。

### 6.6.3 验收

- 无环境变量时，Rust 执行组件可用 => watchdog 默认启动，`closed_loop_supervisors.enabled=true`。
- status/API 返回 `executionBackend=rust/python`，旧字段不缺失。
- 显式 `DEX_CLOSED_LOOP_SUPERVISOR_ENABLED=0` 时 watchdog 可禁用，不影响 Rust 执行组件本身。
- 定向回归、API 契约和 Rust worker 测试全绿；不触发 schema/运行数据迁移。
