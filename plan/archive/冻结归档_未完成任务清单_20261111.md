  checksum sha256:dae667ab…`），`changedRows=0` 是**正确的幂等性**。

### 0.5 口径更正（务必遵守，持续有效）

1. **外部 fiat 价格源不参与任何套利执行判断；但 USDG 已取代 USD 的计价作用。**
   - **作废的是"外部 fiat 价格源"**（预言机 / 交易所指数价 / 人工报价 / 股票 USD 价）。
     原因不是"美元无价值"，而是**好多代币根本没有兑换渠道**，取不到任何 USD 价。
   - **USDG 在绝大多数情况下有兑换渠道**，因此 **USDG 取代 USD 承担计价单位**：
     经济学意义上 `1 USDG == 1 USD`（`R-11`）。凡是以 USD 表述的经济量
     （经济下限、承载能力、名义价值、Gas 成本折算）一律改用**同额 USDG** 表述，
     **不需要**任何外部价格源。
   - `estimated_tvl_usd` 仍仅作排序 tie-breaker 与人工观测，**不作任何门槛**；
     `usdg_amount_decimal` / `capacityBindingRaw` 才是可作判据的计价量。
2. **池深主判据** = 链上价格冲击容量，token 计价，价格冲击 ≤ **10 bps**，
   **零外部 fiat 价格源依赖**（深度本身是池子自身代币计量，不引入任何计价资产换算）。
3. **绑定侧容量**：`min(capacityToken0, capacityToken1)`（decimals 归一化）。
   单侧能吃下但另一侧吃不下 ⇒ 该池对套利路径**不可用**。
4. **USDG 按地址判定**：规范 `0x5fc5360d0400a0fd4f2af552add042d716f1d168`（decimals=6）；
   3 个同符号假币（`0x391f08bf…` / `0x69a17d84…` / `0xe9e75444…`）不参与定价或稳定币判定。
5. **不得依据 TVL 结论下架任何 token 对。**
6. **容量未测量 ≠ 故障**：`capacityGate.verdict=unknown` 默认不阻断；
   仅在 `DEX_V4_CAPACITY_GATE_REQUIRE_MEASURED=1` 下升级为阻断。
7. **快照过期 = 阻断**：`depthSnapshot.stale=true` ⇒ `code=pool_depth_snapshot_stale`。
8. **一个 blocker 不遮蔽另一个**：主因进 `code`，其余进 `secondaryBlockerCodes`。
9. **`best_amount_ladder_incomplete` fail-closed 是安全网，不得放宽。**
   归零靠数据修复，不靠放宽门禁。
10. **Rust `max_workers=16`**（worker pool clamp 到 1..32）；
    healer `--candidate-limit` 是**每轮修复请求提交预算**，与并发无关。
11. **部署二进制必须与源码一致**：`pool_manager_binary_out_of_sync` 是 blocker。

## 0.6 架构审查结论与新增最高优先项（2026-11-12）

> 证据：`logs/plan/runtime_evidence/reports/architecture_review_20261112.json`、
> `logs/plan/runtime_evidence/reports/probe_ladder_sizing_rootcause_20261112.json`

### 0.6.1 结论

**需要调整架构，但调整点与"链下计算绝对真理 + 低延迟直发"提分方案的假设不同。**

- 提分方案的前提（链上重算慢、瓶颈在延迟）在当前系统**部分成立**：
  `preview_arbitrage_best_amount_inner` 确实 `eth_call` 链上
  `OfficialV4FlashArb.previewArbitrageBestAmount`，其内部 `MAX_AMOUNT_SEARCH_STEPS=24`
  会真实执行 `runArbitrage` swap。
- 但**当前的首要阻塞不是延迟，而是仓位域缺陷**：
  复核阶梯恒定从 **1.0 token** 起步，且首次探测失败后**只向下搜索**。
- 实测容量（副本库 94 候选池，binding 侧人类单位）：
  `p50=0.000253` ⇒ 阶梯起点超出中位池容量约 **4000 倍**。
  ⇒ 盈利仓位**在数学上不可达**，"零可执行交易"由此产生，与网络延迟无关。
- 生产实测：近 6 小时 345 条复核中，真正展开的 59 条阶梯
  **首探金额全部为 1.0 token**，**首次结果全部 `NoProfitableRoute`**。

**版本 = 什么**：

```text
pool version = (liquidity_block_number, sqrt_price_x96)
```

前者说"**什么时候**观测到的"，后者说"**价格是多少**"。
两者同时变化，才意味着推荐所依赖的状态真的动了。

**明确**不**算版本的东西**（这是本项设计的核心）：

| 不算什么 | 为什么 |

| **TTL / 超时** | 按时间唤醒正是 ARCH-1 要取代的行为 |

（内部排序），因此同一批行换个顺序重读**不算**变化。

### 8.2 第二轮：生产路径核实与**致命缺陷修复**（2026-11-12 续）

上一轮记的「**ARCH-1 尚未在生产生效**」是**判断错误**，此处更正。

**核实结论**：`flashloan/app_runtime/run.py` 的 `initialize_runtime_background()`
调用 `runtime.scanner.start(chain_id=..., protocols=["uniswap_v4"])`；
`start()` 会拉起 `run_forever()` 线程（`_background_enabled` 默认 `1`，
`periodic_scan_enabled` 默认 `True`）。因此 **Python 扫描器就是生产扫描器**，
版本触发**确实在生产路径上**。

**但核实过程中发现一个致命缺陷——触发器此前永久沉默**：

```text
旧实现：from core.db.storage_chain_markets import load_v4_pool_liquidity
       ❌ 正确模块是 core.db.storage_v4_exchange
```

该 `ImportError` 被 `except Exception` 吞掉并返回空行集 ⇒
指纹恒为空 ⇒ 版本恒"未变化" ⇒ **触发器永远不触发**。
这与 `recent_swap_active` 全 NULL 是**同一类陷阱**：

### 0.6.5 D4 修法修订（2026-11-12：**经济可行性护栏**）

针对"粉尘池应否拉黑"的讨论，结论如下。

#### (1) 共识部分——采纳

- **"纳入雷达探测" != "执行交易"**：两者必须由**不同的判据**分开控制。
  D4 只解决"起点太高导致漏掉中大型池"，**不负责**把粉尘池变成可执行标的。
- **"用规模换微利"是负期望值**：一次失败的微利交易即可吃掉整天累积利润。**采纳为硬约束。**
- **必须先算经济账再花算力**：容量不足以覆盖 Gas 的路径，应当在进入 24 步链上搜索**之前**被否决。**采纳。**

#### (2) 冲突部分——**不采纳"引入实时外部 fiat 价格源"**

用户此前已明确锁定：

> 「ETH 价格源与股票价格都不影响套利执行，因为这些价格无法在套利环境中体现交易价值。」

且已锁定的深度口径为：**链上价格冲击容量，token 计价，epsilon=10 bps，
零外部 fiat 价格源依赖**。注意这与 `R-11`（USDG ≡ USD）不冲突：
USDG 取代的是 **USD 的计价作用**（经济量一律以同额 USDG 表述），
而深度判据**根本不需要计价换算**——它直接用池子自身代币计量，
所以既不需要外部 fiat 价格源，也不需要 USDG 换算。

本次复核进一步给出**实证支持**——生产 88 条闭环的借入代币构成：

| 借入代币 | 闭环数 | decimals | 是否稳定币 |
|---|---|---|---|
| ETH | 38 | 18 | 否（原生） |
| **SPY** | **30** | 18 | 否 |
| GOOGL | 6 | 18 | 否 |
| WETH | 4 | 18 | 否（封装原生） |
| SPCX / CRCL / MU | 8 | 18 | 否 |
| TZ | 2 | 18 | 是 |

=> **86/88（97.7%）的闭环借入的是股票代币（SPY/GOOGL/SPCX/CRCL/MU）**。
这类标的**不存在链上稳定可靠的外部 fiat 价格**（Robinhood 生态内无股票/ETH 兑换池，
"股票价格"只能来自链下报价源），而链下报价源**不得进入执行判据**。

因此 `cap_in_usd < MIN_PROFIT_THRESHOLD_USD` 这条规则**在本链上无法可靠求值**：
它要么引入被明令禁止的外部 fiat 价格源依赖，要么对 97.7% 的闭环退化为
"取不到价格 -> 全部丢弃"。

> **注意（`R-11`）**：这**不是**说"USD 计量不可用"。
> USDG 已取代 USD 的计价作用，**经济量（含经济下限、承载能力、名义价值、
> Gas 成本比较）一律可用同额 USDG 表述，无需任何外部价格源**。
> 真正不可得、也不需要的是**外部 fiat 价格源**（预言机 / 交易所指数价 /
> 链下报价），而不是 USD 这个单位本身。

#### (3) 替代方案——**等价的 token 计价经济下限**（D4-d）

不折算 USD，直接用**代币自身单位**表达"容量能否覆盖 Gas"：

```text
cap_path      = min(binding_capacity[hop] for hop in path)     # token 计价
required_amt  = gas_profit / unit_profit                       # 覆盖 Gas 所需仓位（token 计价）
若 cap_path < required_amt  ->  路径经济不可行，一票否决，不进 24 步搜索
start = clamp(cap_path * frac, required_amt, cap_path)
```

- `gas_profit`：以**借入代币**计价的 Gas 成本
  （ETH/WETH 借入 -> `gas_estimate_eth`；稳定币借入 -> 固定费；其余代币 -> 固定费口径）
- `unit_profit`：单位仓位的利润（token 计价），来自容量—利润曲线
- 该判据与现有 `capacity_covers_amount()` / `required_amount_for_profit()` **同源同构**，
  只是把阈值从"是否覆盖 Gas"提升为"**作为准入门槛**"，而不仅是事后校验。

#### (4) 修正后的"拉黑"边界——**只拉黑经济不可行，不拉黑"外部 fiat 价值低"**

| 分类 | 处置 | 理由 |
|---|---|---|
| 容量 < 经济下限（覆盖不了 Gas） | **拉黑出执行链路**（`dust_unprofitable`），保留在候选集供人工观测 | 无论币价如何都不可能盈利 |
| 容量 < 0.001 token 但 >= 经济下限 | **保留探测**（D4-a 的容量感知起点使其可被覆盖） | 可能存在高单位利润的稀薄套利 |
| 依据外部 fiat 价格"价值低"而拉黑 | **禁止** | 依赖不可得的外部 fiat 价格源（97.7% 闭环无可靠链上外部价格）；经济量已改用**同额 USDG** 表述（`R-11`），但"价值低"本身**不构成任何代币的下架依据**（`R-12`：唯一下架依据是股票代币无法与 USDG 兑换） |

> **重要限制（ARCH-2 已解除）**：D4-d 的 `unit_profit` 依赖**利润曲线**。
> ARCH-2（2026-11-12）已交付**链下 3 跳模拟器**，利润曲线**现在可以链下精确求值**，
> 不再需要链上 `eth_call` preview。
> **但**：模拟器**尚未接入生产链路**（见 §7.6 的 `ARCH-4-A` 前置 `ARCH-2b`），
> 因此 D4-d **当前仍以"最保守单位利润假设"启用**，宁可少放行、不可多放行；
> 待 ARCH-2b 在副本库上证明"链下预测 == 链上 preview"逐笔一致后再切换到精确口径。

#### (5) 与既有口径的一致性

- `minCandidateBindingCapacity = 0.001`（`flashloan/config/depth_policy.json`）
  是**当前唯一已存在的粉尘门槛**，但它按"系统历史尝试过的最小仓位"标定，
  **不是**经济门槛。D4-d 落地后应取代它成为**执行准入**门槛，
  而 `0.001` 退化为**分带标签**（观测用途）。
- 该变更**不触碰**"不得依据 TVL 下架 token 对"约束——
  D4-e 拉黑的是**池子**，依据是**容量与 Gas**，不是 TVL。

## 0.8 ARCH-2b-2 闪电贷手续费口径归因与修正（**2026-11-13，已完成；后续口径修正见 0.9**）

### 0.8.1 根因：链下硬编码 5 bps，链上实为 0 bps

这是一处**与池状态无关的系统性偏差**，此前被误记在"陈旧本地状态"名下。

生产路由走 `OfficialV4FlashArb` 语义，**直接向 Uniswap V4 PoolManager 借币**：
`runArbitrageBest(tokenZ, keysets, directionsets, amountIn, 1)`，末位 `1` 是
`minProfit = 1 wei` 的**利润下限**，**不是手续费**。合约结算为
`required = amountIn + minProfit`，V4 PoolManager **不收闪电贷费**。

副本库中 12 条独立对比的链上 revert（选择器 `0x16301234` =
`ArbitrageNotProfitable(received, required)`）逐条解码后**完全一致**：

| 字段 | 链上值 | 链下假设 | 差额 |
|---|---|---|---|
| `requiredRepay` | `1000000000000000001` | `1000500000000000000` | `500000000000000` |
| 有效手续费 | **0 bps** | **5 bps** | **恰好 5 bps** |

17 条 `offline_v4_sqlite_route_snapshot` 的链上收益与链下算本之差，
**逐条都恰好等于** `ceil(本金 × 5 / 10000)`，无一例外。

### 0.8.2 修正（功能性任务仍在 Rust 管理器内）

| 职责 | 归属管理器 |
|---|---|
| 从链上结算推导有效手续费 | `review_manager::effective_flash_fee_bps` |
| 判定假设费与链上费是否一致 | `review_manager::chain_fee_matches` |
| 手续费假设偏差的独立归因 | `ParityAttribution::FlashFeeAssumption` |
| 遗留 5 bps 残差识别（历史证据） | `review_manager::legacy_fee_residual` |
| 默认值（链上事实） | `review_manager::DEFAULT_FLASH_FEE_BPS = 0` |
| Python | 仅 `RuntimeCore.execute_command("review_parity_replay")` 转发，**零数学** |

**设计要点**：手续费**不再由常量决定**，而由链上自己的结算推导。
链上手续费是 owner 可变的适配器参数
（`setFlashSourceAdapter(kind, enabled, source, feeBps, metadataHash)`），
推导优先于假设；`CHAIN_MIN_PROFIT_RAW = 1` 被单独识别为**利润下限**，
**不得**当作手续费。

### 0.8.3 Python 侧：区分"链上手续费"与"链下预检余量"

此前二者被混为一谈（同一个 `5.0` 常量）。现已拆分：

| 常量 | 含义 | 值 | 允许进入 |
|---|---|---|---|
| `CHAIN_FLASH_LOAN_FEE_BPS` | **链上真实手续费**（链上事实） | `0.0` | 链下算本净收益、链上要求偿还金额 |
| `DEFAULT_FLASH_LOAN_FEE_BPS` | **链下预检余量**（gas / 滑点 / 状态漂移门槛） | `5.0` | 提交门槛、预检余量字段 |

预检余量**不得**进入 `repayAmountRaw`：此前 `repayAmountRaw` 被 5 bps
虚增 0.05%，是**真实生产缺陷**（链上只需偿还本金）。
证据中显式携带的 `flashLoanFeeBps` 仍是**权威值**（它代表当时配置的适配器）。

## 0.9 ARCH-2b-3 复现时间池状态对齐（**2026-11-13，已完成**）

### 0.9.1 根因：复盘口径错误，不是算术错误

原实现拿**当前本地快照**去比较一层发事**之前**的记录。这是比较两个不同的市场，
结果必然偏差，且偏差不能归因于算术。正确口径只有一个：
**要用记录那一笔当时看到的池状态，才能复现那一笔的结论**。

### 0.9.2 关键发现：记录本身就携带了它当时的池状态

`cow_execution_reviews.payload_json` → `quote.candidate_pools[]` 里每个池都带有
`sqrtPriceX96` / `liquidityIndex` / `fee` / `tickSpacing` / `token0` / `token1` / `liquidityReadAt`，
且与 `poolPathKey` 的顺序逐个对应。**复现准确的输入就在记录里**。

池深度单位逐条取证（副本库 179 条记录，按常数与离散度比对）：
按 `liquidityIndex × 1e18` 还原正确的条数是 **179 / 179**，按原值的是 **0 / 179**。
因此 `LIQUIDITY_INDEX_SCALE = 1e18` 是唯一正确口径。

> JSON 写出器对大指数使用科学计数法（如 `9.901032566577074e+17`），
> 解析必须同时支持普通写法与科学计数法，否则会静默丢掉池状态。

> **用户裁定（2026-11-12）**：资金池都可以用 USDG 衡量。

#### 7.7.3 VAL-4-8 落地明细（2026-11-12）

**背景**：`VAL-4-8` 的代码（`flashloan/tools/pool_manager/src/usdg_depth.rs`）在上一轮已经写入，但**从未被验证、从未被归档**，清单里仍标 ⏳。本轮把它当作一次代码审查 + 实测任务处理，结果发现 **3 个真实缺陷**——其中 2 个会让这套证据**静默失真**。

##### 缺陷 1：`u128` 深度溢出 → SQLite 存成 `REAL`（静默精度丢失 + 读取端报错）

- **机理**：`depth_usdg_raw` 是 `u128`，但表的列声明是 `depth_usdg_raw INTEGER`（SQLite 有符号 64 位）。写入端用 `u128::to_string()` 传参，SQLite 的 INTEGER 亲和性在值超出 `i64::MAX` 时**无法转换**，于是把该行**存成 `REAL` 浮点**。
- **实测**（Python `sqlite3` 复现）：`INSERT ... VALUES ('18446744073709551629')` → 读回 `1.8446744073709564e+19`，`typeof` = `'real'`。而 token manager 的读取端是 `row.get::<_, i64>(1)?` —— 对一个 REAL 会直接**类型错误**，整批读取失败。
- **可达性**：`depth_usdg_raw = capacity_raw × valuation / 10^decimals`。18 位小数代币 × 1000 USDG 估值时，1e12 tokens 的容量即产生 `1e21` 的深度，**远超 `i64::MAX`（9.22e18）**。
- **修法**：① `capacity_to_usdg_depth()` 增加 `MAX_USDG_DEPTH_RAW = i64::MAX` 上限，超出即返回 `None`（**不测量 ≠ 测量为 0**）；② 写入端二次校验地址与范围，不合格直接跳过；③ `token_manager::read_measured_depths` 增加占位符过滤。
- **回归**：`a_depth_that_cannot_fit_an_integer_stays_unmeasured`、`a_depth_beyond_the_integer_range_is_not_written`、`a_stored_depth_is_readable_as_an_integer`。

##### 缺陷 2：零地址占位符生成伪深度行

- **机理**：`manager_dex_candidate_pools` 里 **114 行中有 50 行的 `token0` 是零地址**（`0x000...000`），它是"未知池边"的占位符而不是一个代币。但 `chain_tokens` 表里**零地址确实存在且 `token_decimals=18`**（6353 行中的一行），于是它同时具备"能查到 decimals"和"能拿到估值"两个条件。
- **后果**：一旦零地址进入估值报告，`pool-manager` 就会为它写出一行**指向不存在代币**的深度证据；`token_manager` 读取后，`extension_depth_usdg_raw["0x000...0"]` 会成为一个非空值，门禁把它当作一个**真实中间跳**。
- **修法**：新增 `is_depth_bearing_token()`（双端共用语义：空串与零地址都不是代币），在**写入端、读取端双重拒绝**。
- **回归**：`the_placeholder_address_carries_no_depth_evidence`、`a_placeholder_address_never_becomes_a_row`、`the_placeholder_address_is_not_a_measured_hop`、`the_placeholder_address_is_rejected`。

##### 缺陷 3：`depth --apply` 不自建 schema（顺序依赖的失败）

- **机理**：`write_depth_snapshot()` 写入 `capacity_token0_raw` / `capacity_token1_raw` / `capacity_binding_raw` 等 7 个列，但 `refresh_depth()` **从不调用** `ensure_depth_schema()`。生产库 `v4_exchange_pool_liquidity_snapshots` 实测**没有**这些列，因此 `depth --apply` 直接失败：`pool-manager error: no such column: capacity_token0_raw`。
- **为何之前没暴露**：`scripts/mainnet_arbitrage_healer.py` 的修复顺序里先跑 `ensure-depth-schema` 再跑 `depth`，所以**守护器路径被掩盖**；但 `depth` 在 CLI usage 里是独立子命令，单独调用即失败。
- **修法**：把列检查/添加逻辑抽成连接级 `add_depth_capacity_columns()`（幂等），`refresh_depth()` 在 `--apply` 时**先自建 schema 再测量**；`ensure-depth-schema` 子命令复用同一函数。新增返回字段 `depthColumnsAdded` 供观测。

##### 缺陷 3（本轮新发现）：门禁只在内存里移除成员关系，**库里的旧行仍停在 `admitted`**

##### 缺陷 1（本轮新发现）：**基础资产估值报告无法落库**，导致 42 个池被误判"未测量"

`read_valuation_report()` 原本只接受两种包络：带 `report` 键的完整批次报告，或本身就是完整批次报告。
但**基础资产探针**（ETH / WETH / USDC）产出的是**只含 `tokens` 的偏包络**
（顶层是 `source` / `observedAt` / `sources`，没有 `report`），落库时报 `missing field 'source'`。

后果很严重：基础资产估值**从未进入持久化估值库**，于是

* 持久化库里 **194 行**（159 有值 + 35 `no_route`），**没有 ETH / WETH / USDC**；
* 分带工具从库里读估值时，**ETH 侧找不到估值**；

因此"探针报告"与"库中读回的证据"在门禁眼里**无法区分**，也就不会做出不同裁决。

##### 缺陷 1（本轮新发现，**严重**）：**一次探针故障会摧毁全部已知估值**

编排器首次端到端跑时，探针返回 **194 个 `api_unavailable`**（Trading API 在本机
网络不可达），而落库**照单全收**，把库里已有的 **197 行**（162 `route_found`
+ 35 `no_route`）**全部覆盖成 194 行未知**。

后果：估值库被清空 ⇒ 门禁读不到任何估值 ⇒ **194 只股票代币全部变成 `pending`** ⇒
**整个股票池的成员关系依据被一次网络故障抹掉**。

**修法**：`land_valuation_report()` 在写入前读取该网络/链已存的所有 verdict，
遇到**未知** verdict 且该代币已有**已知** verdict（`route_found` / `no_route`）时
**拒绝这次写入**并计入 `protected`。理由是语义上的：**未知不是观察**——
`api_unavailable` 只说明"探针没问出结果"，不说明"该代币有没有路径"。
用一个未知覆盖一个已知，等于**把一次传输故障变成一次经济事实的变化**。
但当该代币**本来就没有任何记录**时，未知**仍然写入**——因为
"我们试了，问不出来"和"我们从没量过"是不同陈述。

**实测（副本库）**：同一份全未知探针再落一次 ⇒
`written=0`、`protected=194`；库中仍是 `route_found=162` + `no_route=35`；
门禁仍给出 `excludedStock=69` / `pending=0`；成员关系**零变化**。

##### 缺陷 2（本轮新发现）：批量估值**全串行**，端点不可达时要跑数小时

`value_tokens_to_usdg_batch()` 原先**完全串行**：194 个代币 ×
（20 秒超时 × 1 + 2 次重试）⇒ 端点不可达时单次全量探针需**数小时**。
第一次跑编排器时实测 **15 分钟未完成**。

**修法**：

1. **并发化**：`value_tokens_to_usdg_batch_with_concurrency()`，默认 **8** 个工作线程，
   按索引回收结果 ⇒ **输出顺序与调用方顺序严格一致**（并发不改变报告的可比性）。
2. **熔断**：连续 **3** 次**传输类**失败即打开熔断，后续代币不再发请求，
   记为 `api_unavailable` + `failure_kind=Transport`，
   **绝不记为 `no_route`**（"没问" ≠ "问了没有"）。

**实测**：194 只全量探针 **107 秒**完成（此前不可达场景需数小时）；
30 只子集 **64 秒**。熔断打开后，被跳过的代币带明确
`"the valuation endpoint was unreachable; the probe stopped asking"` 说明。

##### 缺陷 3（本轮新发现）：编排器**读不到 API Key**，探针静默全空

Trading API 的 key 由环境变量提供，而 key 实际存放在
`flashloan/app_runtime/.env`。编排器**不加载**该文件 ⇒ 探针对**每一个**代币
返回 `api_unavailable`（`failure_kind=MissingApiKey`），而**看起来**只是一个
普通的全未知结果。

**修法**：编排器新增 `_load_env_file()` 桥接（只读 `KEY=VALUE`，
跳过注释与空行，支持 `export ` 前缀，**只填空缺、不覆盖已有环境变量**）。
实测确认：显式环境变量**优先于**文件。

##### `VAL-4-11` 口径文档（`docs/主网自愈编排器/05_数据口径与统计.md` §10）

新增 **§10「经济门禁与 `capacityGate` 的边界」**，写明：

* 两者**作用对象不同**：门禁管**代币库成员关系**，`capacityGate` 管**单池可成交容量**；
* **关键区分**：USDG 取代的是**计价作用**，**不是深度信号**；
* `usdgPegPolicy` 的**完整** `allowedUses`（6 条）/ `forbiddenUses`（6 条）——
  禁止项包含 `depth_admission` / `capacity_admission` / 核心 / 测试 / 扩展池成员关系 /
  广播金额定量；
* **三类代币的 USDG 约束互不相同**：**股票代币 = 硬约束**（不能与 USDG 兑换 ⇒
  不得进股票代币表 ⇒ 也不会进资金池代币）；**核心代币 / 测试代币 = 无约束**；
  **扩展代币 = 传递性约束**（自身不需要估值，池子要满足深度，USDG 关系
  通过股票代币或核心代币间接建立）；
* **失败语义**：只有 `no_route` 是真负；未知**绝不覆盖已知**；
  **未测量 ≠ 测量为 0**。
