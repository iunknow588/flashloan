### 3.3 **诚实边界：`consumers_need_rebuild=1` 没有被清，且不应该被手工清**

它在 `closed_loop_manager` 里的语义是 **"下游消费者尚未按新上游重建"**。
当前下游（复核库）确实还没重建 —— **所以它是真话**。

正确的清除路径是
`closed_loop_manager/src/lib.rs:762-763`：
`if checksum_changed { replace_closed_loop_rows(...) } else if previous.consumers_need_rebuild { clear_consumers_need_rebuild(...) }`
—— 即 **checksum 不再变 + 消费者已重建** 时**自然**清除。

> **强行手工清掉它，只会在复核库仍旧的前提下让 `runtime_core` 变绿 —— 那是掩盖问题，不是修复问题。**
> 因此正确顺序是：**发布 → 物化 → 自然清除**。

## 6. 架构结论（写进开发计划 §2.2）

| # | 含义 | 对设计的约束 |
|---|---|---|
| **A-1** | **调度、计算、记录、发布是四段不同的链路**。前三段都存在且合规，**第四段不存在** | 以后新增任何"复核产出"能力时，**必须同时回答"它发布到哪里"**。**只写 live 表不构成"复核已产出"** |
| **A-2** | **Review Manager 的写入口是全量替换语义**（`replace_review_rows` 先 `DELETE` 再全量 `INSERT`） | **部分提交是数据损坏**。发布必须**聚合到覆盖全集** |
| **A-3** | **`consumers_need_rebuild` 是下游未重建的派生标志**，不是独立缺陷 | 顺序必须是 **发布 → 物化 → 自然清除**。**手工清标志 = 掩盖问题** |

**A-1 的一般化表述**（写入开发计划，作为后续所有工作的判定标准）：

> **一个"产出"只有在其被 Manager 发布并可被 Manager 接口读取时才算产出。**
> 写进中间表、留在内存、或只存在于某个 worker 的局部变量里，**都不算**。
