## 一、裁决摘要（TL;DR）

**可行，建议采纳；但必须对原始设想做三处修正**，否则会踩到「重复广播」这个安全坑。

| # | 议题 | 裁决 | 一句话理由 |
|---|---|---|---|
| `D-1` | 整体可行性 | **可行**（采纳） | 复核记录 **只追加 + 无实时查询**，套利记录 **单调增长 + 需跨月聚合** —— 两者恰好互补，各用各的最优形态 |
| `D-2` | 复核记录是否留在主库 | **留**（只留当前代） | 读路径有 **4 个消费者**且被门禁链高频读取；全搬走 = 改 4 处读路径 = **越界** |
| `D-3` | 复核 JSONL 的角色 | **审计流，不是权威源** | JSONL **可丢、不可查、不可回滚**；任何准入判定都不许读它 |
| `D-4` | 套利记录是否全搬走 | **终结后归档，主库留瘦身行**（否决「全搬走 + 留索引」） | 索引落后 ⇒ 幂等失效 ⇒ **重复广播** = 安全事故 |
| `D-5` | 月归属判据 | 记录 `created_at` 的 **UTC 月**（发起月），**不是**当前时间 | 跨月边界归档错月 = 财务账错月 |
| `D-6` | 精度口径 | `signed_pnl_raw`（**带符号十六进制**）为**唯一权威**，**逐字节原样保留** | 实测 raw 是 `-0x2ee726109c1` 而**非十进制**；`signed_pnl_amount` 是 `REAL`（f64），**必然丢精度** |
| `D-7` | 反压策略 | **分级**：JSONL 可丢 / 月库背压 | 「套利记录强制同步写」会卡死主线程，违反「不能因为写盘卡死套利计算」 |
| `D-8` | 保留期 | **默认 30 天**（原始建议 7 天） | 复核记录是**审计凭据**，7 天覆盖不了一次月度结算周期 |
| `D-9` | 主库写入方式 | **维持现状**（同步事务） | 主库在途行必须与状态行**同事务可见**，不能引入异步丢失窗口 |
| `D-10` | 记录目录推导 | 由主库路径 **确定性推导** | 公开函数签名不变 ⇒ 不新增配置参数 ⇒ 调用方零改动 |
| `D-11` | **v1.1 目录布局**（使用者裁定 2026-11-23） | 复核 **`db/review_record_jsonl/<链路>/<日期>/<方向闭环>.jsonl`**；广播 **`db/broadcast_transaction_db/<链路>/<月份>/trades.sqlite3`**（**全部方向闭环同库**）。**「链路」= `<network>/<chain_id>` 两级**（如 `robinhood/4663`），详见 §3.2 | 复核侧要**按闭环单独读**⇒ 必须拆文件；广播侧要**按币种跨闭环合计**⇒ 必须同库 |

> **`D-4` 是本次唯一一处「否决原始设想」的地方**，也是最要紧的一处 —— 见 §3.4。

### 2.4 三个决定性发现（决定了方案形态）

| # | 发现 | 对方案的含义 |
|---|---|---|
| **F-1** | **主库零套利/广播存量**（相关表 0 行） | 剥离是**纯前向**的，**零数据迁移**、零回填、无历史兼容负担 |
| **F-2** | **复核记录不增长**（每代全量替换） | 复核侧的痛点**不是磁盘**，而是**历史不可追溯**；⇒ JSONL 应定位为**审计流**，不是「省空间」 |
| **F-3** | **复核记录被门禁链高频读取**（完整性 / 新鲜度 / 容量 / 利润 / `BC-1`） | **当前代必须留在主库**；剥离的只能是「历史代」 |

> **F-2 值得特别强调。** 原始设想是「复核记录数据量极大 ⇒ 落 JSONL 解压主库」。

> **所以剥离复核记录不是为了省空间，而是为了「留住每一代」** ——
> 方向是把「当前代物化视图」+「逐代审计流」拆开，而不是把复核数据「搬走」。

## 三、目标架构：三层权威

### 3.1 权威分层

| 层 | 载体 | 权威性 | 可丢 | 参与判定 |
|---|---|---|---|---|
| **L1 主库** | `local_store_4663.sqlite3` | **状态权威**：当前代物化视图 + 状态行 + 幂等台账 | ❌ 不可丢 | ✅ **是** |
| **L2 月度库** | `broadcast_transaction_db/<链路>/<chain_id>/<YYYY-MM>/trades.sqlite3` | **已终结套利记录的唯一权威** | ❌ 不可丢 | ✅ 是（幂等 / 回执关联） |
| **L3 JSONL** | `review_record_jsonl/<链路>/<chain_id>/<YYYY-MM-DD>/<方向闭环>.jsonl` | **审计流**：逐代复核快照 | ✅ 可丢 | ❌ **永不** |

**判据一句话**：**「要拿它做决定」→ L1/L2；「要拿它证明做过什么」→ L3。**

### 3.2 目录结构（由主库路径确定性推导）

**v1.1 布局（使用者裁定，2026-11-23）**：两棵记录树**与主库同目录**；
复核侧**按方向闭环拆文件**，广播侧**按方向闭环不拆文件**（全部闭环同库）。

```text
<主库目录>/                              ← 即 flashloan/db/
├── local_store_4663.sqlite3             ← 主库（不动）
├── review_record_jsonl/                 ← 复核审计流
│   └── <network>/<chain_id>/
│       └── <YYYY-MM-DD>/                ← 按日期建文件夹
│           └── <方向闭环>.jsonl          ← 每个方向闭环一个文件
├── broadcast_transaction_db/            ← 广播（套利）交易记录
│   └── <network>/<chain_id>/
│       └── <YYYY-MM>/                    ← 按月份建文件夹
│           └── trades.sqlite3            ← 全部方向闭环同库
└── record_maintenance/                  ← 清理台账（永不清理）
```

推导规则：**主库路径所在的目录**（即 `flashloan/db/`）。
**不新增配置项、不新增公开参数** ⇒ 4 个读路径消费者**零改动**。

**「方向闭环」的文件名怎么来**：闭环键（`loop_key`）由三个代币地址拼成
（`anchor:y:z`），**含冒号** —— Windows 文件名不允许冒号。因此文件名 =
**安全化后的闭环键 + 原键的 SHA-256 前 12 位十六进制**：

- 安全化 = 只保留 `[A-Za-z0-9._-]`，其余字符换成 `_`，再截断到 64 字符；
- 摘要后缀 ⇒ **两个不同闭环绝不会落到同一个文件**；
- 同一闭环**永远**得到同一个文件名 ⇒ 可重复定位。

**广播侧为何不拆文件**：月度库要回答的是「这个月这个链赚了多少」，**按币种分组**的
合计必须在**同一个库**里算；拆成每闭环一个库会把「跨闭环求和」重新变成
N 次连接。闭环维度由 `loop_key` **列**承担，不靠文件分片。

### 3.3 复核侧写入时序（主库保持权威，JSONL 旁路）

```text
① 主库事务：DELETE 三表 → INSERT 当前代 → upsert 状态行 → COMMIT   ← 权威，仍同步
② 事务提交后 → 构造 JSONL 行（只序列化「这一代」的差异集）
③ try_send 到有界通道（容量 10000）→ 后台 tokio 任务追加写文件
④ 通道满 → 丢弃该行 + dropped 计数 +1（可在 read_review_status 读到）
```

要点：

- **JSONL 写在事务提交之后** —— 写失败**绝不回滚**主库，**绝不阻塞**主库提交；
- **JSONL 是逐代增量**，不是每代全量快照（否则第 24 代就要写 24 份全量 ⇒ 反而更大）；
- 每行自带 `reviewVersion` + `closedLoopVersion` + `materializedChecksum` ⇒ 可自证是哪一代；
- **JSONL 永远不参与准入判定** —— 门禁只读主库当前代（`D-3`）。

### 3.4 广播侧写入时序（**这是与原始设想差别最大的一处**）

原始设想是「套利记录全部搬到按月 SQLite，主库只留索引」。**本方案否决该形态。**
否决理由（**安全级别**，不是风格偏好）：

> 幂等判定读的是主库。索引行若因任何原因落后于月度库（写失败、进程崩溃在两步之间、
> 月度库被锁、清理任务误删），系统会**认为「这个 attempt 从没发生过」** ⇒
> **同一条机会会被再次广播** ⇒ **重复交易 = 资金损失**。
> 而「重复广播一条已终结的尝试」与「多写一条记录」相比，**风险量级完全不同**。

因此采用**有序两步归档 + 主库瘦身**（主库 → 月库 → 主库瘦身行）：

```text
① 尝试发起 → 主库 INSERT（manager_cow_execution_attempts，status=在途）   ← 幂等锚点
② 尝试终结（回执 / 证据 / terminal_at 落定）
③ 先 INSERT OR REPLACE 进【当月库】（terminated 形态，含完整列）
④ 确认月库写入成功后 → 主库把该 attempt 行「瘦身」
   （清空体积列，保留判定列 / 幂等锚点 / 盈亏原值，≈250 B）
⑤ 反向禁止：任何时刻不得「先删主库、后写月库」
```

**为什么这样更安全**：

| 崩溃点 | 结果 |
|---|---|
| ③ 之前崩溃 | 尝试留在主库（**在途**）⇒ 幂等锚点在 ⇒ 不会被重复广播 |
| ③ 成功、④ 之前崩溃 | **两处都有** ⇒ 幂等锚点仍在主库 ⇒ 安全；下次启动由**幂等对账**收敛（月库行覆盖主库行） |
| ④ 之后崩溃 | 主库瘦身行 + 月库完整行 ⇒ 幂等锚点**仍在** ⇒ 安全 ✅ |

**与原始设想的关键差别**：原始设想是「搬走 + 留索引」；本方案是
**「搬走 + 留瘦身行」** —— 瘦身行**不是索引**（不携带路径明细与回执原文），
只承担**「这条 attempt 存在过、别再来一遍」**这一个职责 ⇒
**重复广播风险 = 0**，同时主库增长受控（≈250 B/行而非整行）。

> **⚠️ 为什么不是「墓碑行」**：`status` 列的 CHECK 只允许
> `pending` / `success` / `failed` ⇒ 新增 `'archived'` **必须改主库 DDL** ⇒ **越界**；
> 新增一张墓碑表**同样越界**。⇒ 改为**瘦身**（**不动 `status`、不新增列、不新增表**）。
> 完整论证见 **§5.4**。

### 3.5 跨月查询（**逐库只读** · v1.1 落地口径）

月度库**沿用主库的表名与列结构**（`manager_cow_execution_attempts` 等）。
**原始设想**是用 SQLite 的 `ATTACH` 把历史月库挂到当前连接上一句 SQL 查完：

```sql
ATTACH DATABASE 'flashloan/db/broadcast_transaction_db/robinhood/4663/2026-10/trades.sqlite3' AS m202610;
SELECT signed_pnl_raw, signed_pnl_currency FROM trades WHERE ...;
UNION ALL
SELECT signed_pnl_raw, signed_pnl_currency FROM m202610.trades WHERE ...;
```

要点：

- `ATTACH` **由 `broadcast_manager` 内部完成**，**不暴露给调用方** ⇒ 公开 API 不变；
- 月度库**零新表零新列** ⇒ `manager_db` / 迁移 / `schema_policy.json` **全部不动**；
- `M-6` 守卫按**表名**匹配 ⇒ 沿用主库表名 ⇒ **自动被既有守卫覆盖**（§4.3）。
- **⚠️ 落地修正（v1.1）**：SQL 里**只能取原始行**，**禁止** `SUM(signed_pnl_raw)` ——
  `signed_pnl_raw` 是**带符号十六进制字符串**、且**多币种混存** ⇒ SQL 聚合会
  **差 16 个数量级**（按十进制解析）**且**跨币种求和无意义。
  **落地实现**：按 `signed_pnl_currency` **分组**（`GROUP BY` 只用于**取分组键**，
  **不聚合金额**），金额在 **Rust 侧用 `U256` 精确求和** ⇒ **逐位相等**。
  另：**落地实现改为「月库一个一个只读打开」** —— **绝不**把月库 `ATTACH` 到
  **主库连接**上（避免跨库句柄泄漏、避免主库连接被历史库拖住），
  也**绝不**跨库做 SQL 聚合。跨月结果在 **Rust 侧**合并。

### 3.6 精度口径（对齐 `D-6`）—— **含实测修正**

现网 DDL 实测：`signed_pnl_raw TEXT`、`signed_pnl_amount REAL`（**f64**）。
`REAL` 在 2^53 之外**必然丢精度** ⇒ 金额**不可用它做权威**。

**但「权威字段的格式」与原始设想不同 —— 本轮已实测钉死**（只读统计主网库
`manager_v4_reviews` 中 **14** 条带盈亏的行）：

| 实测项 | 读数 | 含义 |
|---|---|---|
| `signed_pnl_raw` 的实际形态 | `-0x2ee726109c1` | **带符号的十六进制**，**不是**十进制 |
| `raw` 为纯十进制数字的行数 | **0 / 14** | 原始设想里的 `"profit_wei": "1250000000000000"` **与现网格式不符** |
| `raw` 带 `-` 前缀、且与 `amount` 符号一致 | **14 / 14** | ✅ **符号由 raw 携带**（可安全做有符号聚合） |
| `amount` 与 `raw` 的换算 | **≈1e18**（**13/14** 精确为 1e18；余 1 行是 f64 除法舍入，非另一套定标） | `amount = raw ÷ 10^decimals` |
| `signed_pnl_currency` 分布 | WETH **4** / SPY **8** / TZ **2** | ⚠️ **多币种** ⇒ 跨币种求和**没有意义** |

> **⚠️ 原始设想的一处必须修正**：把 `signed_pnl_raw` 当作「U256 的十进制字符串」会
> **得到完全错误的数量级**（把 `-0x2ee726109c1` 当十进制解析 ⇒ 读成约 -3.2e10，
> 而真值是 -3.22e-06）。**正确做法**：JSONL 与月度库
> **原样保留 `signed_pnl_raw` 的十六进制字符串**（**逐字节无损**），
> 额外的十进制派生字段**只在实现了精确的 hex→十进制换算并有逐位测试时才允许出现**。

| 字段 | 类型 | 权威性 | 处置 |
|---|---|---|---|
| `signed_pnl_raw` | `TEXT`（**带符号十六进制**） | ✅ **唯一权威** | JSONL 与月库**逐字节原样保留** |
| `signed_pnl_amount` | `REAL`（f64） | ❌ 派生值 | 保留（兼容既有读路径），但**只作展示**；判正负用 `raw` |
| `signed_pnl_currency` | `TEXT` | ✅ 分组键 | 聚合**必须按币种分组**（§5.5） |
| 派生十进制字符串 | `String` | 派生 | **可选**；未实现精确换算前**一律不写** |

> JSONL 行内**只写字符串**：`"signedPnlRaw": "-0x2ee726109c1"`。
> **不写** `"profit_usd": 3.50`（JSON 数字 = f64）—— 只写 `"profitUsd": "3.50"`。

### 3.7 反压与丢弃（对齐 `D-7`）

两条通道**分级**，因为两类记录的**可丢性不同**：

| 通道 | 容量 | 满时策略 | 理由 |
|---|---:|---|---|
| **JSONL 复核审计流** | 10,000 | **`try_send` 失败即丢弃** + `dropped` 计数 +1 | 审计流丢了**不影响正确性**，只影响「可追溯性」；**绝不能因此卡住复核物化** |
| **月度套利库** | 1,000 | **`send().await` 背压**（等待而非丢弃） | 套利记录**是核心资产**，**不可丢**；背压只会让广播线程慢一点，**不会让记录消失** |

> **与原始建议的一处刻意分歧**：原始建议写「套利记录……可以阻塞几毫秒等待写入，
> **或者强制同步写一次**」。本方案选 **`send().await` 背压**，不选「强制同步写」。理由：
> 「强制同步写」= 在持锁 / 持事务上下文里做磁盘 IO ⇒ **把磁盘延迟传导进主引擎**；
> `send().await` = **在通道处等**，等待发生在**独立任务**里 ⇒ 主引擎只是「稍后拿到结果」，**不持任何锁**。
> 两者最终都不丢数据，但**后者不会把 IO 延迟叠到套利计算上**。

### 3.8 保留期与清理

| 对象 | 保留期 | 清理方式 | 注意事项 |
|---|---:|---|---|
| JSONL 复核审计流 | **30 天**（`D-8`） | **按日期文件夹整目录删除** | **绝不**逐行改写；整目录删除天然规避「文件尾损坏」 |
| 月度套利库 | **永久**（不做自动清理） | 人工 / 显式命令 | 套利是**财务凭据**；自动清理必须先有人工审批（`D-8` 的取舍点） |

清理任务**必须**：① 只删 `review_record_jsonl/` 子树里的**日期文件夹**；
② **绝不触碰** `broadcast_transaction_db/`；③ 记录每次删除的
**路径清单与字节数**（审计台账落在 `record_maintenance/`）。

> **JSONL 格式硬约束**：**一行一个 JSON 对象（JSONL）**，**严禁**写成 JSON 数组。
> 数组格式下，文件尾部一次写入中断 ⇒ **整个文件不可解析**；JSONL 下最多损失最后一行。

## 五、相容性论证

### 5.1 读路径看不出差别

四类消费者读的都是**主库当前代**：

- 复核侧：主库仍写当前代（`manager_v4_reviews` 仍每代全量替换）⇒ `read_review_snapshot` / `read_review_page` **读到的内容与今天完全一致**；
- 广播侧：主库仍写**在途**行与**瘦身后的归档行** ⇒ `read_broadcast_status` / `read_broadcast_snapshot_page` **结构一致**。

⇒ **没有任何一个既有公开函数需要改签名** ⇒ 消费者 crate **零改动**。

### 5.2 幂等与门禁不被削弱

| 机制 | 位置 | 剥离后是否仍然有效 |
|---|---|---|
| **写请求幂等台账** | `manager_write_requests`（`find_write_request` / `persist_submit_write`） | ✅ **完全不受影响**（不在剥离范围，48 行） |
| **批内重复检测** | `validate_attempt_inputs`（`broadcast_manager:1533`） | ✅ 不受影响（读主库在途行） |
| **上游一致性校验** | `validate_expected_upstream` | ✅ 不受影响（读复核状态行） |
| **复核完整性 / 新鲜度 / 容量 / 利润 / `BC-1`** | 复核管理器门禁 | ✅ 不受影响（读主库当前代） |
| **回执关联** | `receipt_json` / `evidence_json` | ⚠️ 见 §5.4 的「瘦身」说明 |

### 5.3 崩溃一致性（有序两步）

| 崩溃点 | 主库状态 | 月库状态 | 后果 |
|---|---|---|---|
| 写月库**之前** | 完整在途/终结行 | 无 | ✅ 安全：记录仍在主库，重启后可重放归档 |
| 写月库**成功**、瘦身主库**之前** | 完整行 | 完整行 | ✅ 安全：**两份都在**；下次归档用 `INSERT OR REPLACE` 幂等收敛 |
| 瘦身主库**之后** | 瘦身行 | 完整行 | ✅ 安全：判定列仍在主库，幂等锚点健在 |

**因此「先写月库、后动主库」是唯一允许的顺序**，且必须由守卫钉死。

### 5.4 「瘦身归档」而不是「删除 + 墓碑」（**重要修正**）

初稿曾设想「归档后删除主库行 + 留一行墓碑」。**实测 DDL 后此路不通**：

```sql
status  TEXT NOT NULL CHECK (status IN ('pending','success','failed'))
```

- `status` 的 CHECK **不允许**新增 `'archived'` 值 ⇒ 要加就要**改主库 DDL** ⇒ **越界**；
- 新增一张墓碑表 ⇒ **同样越界**（主库不能加表）。

⇒ 改为**瘦身归档**：

| 类别 | 列 | 归档后 |
|---|---|---|
| **保留**（判定 / 幂等 / 对账所需） | `attempt_id` · `loop_key` · `network/chain_id/protocol/scope_key` · `status` · `status_reason` · `tx_hash` · `signed_pnl_raw` · `signed_pnl_currency/unit/source` · `created_at` · `terminal_at` · `updated_at`（改为归档时刻） | 原样 |
| **清空**（体积大、判定不需要） | `path_addresses_json` · `path_symbols_json` · `pool_ids_json` · `hop_sqrt_price_limits_json` · `receipt_json` · `evidence_json` | `'[]'` / `'{}'` |

效果：主库行从 **~2–3 KB** 降到 **~250 B**；**零 DDL 变更、零迁移、零 CHECK 冲突**；
`attempt_id` 仍在 ⇒ 幂等锚点在；`status` / `tx_hash` / `signed_pnl_raw` 仍在 ⇒
**运行时的「这个闭环广播过」证据不丢**。

> **已知后果（如实记录）**：`read_broadcast_snapshot_page` 返回的是主库行 ⇒
> **已归档的尝试在页面上不再显示路径明细与回执原文**（仍显示 attempt_id / loop_key / 状态 / tx_hash / 盈亏）。
> 取回完整原文需查月度库。若要在 UI 上补这个能力，需要**新增** `broadcast_manager::read_archived_attempt()`
> **并**在 `manager_api` / UI 侧接线 ⇒ **超出本次范围**，本次**不做**，列为可选后续（§七 `Q-4`）。

### 5.5 跨月聚合的正确姿势（三条硬规则）

**规则 1 · 绝不跨币种求和。**
实测 `signed_pnl_currency` 有 WETH / SPY / TZ 三种 ⇒ 「过去 3 个月的总利润」这个说法
**本身不成立**（不同币种不可加）。正确口径是
**按币种分组，每组一个精确合计**：`{ "WETH": "-0x…", "SPY": "0x…" }`。

**规则 2 · 禁止在 SQL 里做金额聚合。**
SQLite 的 `SUM()` 对 `TEXT` 会做**数值转换**（十六进制串会被直接解析成 0 或错误值）。

```sql
-- ❌ 禁止：精度与格式双重错误
SELECT SUM(signed_pnl_raw) FROM trades;
-- ✅ 允许：只做筛选与取行，聚合在 Rust 侧做
SELECT signed_pnl_raw, signed_pnl_currency FROM trades WHERE ...;
```

**规则 3 · 聚合在 Rust 侧用任意精度做。**
流程：**逐个只读打开**各月库（**不** `ATTACH` 到主库连接）→ 逐行取出 `signed_pnl_raw` → 解析为
`alloy_primitives::U256`（**工作区已有依赖，不新增 crate**）→ 按符号做有符号加法
→ 输出**十六进制字符串**（与存储格式一致，**不引入十进制换算的误差面**）。

> **落地修正（v1.1）**：`broadcast_manager` **不需要** `alloy-primitives` ——
> 聚合实现落在 `review_manager::records`（那里**已有** `alloy-primitives` 依赖），
> 广播侧**只调用** ⇒ `broadcast_manager/Cargo.toml` **零改动**。

### 3.2 `TASK-175`｜复核 JSONL 行模型与写入器

**目标**：定义复核审计流的**行格式**与**写入器**，一次实现、两端复用。

**行模型（schema `review_record.v1`）**


| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | 固定 `review_record.v1` ⇒ 未来改格式可识别 |
| `event` | ✅ | `upsert`（新增/变更）或 `removed`（本代消失） |

### 3.3 `TASK-176`｜JSONL 逐行增量与 `removed` 事件

**目标**：**只写变化**，不写全代快照。

**算法**

1. 在 `replace_review_rows` 的**事务内、`DELETE` 之前**读出旧行（`manager_v4_reviews` 当前 164 行，代价可忽略）；
2. 事务提交后，计算差异：
   - **新增 / 变更** ⇒ 产生 `upsert` 事件行；
   - **旧有新无** ⇒ 产生 `removed` 事件行（**必须**，否则审计流无法还原「这一代少了谁」）；
3. 若**整代 checksum 未变** ⇒ **一行都不写**（重复物化不产生审计噪声）；
4. 差异行 `try_send` 到通道（容量 **10,000**）。

**验收 `AC-225`**

- [ ] 同一代**连续物化两次** ⇒ JSONL **行数不增加**；
- [ ] 变更 1 条复核 ⇒ JSONL **只增加 1 条** `upsert`（不是全代重写）；
- [ ] 删除 1 条复核 ⇒ 增加 **1 条** `removed`，且含 `loopKey` 与 `reviewVersion`；
- [ ] 用 JSONL **可还原**任意一代的复核集合（逐 `reviewVersion` 回放验证）。

**差异算法（定稿）**

```rust
/// Compare the previous generation with the new one and produce the audit events.
pub fn diff_review_generations(
    previous: &[ReviewRowSnapshot],
    next: &[ReviewRowSnapshot],
    review_version: i64,
) -> Vec<ReviewRecordLine>;
```

1. **键**：`loop_key`（复核身份键）。若未来出现同键多行 ⇒ 改用
   `(loop_key, path_text)` 复合键，并在守卫中固定下来；
2. **比较字段**：`review_status` · `review_reason` · `signed_pnl_raw` ·
   `signed_pnl_currency/unit/source` · `path_symbols` · `pool_ids` ·
   `capacity_anchor_raw` · `capacity_binding_pool_id`；
3. **产出**：
   - 键只在 `next` ⇒ `upsert`；
   - 键只在 `previous` ⇒ `removed`；
   - 两边都有但**比较字段任一不同** ⇒ `upsert`（**不产出** `removed`）；
   - 两边都有且**完全相同** ⇒ **不产出任何行**；
4. **整代短路**：若新旧两代的 `materialized_checksum` **相同**
   ⇒ **一行都不产出**（**最外层**先判，省掉逐行比较）。

**「读旧行」放在哪里（关键）**

```text
① 开事务（IMMEDIATE）
② 【事务内】SELECT 旧行 → 快照到内存（164 行，代价可忽略）
③ DELETE 三表 → INSERT 当前代 → upsert 状态行
④ COMMIT                                        ← 权威落定
⑤ 【事务外】diff(旧快照, 新行) → try_send 到通道
```

> **为什么旧行必须在事务内读**：事务外的读会看到「已被别的事务删掉」或
> 「尚未提交」的中间态 ⇒ 差异集不准 ⇒ 审计流会描述一个**不存在的中间态**。
> **为什么 diff 在事务外算**：CPU 计算**不持有锁** ⇒ 不拖慢其它写者。

**测试矩阵**

| # | 用例 | 期望 |
|---|---|---|
| 1 | 同代物化 **2** 次 | JSONL **行数不增加**（checksum 短路） |
| 2 | 改 1 条的 `review_status` | 增加 **1** 条 `upsert`（**不是**全代） |
| 3 | 删 1 条 | 增加 **1** 条 `removed` |
| 4 | 改 1 条的 `signed_pnl_raw` | 增加 **1** 条 `upsert`，且 **raw 原样** |
| 5 | 一增一删同批 | 增加 **2** 条（1 upsert + 1 removed），**顺序稳定** |
| 6 | 全代为空 | 增加 **N** 条 `removed`（N = 旧行数） |
| 7 | **事务回滚** | JSONL **一行都不增加** |
| 8 | 旧行在**事务内**被读到 | 与事务外读到的**可能不同** ⇒ 测试须在**事务内**断言 |

### 3.4 `TASK-177`｜复核管理器接入与丢弃计数

**目标**：把写入器接进复核管理器，并让「丢了多少」**可见**。

**改动点**

| 位置 | 改动 |
|---|---|
| `review_manager/src/lib.rs` | ① `replace_review_rows` 提交后推流；② **新增** `pub fn read_review_record_health() -> ReviewRecordHealth` |
| `review_manager/src/records.rs` | 后台写任务（有界通道 + 独立写线程） |

```rust
pub struct ReviewRecordHealth {
    pub queued: usize,        // 当前排队待写的行数
    pub written: u64,        // 已成功落盘的行数
    pub dropped: u64,        // 因通道满而丢弃的行数  ← 可观测
    pub last_error: Option<String>,
}
```

**写入路径（硬性顺序）**

```text
① 主库事务（DELETE → INSERT → upsert 状态行）→ COMMIT      ← 权威，先提交
② 计算差异行
③ try_send(通道)  ├─ 成功 → 后台写线程落盘
                  └─ 失败（通道满）→ dropped += 1（**丢弃，不阻塞**）
```

- **JSONL 写在 COMMIT 之后** ⇒ 写失败**不回滚**主库；
- `try_send` **绝不阻塞** ⇒ 通道满时**丢弃 + 计数**，复核物化**不受影响**；
- 后台写任务跑在**独立线程 + 独立 current-thread runtime** ⇒
  **不要求调用方在 tokio runtime 内**（避免 `blocking_send` 在 runtime 内 panic，见 `R-9`）。

**验收 `AC-226`**

- [ ] `read_review_record_health()` **新增**且既有公开函数签名**一个都没改**；
- [ ] 通道满 ⇒ `dropped` 递增、**主库物化不阻塞**（用测量断言耗时上界）；
- [ ] 主库 COMMIT 失败 ⇒ **一行 JSONL 都不写**；
- [ ] JSONL 路径**不出现在任何门禁判据的读路径里**（源码级断言）。

**接入点（定稿 · 只碰两处）**

```rust
// review_manager/src/lib.rs —— materialize 路径
let transaction = connection.transaction_with_behavior(TransactionBehavior::Immediate)?;
let previous = read_review_rows_for_diff(&transaction, network, chain_id)?;  // ② 事务内读旧行
replace_review_rows(&transaction, network, chain_id, &desired, &result)?;     // ③ 现有逻辑，不改
transaction.commit()?;                                                      // ④

// ⑤ 事务外：差异 → 通道（丢弃不阻塞）
let events = diff_review_generations(&previous, &desired_snapshot, result.review_version);
for event in events {
    if record_channel().try_send(event).is_err() {
        record_health().dropped.fetch_add(1, Ordering::Relaxed);
    }
}
```

> `replace_review_rows` 的**签名与内部 SQL 一字不改** ——
> 只在**调用方**多读一次旧行、多推一次事件。
> ⇒ **既有行为零变化**（回归可证）。

**写任务（后台线程 · 独立 runtime）**

```rust
static WRITER: OnceLock<RecordWriterHandle> = OnceLock::new();

pub struct RecordWriterHandle {
    sender: tokio::sync::mpsc::Sender<ReviewRecordLine>,
    health: Arc<ReviewRecordHealth>,
}

pub struct ReviewRecordHealth {
    pub queued: AtomicUsize,
    pub written: AtomicU64,
    pub dropped: AtomicU64,
    pub write_errors: AtomicU64,
    pub last_error: Mutex<Option<String>>,
}
```

- 写任务跑在**独立 `std::thread`** + **独立 `current_thread` runtime**
  ⇒ **不要求调用方在 tokio runtime 内**（避免 `blocking_send` 在 runtime 内 panic，见 `R-9`）；
- **唯一消费者** ⇒ 写入**天然串行** ⇒ 文件**不会**交错；
- 进程退出时：`Drop` 里 **flush + 关句柄**（尽力而为，**不阻塞退出超过 1s**）。

**三级降级（反压 · 定稿）**

| 级 | 条件 | 动作 | 是否丢数据 |
|---|---|---|---|
| **1** | 通道**未满** | `try_send` 成功 | ❌ 不丢 |
| **2** | 通道**满** + **不在** tokio runtime 内 | `blocking_send`（**有界等待**） | ❌ 不丢（**可能阻塞调用线程**） |
| **3** | 通道**满** + **在** tokio runtime 内 | **单次同步兜底写**（当前线程直写文件） | ❌ 不丢（**不阻塞等待**） |

> **复核侧其实只会走到第 1 级**：复核 JSONL 是**可丢的审计流**，
> 所以本方案在**第 1 级失败时直接丢弃 + 计数**（**不升级到 2/3 级**）——
> 否则审计流会**反过来拖慢复核物化**。
> **第 2/3 级是给套利记录用的**（**不可丢**），见 §3.6。
> **一句话**：**可丢的流宁可丢，不可丢的流宁可等。**

**测试矩阵**

| # | 用例 | 期望 |
|---|---|---|
| 1 | 正常物化 | JSONL 增加**对应差异**行数；`written` 递增 |
| 2 | 通道**人为填满** | `dropped` 递增；**主库物化耗时**在上界内（**不阻塞**） |
| 3 | 主库 **COMMIT 失败** | JSONL **一行都不写**；`written` **不递增** |
| 4 | 写文件**失败**（目录只读） | `write_errors` 递增；**主库不受影响** |
| 5 | 进程正常退出 | 已入队数据**全部落盘**（flush 生效） |
| 6 | `read_review_record_health()` | 返回 `queued/written/dropped/write_errors/last_error` |
| 7 | 门禁代码路径扫描 | **零处**引用 JSONL 路径 / 记录文件 |

### 3.5 `TASK-178`｜月度套利库（DDL 克隆 / roll-over）

**目标**：建立**与主库同构**的按月分库，**零手抄 schema**。

**改动点**

| 文件 | 改动 |
|---|---|
| `broadcast_manager/Cargo.toml` | 追加 `tokio = { workspace = true, features = ["fs","sync","time"] }`（当前**没有** tokio）；追加 `alloy-primitives.workspace = true`（跨月聚合用） |
| `broadcast_manager/src/records.rs`（**新增**） | 月库打开 / roll-over / DDL 克隆 / `ATTACH` |

**DDL 克隆（防漂移的关键）**

1. 从**主库**读 `SELECT sql FROM sqlite_master WHERE type='table' AND name IN ('manager_cow_execution_attempts','manager_broadcast_attempt_diagnostics')`；
2. 把 `CREATE TABLE ` 前缀改写为 `CREATE TABLE IF NOT EXISTS `，把 `CREATE INDEX ` 改写为 `CREATE INDEX IF NOT EXISTS`；
3. 在月库执行 ⇒ **月库 schema 与主库逐字符一致**（**不手抄、不新增表、不新增列**）。

**打开参数**

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 60000;
```

**Roll-over**

- 写入目标库 = **记录自身 `created_at` 的 UTC 月**（**发起月**，不是当前月）；
- 月份变化 ⇒ 对旧连接 `PRAGMA wal_checkpoint(TRUNCATE)` ⇒ `drop(conn)` ⇒ 打开新月库；
- **句柄切换必须安全**：旧连接 drop 之后**才**打开新库；
- 写入**全部由单一后台任务串行执行** ⇒ 月库**不会**出现并发写。

**验收 `AC-227`**

- [ ] 月库的 `sqlite_master.sql` **等于**主库对应表 SQL（逐字符比对）；
- [ ] 月库**零新表零新列**（`manager_db` / `schema_policy.json` **零 diff**）；
- [ ] 跨月归档 ⇒ 记录落在**发起月**的库，不是归档当月；
- [ ] roll-over 后旧库 `-wal` 被 checkpoint 且**文件句柄已释放**（可删除旧库文件即证）；
- [ ] `cargo build --offline --workspace` **exit 0**（**不引入新外部 crate**）。

**DDL 克隆算法（定稿 · 防漂移的关键）**

```rust
/// Read the live DDL from the main store and materialise it into the month store.
pub fn clone_schema_into(
    main: &Connection,
    month: &Connection,
    tables: &[&str],
) -> Result<(), BroadcastError>;
```

1. 从**主库**读 `SELECT name, sql FROM sqlite_master WHERE type='table' AND name IN (?)`；
2. 同样读 `type='index' AND tbl_name IN (?)`（索引**必须一起克隆**，否则跨月查询变慢）；
3. **改写规则**（唯一的改写点）：
   - `CREATE TABLE ` ⇒ `CREATE TABLE IF NOT EXISTS `
   - `CREATE TABLE IF NOT EXISTS ` ⇒ **原样**
   - `CREATE INDEX ` ⇒ `CREATE INDEX IF NOT EXISTS `
   - `CREATE UNIQUE INDEX ` ⇒ `CREATE UNIQUE INDEX IF NOT EXISTS`
   - **其余一律原样**（**不得**做任何其它改写）
4. 在月库**逐条执行** ⇒ 月库 schema **与主库逐字符一致**（除 `IF NOT EXISTS` 后缀）；
5. **主库缺表 ⇒ 直接报错**（**不得**跳过、**不得**自造表）。

> **为什么必须克隆、不能手抄**：手抄的 schema 会与主库**漂移**（主库加了列，月库没加）
> ⇒ 跨月查询与主库读数**不可比** ⇒ 财务账目对不上。
> **为什么不能改 `manager_db`**：迁移与 DDL **不在允许改动范围**内（用户明确要求主库信息维持不变）。

**月库打开参数**

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;
PRAGMA busy_timeout = 60000;
PRAGMA foreign_keys = ON;
```

**Roll-over 状态机（定稿）**

```text
        写入请求(归属月 M)
              │
              ▼
    ┌───────────────────────┐
    │ 当前句柄的月 == M ?   │──是──▶ 直接写
    └───────────┬───────────┘
                │否
                ▼
   PRAGMA wal_checkpoint(TRUNCATE)   ← 旧库 WAL 落盘
                ▼
            drop(旧句柄)              ← 句柄释放
                ▼
        打开 trades_M.db（新建则先克隆 schema）
                ▼
             写 入
```

- **句柄切换必须安全**：旧连接 `drop` **之后**才打开新库（**禁止**两个句柄同时持有同一个文件）；
- 月归属 = **记录自身 `created_at` 的 UTC 月** ⇒ 跨月归档会**打开上个月的库**；
- **旧库永不删除**（只 `drop` 句柄）。

**月归属判据（定稿）**

```rust
/// The month a record belongs to: the UTC month of its own created_at.
pub fn owning_month(created_at: &str) -> Result<(i32, u32), BroadcastError>;
```

- `created_at` 是 **RFC3339 UTC**（现有写入用 `chrono::Utc::now().to_rfc3339()`）
  ⇒ 直接解析即可；
- 解析失败 ⇒ **归档失败 + 计数**（**绝不**猜测月份）。

**测试矩阵**

| # | 用例 | 期望 |
|---|---|---|
| 1 | 月库首次创建 | `sqlite_master.sql` **等于**主库对应表 SQL（逐字符） |
| 2 | 月库**已存在** | 重复打开**不报错**、**不重建** |
| 3 | 主库**缺表** | **报错**（不静默跳过） |
| 4 | 跨月归档（记录属上月） | 写入**上月**的库；**当月**库**为空** |
| 5 | roll-over | 旧库 `-wal` 被 **checkpoint**；旧库**仍存在**（**未删除**） |
| 6 | roll-over 后写新库 | 新库**自动克隆** schema |
| 7 | `created_at` 非法 | **报错 + 计数**，**不写任何库** |
| 8 | 离线构建 | `cargo build --offline --workspace` **exit 0**；`Cargo.lock` **零 diff** |

### 3.6 `TASK-179`｜终结归档（有序两步 + 瘦身）

**目标**：终结的套利记录**完整**进月库，主库只留**判定所需的瘦身行**。

**写入时序（唯一允许的顺序）**

**幂等**

### 3.7 `TASK-180`｜跨月聚合与月归属判据

**目标**：支持「跨月查利润」，且**不跨币种、不丢精度**。

**改动点**：`broadcast_manager/src/records.rs` 新增

```rust

    -> Result<TradeArchiveSummary, BroadcastError>;      // 按币种分组的精确合计
```

**聚合算法（三条硬规则，见技术方案 §5.5）**

1. **按币种分组** ⇒ `{ "WETH": "-0x…", "SPY": "0x…" }`，**绝不**给出一个跨币种的「总利润」；
2. **禁止 SQL `SUM()`** ⇒ 只在 SQL 里筛选 / 取行；
3. **Rust 侧任意精度** ⇒ `signed_pnl_raw` → `U256::from_str_radix(hex, 16)` → 按符号累加 → 输出**十六进制字符串**。

**`ATTACH` 纪律**

- `ATTACH` 只在**专用查询连接**上做（**不是**主库连接）⇒ 不污染主库连接状态；
- 用完立即 `DETACH`；
- 只读打开月库（`mode=ro`）⇒ **查询绝不写月库**。

**验收 `AC-229`**

- [ ] 跨 3 个月查询 ⇒ 结果**按币种分组**，与手工逐行累加**逐位相等**；
- [ ] 构造 **2^255** 量级的 `signed_pnl_raw` ⇒ 合计**逐位相等**（**不丢一位**）；
- [ ] `signed_pnl_currency` 不同的两行**不被加到一起**；
- [ ] 查询后**主库连接**未被 `ATTACH` 污染（连接状态断言）。

**API（定稿）**

```rust

    chain_id: i64,

}
```

**聚合算法（定稿 · 三条硬规则）**

```rust

/// Add two signed magnitudes and render the result in the same signed hex form.

```

1. **按币种分组** ⇒ `signed_pnl_currency` 不同的行**绝不合并**
   （实测：WETH / SPY / TZ **三种**）；
2. **禁止在 SQL 里做金额聚合** ⇒ SQL 只做**筛选与取行**；
3. **Rust 侧任意精度** ⇒ `U256::from_str_radix(hex, 16)` + `checked_add` /
   `checked_sub` ⇒ 输出**带符号十六进制字符串**（**与存储格式一致**）。

### 3.10 故障注入矩阵（**每个任务都必须跑**）

> **原则**：**故障必须先于修复存在**。每个注入点都要有一条**断言「后果是什么」**的用例，
> 而不是「跑完不崩就算过」。

| # | 注入点 | 注入方式 | 期望后果 | 守恒量 |
|---|---|---|---|---|
| `F-1` | 主库 **COMMIT 失败** | 让事务提交返回错误 | **JSONL 一行都不写** | 审计流不描述不存在的代 |
| `F-2` | 月库**写入失败** | 月库目录**只读** / 磁盘满 | **主库行不被瘦身**；`archive_failed` +1 | 记录**不丢** |
| `F-3` | 月库**被锁** | 另一个连接持有写锁 | 写入**等待**（`busy_timeout`）后失败 ⇒ 同 `F-2` | 记录**不丢** |
| `F-4` | 通道**填满** | 预填 10,000 条 | `dropped` +1；主库物化**不阻塞** | 主库吞吐**不受影响** |
| `F-5` | 记录目录**不可写** | `chmod` 只读 | 写错误计数 +1；**主库不受影响** | 主库吞吐**不受影响** |
| `F-6` | 进程在「写月库后、瘦身前」**崩溃** | 注入 `panic!` | 启动时**对账任务**把该行**重新归档** | 月库与主库**最终一致** |
| `F-7` | 进程在「`try_send` 后、写盘前」**崩溃** | 注入 `panic!` | 该行**丢失**（**可接受**：审计流可丢） | **仅审计流**缺失 |
| `F-8` | 月库文件**损坏** | 截断文件头 | 读取**报错**，**不 panic**；**不影响主库** | 主库**不受影响** |
| `F-9` | 清理任务指向**越界路径** | 构造 `..` / 绝对路径 / 符号链接 | **全部拒绝** | **不误删任何文件** |
