## 2. 最优方案：**方向池 = 唯一选池真相源**

### 2.1 目标形态

```text
                    ┌─────────────────────────────────────┐
                    │  manager_v4_directional_exchange_pools│
                    │  （唯一选池真相源 · 池 × 方向）        │
                    └─────────────────────────────────────┘
                          ▲          ▲          ▲
        写入同源          │          │          │
        纪律 2            │          │          │
              ┌───────────┘          │          └───────────┐
              ▼                      ▼                      ▼
      candidate_edge          candidate_exchange        closed_loop
      （退化为投影）           （退化为投影）            （三跳读同一源）
              │                      │                      │
              └──────────────────────┴──────────────────────┘
                                     ▼
                          review / broadcast（不变）
```

**关键**：`candidate_edge` 与 `candidate_exchange` **不再自行排序**，
它们的排序逻辑（`recommend_direction` / `pool_score`）**退化**为读方向表的序位。

### 2.2 为什么这是最优的（而不是"再加一层"）

| # | 理由 | 依据 |
|---|---|---|
| **1** | **口径不一致从"靠纪律维持"变成"结构上不可能"** | 三跳读同一张表同一列 ⇒ 中间跳不再是特例 |
| **2** | **方向从"运行时反推"变成"存量"** | 消除缺陷 3（`resolve_hop_direction` 错一步即硬失败） |
| **3** | **消除两份方向字符串格式** | `A>B` / `A->B` ⇒ 结构化 `direction` 列（缺陷 2） |
| **4** | **消除按锚点复制池行** | 方向池是**池维度**（无锚点）⇒ 缺陷 4 自然消解 |
| **5** | **它不引入任何新的链上事实** | 纯投影 ⇒ 零新增 RPC（`02 §3.5`） |

### 2.3 三条纪律是方案的**真正承重墙**（`04 §7`）

| 纪律 | 内容 | 失效后果 |
|---|---|---|
| **1 · 真相源唯一** | `direction` 的唯一真相源 = 方向表；hop 的 `pool_id`/`base_pool_id` 是**投影** | 出现第二个真相源 ⇒ 慢慢漂移 |
| **2 · 写入同源** | 四个字段在**同一次写入**里从**同一行方向池**解构 | 分两次写 ⇒ 物理上可能不一致 |
| **3 · 重建期复验** | I-7 / I-11 / I-12 断言，不成立即**拒绝发布** | 拓扑错误被写进库 |

> **纪律 2 的写法**（`04 §7`）值得强调 —— 它用**代码结构**消灭了不一致的可能：
> ```rust
> let DirectionalPool { base, direction, directional_pool_id, .. } = pool;  // 一次解构
> ClosedLoopHopRow {
>     directional_pool_id: directional_pool_id.clone(),
>     hop_direction: direction.as_i64(),
>     pool_id: base.pool_id.clone(),      // 投影
>     base_pool_id: base.pool_id.clone(), // 投影
> }
> ```
> **同一个函数体、同一行方向池** ⇒ 物理上不可能不一致。

## 4. **需要重新裁定的三个设计取舍**（引入方向池后浮现）

> 这三项是 `01`~`04` 已给出处理意见、但**值得使用者复核**的点。

### 4.1 `liquidity_index` 的去向 —— **建议：从"选池"彻底退出，但保留"准入"用途**

现状：中间跳用它**排序**（已证伪，秩相关仅 0.09）；
同时 `abnormal_reasons` 用它做**准入**（`liquidity_index_not_positive`）。

**建议**：
- **排序**用途：随 `pool_score` 一并删除（P3）⇒ 中间跳不再用它选池；
- **准入**用途：**保留**，但**降级为"健康信号"而非"质量信号"** ——
  它能识别"这个池的流动性状态异常/缺失"，这仍然有用；
  只是**不得**再被解读为"这个池更深"。

**理由**：一刀切删除会损失一个有效的健康信号；保留排序用途则会保留本方案要消除的缺陷。
**分清"排序"与"准入"两种用途**是最干净的切法。

### 4.2 方向量与排序的耦合 —— **建议：保持现状（主序/次序分离），但补一条不变式**

现状（`02 §3.3`）：主序 = `directional_output` → tick 序 → fee → pool_id；
**次序** = `input_capacity_raw`（容量门禁输入，**不参与主序**）。

**这个分离是对的**，理由：`input_capacity_raw` 是**原始数量**，
跨代币对比较是**单位错误**（`01 §4.2`）⇒ 它天然只能在 `(pair, direction)` 内作次序。

**建议补充的不变式**：新增 **I-8'**（暂编号）：
> `pair_direction_rank` 的主序**不得**被 `input_capacity_raw` 影响 ——
> 即"容量大的池"**不得**因此被排到前面。

**理由**：这条不变式把"主序/次序分离"从**文档约定**变成**可执行断言**，
防止后续有人"顺手"把容量并进主序 —— 那会**静默改变**两侧跳的现有行为（`recommend_direction` 一致性被破坏）。

### 4.3 `pair_direction_rank` 的作用域 —— **建议：确认维持 `(pair_key_id, direction)`，但要显式登记它的"非全局性"**

现状：序位在 `(pair_key_id, direction)` 内计算（`02 §3.3`、`I-6`）。

**这是正确的**（跨代币对比较 raw 容量是单位错误），
但**风险在于误用** —— 若有人把 `pair_direction_rank = 1` 当成"全局最好的池"，
就会跨代币对做出错误选择。

**建议**：在 `02 §3.3` 补一句**显式警示**（该文档已有 `idx_v4_directional_pools_direction` 索引，
其注释写明"**仅用于展示与诊断**，选池一律以 `(pair, direction)` 内的序位为准" ⇒ 方向已对，
只是需要在**序位列的注释**上再钉一遍）。

## 5. 一个**更省事**的替代方案，为什么**不行**

**替代方案**：把方向池做成**数据库视图**（`CREATE VIEW`），而不是物化的表。

| 维度 | 视图方案 | 表方案（推荐） |
|---|---|---|
| 写入成本 | **零** | 一次物化（幂等） |
| 漂移风险 | **零**（永远现算） | 靠版本+校验和门禁 |
| **I-9「两行除方向字段外逐列一致」** | ❌ **无法验证**（视图无持久化行） | ✅ 可断言 |
| **跨层引用（hop → 方向行）** | ❌ **无法引用**（视图不可作外键目标） | ✅ `directional_pool_id` 可解析 |
| **P2 的 `directional_pool_id` 列** | ❌ **无处落** | ✅ 落库 |
| **性能** | 每次取池都重算 | 一次算、多次读 |

**决定性的一条**：方案要求闭环 hop **引用**方向行（`directional_pool_id` + `hop_direction`）
并**在重建期复验**（I-7 / I-11 / I-12）。**视图无法作为引用目标，也无法被复验。**
⇒ **表方案是唯一可行的**。这一条已在 `02 §3.1` 用 `ux_v4_directional_pools_id` 索引
（为将来升级为硬外键预留）体现。
