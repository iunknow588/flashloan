## 1. 目标与完成定义

构建链无关的代币→池→闭环→复核→广播自愈链。所有交易量、容量和盈亏结论由 Rust 内核使用当前内存状态计算；
只有证据完整、状态新鲜、利润为正且权限符合时才允许进入广播。

生产稳定须连续 3 个至少 30 分钟的窗口满足 `blockers=[]`、`missingValue=0`、`positive>0`，
且复核、广播请求和链上回执可关联。

### 2.2 v12.9 新增的根因结论（**架构层，不是待办**）

第 63 轮实测确认了一条此前未被记录的事实，它改变了本项目的**架构认识**：

> **Rust 生产工作线程一直在产出完整复核**（live `cow_execution_reviews` 48,532 行且持续增长，
> 每行带完整 `bestAmount` 判定、完整 `probeRecords` 阶梯、签名盈亏与 `loopKey`），
> **但没有任何生产路径把这些复核发布到 Review Manager 的复核库**
> （`manager_v4_reviews` 停在 164 行 / 150 `data_incomplete`）。

**三条架构含义**：

| # | 含义 | 对设计的约束 |
|---|---|---|
| **A-1** | **调度、计算、记录、发布是四段不同的链路**。前三段都已存在且合规（Rust），**第四段不存在** | 后续新增任何"复核产出"能力时，必须同时回答"它发布到哪里"。**只写 live 表不构成"复核已产出"** |
| **A-2** | **Review Manager 的写入口是全量替换语义**（`replace_review_rows` 先 `DELETE` 再全量 `INSERT`） | ⇒ **部分提交是数据损坏**。发布必须**聚合到覆盖全集**。这决定了 `TASK-165` 的实现形状 |
| **A-3** | **`consumers_need_rebuild` 是下游未重建的派生标志**，不是独立缺陷 | ⇒ 顺序必须是 **发布 → 物化 → 自然清除**。**手工清标志等于掩盖问题** |

**A-1 的一般化表述（写入本计划，作为后续所有工作的判定标准）**：
> **一个"产出"只有在其被 Manager 发布并可被 Manager 接口读取时才算产出。**
> 写进中间表、留在内存、或只存在于某个 worker 的局部变量里，**都不算**。

## 3. 架构约束

### 3.1 内存对象处理约束（MIO-1..MIO-8）

- **MIO-1** SQLite 只在初始化/持久化/审计时读写；review/depth 处理循环不得逐条 SQL 查询业务状态。
- **MIO-2** 全局内存上下文持有池、闭环和运行时快照；运行期计算只消费该上下文。
- **MIO-3** token decimals 是内存上下文的一部分，金额缩放必须使用对应 token 的精度。
- **MIO-4** WSS/监控器更新内存快照；状态版本和新鲜度必须随计算证据传播。
- **MIO-5** Review Manager 通过 Rust 内核/管理接口消费业务状态，不由 Python 另建权威路径。
- **MIO-6** Python 只消费内核发布的金额、利润、路线和状态，**不重算、不拼接闭环身份**。
- **MIO-7** Rust 内核发布有符号利润及 `signedPnl.amount`，包含 raw 值、币种/精度、来源和测量状态；测得零与未测量严格区分。
- **MIO-8** 每条链使用独立 SQLite、chain ID、RPC、权限和内存状态，禁止跨链读取或写入。
- **MIO-9** 记录读取由 **Rust Manager 拥有**：复核 / 广播 / 闭环目录 / 闭环身份的读取走 Manager 接口；**Python 侧不得直查 manager 拥有的表**，**不得**把记录缓存为内存对象当权威；Manager 未发布的读数**如实显示为未测量**，**不得**由 Python 代为推导。

**补充（v12.9）**：单次请求内的**展示快照**可以存在，但**不得**作为后续读数的来源，
**不得**跨请求保留，**不得**用内存对象覆盖 Manager 已发布的内容。

### 3.2 闭环身份与路径匹配

- 闭环身份由**内核**计算并随路线结果发布，**Manager 存储**它，消费者**读取**它。
- **身份是可选的**：对未发布任何闭环的目录发布，路线**没有**身份 —— 这是**缺失**，不是**不匹配**。
- 路径匹配必须**精确有序**；**未匹配不得猜测**。

### 3.3 级联与计算边界

- 金额 / 容量 / 利润**只能**由 Rust 内核从**当前内存状态**计算。
- **禁止**用历史数据回填掩盖当前计算缺陷。
- **禁止**把复核阶段的预期金额当作已实现盈亏。

### 3.3.0 写库分类学：**基础框架库** vs **动态记录**（**绑定性**）

| 类别 | 内容 | 处置规则 |
|---|---|---|
| **基础框架库** | DDL / migration / 表结构 / 列 / 约束 / 索引 / 视图 | **验证通过 ⇒ 必须实盘写入目标生产库。**不需额外授权。 |
| **动态记录** | review / depth / ladder / PnL / closed loop / broadcast attempt 等测量与运行记录 | **可以不写**；要写时按任务清单 §3 的授权流程走 |

**判定口径**：不改变任何测量值、只让结构与代码对齐 ⇒ 基础框架库；
写入的是某时刻的测量结果 ⇒ 动态记录。

**v12.9 落点**：`TASK-165` 交付**代码**（基础框架性质的实现），**不是**写库动作；
它**触发**的复核物化属**动态记录**，**必须**单独授权。**两者不得混为一谈。**

### 3.3.1 ETH 与 WETH 是两个独立资金锚点（**不做特殊处理，不做互相转换**）

- 结算对象是**资金锚点**，不是 `signed_pnl_currency`。
- **不新增** `isNative` / `isAddressZero` 分支；**不引入**任何包装 / 解包能力。
- 跨锚点借用**必须被拒**（第 60 轮实测：39,466/39,466 全被拒）。

### 3.4 `pool_depth_audit` 分类口径（已变更，随代码归档）

池深度分类以**当前** `pool_manager` 的分类实现为准，历史分类表**不再**作为判定依据。

### 3.5 【R-164-A / R-164-B】调度与发布归属（**绑定性 · v12.9 强化**）

> **R-164-A**：*"无论是生产队列还是消费队列都是 RUST 实现的，PYTHON 仅仅负责数据展示。"*
> **R-164-B**：*"UI 触发的手动复核以及广播，仅仅调用 RUST 侧的接口……且RUST侧仅仅把排队等待时间修改为0，
> 后续统一处理的。不需要特殊的处理流程。"*

**已有实现（第 61 轮闭合，本版不改）**：

| 能力 | 位置 | 事实 |
|---|---|---|
| 复核主线程 | `flashloan/tools/review_manager/src/runtime.rs` `ReviewSupervisor`（`:26-83`） | **专属主线程** + `mpsc::channel` + 消费循环 |
| 工作线程池 | 同文件 `ReviewRuntime`（`:108-171`） | 有界池 + `Condvar` + RAII `ReviewPermit` |
| 生产接入 | `flashloan/rs-src/src/worker_pool.rs` `:447` / `:4308` / `:4478` / `:4676` | 每组一个常驻线程 `rust-closed-loop-{seq}`；主线程 `review-manager-main` |
| 手动复核 / 广播 | `worker_pool.rs` `trigger_immediate_review_inner` `:4414` | **仅清零等待时间** → 统一流水线后续处理。**无特殊流程** |
| Python 回退闸门 | `flashloan/src/dex/runtime/dex_closed_loop_review_queue.py` | `native_rust_enabled` 探针 + `_rust_owns_scheduling()` **fail-closed** |

**v12.9 强化的第三条（从 R-164-A 推导，**不是新规则**）**：

> **R-164-A 要求"调度与消费在 Rust"。**
> **"把 Rust 算出来的结果发布到 Manager 库"同样属于 Rust 的职责**，
> 否则 Python 侧就不得不承担"调度 + 计算 + 发布"三者中的发布一环，
> **实质上就回到了 Python 实现记录写入**，**违反 R-164-A**。

因此 `TASK-165` 的方向**不是**"给 Python 加一个发布器"，**而是**"让 Rust 把已经算好的东西发出去"。
**这两者在代码上是天壤之别，在架构上是同一件事。**
