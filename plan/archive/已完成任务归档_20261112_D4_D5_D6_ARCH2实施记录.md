### 0.6.7 ARCH-2 实施记录（2026-11-12，已完成）

**背景**："盲发/直发"（废除链下 Quoter、直推排序器）的唯一前提是
**链下计算与链上计算逐位等价**。此前只有单跳数学
（`v4_pool_capacity.py`），缺多跳串联与等价回归，因此"盲发"不成立。

**落地**：`flashloan/src/dex/intent_trade/chains/robinhood/v4_multihop_simulator.py`

| 能力 | 契约来源 | 说明 |
|---|---|---|
| `flash_fee(a, bps)` | `RobinhoodPausedFlashLoanExecutor.sol:1092` `_fee` | `(a*bps + 9999)/10000`，**向上取整**；向下取整会让链下比链上乐观，可能报出链上会回滚的"盈利" |
| `required_repay(a, bps)` | 同上 `:1097` `_requiredRepay` | `a + fee(a,bps)` |
| `simulate_route(...)` 结算 | 同上 `:702` `_handleV4FlashAccountingCallback` | `profit = max(0, balance - requiredRepay)`；`executable` 当且仅当 `profit > 0` |
| 单跳输出 | Uniswap V4 规范公式 | 复用 `v4_pool_capacity.swap_amount_out`（与 Rust `fallback_swap_amount_out` 同源同舍入） |
| `route_min_capacity_raw(...)` | 木桶效应 | 路径级最小容量，token 计价，**零 USD 依赖** |

**关键口径澄清（实测）**：

- **生产合约** `RobinhoodPausedFlashLoanExecutor` 的利润口径是
  `balance - requiredRepay`（**含 flash 费**），模拟器与之逐条对齐。
- **测试网合约** `OfficialV4FlashArb.sol:590` 的利润口径是
  `outTz - amountIn`（**不含 flash 费**），`minProfit` 是门槛而非费用。
  两者**不是同一口径**，模拟器**以生产合约为准**；若将来切到测试网，
  需显式切换 `flash_fee_bps=0` 的结算分支，不可混用。

**回归**：`flashloan/app_runtime/tests/unit/test_v4_multihop_simulator.py`（**23 项**）

- 费用/还款与合约 `_fee`/`_requiredRepay` 逐向量对齐（含向上取整断言）
- 单跳输出与 `v4_pool_capacity.swap_amount_out` 一致
- 单跳输出与 **Rust `fallback_swap_amount_out` 独立复刻**一致（防两侧同时漂移）
- 结算口径、非闭合路径拒绝、token 断链拒绝、零输入拒绝、空路由报错
- 路径级最小容量取最紧一跳；容量与流动性**成正比**（token 计价）
- **架构护栏**：模块**不读取** USD 价格 / TVL / 网络 / 存储（按**可执行代码**扫描，
  非文档散文）；除价格冲击观测外**全部整数运算**

**负向对照（证明护栏真的会响）**：注入 USD 价格读取 / 注入网络 import /

### 0.6.6 D5 / D6 实施记录（2026-11-12，已完成）

**背景**：D4 让阶梯能按容量起步，但**容量数据从未到达尺寸计算路径**。
W6 副本演练暴露两个 P0 缺陷，二者叠加后 D4 的容量感知起点**仍会走回退分支**。

#### 缺陷 D5（P0）——`depth --apply` 只写快照表，候选表永不更新

- **根因**：`write_depth_snapshot()` 只 UPDATE `v4_exchange_pool_liquidity_snapshots`；
  `dex_candidate_pools` 仅由 `upsert_eligible_pool_rows()` 写入，而该函数
  只在 `refresh_pair()` / `refresh_key()` 路径触发，**`refresh_depth()` 从不调用**。
- **为什么致命**：尺寸计算路径读的是**候选表**
  （`core/db/builders.py:688`、`:823` → `"balances": _json_loads(pool.get("balances_json"))`），
  经 `dex_quote_evidence_size.py:172 _liquidity_cap_raw()` 消费。
  快照表填得再满也不起作用。
- **副本库实测（修复前）**：
  `snapshot balances 94/4669`、**`dex_candidate_pools.balances_json 0/47`**，
  而 47/47 候选池**都有**已测快照 ⇒ 纯属传播缺失，非采集缺失。
- **修法**：新增 `pool_manager/src/lib.rs::propagate_balances_to_candidate_pools()`，
  在 `refresh_depth()` 的 `options.apply` 分支中以**相关子查询**把快照载荷
  UPDATE 进 `dex_candidate_pools.balances_json`，并输出 `candidateBalancesPropagated`。
  **无实测快照的行保持原样**（缺失测量必须保持缺失，不得伪造为零）。
- **修复后副本库实测**：`candidateBalancesPropagated=47`，
  `dex_candidate_pools.balances_json` **47/47 非空**。

#### 缺陷 D6（P0，潜伏）——候选表 `balances_json` 写的是 token **地址**

- **根因**：`upsert_eligible_pool_rows` 原写
  `"token0": pool.token0, "token1": pool.token1`，二者来自
  `v4_exchange_pools.token0/token1`，即 **`0x` 地址**。
- **为什么致命**：消费端 `_pool_borrow_side_amount()` →
  `_positive_decimal_or_none()` → `_decimal()` 对 `0x...` **抛
  `ValueError("invalid decimal amount")`**（而非返回 `None`）；
  `rust_closed_loop.py:3509` 调用 `_liquidity_cap_raw()` **无 try/except**，
  ⇒ 候选表一旦被填充，复核循环会因未捕获异常中断。
- **潜伏原因**：此前候选表 `balances_json` 恒为 `{}`，该异常从未被触发；
  D5 修好传播后必然暴露，故两者**必须同批修复**。
- **修法**：`token0`/`token1` 改用**实测快照数量**；地址身份保留在显式键
  `token0Address`/`token1Address`；无实测快照时写 `Value::Null`（安全退化到 `None` 回退）。
