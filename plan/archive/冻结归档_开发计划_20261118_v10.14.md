## 2. 项目目标与完成定义

### 2.1 总目标

交付一个可审计、可回滚、默认 fail-closed 的 Robinhood 主网套利闭环：Rust manager 负责 token、pool、
edge、exchange、closed-loop、review、broadcast 和 composite 权威逻辑；Python 仅通过
RuntimeCore/Manager API 调用；生产写入、Authority 切换和广播均受显式授权与停机窗口控制。

### 2.2 版本 1 范围

允许：

- 多跳闭环，但当前业务闭环固定为恰好 **3 hops**。
- 每一跳按最终实际输入量进行 single-tick 精确复核。
- YC、Y-Z、ZC 等既有闭环结构，由 `closed_loop_manager` 统一管理。
- 链上 Quoter 仅作为影子对照、偏差归因或受控降级路径。
- 跨 tick 接口和离线算法保留，作为后续版本输入。

禁止：

- 跨 tick 结果进入候选排序、最佳交易量、收益复核、广播或生产闭环。
- Python 新增或保留 token/pool/route/review/broadcast 权威判断。
- 动态费率池进入备用、观察、候选、推荐或闭环角色。
- 外部 fiat 价格源、TVL、相关性、`li<1` 或 `market_depth_exhausted` 成为池深准入依据。
- 未授权写生产库、切换 Authority、广播或替换被锁定二进制。

### 2.3 最终完成定义

系统同时满足以下条件才可宣布版本 1 完成：

1. 每个生产结论只有一个 Rust authority，Python 重复业务判断已退役并受架构守卫约束。
2. `core4 = [core, stocks]`、`candidate_exchange = [core, stocks]` 成为唯一主路径 scope；
   扩展库仅审计，测试库仅保留数据库与启动校验用途。
3. 所有生产池满足固定费率 `0 < fee <= 30000`、非动态费率、hook/深度规则，生产池表总量不超过 3000。
4. 候选池每方向 TOP-5、推荐池每方向 TOP-1，推荐池为候选池确定性子集，消费者不跨状态版本。
5. 每条闭环恰好 3 hops，所有 hop 命中 active candidate pool，并按最终输入量证明 single-tick。
6. P0-8/P0-9/P0-2/P1、ARCH-2b/D4-d、ARCH-3、ARCH-4-B/C、W6/W7/W8、生命周期与运维门禁全部通过。
7. ARCH-4 影子旁路连续 7 天、纯内存观察连续 30 天，且不可归因差异为 0。
8. 生产写入有授权、备份、恢复演练、checksum、幂等报告和明确回滚点。
9. 回归、编码、证据、观察和广播门禁全部通过，活动 checklist 已清零并完成归档。

## 4. 架构与口径硬约束

- 权威业务逻辑位于对应 Rust manager；Python 只通过 RuntimeCore/Manager API 间接工作。
- 精确数学复用 Rust `pool_manager` / Uniswap SDK；版本 1 每跳只允许 single-tick，跨 tick 仅保留接口。
- fixed fee 范围 `0 < fee <= 30000`；动态费率池在所有池角色中排除。
- 候选排序为 normalized single-tick 精确输出降序 → 方向 tick 顺序 → fee → pool id。
- USDG 在经济计价上替代 USD，但外部 fiat 价格源与 TVL 不得进入池深准入。
- 股票代币受 USDG 可兑换性约束；核心/测试仅在 token 分类层豁免部分估值门禁，
  但测试库不得因此进入候选、观察、闭环或广播；扩展代币只做完整性与传递关系审计。
- 成熟 SDK 可复用，但一个生产结论只能有一个 Rust authority；Python 不得成为第二 authority。
- scope 契约：`core4 = [core, stocks]`、`candidate_exchange = [core, stocks]`；扩展库与测试库不得进入主路径。
- 测试代币允许保留在数据库和内部启动校验中，但不得展示在 UI，也不得进入候选、观察、闭环、统计或广播。
- 无显式授权不得写生产库、切换 Authority、广播或替换被锁定二进制。
- 数据分层：token 与 pool 基础数据是长期权威事实；review / submission / broadcast 记录是可再生瞬时运行记录。
- 不得为 review / submission / broadcast 记录扩展长期持久化 schema。
- 瞬时记录清理必须走管理器清理接口，不得由 Python 直接写业务库。
- `liquidity` / `capacity_raw` 等 uint128 十进制值禁止以 SQLite `INTEGER` 或 Rust `i64` 读取、比较或排序。

### 4.1 内存对象处理约束（MIO-1..MIO-8，强制）

本节是**架构硬约束**，不是建议。任何工作包、缺陷修复或新增功能都必须遵守；
违反本节的实现即使功能正确也判定为**不合格**，必须在本轮内修正。

#### 4.1.1 数据流约定

系统只有一条合法数据流：

```text
SQLite（系统初始化时读取一次）
        ↓
全局内存对象（RuntimeCore / WorkerPool ContextCache / 闭环目录等）
        ↓ 实时数据由 WSS 监控持续更新内存对象
业务处理（全部通过内存对象直接计算，不回查数据库）
        ↓ 结果经队列传递
队列 → 对应处理模块 → 回写 SQLite（唯一持久化出口）
```

| 编号 | 约束 | 验收方式 |
|---|---|---|
| MIO-1 | SQLite 只在**系统初始化/刷新**时读取。处理路径**不得**逐次查询数据库 | 静态审计：处理函数内不得出现按需查询 |
| MIO-2 | 实时数据（WSS 监控得到的链上状态）必须写入**全局内存对象**，处理模块读内存对象 | 内存对象持有该字段，且处理路径只读内存对象 |
| MIO-3 | 最佳交易量、闭环容量、池状态、代币元数据等**全部业务数据**都由内存对象提供 | 处理函数的入参来源必须是内存对象 |
| MIO-4 | 处理结果**经队列**传递给对应处理模块，再由该模块落库 | 存在明确的队列发送点与落库点 |
| MIO-5 | Python 只做**纯消费与展示**：读取内核已产出的结构，不得拼装业务对象 | Python 不得出现业务字段的拼接/推导逻辑 |
| MIO-6 | Python 不得成为第二 authority：不得重建闭环身份、容量、盈亏等权威值 | 违规拼装必须删除，改为消费内核字段 |
| MIO-7 | 闭环身份（loop key）、闭环容量、复核盈亏必须来自**闭环管理器内核对象** | 值与 manager 表逐字一致 |
| MIO-8 | 链隔离是**硬边界**：每条链独立 SQLite，任何查询必须同时带 network + chain_id | 跨链查询即判定失败 |

#### 4.1.2 明确禁止的实现方式

以下写法在本项目中**一律禁止**，即使能跑通：

| 禁止 | 原因 | 正确做法 |
|---|---|---|
| Python 用路由地址拼接 `loopKey` | Manager 可能对同一 symbol path 发布多个 loop，自拼会张冠李戴 | 消费内核发布的 `closedLoopKey` |
| Python 调用 manager API 取容量后再塞回 route | 违反 MIO-5；且形成「Python 组装 → Rust 计算」的回环 | 内核在 worker 内直接读内存对象 |
| Rust 处理函数内每次 `read_closed_loop_snapshot` | 违反 MIO-1 | 闭环目录并入 `ContextCache` 内存对象 |
| Python 依据 `attempts` 推导 `signedPnl` / `executable` | 违反 MIO-6 | 由 Rust 内核在结果中直接给出 |
| Python 依据路由地址计算单 tick 容量 | 违反 MIO-7 | 消费 Manager 发布的折叠容量 |
| 任何一层用路由地址**兜底重建** `loopKey` | 违反 MIO-6；兜底路径同样会张冠李戴 | 无身份即**不予复核**，由编排器重新复核该 loop |
| 内核只发布 raw 盈亏、不发布人类可读金额 | 复核 DTO 缺 `signedPnl.amount`，复核记录无法落库 | 内核按内存对象中的 `token_decimals` 自行换算并发布 |
| 内核只把盈亏发布在**顶层**，不发布到 `runArbitrage` 内 | 复核管理器读的是嵌套对象，字段缺失即拒绝 | 内核同时发布到顶层与 `runArbitrage` 内（同一结论） |
| 处理路径按需回查 `token_decimals` | 违反 MIO-1 / MIO-3 | 位数并入内存对象，初始化时读取一次 |

#### 4.1.3 复核证据的内核发布形态（强制）

复核管理器对每条证据的字段要求是**固定的**，内核必须一次性把结论发布到位，
任何一层都不允许"补齐"或"折算"：

| 证据字段 | 要求 | 权威来源 |
|---|---|---|
| `evidence[].loopKey` | 非空，且必须是闭环管理器已发布的 key | 内核 `closedLoopKey` |
| `evidence[].runArbitrage.ok` | bool | 内核 |
| `evidence[].runArbitrage.executable` | bool | 内核（合约是否接受该路由） |
| `evidence[].runArbitrage.signedPnl.raw` | signed raw 字符串 | 内核 |
| `evidence[].runArbitrage.signedPnl.amount` | **f64**（人类可读金额） | 内核按 `token_decimals` 换算 |
| `evidence[].runArbitrage.signedPnl.currency` | 借款代币符号 | 内核 |
| `evidence[].runArbitrage.signedPnl.address` | 借款代币地址 | 内核 |
| `evidence[].runArbitrage.signedPnl.unit` | `"raw"` | 内核 |
| `evidence[].runArbitrage.signedPnl.source` | `"native_rust_ladder"` | 内核 |
| `evidence[].runArbitrage.blockNumber` | 区块高度 | 内核 |
| `evidence[].runArbitrage.diagnostics` | 诊断数组（可为空） | 内核 |

`amount` 的换算只能由内核完成：代币位数随链而异，属于链级内存对象的一部分，
由内核在初始化时读入 `ContextCache`，在复核时直接使用。

#### 4.1.4 与既有约束的关系

- MIO-1 与 §4「权威业务逻辑位于对应 Rust manager」一致，并进一步明确**读取时机**。
- MIO-5 与「Python 只通过 RuntimeCore/Manager API 间接工作」一致，并进一步明确
  Python **不得**成为数据组装层。
- MIO-7 与「一个生产结论只能有一个 Rust authority」一致，是其在闭环层的具体化。
- 违反 MIO 的实现**不得**计入任何已完成工作包；相关任务在本轮内必须回到未完成状态。

### 4.2 代币缺失信息时的处理规则（强制）

代币层是整条链的**根**：候选池、观测池、闭环、hop 全部按代币地址引用代币。
一个既没有可用符号、也没有可用精度的代币，不是「先留着以后再说」的行，
而是一个**缺陷**，它会被下游每一层继承。

因此代币层的处理规则是**二选一，没有第三条路**：

| 情况 | 处理 | 责任工具 |
|---|---|---|
| 能找到可用的符号与精度 | **修复**该代币 | `token-manager materialize-libraries` / `POST /v1/tokens/resolve` |
| 找不到可用的符号与精度 | **删除**该代币，并同步删除所有引用它的记录 | `token-manager prune-incomplete-tokens` |

**「缺少关键信息」的判定边界（只有必备信息）**：

| 字段 | 缺失时 | 说明 |
|---|---|---|
| `token_symbol` | **删除** | 没有符号就无法在界面上区分资产 |
| `token_symbol` 为工厂占位符 | **删除** | `0X########` 与 `UNRESOLVED:0X########` 都是占位符，不是名字 |
| `token_decimals` | **删除** | 没有精度就无法把 raw 金额换算成人类可读金额 |
| `token_decimals` 超出 0..=36 | **删除** | 荒谬的精度等价于没有精度 |
| `token_name` | **保留** | 显示名是可选信息，缺它不影响计价与路由 |
| `token_kind` / `is_native` / `is_stable` / provenance | **保留** | 同上，都是可选信息 |

判定只认上表，**不因任何其他字段的缺失而删除代币**，以免该命令退化成无边界的清理。

#### 4.2.1 删除时的级联顺序（强制）

删除一个代币必须**连同它的依赖一起删除**，否则库里会留下指向不存在代币的行：

```text
1. v4_closed_loop_optimizations   （引用 hop）
2. v4_closed_loop_hops             （引用 loop）
3. v4_closed_loops                 （引用 chain_tokens: anchor_address）
4. v4_exchange_pool_liquidity_snapshots（引用 pool）
5. v4_exchange_pools               （引用 chain_tokens: token0/token1）
6. dex_candidate_* / market_observation_*（引用 chain_tokens）
7. chain_tokens                    （最后删本体）
```

外键是 `NO ACTION`（限制）而非 `CASCADE`，所以**顺序错了数据库会直接拒绝**。
闭环的 `path_addresses_json` 里也含代币地址，因此闭环是否受影响要**同时**检查
`anchor_address` 与路径中的每个地址。

#### 4.2.2 该命令的其它约束

- **链隔离**：只能剪自己那条链的库，`chain_id` 不符直接拒绝。
- **必须先试运行**：不带 `--apply` 只报告，不写库；编排器的 `--mode check` 走的就是只读路径。
- **闭环目录由闭环管理器拥有**：剪枝只剪**引用了**该代币的闭环，不重建闭环库。

### 4.3 核心 vs 链特定的分离约束（强制，v10.11 新增）

> **系统数据与处理流程是分开的，处理流程不得依赖具体链。**
> 这不是风格偏好，而是本系统判定缺陷归属与决定修复位置的**唯一口径**。

#### 4.3.1 为什么需要这条约束

一条链上出现异常时，只有两种可能：**流程本身错了**（核心缺陷）或
**这条链的数据内容不满足要求**（链特定数据条件）。
两者的修复位置、影响面和授权边界完全不同：
核心缺陷影响**所有链**，链特定条件只影响**一条链**。
把链特定条件误判为核心缺陷，会导致为一条链在核心里加特判，
最终使编排器失去链无关性——这正是第 33 轮要根治的问题。

#### 4.3.2 四步判定流程（缺一不可）

| 步骤 | 动作 | 判据 |
|---|---|---|
| 1 | 在**两条链**上用**同一条代码路径**复现 | 两条链缺陷签名一致 → 指向核心 |
| 2 | 定位缺陷代码，检查是否引用链标识（`chain_id` / `network` / `market_id` / 地址常量） | 代码内**不含**链标识 → 指向核心 |
| 3 | 检查缺陷是否由该链的**数据内容**触发（深度、精度、符号、费率、流动性） | 数据触发 → 链特定 |
| 4 | 验证修复只改**核心代码**或**共享策略文档** | 改核心后两条链同时受益 → 确认核心缺陷 |

#### 4.3.3 修复位置规则（强制）

| 缺陷性质 | 允许的修复位置 | 禁止 |
|---|---|---|
| **核心缺陷** | 核心代码（Rust 内核 / 链无关的编排器 / 共享策略文档） | 为某条链加特判；只在一条链上打补丁 |
| **链特定数据条件** | 该链的管理工具（代币管理 / 池管理 / 闭环管理 / 复核管理 / 广播工具） | 改核心代码绕过；改共享策略门槛迁就单链 |

- **共享策略文档**（`flashloan/config/depth_policy.json` 等）的任何变更都**全链生效**。
  修改前必须先完成 §4.3.2 的四步取证，证明该缺陷**不是**核心缺陷，
  且不得以"调参"的方式掩盖一个真实的流程缺陷。
- 每条链的 SQLite 是**独立**的：主网 `local_store_4663.sqlite3`、测试网 `local_store_46630.sqlite3`。
  任何查询必须同时带 `network + chain_id`（MIO-8），跨链查询一律判定失败。

#### 4.3.4 第 33 轮的取证实例（本节为范例，不得省略取证）

| 缺陷 | 两链复现 | 代码是否引用链标识 | 修复位置 | 结论 |
|---|---|---|---|---|
| 闭环池解析只查锚点作用域面 | 主网 92 跳不在观察面、88 跳不在候选面；链级表覆盖 36/36；测试网同一路径 | 否 | `market_observation_core.py` 链级回落 | **核心缺陷**（主网 0 → 6 序列） |
| Rust 内核准入判决未发布到链级快照 | 主网 `kernelAdmitted` 覆盖 0/2480；测试网同构 | 否 | `rs-src/src/evidence.rs` + `tools/pool_manager/src/*` | **核心缺陷** |
| 测试网闭环池实测为 `dust`/`shallow` | 仅测试网；逐跳判决 38/38 闭环全被挡 | 判决由共享策略给出 | 测试网池管理工具补深度 | **链特定数据条件** |

> 结论：**主网的问题就是核心的问题**——它同时也是测试网的问题，只是测试网还额外叠加了链特定数据条件。

#### 4.3.5 与内存对象约束的关系

§4.1 的 MIO-1..MIO-8 规定的是**数据流**，本节规定的是**缺陷归属**。两者共同约束实现：

- 链级回落的实现（`CORE-R33-01`）读取的是**链级内存对象/链级表**，
  不是为某条链额外拼装数据，因此不违反 MIO-1/MIO-3。
- 内核准入判决（`CORE-R33-02`）的**唯一来源**仍是 Rust 内核 + 共享策略文档，
  Python 只消费判决，不新增任何本地阈值，因此不违反 MIO-5/MIO-6。
- 若为修复一条链的数据条件而需要读取别的链的数据，或在 Python 侧重建判决，
  则同时违反 MIO-5/MIO-6/MIO-8，**一律判定不合格**。

### 6.1 P0-8-L 在编排器级联链中的位置（v10.8 修订）

> **编号约定（避免歧义）**：本计划有两套「层」编号，**含义不同**，阅读时务必区分：
>
> - **级联层 L1–L5**：编排器的**判定层**，指
>   `L1 代币 → L2 池 → L3 闭环 → L4 复核 → L5 广播`（见 §7.0.2）。
> - **P0-8-L 段**：主网 scope / 闭环 / 复核 / 广播的一次性收口工作，
>   在 v10.8 中**已并入级联链的 L2–L5**，不再单独作为人工授权段执行。

| P0-8-L 范围 | 在级联链中的位置 | 修复工具 | 回滚粒度 |
|---|---|---|---|
| scope 策略 + 闭环库重物化 + legacy 闭环降级 | **L2 池** → **L3 闭环** | `pool-manager materialize-scope`、`composite-manager materialize-arbitrage` | 闭环库单表恢复 + scope 配置回滚 |
| `manager_v4_reviews` 物化，每条复核带明确盈亏 | **L4 复核** | `POST /v1/reviews/run` + `rereview_missing_pnl` / `fill_missing_reviews` | review 表按 key 批量删除/重建 |
| 广播检测 → 错误修正 → 持续观察统计 | **L5 广播** | `POST /v1/broadcasts/finalize` | 广播开关回退为关闭 |

**v10.7 的三段人工授权模型已被取代**：当时担心「scope、复核、广播混在一个窗口，
广播异常会回滚波及已正确的 scope 与复核数据」。v10.8 用**两级回滚**解决同一问题，
更精确且不需要人工分段授权：

1. **级联层内回滚**：每层修复后立即只读复验该层 `valid`，不通过即回滚**该层**，
   其他层已收敛状态不受影响（`TASK-135` 负责用实际演练证明）。
2. **派生表可重建**：scope / 闭环 / 复核都是**可重建的派生表**，
   重建成本低、幂等性强，不需要额外的授权段隔离。

真正需要隔离的**不可逆动作**（Authority 切换、二进制替换、合约部署）
**仍然保留人工停机窗口**，不因级联模型而放开。

### 6.2 阶段退出准则

## 7. 详细工作包

### 7.0 主网自愈编排器驱动的级联闭环（本版核心新增）

> **本节是 v10.8 的执行主轴。** 前面 §7.1–§7.11 的工作包不是彼此独立的清单，
> 而是由**主网自愈编排器**（`scripts/mainnet_arbitrage_healer.py`）按依赖关系串联起来的
> 一条**自动收敛链**。开发任务 = 补齐这条链上缺失的能力，然后让编排器自己把它跑完。

#### 7.0.1 编排器是链无关机制

自愈编排器**本身与链无关**——它是一种**处理机制**，不是某个链的专用逻辑：

- 它读取一条链的 `(network, chain_id)` scope，套用同一套层级判定与修复动作；
- 判定规则、动作序列、停止条件、证据格式全部与 `robinhood/4663` 无耦合；
- 主网 `robinhood/4663` 与测试网 `robinhood-testnet/46630` 跑的是**同一份代码**，
  只由 `--chain-id` / `--database` / `--network` 参数区分 scope；
- 因此「在主网修好一个问题」和「在测试网验证同一个问题」是**同一条命令**，
  差别只在 scope 参数——这正是第 17 轮测试网全链收敛能反过来证明主网链路的原因。

**结论**：本节所有修复能力都必须在编排器里实现为**通用动作**，
不得写死 `robinhood`、不得写死 `4663`、不得在编排器里散落业务判断。
链特有的事实（地址、registry、RPC）一律通过 chain scope 配置注入。

#### 7.0.2 层级判定与级联修复链

编排器按**固定顺序**自上而下判定，每层只在上层有效后才进入：

```text
L1 代币层  tokens
    │  判定：admitted>0 且 无 missing_decimals / missing_symbol
    │        且 无 funding 地址错配 / 假币 admission / 股票 provenance 非法
    │  修复：token-manager materialize-libraries（+ value-tokens / land-valuations 刷新估值）
    │        或 Manager API POST /v1/tokens/resolve（单币种解析修复）
    ↓
L2 池层  pools
    │  判定：候选池准入通过 且 深度快照新鲜 且 best_amount 非 missing
    │  修复：pool-manager materialize-scope / refresh-key / depth / ensure-depth-schema
    │        （Manager API POST /v1/pools/scopes/repair）
    ↓
L3 闭环层  closedLoops
    │  判定：闭环数>0 且 每条恰好 3 hops 且 hop 全命中 active candidate scope
    │        且 pool_scope_checksum 属 core4 且 consumers_need_rebuild=0
    │  修复：composite-manager materialize-arbitrage
    │        （Manager API POST /v1/closed-loops/rebuild）
    ↓
L4 复核层  reviews
    │  判定：复核总数>0 且 每条带明确盈亏数值 且 best_amount 可回溯
    │  修复：POST /v1/reviews/run（携 expectedUpstream）
    │        + rereview_missing_pnl / fill_missing_reviews / rereview_historical_positive
    ↓
L5 广播层  broadcast
       判定：出现自动广播交易 且 失败交易已被修正 且 盈亏可统计
       修复：POST /v1/broadcasts/finalize（失败尝试终态化）
```

**级联不变式（必须始终成立）**：

| 编号 | 不变式 | 违反时的处理 |
|---|---|---|
| INV-1 | 代币有效 ⇒ 可进入候选计算 | 阻断 L2，先修 L1 |
| INV-2 | 池子有效 ⇒ 闭环可构建 | 阻断 L3，先修 L2 |
| INV-3 | 闭环有效 ⇒ 复核可生成 | 阻断 L4，先修 L3 |
| INV-4 | 复核带明确盈亏 ⇒ 才允许进入广播判定 | 阻断 L5，先修 L4 |
| INV-5 | 广播只在**正净收益**复核上触发 | `no_profit` 不修、不广播 |

**方向性不变式**：修复**只允许从上往下**。不允许「池子无效但先修闭环」，
也不允许「复核缺值但先广播」——那正是第 12 轮 `preflight_running` 永久卡死的根因类别。

#### 7.0.3 循环收敛（Repeat-Until-Healthy）

单次 repair 不足以收敛——每一层修复都会暴露下一层的问题。因此编排器必须**循环**执行：

```text
loop:
    before = build_report(scope)                    # 只读快照
    actions = healing_actions(before)               # 判定层 + 选定动作
    if 上游层无效:
        outcomes += repair(scope, apply)            # 修 L1/L2/L3
        continue                                    # 回到 loop 重新判定
    outcomes += converge_reviews(scope, apply)      # 复核收敛（直到每条带明确盈亏）
    outcomes += fill_missing_reviews(scope, apply)
    outcomes += rereview_historical_positive(scope, apply)
    outcomes += repair_broadcast_failures(scope, apply)   # ★ v10.8 新接入
    after = build_report(scope)
    if after.healthy and after.blockers == []:
        break                                       # 收敛完成
    if 连续 N 轮 after.blockers 不变且无可执行动作:
        break with reason=stalled                    # 停滞，必须升级人工
    sleep(interval)
```

**收敛判据（阶段退出的唯一依据）**：

| 指标 | 阈值 | 来源 |
|---|---|---|
| `layers.tokens.valid` | `true` | `audit_tokens` |
| `layers.pools.valid` | `true` | `audit_pools` |
| `layers.closedLoops.valid` | `true` | `audit_loops` |
| `layers.reviews.valid` | `true` | `audit_reviews` |
| `layers.broadcast.valid` | `true` | `audit_broadcast` |
| `reviews.stats.missingValue` | `0` | `pnl_stats` |
| `reviews.stats.positive` | `> 0` | `pnl_stats` |
| `blockers` | `[]` | `build_report` |
| `productionState` | `healthy` | `build_report` |

**停滞（stalled）判定**：连续 N 轮（默认 N=3）`blockers` 集合不变且
`healing_actions` 返回的动作全部已执行但状态无变化 ⇒ 判定 stalled，
**必须升级人工**，不得无限循环、不得伪造状态。

#### 7.0.5 从资金代币到候选代币的全范围考察

**资金代币（funding token）**是闭环的锚，必须最先确认：

| 检查项 | 检测方式（编排器已有） | 失败修复 |
|---|---|---|
| 官方资金代币地址一致性 | `OFFICIAL_FUNDING_TOKEN_ADDRESS_BY_SYMBOL` 比对 | `POST /v1/tokens/resolve` 修正 |
| 假币（counterfeit）admission | `KNOWN_COUNTERFEIT_FUNDING_TOKEN_ADDRESSES` 扫描 admitted 行 | 移除 admission + `materialize-libraries` |
| `missing_decimals` / `missing_symbol` | `audit_tokens` 的 `missing_decimals` / `missing_symbol` | `materialize-libraries` 重新标准化 |
| 股票 token provenance | `metadata_source='robinhood_assets_api'` + `source_json` 匹配 | `POST /v1/tokens/resolve` |

**候选代币（candidate token）**进入候选集前必须过 **USDG 经济门禁**：

| 检查项 | 工具 | 修复路径 |
|---|---|---|
| USDG 可兑换性（magnitude） | `token-manager value-tokens` | `scripts/refresh_robinhood_token_libraries.py` 探测 |
| 估值落库 | `token-manager land-valuations` | 写入持久估值库 |
| membership 刷新 | `token-manager materialize-libraries` | 按 TTL 重新物化四库 |
| magnitude TTL | `band_robinhood_candidate_usdg_capacity.py` 读估值时门禁 | 过期即阻断，不得用陈旧估值 |

**候选代币 → 池 → 闭环的贯通考察**（`TASK-129` 必须覆盖的矩阵）：

```text
资金代币集合 F（官方地址唯一、decimals/symbol 完整）
   ∪ 候选代币集合 C（USDG 门禁通过、估值新鲜）
        ↓  配对
   候选池 P（固定费率 0<fee<=30000、非动态、hook=0、深度已确认、pool_id 可重算）
        ↓  三跳组合
   闭环 L（恰好 3 hops、hop 全命中 P、pool_scope_checksum ∈ core4）
        ↓  逐 hop 最终输入量 single-tick 复核
   复核 R（每条带明确盈亏、best_amount 可回溯、不跨 tick）
        ↓  正净收益
   广播 B（交易成功、盈亏可统计）
```

任一环节为 0（空集）都必须在编排器报告里**显式呈现为 0**，而不是「跳过」——
空集是上游断裂的信号，沉默会让收敛循环误判为健康。

#### 7.0.6 生产库写入的自动解除（不再长期关闭）

> **用户裁决**：生产库限制**不得长期关闭**。前提依赖解决后，编排器**自动解除**限制。

当前 v10.7 把生产写入当作「需逐次人工授权」的静态门禁，导致计划执行到一半就卡死。
v10.8 改为**前提依赖驱动**的自动解锁：

**解锁条件（全部满足即自动解除，无需再次人工确认）**：

| 编号 | 条件 | 判定来源 |
|---|---|---|
| UNLOCK-1 | 备份完成且**副本恢复演练成功**、恢复后 checksum 一致 | `AC-177` + 恢复演练记录 |
| UNLOCK-2 | 生产窗口命令单已冻结，每步含 precondition / rollbackCommand / abortCondition | `AC-176` |
| UNLOCK-3 | 变更清单与 P0-9 `projectedTarget` **零差异** | `AC-178` + `AC-182` |
| UNLOCK-4 | 全量回归门禁 `newFailuresIntroduced == 0` 且 `failedAfter == 0` | `AC-185` |
| UNLOCK-5 | 3 项 manager migration 可在**副本**成功应用（`unknownMigrationCount=0`） | 副本演练记录 |
| UNLOCK-6 | 编排器五层级联在**副本/测试网**已跑通并收敛（`blockers=[]`） | 测试网收敛证据 |

**解锁后的行为**：

- 编排器 `supervise --apply` 在主网上自动执行 L1→L5 级联修复；
- 每次写操作仍然走**单步 precondition 校验**，任一步 precondition 不满足即**中止并回滚该层**；
- 每层修复后立即只读复验该层 `valid`，不通过则回滚该层并记录原因；
- 所有写入仍有机器证据、回滚点和 row count / checksum 记录；
- **一次性写操作**（Authority 切换、`manager-api.exe` 替换、合约部署）**仍需人工停机窗口**，
  不在自动解锁范围内——这三类不可逆动作不因前提满足而自动执行。

**解锁状态机**：

```text
locked ──(UNLOCK-1..6 全满足)──▶ unlocked
unlocked ──(单步 precondition 失败)──▶ rolled_back_layer ──(修复后)──▶ unlocked
unlocked ──(连续 3 轮 stalled)──▶ escalated_to_human
```

**仍然禁止的动作（不因解锁而放开）**：

- 伪造 signer / nonce / RPC —— 编排器**只审计与终态化**真实广播尝试，不自己造交易；
- 把 `no_profit` / `pending` 当作缺陷去"修复"；
- 跨层逆向修复（跳过上游直接改下游）；
- 在 `dry_run` / 副本证据上宣称生产完成；
- 未经停机窗口的 Authority 切换、二进制替换、合约部署。

### 10.2 证据状态机（本版新增）

```text
draft ──▶ dry_run ──▶ testnet ──▶ production ──▶ archived
   │          │            │             │
   │          │            │             └─ 失败 → rollback_verified → archived
   │          │            └─ 失败 → rejected（回到 draft）
   │          └─ 失败 → rejected
   └─ 未通过 Definition of Ready → rejected
```

状态转移规则：

| 转移 | 条件 |
|---|---|
| `draft → dry_run` | Definition of Ready 全部满足 |
| `dry_run → testnet` | dry-run `changedRows=0`、幂等通过、备份可恢复 |
| `testnet → production` | 取得对应授权类型（§8.2）、命令单冻结、回滚点验证 |
| `production → archived` | 目标 AC 全部满足 + 人工摘要 + 归档索引登记 |
| 任意 → `rejected` | 失败码非空或 AC 未满足 |

**禁止**：`draft` 状态证据直接用于宣称阶段完成；`dry_run` 状态证据用于宣称生产完成。

## 13. 停止条件

出现任一条件立即停止当前阶段，**不得通过人工解释继续推进**：

- RPC/WSS 不可信、状态版本漂移、快照陈旧或跨块不一致。
- 动态费率池、扩展库或测试库成员进入版本 1 主路径。

- 生产库写入超出授权范围或目标库不是预期库。
- 备份不可恢复，或回滚命令未经演练。
- 回归新增失败、二进制与源码不一致、架构守卫失效。
- `safeToAutoBroadcast` 依据不完整，或 review source 存在未解释分歧。
- 复核缺明确盈亏而被估算值或零值填充。
