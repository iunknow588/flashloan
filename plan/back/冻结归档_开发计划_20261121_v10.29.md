## 3. 架构约束

### 3.1 内存对象处理约束（MIO-1..MIO-8）

- **MIO-1** SQLite 只在初始化/持久化/审计时读写；review/depth 处理循环不得逐条 SQL 查询业务状态。
- **MIO-2** 全局内存上下文持有池、闭环和运行时快照；运行期计算只消费该上下文。
- **MIO-3** token decimals 是内存上下文的一部分，金额缩放必须使用对应 token 的精度。
- **MIO-4** WSS/监控器更新内存快照；状态版本和新鲜度必须随计算证据传播。
- **MIO-5** Review Manager 通过 Rust 内核/管理接口消费业务状态，不由 Python 另建权威路径。
- **MIO-6** Python 只消费内核发布的金额、利润、路线和状态，**不重算、不拼接闭环身份**。
- **MIO-7** Rust 内核发布有符号利润及 `signedPnl.amount`，包含 raw 值、币种/精度、来源和测量状态；测得零与未测量严格区分。
- **MIO-8** 每条链使用独立 SQLite、chain ID、RPC、权限和内存状态，禁止跨链读取或写入。

### 3.2 闭环身份与路径匹配

> **闭环身份 = 资金锚点 + 方向池子。**

**系统设计中不存在"旋转"这一概念。** 闭环的业务身份由两件事共同确定：**资金代币（锚点）** 与**有方向的池子序列**。中间代币不一定是某条路由的资金代币，因此一条以中间代币为起点的路径是**另一个闭环**，有自己的身份、容量、池集合、估值与阈值。

由此得到的约束是**设计约束**，而不是行为约束：

- 代码里**不存在**闭环旋转查找、旋转归一化、旋转 alias merge、canonical rotation 这一类能力。任何层（Rust 内核、Python 运行时、脚本层）都**不得定义、不得调用、不得导入**这类能力。
- 闭环关键字 = 资金锚点 + 方向池子，即 Manager 发布的**完整有序路径**；匹配一律**精确匹配**。
- 精确匹配失败时**不借用**任何其他闭环的 loop key、pool IDs、capacity、USDG valuation 或 threshold，并 fail-closed 返回可定位的 identity mismatch。
- 因为"旋转后的路径是否命中"在系统中**不存在可观测行为**，所以**不得**把它写成验收项、指标或测试断言；那类检查项是**假问题**，应当删除而不是改写。

**同一资金锚点下可以有多条方向闭环，它们各自独立。** 例如 `X-Y-Z-X` 与 `X-Z-Y-X` 共享锚点 `X`，但方向池子不同，因此是**两条闭环**，各自拥有独立的 loop key、池集合、折叠容量、绑定池、阈值与运行时状态行（实证见 §7.4）。**一个锚点 ≠ 一条闭环**；不得把同锚点的多条方向闭环聚合为一条，也不得把一条拆成多条。

**观测层不是闭环身份层。** `market_observation` 层的 `group_key = anchor|direction_key`（现更名 `edge_group_key`）是按**池边（X-Y 入口边）**的**观测分组**，用于收集该边的桥接池；闭环身份在 Manager 发布层与 Rust 内核目录层。二者**不得**混淆。

**没有例外，没有"仅限状态表"的例外命名空间**。运行时状态行与 Manager 闭环身份使用同一套精确匹配契约：

| 命名空间 | 键 | 规则 |
|---|---|---|
| **Manager 闭环身份** | `loop_key` / `pool_ids` / `single_tick_capacity_*` / `borrow_token_usdg_value_*` / `cross_tick_*` / review→loop 归属 | 只精确匹配；不借用其他闭环的任何字段 |
| **运行时状态行** | `v4_closed_loop_runtime_state.loop_key` | 与 Manager 闭环身份**同一套精确匹配**；不承载 capacity / pool / USDG / threshold，不决定 review 归属 |

**实现落点**：Rust 闭环目录与身份匹配层（`flashloan/rs-src/src/closed_loop_identity.rs`、`worker_pool.rs`）、Python 运行时状态机（`flashloan/src/dex/runtime/closed_loop_state_machine.py`）与 Rust 复核管理器（`flashloan/tools/review_manager/src/lib.rs`）及其守卫测试。**不在** healer、Python 复核或脚本层做路径规整；Python 侧只消费内核权威结果。

**关闭条件**：系统内不存在任何旋转能力（源码级守卫可证），全部闭环身份与状态键按资金锚点 + 方向池子精确匹配，且**实盘证据齐备**（仅通过单元测试不构成关闭依据）。

### 3.3 级联与计算边界

- 处理顺序固定为代币→池→闭环→复核→广播；某层失败只关闭该层执行路径并继续诊断，不删除候选项或越级放行。
- 关键 token 字段优先由代币管理器修复；只有无法修复的关键字段才允许删除，且必须清理所有依赖引用。池代币精度以 token admission 为权威。
- 闭环身份匹配遵循 §3.2 的资金锚点 + 方向池子契约；缺少精确身份时按未解决依赖处理，**不得猜测或复用其他闭环的容量与估值**。
- Rust 负责单 tick 起始量、跨 tick 最佳金额、容量和利润。跨 tick 使用真实闭环输入/输出和既有 double/halve 搜索，不执行 tick 遍历；**单 tick 初值为 0 时不得启动跨 tick**。
- 未测量的金额或利润必须**缺值并附责任原因**；不能用默认零、历史估算或 SQL 回填伪装测量。
- 广播前检查正利润、具体金额、链/账户/nonce/gas/目标/快照/授权和幂等性。**无明确授权不得真实提交。**

### 3.3.1 ETH 与 WETH 是两个独立资金锚点（**不做特殊处理，不做互相转换**）

**结论先行：ETH（`address(0)`）与 WETH（`0x0bd7…ad73`）在本系统里就是两个不同的资金锚点，各自成环。ETH 锚点的闭环用 ETH 结算，WETH 锚点的闭环用 WETH 结算。两者之间不做任何包装/解包转换，也不做特殊处理。**

- Uniswap V4 把原生 ETH 作为 `Currency` = `address(0)`，与 WETH（普通 ERC-20）是**两个不同的 Currency**（并列，而非一致）。
- **本系统的强制口径**：闭环身份 = 资金锚点 + 方向池子；`loop_key = "{anchor_address}:{y_address}:{z_address}"`（`flashloan/tools/closed_loop_manager/src/lib.rs` 约 2390 行），**锚点地址在键里** → ETH 锚点闭环与 WETH 锚点闭环键值不同，天然是两条独立闭环。**不合并、不互转。**
- **不需要“原生 vs 包装”的特殊分支**：`normalize_address()`（`flashloan/tools/manager_contracts/src/ids.rs` 约 272 行）只做小写 + 长度 + 十六进制校验，对 `address(0)` **无任何特判**；单测 `native_zero_address_is_valid_and_distinct_from_weth`（约 323 行）断言两者 `currency_key()` 不相等。**不要引入 `isNative` / `isAddressZero` 分支去“特殊处理”原生 ETH。**
- **结算跟随锚点，不跟随路径中间段**：闭环借出与偿还都以锚点代币计（内核注释：*"The borrow token is the anchor token: it is the token the loop spends first and receives last, so its USDG value is what values the profit."*，`flashloan/tools/closed_loop_manager/src/lib.rs` 约 2188–2193 行）。路径中经过 WETH 池（或 `address(0)` 池）只是**该段的计价币种**，不等于把锚点资产换成另一种。
- **禁止的动作**：把 ETH 转成 WETH、或把 WETH 转成 ETH —— 任一方向都会**改变闭环锚点**，语义上就不是同一个闭环，且要付出两次 ERC-20 `transfer` + `approve` 的 gas。
- **与现有资产边界的关系**：本系统中 ETH（`address(0)`，`token_kind='native'`）与 WETH（`0x0bd7…ad73`，`token_kind='wrapped_native'`）是两个独立的 Currency，各自拥有独立的 USDG 估值（实测 ETH `2461669444` / WETH `1804537685`，均为 18 小数）。**不得**把两者当作同一资产（属于“不同估值”而非“同值”）。
- **实现落点**：`flashloan/rs-src/src/execution.rs`（`route_currency()` / `build_v4_flash_executor_request()`）与外部 V4 闪贷执行器合约。本系统不直接调用 PoolManager 的 `take`/`settle`，而是构造对外部执行器的请求（`token` / `amount` / `swapTargets` / `swapCalldatas` / `finalToken` / `minProfit` / `minAmountOut`）；请求体只带**一个** `token` 字段（值 = 该闭环锚点地址）与 `finalToken`，借出与偿还用**同一个锚点代币**，中间 hop 的池币种由各自 `currency0`/`currency1` 决定。**要求：不得引入任何把锚点资产换成另一种的转换路径。**
- **证据口径**：本规则不以单元测试通过即算完成；需在对应任务中以**实盘请求的 `token` 字段等于该闭环锚点地址**（ETH 锚点闭环即 `address(0)`，WETH 锚点闭环即 WETH 地址）可被独立核验、且请求体中**不存在**跨锚点转换动作时才能关闭。


### 3.4 `pool_depth_audit` 分类口径（已变更，随代码归档）

“坏读数（TVL 超上限）”与“薄池（TVL 低于下限）”是**两个不同分类**，不可混同：

### 7.6.1 「方向池子」这一半目前是哑保险

1. **结果层面：正确。** 闭环身份确实由**有序地址路径**唯一决定；池集合是路径的确定性函数，比对与否不改变判定结果。已发布的 164 条闭环容量 164/164 > 0、44/44 review 池集合与 Manager 一致，均无偏差。

### 7.10.2 关键实测结论：ladder 是**分支** double/halve 搜索，不是线性链

这是本轮最重要的发现，也是初版采集器判错的根因。

内核 `official_v4_best_amount`（`flashloan/rs-src/src/execution.rs`）执行的是**分支搜索**：

1. 先探测**自己推导出的起始量** —— `derive_initial_amount_raw`：
   容量 × `ladderStartCapacityFraction`（默认 0.5），可被 `economicFloorRequiredAmountRaw`
   与 `minProbeAmountRaw` 抬高，并**夹取到容量**；
2. 首探测成功 → `bounded_double` 向上翻倍（利润变好才继续），变差则 `bounded_half` 向下；
3. 首探测 revert → 先**向下**折半搜，再**向上**翻倍搜，两分支**按探测预算交织**。

因此「每相邻两行必须是 double 或 half」这个判据**本身不成立**：
分支点会出现 `other`，那是内核合法的**换向**。实测 8 行 ladder：

```
0xd5ca3088c29b93  ← 起始量（内核自推导）
0x6ae51844614dc9  ← 折半
0x35728c2230a6e4  ← 折半
0x1ab94611185372  ← 折半
0xd5ca3088c29b9   ← 折半（触及 floor）
0x6ae51844614dc   ← 向上分支（×2 回溯）
0x38d7ea4c68000   ← floor 夹取（1e15 = 0.001 @18dp）
0x1ab946111853726 ← 继续翻倍
```

### 7.12.5 V4 的 `Currency` 与原生资产（协议核对）

> 常见说法：“V4 里借入原生 ETH 后可以直接套利，不需要强制转换成 WETH。”
> 结论：**机制上基本准确**，但有 **4 处必须校正**。

**准确的部分**：

- V4 的 `Currency` 类型同时处理原生资产与 ERC-20；`address(0)` 是**原生 ETH 的正式代表**。
  WETH 是**普通 ERC-20**，在 V4 眼中与 `address(0)` 是**两个不同的 Currency**。
- 原生 ETH 的偿还路径不需要 ERC-20 `transferFrom`：`settle{value: amount}(address(0))` 通过 `msg.value` 结算。
- 本仓库实测支持上述区分：`manager_dex_candidate_pools` 中 **36/180** 个池配对 `address(0)`（原生 ETH），其余 144 个为 ERC-20；
  token 库中 ETH = `token_kind='native'`、WETH = `token_kind='wrapped_native'`，各自 18 小数。

**必须校正的 4 点**：

1. **原生 `settle` 仍需先 `sync(address(0))`**。V4 `PoolManager._settle` 的注释明确：
   *"if settling native, integrators should still call `sync` first to avoid DoS attack vectors"*。
   所以“原生结算完全独立、更简单”这一说法**不精确**：原生路径是 `sync` → `settle{value:}`，
   比 ERC-20 路径 `sync` → `transfer` → `settle` **少一次 token 转账**，但**不是“不需要 sync”**；`sync` 只重置差额账本，不记资产。
2. **原生支持是“池的货币”属性**，**不是“借贷形式”**。
   一条路径的任意一段若为 WETH 池，就**必须**用 WETH 交易（可选的是那个池**本身**的属性）。
   “路径终点是 V4 WETH 池 / 涉及 V2/V3 后续路由”需要解包才能 `settle{value:}` ——
   但这是**路径选择的产物**，而非 V4 闪贷本身的强制要求。
3. **“V4 重新引入原生 ETH 支持”的口径需要精确**：对 V4 而言成立（V3 也支持原生 ETH，`ETH/WETH` 池是典型）；
   但“V4 在底层重新引入完整支持”这个说法，对 V4 而言**不是新特性**，而是**统一的 Currency 形态**。
4. **“Router 自动包装/解包”是路由层行为**，不是 PoolManager 自身行为**。
   Universal Router / 路径专用 Router 会处理这种转换，但 **PoolManager 层不会自动包装**。
   本仓库不直接调用 PoolManager 的 `take`/`settle`，而是构造对**外部 V4 闪贷执行器合约**的请求
   （`build_v4_flash_executor_request`，`flashloan/rs-src/src/execution.rs` 约 529 行；`route_currency()` 约 517 行读 `currency0`/`currency1`）。

### 7.12.6 本项目的落实结论

**本项目的落实要求**（见 §3.3.1）：ETH 与 WETH 是**两个独立资金锚点**，各闭环用各自锚点代币结算，
**不互相转换、不特殊处理**。这一条与上述协议保证是一体的两面：**协议保证**说明为什么两个 Currency 可以并立，
**§3.3.1 规则**说明本系统怎么用它们 —— 即**不跨锚点转换**，而不是“用 `msg.value` 特判原生 ETH”。

- **TASK-141**：测试网**完整级联**先通过，主网**同码**逐层验证且 DB/链配置独立；运行时 API 与 Manager API 健康**仅作服务检查**，不替代业务验收；连续 **3 个各 ≥30 分钟**窗口满足 `blockers=[]`、`missingValue=0`、`positive>0`，每窗关联复核/广播请求/hash/receipt/实际盈亏并记录 gas、借款费、滑点与模型偏差；stale WSS、版本漂移、重复提交、错误激增或实际亏损触发**广播准入关闭**同时保留诊断/修复通道。
  > **关于 `positive>0`**：这是**真实业务结果**，不是工程指标。工程侧正确做法是**把观测与门禁做到位、窗口如实记录**；**不得**通过放宽门槛、延长陈旧容忍度或调整口径来"制造" `positive>0`。若连续窗口 `positive=0`，应如实记为**业务无套利机会**，而非工程缺陷。

### 9.7 全局停止条件（任一命中即停止广播并归档）

- 缺 amount / PnL、快照陈旧、闭环身份不唯一、签名授权不足、重复提交或 receipt 无法关联。
- 无完整正利润且无用户明确授权。
- 任何跨链读取/写入，或跨链状态污染。
- 用历史深度/业务数据回填，或用默认零/估值掩盖缺陷。
- 处理顺序固定为 **代币 → 池 → 闭环 → 复核 → 广播**；某层失败只关闭该层执行路径并继续诊断，**不删除候选项、不越级放行**。
