## 1. 目标与口径

- 只推进 Robinhood V4 测试网实盘观察，不扩多链。
- 执行依据必须是实时行情/链上 Quoter（`dex_quote_routes`、live Quoter 或 `eth_call`），历史快照只作审计，不作可执行计划。
- 测试网广播开关保持 `true`；主网、paused-deploy、executor canary 广播保持 `false`。
- 方向完成门槛为 1 条活跃候选，5 仅作推荐池数量上限；除 `TZ -> TA -> TB` 主动测试注入流动性外，其他闭环不自行注入流动性。
- readiness 只由 CLI 写入，禁止手工改 `latest.json`。
- 无 signed 数值时 P&L 保持 `null` + `missingReason`，不写零占位。
- SQLite 是提交记录唯一在线存储；旧 JSONL 只作历史迁移源或归档审计。
- 提交记录与复核记录语义分离：提交记录只展示 `execution_success` / `execution_failed`，复核记录独立展示。
- 所有结论必须来自命令输出或 evidence 文件，不伪造链上结果。
- 参数/搜索模式调整前必须有链上 mulch 或 ladder 降额 evidence。

## 4. 分阶段排期

### Phase A 持续观察与可自主推进（立即开始）

1. 每轮先查 SQLite 最新 attempt 时间，确认是否有新窗口。
2. 有新窗口时按顺序执行 M1-1 四类 evidence 与 validate；旧窗口保留在带时间戳归档目录。
3. 扫描 `quote.live_onchain_evidence.readyForTransactionPreflight=true` 与顶层提交候选状态；出现可提交 live-ready 行后立即进入 M1-2。
4. M1-2 按序执行：build 当前包（按 ready 行实际 pair 传参）-> audit -> `--strict-live --no-write`；禁止用旧 `live_verified` 或手工 attempt JSON 冒充当前包。
5. 每轮复检 M5-2：live strict、predeploy fork、主网只读 gate 均用 `--no-write`，保持 fail-closed。
6. 持续观察 M6-2：worker `broadcastGate`、`auto_broadcast_count`、`execution_success` / `tx_hash` 落库情况。

### Phase B 链上成交验证（等待新 unique success）

- 出现新 unique success 后按 M2-1 -> M2-2 -> M2-3 -> M2-4 顺序推进。
- 先确认 `broadcast_history` 自动落库为 `execution_success` / `tx_hash`，再重跑 P&L、auto-scan 与 expected-vs-actual。
- 无新 success 时保持未勾选，只记录最近一次核对时间。

### Phase C 回填性能（等待维护窗口）

用户/运维确认维护窗口后按序执行：

1. 停止周期扫描 / auto-execute。
2. 备份 `flashloan/src/runtime/local_store.sqlite3`。
3. 小 batch 验证：`--candidate-backfill --pool-ids <样本> --batch-size <小值>`，确认 TLS 与零流动性清理正常。
4. 窗口内逐步扩大批次。
5. 完成恢复扫描，重跑 M1-1 四类 evidence。

最终验收为 T21 出现 signed 数值；未确认窗口前不启动全量 backfill。

### Phase D 部署运营（等待外部审批/登记）

- M4-1：canary/executor evidence 齐备后重跑 predeploy readiness，确认两项 blocker 清除且 canary 前三项广播均 `false`。
- M4-2：P0-14 业务审批完成后补主网 static-call/readback evidence，readback 保持 fail-closed。
- M4-3：P2-04 负责人登记后完成 SLO/告警配置、失败回滚演练与 USD 盈利观察。

## 5. 标准作业流程

每轮推进建议按以下顺序执行：

1. 检查生产进程与 SQLite：确认 scanner 是否运行、`cow_execution_attempts` / `cow_execution_reviews` 最新时间。
2. 有新窗口时执行 M1-1 全部验收命令。
3. 检查 `readyForTransactionPreflight=true` 行、`chain_submission_candidate`、`can_submit_order`、`checks_passed`，判断 M1-2 是否触发。
4. 检查 `execution_success` / `tx_hash`，判断 M2 链是否触发。
5. 检查 failover 数量与 `rpc_transport_error`，有新增则单独记录切换前后结论。
6. 检查维护窗口、审批状态，判断 M3-1 与 M4 是否可推进。
7. 更新本计划与源任务清单：记录最近核对时间、新 evidence、状态变化。
8. 全程不重启用户/生产进程，不改 `latest.json`，不跨 RPC 重发广播。

## 7. 安全边界

- 测试网广播开关保持 `true`；主网、paused-deploy、executor canary 广播保持 `false`。
- readiness 只由 CLI 写入，禁止手工改 `latest.json`。
- 无 signed 数值时 P&L 保持 `null` + `missingReason`，不写零占位。
- native `initialAmountRaw` 缺失或为 `0x0` 占位时，初始测试交易量保持未记录/`null`。
- SQLite 是提交记录唯一在线存储；成交提交类只写入 `cow_execution_attempts`，复核类只写入 `cow_execution_reviews`。
- RPC failover 只用于只读复核；广播/提交不自动跨 RPC 重发，避免双提交。
- `readyForTransactionPreflight=true` 由链上报价复核自动计算，不手工设置。
- 任何参数/搜索模式调整必须先有链上 evidence。
- 历史自动扫描成交 14 条（含非 TZ 8 条 / TZ 6 条）仅存于 evidence/归档；在线 SQLite 无 success 时不伪造提交记录。
- 不擅自重启生产进程、不 kill worker、不清理/压缩链路记录；受控操作必须确认无进行中复核。

## 8. 更新机制

- 每次 evidence 有实质变化（新成功 `txHash`、T21 signed、cleanup 触发、RPC failover 切换、参数调整）后，同步更新源任务清单、源开发计划与本计划。
- 任务推进类型变化时，先更新排期表状态，再更新任务清单对应行。
- 已在源文档收口的任务只保留复测入口，不重新进入待推进表。
- 若链上长期无新窗口，链上成交与回填任务保持未勾选，只更新最近核对时间。

## 11. M6-2 Rust 广播失败回传修复记录（2026-10-26 晚间 +08:00）

- 追加根因：Rust `maybe_broadcast()` 在 `profitable_amount_found` 后任何广播异常都会返回 `Err`，`run_native_review()` 随即整体返回错误，worker 把 `last_result` 置空、只留 `last_error`。此时 Python 桥接无法拿到已算出的 `selectedProfitRaw`/`routes`/`costModel`，只能落成泛化的 `rpc_verification_failed`，PnL 与具体广播失败原因同时丢失。
- 修复：`worker_pool.rs` 在 `on_phase("broadcasting")` 后捕获 `maybe_broadcast()` 的 `Err`，新增 `record_broadcast_failure()` 写回 `broadcast={ok:false, attempted:true, failed:true, status:"broadcast_failed", error, txHash:null}`、`broadcastError` 与 `broadcastExecuted=false`；worker 仍返回 `Ok(payload)`，`last_result` 完整保留 `profitable_amount_found`、选中金额/利润与路由证据。
- Python 桥接：`_attach_native_auto_execute_to_attempt()` 对无 txHash 的广播结果补 `auto_execute.reason="broadcast_failed"`，attempt 进入 `execution_failed` 且 `error`/`blocked_reasons` 保留 Rust 原文；`_row_failure_reason_text()` 与 `dex_submission_records.js`/`dex_submissions.html` 增加 `broadcast_failed`/`broadcast_error` 中文标签，失败原因列完整透传 `auto_execute.reason` + `auto_execute.result.error`。

- 设计问题确认：pid 文件用于跨进程找回已 detach 的 observer 子进程，并配合“进程存在 + 命令行匹配”校验；身份参数本身无法阻止第二个进程以同一 ID 再启动。当前 `observer.pid` 只放 `runtime/`，`liquidation_daemon` 使用状态 JSON + pid + 心跳陈旧检测，均符合 README 的 pid 文件规范；被归档的 `venus_*.pid` 是历史脚本遗留，无代码引用。
