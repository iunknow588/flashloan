## 1. 关键根因裁决（本版新增，优先级高于一切排期）

### 1.1 TASK-149 的缺陷在代码中已定位到具体行

`flashloan/rs-src/src/closed_loop_identity.rs:68-89` 的 `ClosedLoopCatalog::identity_for`：

```rust
pub fn identity_for(&self, symbols: &[String]) -> Option<&ClosedLoopIdentity> {
    let key: Vec<String> = symbols.iter().take(3).cloned().collect();
    if let Some(identity) = self.by_symbol_path.get(&key) { return Some(identity); }
    // The route was discovered under a rotation of the published order.
    for offset in 1..key.len() {
        let mut rotated = key[offset..].to_vec();
        rotated.extend_from_slice(&key[..offset]);
        if let Some(identity) = self.by_symbol_path.get(&rotated) { return Some(identity); }
    }
    None
}
```

同时 `closed_loop_identity.rs:109-181` 的 `catalog_from_rows` 用 `path_symbols_json` 的**前三个符号**建索引，且 `take(3)` 丢弃了 Manager 发布的第 4 个符号（回环锚点）。

**Manager 侧发布契约**（`flashloan/tools/closed_loop_manager/src/lib.rs:2397-2404`）：
```rust
let path_symbols = vec![anchor.token_symbol, y.token_symbol, z.token_symbol, anchor.token_symbol];
let loop_key = format!("{anchor_address}:{y_address}:{z_address}");
```

**缺陷链（三方叠加）**：

1. Manager 发布 `path_symbols = [A, B, C, A]`（长度 4，含回环锚点），`loop_key = A_addr:B_addr:C_addr`。
2. 内核 `catalog_from_rows` 用 `.take(3)` 把索引键截成 `[A, B, C]`，**丢弃了 Manager 明确发布的完整有序身份**。
3. 内核 `identity_for` 在精确匹配失败后，**按 1..3 偏移做循环位移**，把 `[B, C, A]`、`[C, A, B]` 都映射到同一条 `ClosedLoopIdentity`。
4. 结果：不同起点的闭环**共用同一份 capacity / pool_ids / USDG valuation / threshold**。`single_tick_capacity_anchor_raw` 被借给从未被证明过的路线。

**这正是 TASK-149 描述的"符号旋转匹配"缺陷，且已实际存在于生产代码路径上。** `worker_pool.rs:2811` 的 `apply_closed_loop_identity` 消费该 lookup 结果，把 `singleTickCapacityRaw`、`borrowTokenUsdgValueRaw`、`crossTickReviewThresholdUsdgRaw`、`closedLoopPoolIds` 写入 route config —— **被借用的不只是 capacity，是整个闭环身份**。

现有单元测试 `a_rotated_route_borrows_the_published_identity_of_the_same_cycle`（`closed_loop_identity.rs:236-259`）**明确断言旋转必须命中**，与 AC-214 要求**直接冲突**。该测试必须随实现一起改写，不能保留。

### 1.2 缺陷与 GOOGL 缺金额样本的关系

主网 healer check（2026-11-19 12:13Z）中唯一缺最佳金额的样本：

```
reviewId 69547, requestedSymbol GOOGL, probeCount 0,
reason: best_amount_ladder_blocked: ... (single_tick_capacity_unavailable)
loopKey: 0x2e0847e8910a9732eb3fb1bb4b70a580adad4fe3:0x0000...0000:0x5fc5360d0400a0fd4f2af552add042d716f1d168
```

注意该 `loop_key` 的 **Y 段是全零地址** —— 即 `0x0`。这是 Manager 侧一个**退化路由**（anchor → 0x0 → Z），其发布身份与真实路由不同。内核在精确匹配失败后靠旋转"碰巧"匹配到一条 capacity 正常的闭环，于是把那条闭环的 capacity 借给了这个退化路由；随后在另一层（容量有效性/池状态校验）被拦下，表现为 `single_tick_capacity_unavailable`。

**因此 TASK-149 与 TASK-148 不是"先后修复"关系，而是同一缺陷的两面**：

- 修好 TASK-149（严格精确匹配、fail-closed）后，该退化路由会**立刻变成可诊断的 identity mismatch**，而不是一个带错误 capacity 的静默阻塞 —— 这本身是改进。
- 但**真正的容量缺失**（`single_tick_capacity_anchor_raw` 本身为 NULL 或 0）仍需 TASK-148 单独修，否则会从"借错 capacity"变成"诚实缺 capacity"，缺金额样本**数量不减**。

**结论**：TASK-149 修复后必须**立即重跑主网 review**，把"因借错 identity 而阻塞"与"因真实缺 capacity 而阻塞"两类样本分离开，分别归属 TASK-149 与 TASK-148。否则会出现"TASK-149 已关闭但 TASK-148 缺金额样本反而变多"的误判。

#### 1.4.3 为什么这是"拼接解析"而非合法消费

内核**已经**发布权威身份，Python 侧却绕开它重新推导：

- **内核发布**：`flashloan/rs-src/src/worker_pool.rs:1372-1373` → `payload["closedLoopKey"] = route_config.get("closedLoopKey")`；
  `worker_pool.rs:2814` → `route_config["closedLoopKey"] = json!(identity.loop_key)`。
- **桥接已消费**：`flashloan/src/dex/runtime/rust_closed_loop.py:1521` → `loop_key = str(result.get("closedLoopKey") or "").strip()`，
  且注释明确写 "**Python does not assemble it**"；`rust_closed_loop.py:2273` → `"loopKey": loop_key` 写回 review evidence。
- **healer 却另起炉灶**：`scripts/mainnet_arbitrage_healer.py` 从 DB 的 `payload_json`/`summary_json` 里
  翻找 `("loopKey","loop_key","closedLoopKey","libraryLoopKey")` **四种键名**，找不到就
  `":".join(route[:3])` **从地址重新拼**。

**即：Python 在"读"内核已经发布好的身份字段，却把它当成缺失而重新解析、重新拼装、重新归一化。**
这正是 MIO-6「Python 只消费内核发布的金额、利润、路线和状态，不重算、不拼接闭环身份」被违反的确切形态，
也正是 TASK-149 禁止的"符号旋转匹配"在 Python 侧的**镜像实现**。

#### 1.4.5 影响

healer 是**主网 review → 广播门禁**这条链上的执行者。它做的三件事都建立在旋转归一化上：

1. `review_row_matches_rotations`（3395）：把 review 归到"同循环"而非"同身份"。
2. `resolve_registered_group_key`（3782）：按旋转找 worker，可能把 **A 起点闭环的 review 记到 B 起点闭环名下**。
3. `3929/3936`：用旋转集合决定"哪些闭环还没被 review 过"，导致**重复 review 或漏 review**。

在 TASK-149 落地（Rust 侧不再旋转）之后，若 Python 侧继续按旋转归并，则：
- Rust 侧的 fail-closed（identity mismatch）诊断到了 Python 侧会被**旋转重新命中**，
  **fail-closed 语义被 Python 侧悄悄撤销**；
- 即便 Rust 修好了，healer 仍会用旋转把不同起点的 review 归并到一起 —— **闭环身份在最后一公里被重新污染**。

**因此 TASK-149 必须同时包含 Rust 侧精确匹配与 Python 侧纯消费两部分，否则修不完整。**
这是本次新增的关键裁决：**TASK-149 的 Python 侧清理不是"顺带"，是 AC-214 的必要组成部分。**

#### 1.4.5.1 实施期新发现：`flashloan/src/` 另有三处旋转归一化（计划 §1.4.2 表未列）

`directed_cycle_rotations` / `canonical_directed_cycle_key`，且都位于 `flashloan/src/` 内部：

|---|---|---|
| `dex/runtime/dex_opportunity_scanner_rust_mixin.py:44-52` `_directed_loop_config` | 在 `config_by_loop_key`（物理地址路径 → route config）里按**旋转**回退查找 route config | **属于身份裁决，必须改精确** |

**裁定（两个命名空间必须分开）**：

1. **Manager 闭环身份命名空间**（`loop_key` / `pool_ids` / `single_tick_capacity_*` /
   `borrow_token_usdg_value_*` / `cross_tick_*` / review→loop 归属）——
   **绝对禁止** Python 侧旋转裁决。这一条已由 §4.6 落地：healer 15 处调用点、
   `closed_loop_identity.py` 三个旋转函数、`_directed_loop_config` 均改为精确匹配。

2. **运行时状态行命名空间**（`v4_closed_loop_runtime_state.loop_key`）——
   该表由 `_resolve_directed_loop_key` 自己写入，键空间是**物理地址路径**。
   此处的旋转回退是为了让**同一个物理闭环的多个历史锚点**收敛到**同一行状态**，
   属于"同一闭环的别名归并"，**不是**"把 A 起点的观测记到 B 起点名下"。
   该命名空间**不承载 capacity / pool / USDG / threshold**，因此不受 MIO-7 约束。

3. **判定标准（写入 MIO 守卫）**：一个 Python 旋转调用是否违规，取决于它是否跨越
   **Manager 闭环身份**边界。判据：

   - 旋转结果被用于**选择** Manager 发布的身份字段（loop key / pool ids / capacity /
     USDG / threshold）或**决定 review 归属哪个闭环** → **违规**，必须精确匹配。
   - 旋转结果只用于**运行时自身状态表的行归并**（同一物理闭环的别名） → **允许**，
     但必须保留 fail-closed 诊断，不得据此放宽任何准入判定。

4. **本轮实施结果**：`_directed_loop_config` 已改为精确匹配（route config 携带的是
   **另一个起点的** pool 集合与 Manager 身份，用旋转回退等于让路由借用他环身份）。
   `closed_loop_state_machine.py` 的三处保留为状态行归并，但**新增 MIO 守卫**，
   把"跨 Manager 身份边界的旋转"显式列为禁止形态，防止后续新增调用点越界。

#### 1.4.6 处理原则（与 Rust 侧同一条契约）

1. **Rust 内核是闭环身份的唯一裁决者**。Rust 侧按 §4.2 改为精确匹配并 fail-closed。
2. **Python 侧删除全部旋转归一化能力**：
   - `flashloan/src/dex/runtime/closed_loop_identity.py` 中 `directed_cycle_rotations`、
     `canonical_directed_cycle_key`、`directed_cycle_keys_match`、`resolve_registered_group_key`
     —— **删除或改为"仅精确相等"**。
   - healer 的 15 处调用点 —— 改为**直接消费内核发布的 `loopKey`/`closedLoopKey`**。
3. **禁止 Python 侧从 route 地址拼装身份**（`":".join(route[:3])` 一律删除）。
4. **禁止多键名猜测**（`("loopKey","loop_key","closedLoopKey","libraryLoopKey")` 四选一 —— 收敛为**唯一**键名）。
   内核发布的键名是 `closedLoopKey`（payload）与 `loopKey`（evidence 顶层），
   两者语义相同、来源相同；**不得**因为键名不同就再发明匹配逻辑。
5. **补强 MIO 守卫**（新增 3 项检查）：
   - 禁止 `flashloan/src/` 与 `scripts/` 出现 `directed_cycle_rotations` / `canonical_directed_cycle_key` /
     `resolve_registered_group_key` / `directed_cycle_keys_match` 的**定义或调用**；
   - 禁止 Python 从 route 地址**拼接**循环身份（覆盖函数实参位置的 `":".join(...)` 与 `"|".join(...)`）；
   - 禁止**多键名猜测**（同一身份在多个候选键名间 fallback）。
6. **回归要求**：删除旋转后，healer 的 review 归并必须仍能正确工作。
   因为内核发布的 `loopKey` 是 **Manager 的权威键**（`loop_key = anchor:y:z`，Manager 侧 ETH-anchored），
   而 runtime 的 worker 按**发现顺序**注册 —— 二者可能不同。
   **这一点必须先验证**：若 Manager 的 `loop_key` 与 worker 注册键确实不同，
   则"纯消费"需要一个**内核侧的**桥接（内核把 Manager 身份写进 route config，worker 以此注册），
   **而不是** Python 侧再算一遍。该验证属于 TASK-149 Step 3 的一部分（见 §4.2）。

## 4. S1a — TASK-149 闭环起点身份精确匹配（P0，AC-214）

### 4.1 目标语义（不可协商）

> **闭环起点是闭环业务身份的一部分。起点不同即不同闭环。**
> 禁止对 token path 做循环旋转归一化；禁止借用另一闭环的 loop key、pool IDs、capacity、USDG valuation、threshold。
> 精确匹配失败时 **fail-closed**，报告 identity mismatch。

### 4.2 实现步骤（按序）

**Step 1 — 身份键升级为完整有序序列**

- **文件**：`flashloan/rs-src/src/closed_loop_identity.rs`
- **改动 A**：`catalog_from_rows` 的 `.take(3)` 改为**保留 Manager 发布的完整 `path_symbols`**（长度 4，`[A,B,C,A]`）。索引键使用完整序列，**不回环截断**。
- **改动 B**：`identity_for` **删除旋转分支**（`for offset in 1..key.len()` 整段移除）。只保留一次精确查找。
- **改动 C**：`identity_for` 的入参语义从"取前 3 个符号"改为"完整有序路径必须等于 Manager 发布序列"。
- **关键设计问题（必须在实现前裁决）**：Manager 发布 `[A,B,C,A]`（4 元素，含回环锚点），而内核收到的 route `routeSymbols` 是 **3 元素还是 4 元素**？
  - 若 route 侧为 3 元素 `[B,C,A]`，则**永远无法精确匹配** `[A,B,C,A]` —— 这会把所有路由打成 miss，比现状更糟。
  - **裁决方向**：以 **route 的完整有序 token 序列**为查询键，与 Manager 发布的**去回环锚点后的完整有序序列**`[A,B,C]`做**有序全等**比较。即：Manager 侧发布 4 元素（保留回环信息），内核侧建**两个索引**——完整序列 `[A,B,C,A]` 与去锚点序列 `[A,B,C]`——但**查询时不做任何位移**，只用 route 的完整有序序列去精确查。
  - **禁止**：为了让 miss 变少而引入"取任意 3 个符号后匹配"这种子串式匹配 —— 那等于把旋转匹配换个马甲。
- **Step 2 — 补齐 pool identity 校验**
- 精确命中后，额外校验 `loop_key` 的三段地址与 `pool_ids` 的 ordered 长度一致；同一符号路径对应不同池身份时**不得覆盖或误配**。
- **Step 3 — fail-closed 诊断**
- lookup miss 时，在 route config / review 结果中写入：`closedLoopIdentityStatus = "mismatch"`、`repairTarget = "closed_loop_manager"`、`identityMismatch = { querySymbols, reason }`。
- **禁止**：任何 Python 侧兜底匹配（healer、review、脚本层一律不做路径规整）。
- **Step 4 — 单元测试改写**
- **必须删除/反转**：`closed_loop_identity.rs:236-259` 的 `a_rotated_route_borrows_the_published_identity_of_the_same_cycle`（与 AC-214 直接冲突）。
- **必须保留**：`the_reverse_path_never_borrows_the_other_loops_identity`（反向仍 miss，符合新语义）。
- **必须新增**：Manager 只发布 `[A,B,C]` 时，`[B,C,A]` 与 `[C,A,B]` 均 miss，且不继承任何字段；miss 后不返回任何 `ClosedLoopIdentity`；同符号路径不同 pool 身份不误配。
