## 0. 执行原则

1. **Rust Manager 权威**：代币、池、候选边、候选交易池、闭环、复核、广播和组合编排的功能逻辑必须位于对应 Rust manager；Python 只负责 RuntimeCore 桥接、配置输入、页面展示和历史兼容。
2. **生产写入需授权**：未经用户明确授权，不得写 `flashloan/db/local_store_4663.sqlite3`。
3. **停机动作需窗口**：W7/W8、二进制替换和 Authority 切换必须取得停机窗口。
4. **版本 1 只做 single-tick**：每跳不得跨 tick；跨 tick 接口保留但不优化、不进入主路径。
5. **准入约束**：固定费率 `0 < fee <= 30000`；动态费率池排除；hook、深度和池角色约束继续生效。
6. **USDG 口径**：经济学意义上 `1 USDG == 1 USD`；USDG 替代 USD 的计价作用，但不得把外部 fiat 价格源或 TVL 引入深度准入。
7. **RPC 预算**：QuickNode 免费额度不超过 15 req/s；pool-manager 默认 8 req/s、batch 50。
8. **SDK 优先但 authority 唯一**：优先使用成熟 Rust SDK；任何新数学 SDK 必须先完成 parity、舍入、性能、许可证和回滚评估，不得形成双生产 authority。
9. **`app_runtime` 边界**：`flashloan/app_runtime` 必须纳入架构审计；Python 页面和任务只能调用 RuntimeCore/Manager API，不得直接恢复 fee/token/pool/route/review/broadcast 业务判断。
10. **首版逐跳 single-tick**：每条闭环的每个 hop 都必须按实际最终输入量通过 single-tick 精确复核；任一 hop 跨 tick 时整条路线 fail-closed。
11. **角色权威源**：候选、推荐、备用和 Y-Z 观察池按现有表与 manager 输出解析，不虚构单一 `pool_role` 字段；清理必须基于角色集合。
12. **证据格式**：阶段报告必须使用统一机器可读 JSON，包含模式、版本、checksum、三态结论、失败码、回滚点、RPC 请求数和测试摘要。

#### 本阶段新发现并修复的传输层根因

上一轮把「区块钉住」当作状态一致性的充分条件，实测证明并不充分：`extsload` 批量本身会部分失败，而失败被静默吞掉。

1. **批量突破节点 15 req/s 上限**：`POOL_STATE_BATCH_SIZE=50`，24 个请求作为一次突发发出（`throttle_rpc_call` 是空实现，批次间等待只发生在批次之间），实测 **9/24** 个请求返回 `-32007 "15/second request limit reached"`。→ 批量大小改为 8（由速率上限派生），批次间等待改为覆盖整个批次。
2. **读取失败后静默回退陈旧快照**：失败时 `sqrt_price_x96` 为空，解析失败后保留数据库陈旧值，同时又用 live 的 `tick`/`liquidity` 覆盖旧值，形成既不描述存储块也不描述 live 块的**混合态**。→ 新增 `V4PoolState.complete`，仅当 `slot0` 与 `liquidity` 两次读取都成功且价格非零时才算完整测量，且**绝不半替换**。
3. **失败池仍被标注同块**：原实现对批次内每个池都写 `block:{N}`，包括读取已失败的池，制造虚假一致性。→ 仅完整测量写块号；失败池保留存储版本戳。同时收紧 `pool_state_versions_agree`：**时间戳与块号不再视为一致**（此前恰好掩盖了本次真实故障）。

#### tick_range_gate 与 tick_boundary 的单列结论

- **`tick_range_gate`（修复后 6 条）**：版本 1 single-tick 的 **fail-closed 语义**，不是精度差距。记忆侧原因串为 `the price limit is not below the current price` / `the hop leaves the current tick range (max input … raw)` / `pool state is not usable`；链侧未施加同等约束。结论 `accepted_limit`，不并入 unexplained，不修改单 tick 算术。
- **`tick_boundary`（修复后 11 条）**：相对偏差实测全部 ≤ `0.0010`（约 0.1%），属跨 tick 边界处的舍入级差异。结论：可接受，**全局容差不放宽**（`DEFAULT_SHADOW_TOLERANCE=1e-9` 保持不变）。

#### 本阶段发现的真实缺口

`token_usdg_valuations` 表**一直**保存 `measured_at`，但 **P0-5 之前没有任何代码
读取这个时间戳来判断观察是否还能用**——门禁把每一条存下来的行都当成刚测的。

| 环节 | P0-5 之前 |
|---|---|
| 写入 `measured_at` | ✅ |
| 读出 `measured_at` | ✅ |
| **判定是否过期** | ❌ **无** |
| **过期后如何影响成员关系** | ❌ **无** |

后果有两类，方向相反但根因相同：

- 过期负面被**永久保留**（几个月前的 `no_route` 让一个代币永远留在"已排除"）；
- 过期正面被**永久保留**（几个月前的 `route_found` 让一个代币以早已不存在的估值留在库里）。

**根因不是"TTL 设得太长"，而是"根本没有 TTL"。**

#### 口径定案

| 维度 | 定案 |
|---|---|
| **TTL（成员关系）** | **24 小时**（`MEMBERSHIP_MAX_AGE = 86400s`）——"有没有 USDG 路径"是粗粒度事实，变化慢 |
| **TTL（数值幅度）** | **1 小时**（`MAGNITUDE_MAX_AGE = 3600s`）——"一个单位值多少"是市场观察值，参与承载能力分档 |
| **过期语义** | 过期 = **未知**。过期 `no_route` **不再是负面**，过期 `route_found` **不再是正面** |
| **过期行** | **不删除**。过期是读取规则，不是清理任务；落库本身幂等 |
| **fail-closed** | 时间戳缺失 / 不可解析 / 位于未来 / 超出容忍度 → 一律**未知**，无一条解析为负面 |
| **本地 no-route 近似** | **不采用**，且由代码强制（见下） |

> **支点规则**：过期的 `no_route` 不再是负面 ⇒ 过期观察**永远无法**把代币踢出库，
> 只能让它回到 `pending`；反过来过期正面也保不住成员关系。
> 两个方向由 `valuation_freshness::effective_verdict` 单点实现。

#### no-route 近似为什么不采用

1. 真负在当前体系里**只有一个生产者**：上游路由服务明说没有路径。
2. 本地启发式最多得出"**大概**没有路径"，那是另一个命题。
3. "不依赖外部 API"的动机不成立——真正的问题不是"API 不可用"，
   而是"API 不可用时我们**不知道**"；近似恰好把"不知道"伪装成"知道"。

**代码强制**（不只文档约定）：

```rust
// token_manager::valuation_freshness
pub enum ValuationApproximation { Rejected }             // 默认值即 Rejected
pub fn approximation_may_promote_to_negative(_kind: &str) -> bool { false }
```

若将来确需引入近似，必须同时满足：独立判定值且归类为未知 / 仅作筛查提示 /
永不写入 `no_route` / 永不改变成员关系。

### 2.5.3.1 单 Tick 池状态突变处理算法（新增，必须纳入后续实现）

> 依据：`docs/关于Robinhood/V4单Tick套利池子状态变化处理与算法优化.md`。
> 当前版本只处理单 Tick 套利；跨 Tick 最佳交易量属于后续版本预留能力。目标是建立**极简、安全、可放大容量**的单 Tick 专用路径。

| 状态 | 判定 | 链上动作 | 链下预算/证据要求 |
|---|---|---|---|
| **致命变化** | 当前 `sqrtPriceX96` 已跨出预设 Tick 区间，或活跃流动性不可证明/显著消失 | 当前闭环立即 `revert`；批次中的其他闭环继续执行 | 记录 `cross_tick` / `liquidity_state_unusable`；不得重试扩大额度 |
| **状态变坏** | ZeroForOne 时当前价格高于基准；OneForZero 时当前价格低于基准 | 当前闭环立即 `revert` | 记录 `adverse_price_move`；基础价差已被压缩，不继续消耗 gas |
| **状态变好** | 价格朝有利方向移动且仍在同一 Tick 内 | 按**当前距离边界比例**重算并放大该跳容量；禁止沿用旧 M_cap | 记录旧/新 `sqrtPriceX96`、边界、比例分子/分母、放大后容量；放大倍率受硬上限约束 |

**单跳容量比例公式（必须区分 token 侧）**：

- token1 侧：`K = L·|Δ√P|`，容量比可用 `|s_b-s₂| / |s_b-s₁|`。
- token0 侧：`K = L·|Δ√P| / (s_cur·s_b)`，容量比还必须乘 `s₁/s₂`；
  **不得直接套用 token1 的距离比例，否则会高估容量并越过 Tick 边界**。
- 推荐链上口径：链下算好比例分子/分母，链上仅执行
  `newCap = (mCap * newDistanceNum) / newDistanceDen`，并设置放大倍率硬上限。

**复杂度优化边界**：

- 当前版本只实现单 Tick 专用路径：“基准容量 + 距离比例 + 方向/跨 Tick 判定”，复杂度 O(1)/O(log n)。
- 在 Tick、流动性与方向确定时，容量比例可在链下 O(1) 计算；链上保持常数次减法、乘法和除法。
- 跨 Tick 最佳交易量属于**后续版本预留能力**：当前版本不实现、不优化、不接入候选、复核、广播或链上仲裁，也不得作为单 Tick 结果的回退来源。

### 2.5.3.2 单 Tick 安全不变量（新增）

- [ ] 任一跳跨 Tick，当前闭环必须 revert，不得由重算继续执行。
- [ ] 任一跳状态变坏，当前闭环必须 revert，不得按旧经济假设成交。
- [ ] 状态变好时 M_cap 必须按当前价格重算；旧 M_cap 只能作为基准输入，不能作为最终额度。
- [ ] token0/token1 的比例口径必须分别计算，禁止用统一距离比例覆盖两侧。
- [ ] 链上必须传当前 Tick 的 `sqrtPriceLimitX96`，不得使用全局极值代替。
- [ ] 最终 Swap 必须保留 `amountOutMinimum`；利润不足时整笔回滚。
- [ ] 批次内闭环必须隔离：单闭环 revert 不阻塞其他独立闭环。
- [ ] 链上容量放大倍率必须有硬上限，且 M_cap 不得超过原 Tick 物理边界推导值。
- [ ] 异步状态同步不得阻塞 EVM 执行；状态更新与仲裁证据分别记录。
- [ ] 任意状态变化都必须产生可审计证据：旧状态、新状态、判定分支、比例、最终容量、失败原因码。

| 动态 Gas 预算 + 30% 缓冲 | 记入 P1-3 批次 |

### 2.5.5 与既有任务的关系

- **不改变** P0-6 单 Tick 终审门禁的 fail-closed 契约（该门禁对**给定**输入量判定，语义不变）。
- **不改变** P0-2 `selection_basis` 口径与 P0-5 估值 TTL 口径。
- P0-8 是 P1-3「候选/推荐池重新物化」的**前置**：重新物化时必须按修正后的 M_cap 截断，
  否则物化出的候选仍带量纲错误。
- **新增 P0-8-e**：实现并验证单 Tick 池状态突变三态处理链上仲裁（致命变化/状态变坏/状态变好），

## 10. P8｜池生命周期、WSS 与 3000 池上限

- 备用池：最近 3 天有交易，且满足基本深度、固定费率和 hook 限制；清理开关默认关闭，只有正式运行且数据量达到配置阈值后才可启用；按每 3 个自然日的当日 24:00（即次日 00:00）清理。
- 候选池：每方向 TOP-5，不清理，动态更新。
- 推荐池：每方向 TOP-1，不清理，动态更新。
- WSS 缺失或状态不可信时，备用池清理 fail-closed 停用。
- 动态费率池不得进入备用、候选或推荐角色，也不得参与晋升排序。
- 池表总量不得超过 3000；超过时按角色保护、交易活跃度、深度、费率、更新时间确定性淘汰。
- 清理配置必须显式包含：启用开关、数据量启用阈值、3 日保留窗口、Asia/Shanghai 调度时区、WSS 健康门禁、单次最大删除量和 dry-run/apply 模式；具体配置名由 Rust `pool_manager` 定义。
- 候选/推荐动态刷新与备用池清理必须使用同一 pool state version，避免先清理后晋升造成竞态。
- 验收：监听→状态更新→活跃判定→晋升/降级/淘汰全链路验证。
