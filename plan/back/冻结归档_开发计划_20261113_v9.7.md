## 2. 最终完成定义

系统只有同时满足以下条件才可称为完成：

1. 单 tick 版本的代币、池、候选、闭环、复核和广播逻辑全部由 Rust manager 权威实现。
2. 股票代币准入遵守 USDG 可兑换性；核心/测试豁免；扩展代币满足深度和传递 USDG 关系。
3. 池库只保存固定费率 `<=30000`、非动态费率、满足 hook/深度规则的池，总量不超过 3000。
4. 候选池每方向 TOP-5、推荐池 TOP-1，动态更新且不清理；备用池按三日活跃规则受控清理。
5. ARCH-4-A 差异可逐笔归因；完成 ARCH-3 后，经过 7 天影子旁路和 30 天纯内存观察门禁。
6. W6/W7/W8 生产迁移完成，Python 只经 RuntimeCore/Manager API 工作。
7. 回归、观察、回滚、编码和证据门禁全部通过。
8. 首版每条闭环的每一跳都经最终输入量复核为 single-tick；跨 tick 路线必须在复核阶段被识别并阻断，不能进入广播或生产候选。
9. “版本 1”只指下述 single-tick 主路径，不代表关闭跨 tick 接口、不代表离线回测能力，也不代表取消后续版本扩展。

## 2.1 版本 1 范围定义

版本 1 是首个可上线套利闭环，范围固定为：

- 允许：多跳闭环，但每一跳都必须满足 single-tick 精确复核。
- 允许：YC、Y-Z、ZC 等现有闭环结构，由 `closed_loop_manager` 统一管理。
- 允许：链上 Quoter 作为影子对照或降级取数路径，但不得改变 single-tick 主路径口径。
- 禁止：实际执行跨越 tick 的 swap，即使内存接口能够计算跨 tick 结果。
- 禁止：把跨 tick 结果用于候选排序、收益复核或广播许可。
- 不承诺：版本 1 的压力测试覆盖度、跨 tick 收益机会或未来版本兼容性。

## 4. 架构责任与 SDK 决策

### 4.1 Rust Manager 责任矩阵

| 组件 | 权威职责 | 不得承载的职责 |
|---|---|---|
| `token_manager` | token 分类、股票 USDG 可兑换性、核心/测试豁免、扩展 token 传递关系、估值证据状态 | 池深数学、候选池排序、广播许可 |
| `pool_manager` | 链状态、固定费率/hook/深度准入、single-tick capacity、WSS 活跃度、备用池清理、3000 池上限 | 多跳闭环、收益复核、交易广播 |
| `candidate_edge_pool_manager` | 每方向精确排序、TOP-5/TOP-1、`selection_basis`、候选与推荐角色 | token 准入、链上广播 |
| `candidate_exchange_pool_manager` | 基于候选边组装交易方向和 exchange 候选，保持版本/checksum 一致 | 重复实现 AMM 数学或重新判定 token/pool 准入 |
| `closed_loop_manager` | 闭环身份、hop 组合、single-tick 路径约束、候选集引用完整性 | 自行查询外部价格或放宽复核门禁 |
| `review_manager` | 精确 amount/profit/gas/fee 复核、差异归因、fail-closed 分类 | nonce 管理、广播提交 |
| `broadcast_manager` | authority、预检、nonce、幂等提交、确认和失败归因 | 重新选择池、重算业务路线 |
| `composite_manager` | manager 版本编排、依赖顺序、checksum、物化事务和恢复点 | 绕过各 manager 的领域规则 |
| `RuntimeCore` / `manager_api` | Rust 大对象生命周期、查询视图、命令边界和兼容协议 | 承载第二套业务判断 |
| Python `app_runtime` | 配置输入、RuntimeCore 桥接、页面展示、运维入口和临时兼容 | fee/token/pool/route/review/broadcast 权威逻辑 |

### 4.2 SDK 采用策略

| SDK | 计划定位 | 采用门禁 |
|---|---|---|
| `uniswap-v4-sdk` | 当前已直接复用精确数学；tick 存储布局遵循 `PoolManagerLens`，但 `SimpleTickDataProvider` 尚未直接接入，需先决定迁移还是保留经验证的自定义 provider | 锁定 Rust/toolchain/依赖版本；本地数学与链上 Quoter 形成可解释 parity；provider 决策必须有基准、回滚和单一 authority；不得在 Python 再实现一套 |
| `Dex-Math-Core-rs` | 作为链下精确计算候选引擎进行基准和 parity 评估 | 只有正确性、舍入、性能、维护性和许可证审查全部通过，且确定唯一数学 authority 后才可接入；不得长期双引擎给出互相冲突的生产结论 |
| `arena-core` | single-tick 生产基线稳定后，用于离线压力测试、情景模拟和回测 | 不进入版本 1 实时交易依赖，不得替代链上状态和生产复核证据 |

### 4.4 池角色权威源

当前 schema 没有单一 `pool_role` 枚举，版本 1 不新增虚假的角色字段。池角色必须按现有权威结构解析：

| 角色 | 权威来源 | 规则 |
|---|---|---|
| 候选池 | `dex_candidate_pools` 及 candidate-edge/exchange manager 物化结果 | 每方向最多 TOP-5；动态更新；不参与 TTL 清理 |
| 推荐池 | `dex_candidate_pool_recommendations.is_first_hop_recommended` / `is_third_hop_recommended` | 每方向 TOP-1；与候选物化版本/checksum 一致；不参与 TTL 清理 |
| 备用池 | candidate-edge 输出的 `first_backup_pool_ids` / `third_backup_pool_ids` 及对应持久化引用 | 保留最近三天有交易且满足深度、固定费率、hook 规则的池；只在正式运行、数据量充分且清理开关启用后受控清理 |
| Y-Z 观察池 | `market_observation_intermediate_pools` 及 observation manager 物化结果 | 属于中间跳观察面，不得被误当成首版正式推荐或广播 authority |

同一 `pool_id` 可同时承担候选和推荐角色；清理判断必须以角色集合为准，不能仅依据是否存在于某个候选表。

### 4.3 版本 1 非目标与硬边界

- 不优化跨 tick 交易，不把跨 tick 接口接入主路径。
- 首版的 single-tick 约束不是“当前价格位于同一 tick”即可；必须按该跳实际最终输入量，在实际 initialized tick/liquidity 状态下验证最终输出不跨越下一 tick。
- 交易量、费率、hook、tick spacing、liquidity 或状态版本变化导致跨 tick 时，该跳必须在进入复核和广播前 fail-closed。
- 不建设 Python 侧第二套 token/pool/route/review 业务体系。
- 不以外部 fiat 价格、TVL、相关性或 `li<1` 作为深度准入。
- 不在未授权情况下写生产库，不在未获停机窗口时切换 Authority 或替换被锁定二进制。

## 6. 阶段 A｜低风险收口

阶段 A 允许只读调查、代码修复、单元测试、测试网验证和数据库副本 dry-run；默认禁止写生产数据库、切换生产 Authority、启动正式广播或替换被锁定二进制。所有可能写生产或改变运行状态的动作仍分别受 P1/P5 授权与 P6/P7 停机窗口约束。

### A0 架构边界与 SDK 决策

- 对 `flashloan/app_runtime`、RuntimeCore、Manager API 和全部 Rust manager 做调用链审计，形成“功能 → 唯一权威组件 → Python 入口 → 证据”的映射。
- 固化 `uniswap-v4-sdk` 的实际采用范围：精确数学已直接使用，tick 槽位布局参考 `PoolManagerLens`，自定义 `TickDataProvider` 与 `SimpleTickDataProvider` 的取舍仍需 ADR；对 `Dex-Math-Core-rs` 建立只读 parity/benchmark 决策任务。
- 出口：没有新增 Python 权威业务逻辑；没有两套生产数学 authority；依赖版本、许可证、回滚和测试策略均有记录。

### A0.5 版本 1 范围、池角色与证据契约冻结

- 冻结版本 1 范围：允许多跳闭环，但所有 hop 必须 single-tick；跨 tick 只保留接口，不得参与候选、复核或广播。
- 核对候选、推荐、备用、Y-Z 观察池的现有权威表和 manager 输出，形成角色来源映射；不得新增虚构的统一角色枚举。
- 冻结统一机器报告最小字段：`mode`、`productionWrite`、输入/输出版本、row count、checksum、passed/blocked/failed、failure codes、回滚点和 RPC 请求数。
- 出口：范围定义、角色映射和证据 schema 写入活动文档/ADR；现有表结构与文档一致；无生产写入。

### A1 影子差异专项

- 对剩余 4 条逐条读取 live state、initialized tick、hook、Quoter revert 和字段可观测性。
- 输出 attribution 报告和异常台账更新。
- 出口：无未经解释的执行差异；接口不可观测限制有明确批准记录。

### A1.1 首版 single-tick 最终门禁

- 候选排序阶段使用 single-tick 精确输出只是一层筛选，不能替代执行前复核。
- 在 `review_manager` 的最终复核阶段，对闭环每个 hop 使用实际最终输入量重新计算 single-tick 输出，并验证不跨越下一 tick。
- 任一 hop 跨 tick、状态版本漂移、容量不足或无法证明 single-tick 时，路线整体标记为不可执行，不得进入广播。
- 该门禁必须覆盖 YC、Y-Z、ZC 以及未来闭环中的全部 hop，不能只验证第一跳或第三跳。

### A2 候选排序副本物化

- 在同一副本、同一 pool state version 上比较旧/新排序。
- 固定排序口径：normalized single-tick 精确输出降序 → 方向 tick 顺序 → fee → pool id。
- 在生产物化前将旧 wire label `direction_tick_ordering_then_fee_pool_id` 迁移为 `direction_single_tick_exact_output_then_tick_fee_pool_id`，并同步测试、报告和 checksum 口径。
- 输出 TOP-5/TOP-1、无价格池、不同方向排序、确定性重跑结果。
- 出口：无价格池不错误压过可报价池；候选数和推荐数符合规则。

### A4/A5 实窗与 VAL 决策

- 测量版本变化触发重算延迟。
- 定案估值 TTL、过期策略、本地 no-route 近似边界并写入长期手册。

## 7. 阶段 B｜生产池库收敛

### 前置

- 用户显式授权；生产备份、hash、行数、磁盘空间和副本回滚演练完成。

### 执行

1. prune 超门槛/动态费率池及引用；
2. 重新物化 pool scope；
3. 使用 `direction_single_tick_exact_output_then_tick_fee_pool_id` 重新物化 candidate edge/exchange；
4. 比较 checksum、行数和 orphan；
5. 幂等重跑。

### 回滚

- 任一 orphan、checksum 异常、候选覆盖下降或事务失败立即回滚；不得继续 W6。

## 10. 阶段 E｜W7 闭环重建

- 取得停机窗口，停止 worker，执行 cleanup/refresh/scope/composite。

## 11. 阶段 F｜W8 Authority 与广播移交

## 12. 阶段 G｜ARCH-4-B/C

- 阶段 B：内存主算、`eth_call` 影子，连续 7 天无不可归因差异。
- 阶段 C：ARCH-3 和新鲜度门禁上线后，连续观察至少 30 天。
- 保留回切和 Multicall 补数据路径。

## 13. 阶段 H｜生命周期与长期治理

- 落地备用池受控清理、WSS 监听、RPC 限速和池表 3000 上限；清理开关默认关闭，仅在正式运行且数据量达到阈值后启用，并按每 3 个自然日的当日 24:00（即次日 00:00）执行。
- 完善 token/route/window PnL 长期统计。
- 退役 Python 重复业务判断，补强架构守卫。

## 14. 每阶段固定交付物

1. 机器可读 JSON 报告；
2. Markdown 人工摘要；
3. 输入版本、checksum、行数、耗时；
4. 失败原因、回滚点和是否写生产；
5. 测试命令与结果；
6. UTF-8、无 BOM、LF 验证。
7. 责任 manager、输入版本、输出表/内存对象和 Python 调用入口映射。
8. SDK/依赖版本、是否新增生产依赖、许可证与可回滚性说明。
9. 对 single-tick 路线，附逐 hop 的 initialized tick、实际输入量、精确输出、下一 tick 距离和 bound 结论。

## 14.1 统一证据判据

所有阶段报告必须使用机器可读 JSON，并至少包含：

- `schemaVersion`、`generatedAt`、`stage`、`component`；
- `mode`：`read_only` / `dry_run` / `testnet` / `production`；
- `productionWrite`：`true` / `false`，以及授权文本或 dry-run 标识；
- `inputVersion`、`outputVersion`、相关表/内存对象的 `rowCount` 与 `checksum`；
- `passed`、`blocked`、`failed` 三态结论和结构化 `failureCodes`；
- `rollbackAvailable`、`rollbackPoint`、`durationMs`、`rpcRequestCount`；
- single-tick 路线附逐 hop bound 证据；池生命周期附 WSS 健康、state version 和清理阈值；
- 测试命令、退出码、测试数量和失败集合摘要。

“无异常日志”“页面可见”“口头确认”不能替代结构化证据。阶段退出以 checklist 中对应验收项全部满足为准，而不是以文件存在为准。

## 15. 阶段进入与完成门禁

### Definition of Ready

- 责任 manager、输入数据、目标库、是否写生产和授权要求明确。
- 副本/备份/回滚点和最小测试集合已准备。
- SDK 与 RPC 依赖可用，版本固定，限速策略明确。

### Definition of Done

- 代码、测试、机器报告、人工摘要、checksum 和回滚证据齐全。
- 活动 checklist 对应项可由独立人员复核；完成项移入 `back/` 后从活动清单删除。
- Python 未新增权威业务判断，生产库未发生未授权写入。

## 16. 停止条件

- RPC 不可信、状态版本漂移、动态费率池进入候选、任一 hop 最终输入量跨 tick、single-tick capacity 无法证明、生产无备份、无授权写入、停机窗口未批准、回归新增失败、orphan 非零、checksum 不一致：立即停止。
