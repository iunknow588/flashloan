## 4.5 多闭环批处理口径（2026-11-15）

广播管理器此前**不能**一次打包多个盈利闭环：worker 只保留 `best_route`，
每条闭环各发一笔独立交易。现已实现受限批处理：

- 合约入口 `requestV4FlashLoanBatch`，单批上限 `MAX_BATCH_REQUESTS = 16`；
- 每项通过合约自调用形成独立回滚边界，失败项只记录 revert selector；
- 每项余额必须独立覆盖自身 `minProfit`，禁止前序利润串用；
- Rust 批次分支默认关闭，仅 `executorBatchEnabled=true` 时启用；
- 未部署、未切换 Authority、未广播。

机器证据：`runtime_evidence/reports/p0_8_bounded_v4_flash_batch_20261115.json`

## 4.6 输出下限口径（2026-11-15）

Uniswap V4 原生 `swap` **没有** `amountOutMinimum` 参数，只有 `sqrtPriceLimitX96`。
因此链上唯一能表达的成交价约束是限价，不是输出下限。

当前实现是**路线级** reviewed minimum output：

- Rust 从成功的复核结果读取 `selectedKeys`、`selectedDirections`、`outTb`、`outTa`、`outTz` 与三跳限价，自动构造 bounded executor 请求；
- `swapTargets` 全部解析为 pool 基础目录中三只池共同的 PoolManager，`swapCalldatas` 为确定性编码的三笔 exact-input `swap`；
- 路线级 `minAmountOut` 取复核最终输出 `outTz`（raw units）；
- 该值经请求既有 `gasReserve` 字段传入——V4 记账路径从未强制该字段（gas 是沉没成本，
  余额判定只用 `minProfit`），复用它不改变既有语义，也不需要改动处于 EIP-170 极限的热路径 ABI；
- 合约在利润门禁与结算之前比较本次路线的**增量输出**：`balanceAfter >= balanceBefore + minAmountOut`，旧余额不得补贴劣化成交；
- Rust 侧拒绝没有可证明下限的路线进入 executor batch。

自动构造只使用 pool 基础目录与当次可再生复核结果，不为 review/submission/broadcast 增加长期持久化字段。

**逐跳输出下限仍未实现**：逐跳需要新 ABI，实测主网 Executor 无 EIP-170 字节余量
（热路径结构体新增任一字段即超限 101–276 字节）。

机器证据：`runtime_evidence/reports/p0_8_reviewed_minimum_output_profit_lock_20261115.json`、
`runtime_evidence/reports/p0_8_executor_request_autobuild_20261115.json`

### 4.6.1 scope 漂移根因（已定位并修复自愈死锁）

**闭环 hop 本身健康**：318 个 hop 的 65 个 distinct pool 全部命中
`v4_exchange_pools_candidate_exchange`，`missingPoolHopCount=0`、`affectedLoopCount=0`。
缺陷是**闭环库记录的 checksum 属于错误 scope**：

| 项 | 数据库现值 | Rust 源码目标 |
|---|---|---|
| 闭环库 `pool_scope_checksum` | `sha256:8ceb9e02...dfc1`（`candidate_exchange`） | `sha256:5434a25c...c9926`（`core4`） |
| `core4` scope `library_keys` | `["core"]` | `["core", "stocks"]` |
| `candidate_exchange` scope `library_keys` | `["core","stocks","extension","test"]` | `["core","stocks"]` |

生产库闭环库于 2026-11-09 物化，早于 Rust `closed_loop_pool_scope_checksum` 修复落地。

**自愈死锁**（已修复）：闭环重建原本只由 `consumers_need_rebuild>0` 或闭环层 `valid=false` 触发，
而从错误 scope 物化的闭环库自认为最新 → 重建永不触发 → 漂移永久存在。
现触发条件扩展为 `consumers_need_rebuild>0 || 闭环层 invalid || 闭环层 scope 漂移`。

同时修复 dry-run 假失败：`ensure-indexes` / `ensure-depth-schema` 在无 `--apply` 时按设计非零退出，
旧逻辑把它读成 tool failure，导致每次 dry run 都报「链路损坏」。

### 4.6.2 池子准入规则与动态流水线（已在 Rust 管理器实现并核对）

| 规则 | 实现位置与行为 |
|---|---|
| 费率 | `fee == 0` 或 `fee > MAX_CANDIDATE_FIXED_FEE` → `fee_not_fixed_candidate_range` |
| 动态费率 | `is_dynamic_fee_pool` → `dynamic_fee`，永不进入候选角色 |
| 特殊费率 | `special_fee != 0` 或超 `V4_MAX_FEE.min(V4_SPECIAL_FEE_THRESHOLD)` → `special_fee` |
| hook | `pool_key.hooks != ZERO_ADDRESS` → `non_zero_hook` → `pool_status = blocked` |
| 深度 | `has_liquidity != 1` → `liquidity_not_confirmed`；`liquidity_index <= 0` → `liquidity_index_not_positive` |
| 身份 | 存储 `pool_id` 与重算值不一致 → `identity_mismatch` |
| 动态补充 | scope 物化每次从原始 `v4_exchange_pools` 全量重算，缺失数据按新接收信息补齐，并输出 `skip_reason_counts` |

动态流水线：**观察池（`candidate_exchange`）→ 候选池（`core4`，每方向 TOP-5）→ 推荐池（每方向 TOP-1）**。

## 5. 版本 1 硬边界

- 当前版本只处理 **single-tick** 套利；允许多跳闭环，但每一跳都必须按最终输入量证明不跨 tick。
- 跨 tick 最佳交易量算法只保留为后续版本候选参考，不得进入候选、复核、广播或生产闭环。
- 单 Tick 在线容量使用 SDK 精确 delta 与 O(1) 边界距离逻辑；不得以跨 tick 探针阶梯替代。
- 任一 hop 缺 tick 状态、状态版本漂移、容量无法证明或最终输入量跨 tick，整条路线 fail-closed。
- 状态突变三态：跨 tick/流动性不可证 → revert；状态变坏 → revert；状态变好且仍在同 tick → 受硬上限约束地重算容量。
- 链上必须使用当前 tick 的 `sqrtPriceLimitX96`，并保留 `amountOutMinimum` 利润锁与批内单闭环失败隔离。

## 6.5 数据分层原则（2026-11-14 用户裁决）

**复核、提交、广播结果属于可再生瞬时运行记录，不具备长期统计意义；
真正具有长期价值的是代币基础数据与池基础数据。**
价格与链上状态实时变化，但基础信息不变；只要系统结构正确，
实时数据可以随时重新生成大量有效信息。

| 数据类别 | 长期价值 | 处置策略 |
|---|---|---|
| token 元数据、分类、准入、库范围 | 长期权威事实 | 只增不删，结构优先 |
| pool 元数据、PoolKey、费率/hook、scope | 长期权威事实 | 只增不删，结构优先 |
| review / submission / broadcast 记录 | 瞬时、可再生 | 禁止扩展长期 schema；走管理器接口清理 |
| 实时价格、流动性、tick、容量 | 可再生实时数据 | 按需重算，不作长期事实 |

强制约束：

1. 不为 review / submission / broadcast 扩展长期持久化 schema。
2. 清理一律走管理器提供的清理接口，Python 不得直接写业务库。
3. 清理必须支持 dry-run、幂等键与精确 scope 匹配，且不触碰 token/pool 目录。
4. 开发资源优先投向"基础结构正确 + 实时数据生成链路"。

已落地入口：`POST /v1/reviews/clear`（HTTP）、`RuntimeCore` 命令 `clear_reviews`（Rust）、
`POST /api/dex/submissions/clear` + `recordKind=review`（Python 运维入口）。

机器证据：`runtime_evidence/reports/p0_10_review_cleanup_and_catalog_preservation_20261114.json`

出现以下任一条件立即停止：RPC 不可信、状态版本漂移、动态费率池进入候选、任一 hop 跨 tick、容量无法证明、生产无备份、停机窗口未批准、回归新增失败、orphan 非零、checksum 不一致。

## 11. 归档规则

1. 完成项不得在活动任务清单或 Checklist 中保留 `[x]`。
2. 完成任务必须先生成机器证据 JSON 和人工摘要 Markdown。
3. 将完成结论与证据路径登记到**当轮新建**的 `back/已完成任务归档索引_<日期>_<版本>.md`；索引一经登记不得覆盖修改，下一轮另建新版本（v9.8 → v10.2 → v10.3 → v10.4 → v10.5 → v10.6）。
4. 再从活动任务清单与 Checklist 删除对应条目。
5. 活动清单与 Checklist 每轮结束必须复核 `[x]` 计数为 0；发现遗留 `[x]` 即视为归档纪律缺口，需立即补登记索引并从活动文档移除。
6. 每轮大规模整理前，先在 `back/` 创建不可覆盖的冻结快照：`back/冻结归档_<活动文档名>_<日期>_<版本>.md`，正文须与归档前活动文档逐字节一致。
7. 历史文档只追加归档，不覆盖、不重新激活。
8. 归档不得越权改写结论：即使代码、报告或页面已就绪，只要 Checklist 验收项未全部满足，条目必须保留在活动清单中并标注阻塞原因。
9. 每轮归档后必须做一致性复核：三份活动文档版本号一致、`[x]` 计数为 0、已归档 ID 不再作为活动条目出现、归档索引登记项与冻结快照可解析、证据路径存在。
10. **v10.6 口径补充**：闭环所有步骤必须共用**单一权威数据库解析器**，且必须绑定被处理链的 chain scope；进程默认链为主网时，测试网扫描不得写入主网库。测试必须拦截真实链库的**写入口**（含按名 import 的模块级绑定），并隔离 `FLASHLOAN_KV_PATH`、chain runtime registry、工作目录与 RPC offline 状态；`v10.6` 编号契约为任务上限 `TASK-110`、验收上限 `AC-175`。
11. **v10.5 口径补充**：配置项不得因"看似冗余"而删除——若仍被代码或部署流程依赖，必须**迁移路径**并同步所有引用与守卫 allowlist；`v10.5` 编号契约为任务上限 `TASK-106`、验收上限 `AC-170`。
12. **v10.4 口径补充**：活动文档中的 `[x]` 字样仅允许作为**归档纪律描述的正文引用**出现，不得作为任务勾选状态；每轮必须逐行区分二者后再判定 `[x]` 计数。编号契约随当轮归档同步更新（v10.4：任务上限 `TASK-100`、验收上限 `AC-164`）。归档快照必须覆盖**全部四份**活动文档（含 checklist）。

## 12. 文件格式

- Markdown / JSON：UTF-8 无 BOM、LF。
- JSON：稳定键顺序，`ensure_ascii=false`。
- 文件路径使用仓库相对路径。
- 活动文档中的状态、任务编号和执行顺序必须互相一致。
