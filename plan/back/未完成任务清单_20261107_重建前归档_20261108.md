## 计划层级与执行边界

- `P0` 是主网运行验收：验证当前实际 authority、当前表和当前进程的可观察行为，
  不承担 Rust Manager 的建表、数据迁移或 authority 切换。
- `M0-P` 至 `M8-P` 是生产 authority 迁移：必须在 copy DB、真实副本双读、
  dry-run、维护窗口和回滚演练门禁下推进；隔离演练可与 P0 分线并行。
- `P1` 是架构收敛的跟踪标签，不构成独立执行队列。`P1-1` 至 `P1-8` 的完成事实
  以对应 `M1-P` 至 `M8-P` 为准，不重复开工、不单独维护第二套状态。
- `UI-R`、`P2`、`P3` 分别承担 UI 收口、长期统计和运维治理；不得替代 `P0` 的
  运行验收，也不得把工程完成表述为生产完成。
- authority 切换后，依赖被切换表的既有验收结论不再自动有效。必须按
  “P0 与 authority 切换边界”执行增量回归，并在证据中重新记录 authority、
  版本和 checksum。

## 7. 任务执行模板

每项任务按同一顺序执行，避免在文档里只留结论、不留可复现路径：

1. 只读基线：先记录当前表数量、版本、checksum、运行态，并写入
   `runtime_evidence/reports/`。
2. 依赖检查：确认上游 authority、依赖任务和门禁版本；不满足则任务不开始。
3. 隔离验证：先跑单测、临时库、copy DB、compare-only 或 shadow，不允许直接
   生产 apply。
4. 生产 apply：只在维护窗口执行；apply 前记录备份和 checksum，apply 后立即
   复测。
5. 结果登记：记录命令退出码、前后数量/checksum、成功/failed/idle、修复动作。
6. 归档同步：完成项移入 `back/已完成任务归档_*`，并从本未完成清单删除。

拆解规则：
- 只读验证、dry-run、生产 apply、回滚和证据登记不得混在一个任务里。
- 父任务只能在所有子任务完成且父任务完成标准全部满足后标记完成。
- 新子任务必须分配独立编号、依赖和完成标准，不能把无法验收的描述放进执行
  队列。

### 8.1 命令与只读约束

```powershell
python scripts/audit_closed_loop_runtime_sync.py `
  --store flashloan/db/local_store_4663.sqlite3 `
  --network robinhood `
  --chain-id 4663 `
  --protocol uniswap_v4 `
  --market-id dex-arbitrage-4663-uniswap-v4 `
  --key-mode directed-symbol `
  --output logs/plan/runtime_evidence/reports/closed_loop_runtime_sync_<UTC>.json
```

- `network`、`chain-id`、`protocol`、`market-id` 必须显式提供；脚本不提供
  全库通过口径，跨 scope 行只进入独立 `outOfScope` 清单。
- 使用 SQLite `mode=ro`、`PRAGMA query_only=ON` 和单个只读事务抓取一致快照。
- 不得调用会自动建表的 `ensure_runtime_state_table` 等写路径。
- `--key-mode` 至少支持 `loop-key`、`route-key-id`、`directed-symbol` 和
  `yz-group`。`loop-key` 是改造后的生产主键模式；`directed-symbol` 和
  `yz-group` 用于当前基线与迁移诊断。无论选择哪种 key mode，报告都必须同时
  列出有向符号、无序 Y/Z 组、物理 `loop_key` 和 scope 外视图。

### 8.2 Canonical 规则

1. scope 统一小写，`market_id` 使用 canonical 形式；跨 scope 行只进入
   `outOfScope`，不得计入当前 scope 的缺失或孤儿。
2. 闭环地址型 `loop_key`、地址和符号均去空白并转小写；地址路径必须为闭合
   四段，任何比较都不得排序 Y/Z 后覆盖原路径。
3. `directed-symbol` 使用 `anchor|y|z`，保留 Y/Z 方向；`yz-group` 使用
   `anchor|sorted(y,z)`，只能证明组存在，不能证明两条有向闭环独立覆盖；
   物理 `loop-key` 必须直接比较闭环表与运行态表的完整地址路径。
4. `exactMatched`、`exactMissing` 和 `orphan` 均按 `--key-mode` 解释，报告
   必须同时输出不受 key mode 影响的三个诊断视图。每条闭环最多命中一条运行态；
   重复 canonical key、空 key、JSON 解析失败和未解析占位符号均生成 finding。
5. `outOfScope` 是独立清单：同一 SQLite 中属于其它 network/chain/protocol/
   market 的记录只登记、不参与当前 scope 匹配，也不单独导致主网审计失败。
   `scopeLeak` 仅表示当前 scope 的查询结果或映射实际混入其它 scope 记录。
6. 输出按 scope、闭环键和 finding code 稳定排序，便于跨窗口比较。
