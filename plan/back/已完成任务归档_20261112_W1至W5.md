### 关键事实更正

**原计划把"全量 `depth` 挂起"归因于 `rpc.ordofi.network` DNS 失效，实测并非真正阻塞。**

- `rpc.mainnet.chain.robinhood.com` 与 `robinhood-rpc.publicnode.com` DNS/连通均正常；
  `extsload(bytes32)` 批量调用实测 1.54s–3.34s 成功。
- `rpc.ordofi.network` 仅是 `rpc.fallbacks` 末位；
  `chain.rs:447` `read_v4_pool_states_with_fallback` 在**第一个返回 states/errors 的端点即返回**，
  主端点成功时根本不会触达失效端点。
- **真正的挂起根因是扫描范围**：`lib.rs:1172` `collect_candidate_pool_ids`
  默认取 `SELECT DISTINCT pool_id FROM v4_exchange_pool_liquidity_snapshots`
  = **4669 个池**（实测 dry-run 两次分别超时 304s / 244s 被杀）。
- 结论：`DEP-P1-9` **降级**为次要加固项（DNS 预检 + 移除死端点），
  不再作为"全量 depth 会挂起"的解释。

## 5. W5｜池容量口径复核、并发口径与文档

### 5.1 `DEP-4.2` 容量分带重定义 ✅（**本批最重要的语义变更**）

#### 发现的问题

原始单位分带（100 / 1,000 / 10,000）把 **6 位小数的 USDG** 与
**18 位小数的 token** 放在同一阈值下比较：

- 94 个候选池中 **93/94 被判成 `deep`** —— 等于没有区分度。
- `capacityRaw = max(token0, token1)` 掩盖了"弱侧吃不下"的情况：
  **15/93 个池的 `capacityToken0Raw == 0`**。

#### 修法：decimals 归一化的**绑定侧**容量

```text
capacityToken0 = capacityToken0Raw / 10**decimals(token0)
capacityToken1 = capacityToken1Raw / 10**decimals(token1)
bindingCapacity = min(capacityToken0, capacityToken1)
```

- 取**两侧较小值**：单侧能吃下但另一侧吃不下，该池对套利路径不可用。
- `decimals` 取自 `chain_tokens.token_decimals`
  （候选池 token 覆盖 **186/186 = 100%**）。
  取不到时回退原始 wei，并显式标记 `bindingCapacitySchemaPresent=false`。

#### 新分带（token 单位）

| 分带 | bindingCapacity 阈值 |
|---|---|
| `deep` | >= 0.1 |
| `medium` | >= 0.01 |
| `shallow` | >= 0.001 |
| `dust` | < 0.001 |

- `minCandidateCapacityRaw = 100` 降级为**尘埃护栏**，不参与分带。
- 准入下限 `minCandidateBindingCapacity = 0.001`。

#### 阈值锚定方式

以**实测尝试仓位**为锚，不使用分位数：

| 统计量 | `cow_execution_reviews.final_delta_amount` 绝对值 |
|---|---|
| 中位数 | ≈ 0.0208 |
| p25 | ≈ 0.1459 |

`shallow` = 最小尝试仓位 0.001，`medium` = 10×，`deep` = 100×。

#### 实测结果（94 个候选池）

**19 deep / 11 medium / 6 shallow / 58 dust**

测量来源：`pool-manager depth --dry-run --depth-scope candidate`
（94 池 / 13.05s / 0 errors），并可由 `capacityBindingRaw` **独立重算复现**
（`deep 19 / medium 11 / shallow 6 / dust 58`，合计 = 池数 94）。

| 指标 | 值 |
|---|---|
| 池数 | 94 |
| decimals 未解析的池 | **0** |
| 绑定侧容量为 0 的池 | **15** |
| 有容量错误的池 | 1 |

绑定侧容量分位数：

| p0 | p10 | p30 | p50 | p70 | p90 | p100 |
|---|---|---|---|---|---|---|
| 0 | 0 | 1.18e-06 | 2.53e-04 | 0.0171 | 2.685 | 99.92 |

> 该测量同时写入 `flashloan/config/depth_policy.json` 的
> `_bandCalibration.measuredOnCandidatePools`，作为分带阈值的校准依据。

### 5.2 `DEP-4.3` 并发口径拆分 ✅

**问题**：healer 与 Rust 运行时有两个都像"worker 限制"的数字，
被读成同一件事：`--candidate-limit 1` 看起来像单 worker 系统，
而实际常驻 16 个 worker。

**修法**：报告新增顶层 `concurrency` 段，三条轴分列：

| 字段 | 含义 |
|---|---|
| `concurrency.scanRequestCount` | 本轮**检查**了多少行/池（窗口属性） |
| `concurrency.scanReviewCount` / `scanPoolCount` | 上述计数的分项 |
| `concurrency.workerConcurrency*` | Rust 运行时**同时**能跑多少复核 worker |
| `concurrency.candidateLimitPerRound` | healer **每轮提交**的修复请求数（**不是**并发） |

- Rust `max_workers` 默认 **16**，worker pool 内部 clamp 到 `1..32`。
- healer `--candidate-limit`（默认 5）只限制每轮主动 repair 请求数，
  仍可由 16 个 worker 中任意一个执行。**两者无关。**
- `runtime_concurrency_snapshot()` 从 runtime API 读活体计数；
  runtime 不可用时**显式标记 unknown**，绝不猜。

**实测输出**：
```text
CONCURRENCY  workers(active/configured)=None/16 ceiling=32 unknown=True
             scanRequests=1470 (reviews=1356 pools=114) candidateLimitPerRound=5
```

### 5.4 `DEP-P2-9` CI 二进制 vs 源码一致性检查 ✅

**新增** `scripts/verify_pool_manager_binary_matches_source.py`，
比较两个独立事实：

| 项 | 含义 |
|---|---|
| `commandSet` | 部署二进制 usage 行宣告的子命令 vs 源码 dispatch 实现的子命令（含别名） |
| `sourceDigest` | 对 crate 源码（`src/**/*.rs` + `Cargo.toml`）的 SHA-256 摘要 |

- 退出码 0 = 一致；1 = 不一致，并列出 `problems`。
- stamp 文件 `flashloan/tools/target/debug/pool-manager.source-stamp.json`
  由 `--write-stamp` 生成。
- **已接入 healer**：`tooling.sourceConsistency` →
  新 blocker `pool_manager_binary_out_of_sync`。
  校验**未执行**时标 `verified=false` / `valid=null`，**不当作通过，也不当作缺陷**。

#### 首次运行即发现真实部署缺陷

首次生产只读验收时报告：

```text
L0 tooling   valid=True binary=pool-manager.exe missing=none
     sourceSync verified=True valid=False problems=binary_is_behind_source,source_stamp_missing
productionState=tooling_deployment_gap reason=pool_manager_binary_out_of_date
```

即：部署的 `pool-manager.exe` 落后于源码（缺 `update-pair` / `rebuild-scope` / `scope` 别名宣告），
这正是 `AUD-P0-6` 那一类**静默 no-op**。已处置：

1. 重新构建并部署 `pool-manager.exe`；
2. 在源码 usage 行**显式列出全部别名**，使命令集可核对；
3. 写 stamp 并复检 → `valid=True`。

复检后 `productionState` 由 `tooling_deployment_gap` 回到 `pool_scope_drift`，
工具门禁恢复健康。
