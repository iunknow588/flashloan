## 7. 调度分工与错误证据专项（本轮新增基线）

### 7.1 目标线程模型

本系统必须按“监督线程常驻、工作线程按需消费、单路线故障隔离”的模型运行：

```text
scanner-main（常驻）
  -> 只负责增量扫描、生成/刷新 route snapshot

review-supervisor（常驻）
  -> 消费待复核 loop
  -> 回收超时 review lease
  -> 以 canonical loop_key CAS 领取
  -> 最多提交 16 个 review worker

review-worker[0..15]
  -> 执行单个 loop 的 live quote/static-call/review
  -> 成功、失败、异常都必须写回 cycle 和 runtime state
  -> 单个 loop 超时或异常只能隔离该 loop

broadcast-supervisor（常驻）
  -> 只消费 executionQueue
  -> 检查 executionQueued、queue age、scope isolation
  -> 不直接重发 raw transaction

broadcast-worker[2/4/8]
  -> 领取一个 execution task
  -> 执行一次广播和链上确认
  -> 透传完整 broadcast result/error evidence
```

当前 Rust pool 的 dispatcher、per-group resident worker 和 execution worker 可以作为实现基础，但必须补齐 supervisor 语义：

- scanner 不得承担结果回写和全部复核调度责任；
- review worker 必须使用同一 canonical key：`anchor|sorted(bridge_a,bridge_b)`；
- review claim 必须有 lease/heartbeat/过期回收；
- 单个 worker 异常不得终止 supervisor 或阻塞其他 route；
- broadcast 统一通过 executionQueue，禁止复核 worker 绕过队列直接广播；
- 进程异常退出后不得自动重发同一 raw transaction。

### 7.1A 主线程与工作线程的明确分工（执行契约）

本节将“常驻”定义为线程生命周期和消费循环，而不是“进程仍存在”。每个 supervisor 必须在异常后捕获、记录并继续消费；单条任务的 RPC、链上调用、数据库回写和序列化异常只能结束该 task，并由 supervisor 回收 lease/生成隔离状态。

| 组件 | 生命周期 | 只负责 | 不负责 | 单条任务异常后的动作 |
|---|---|---|---|---|
| `scanner-main` | 常驻，每个扫描窗口 tick | 读取增量游标、刷新机会/闭环输入、投递 review queue | 等待链上复核、直接广播、阻塞等待某条 route | 记录 scan error，保留游标，继续下一窗口 |
| `review-supervisor` | 常驻，持续消费 review queue | 去重 canonical key、检查 scope/隔离、CAS claim、分派最多 16 个 review worker、回收超时 lease | 执行具体 RPC、直接写广播结果 | 标记该 cycle 的 error/disposition，继续领取其他 loop |
| `review-worker[n]` | 按需创建或从 bounded pool 取出，n=0..15 | 只处理一个 `review_cycle_id`，执行 fork/static-call/on-chain review，心跳和一次性结果回传 | 领取第二条 loop、直接广播、修改其他 loop 状态 | `finally` 回传失败并释放/隔离自己的 lease，不能杀 supervisor |
| `broadcast-supervisor` | 常驻，持续消费 execution queue | 检查 live-ready、scope、cooldown、CAS claim、超时回收和结果落库调度 | 重签、重发、替换 raw transaction | 生成结构化 broadcast failure/isolation，继续其他 task |
| `broadcast-worker[n]` | 按需创建或 bounded pool，默认 2/4/8，硬上限 16 | 一次领取一个 execution task，执行一次既定 raw transaction 广播及确认查询 | 生成新 nonce、修改 gas、同 raw transaction 重试/重签 | 透传错误证据，按 disposition 进入 failed/pending/quarantine |
| `persistence-writer`（可由 supervisor 内部实现） | 常驻或串行写入器 | 以 generation/CAS 写 attempt、review、broadcast 和审计结果 | 重新计算机会、代替 worker 重试 | 写入失败只影响当前结果，产生 `persist_failed`，不阻塞其他 loop |

硬约束：

- supervisor 使用 bounded queue，队列满时记录 backpressure，不在 scanner 或 worker 中无限等待；
- review worker 与 broadcast worker 不共享“全局单任务锁”，只按 canonical key/generation 做 CAS；
- 一条 loop 卡在 `preflight_running` 或 `execution_running` 时，只回收该 loop 的 lease，其他 loop 仍可被领取；
- worker 的超时必须有上限，超时后进入 `review_timeout`/`broadcast_timeout`，不得依赖线程自然返回；
- `executionQueue` 是广播唯一入口；review 结果只能产生 `execution_queued`，不能在 review 调用栈内直接发送交易；
- 每个窗口必须记录 `queue_depth/claimed/running/completed/failed/isolated/skipped`，以证明“系统持续运行”确实等于“持续消费”。

### 7.1B 当前停滞问题的验证重点

针对 2026-10-29 最后一条复核记录，下一轮代码和运行 evidence 必须分别证明：

1. scanner-main 在最后一条记录之后仍产生了扫描 tick 和新的增量 snapshot；
2. review-supervisor 仍在消费，且没有因某个 `NoProfitableRoute`/RPC timeout 持有全局锁；
3. 失败的 review cycle 已写入 `finished_at/state_after/errorKey/disposition`，没有遗留不可再次领取的 claim；
4. 有利润的 route 进入 broadcast queue 后，提交失败仍能落库真实错误，而不是只显示 `execution reverted`；
5. 没有新的 review/broadcast 时，系统记录“本窗口未触发”，不得把旧记录伪装成新复核。

### 7.2 Review lease 与 cycle 记录

每一轮复核必须可区分“未触发、执行中、已完成、结果落库失败、已隔离”。至少记录：

- `loop_key`、`generation`、`review_cycle_id`；
- `claimed_at`、`heartbeat_at`、`lease_until`；
- `worker_id`、`started_at`、`finished_at`、`persisted_at`；
- `result_fingerprint`、`state_before`、`state_after`；
- `errorKey/errorCode/disposition/isolationReason`。

过期 `preflight_running` 只能通过 CAS 回收到 `offchain_estimate` 或自动隔离，不能手工修改 SQLite，也不能跨 loop 清理。

### 7.3 广播失败证据透传

广播提交失败不得只保存 `execution reverted`。Rust RPC 层、worker payload、Python attempt、SQLite summary 和页面必须尽力保留：

- `rawError`、`error`、`errorKey`、`errorCode`、`errorName`、`disposition`；
- `revertData`、`revertSelector`、解码后的 `revertReason`；
- `rpcMethod`、`rpcUrl`（脱敏）、`broadcastChannel`、relay 名称和 relay errors；
- `submitted`、`txHash`、receipt status、block、gasUsed、effectiveGasPrice；
- 无 `tx_hash` 时明确标记 `submission_rejected_before_acceptance`；
- 有 receipt status=0 时明确标记 `execution_reverted_onchain`。

`requires_live_quoter` 只能表示报价证据门禁，不得覆盖 `eth_sendRawTransaction` 的广播错误。没有 revert data 时必须显示“具体合约原因不可验证”，不得伪造具体原因。

### 7.4 本专项验收

- 一条 loop 卡在 `preflight_running` 时，其他 loop 仍能复核、落库和进入队列；
- canonical key 不再产生三段 claim/四段回写分裂；
- review lease 过期后只回收对应 loop，并生成审计记录；
- review worker 异常、RPC timeout、结果回写异常均不会杀死 supervisor；
- 2/4/8 broadcast worker 不重复领取或广播；
- `execution reverted` 且无 tx hash 的记录包含 `submission_rejected_before_acceptance`；
- 有 tx hash 且 receipt status=0 的记录包含 `execution_reverted_onchain`；
- `requires_live_quoter` 不再作为广播提交失败的唯一原因；
- 既有 SQLite、历史 evidence、latest.json 不通过手工补字段修改。
