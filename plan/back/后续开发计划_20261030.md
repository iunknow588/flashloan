### 3.4 链上合约单一最新版本与测试网先行验证（2026-10-31 更新）

本轮目标：链上只维护并调用一个最新可用的 `OfficialV4FlashArb` 版本；不继续用多个合约地址做对比测试，也不关心已废弃版本。测试网先用最新合约稳定产生复核/广播记录，之后再按同样流程迁移主网。

根因结论与已完成的定位工作：

- 之前使用手写 Python calldata 直连测试网时出现空 revert，实际是 calldata 编码问题，不是合约问题。用 ethers 正确编码 `previewBestPoolDetailed` 后，测试网最新合约 `0x1A8Cc533EaBA93Ec7f68Ac6c428cDa948D7bB8DE` 对官方路线 ETH -> `0x5884ad2f...` -> `0xc9f9c869...` -> ETH 成功返回数值（`netProduct=999727175024391723`，当前为低收益/不可盈利，但调用本身成功）。
- 测试网最新合约本地 artifact `deployedBytecode` 与链上 `eth_getCode` 长度一致（11415），selector 均含 `c5e1d636`/`eaeeafa8`，链上部署版本与本地源码一致。
- 测试网运行时 `flashloan/src/chains/robinhood-testnet/chain.json` 之前仍指向旧地址 `0x9b4FEB...`，这是运行时预览/广播使用旧合约的直接原因。现已统一到最新地址 `0x1A8Cc533EaBA93Ec7f68Ac6c428cDa948D7bB8DE`。
- 主网旧地址 `0xf73f921f0EcA56c8e5816390d2Af378fC8173D3F` 不再作为对比测试目标；主网部署新版本只会在测试网稳定后执行。

本轮新修复（2026-10-31）：

### 3.5 默认链一致性根因与修复（2026-10-31）

问题表现：测试网 46630 一直能正常运行，主网 4663 切过去后出现“默认值只影响主网”的现象。根因不是主网代码分支缺失，而是历史默认链在多个层级隐式指向测试网：

- 早期 `registry.json`、启动脚本和链选择逻辑的兜底默认是测试网 46630；任一默认层没有被同步时，未显式传 `chain_id` 的组件都会静默回退到测试网数据库。
- 测试网因为有完整旧数据，即使回退也“看起来能跑”；主网没有同样的测试网兜底数据，于是表现为主网不能正常扫描/复核/广播。
- 此外 `chain_selection` 仍可能信任 SQLite 旧 `is_default`，导致页面/接口在切链后读到过期默认。

已实施修复：

- `flashloan/src/chains/registry.json` 的 `default_chain_ids` 统一为 4663。
- `flashloan/app_runtime/run.py` 在启动时按 active chain 一次性写入 `FLASHLOAN_DEFAULT_CHAIN_ID_DEX_ARBITRAGE/FLASH_LOAN_POOL_PAGE/LIQUIDATION`，并显式写入 `FLASHLOAN_KV_PATH`。
- `chain_selection.py`、`market_profiles.py`、`chain_route_selector.py` 等链选择器优先以运行时 active/default 为准，不再依赖旧库 `is_default`。
- `.env` 同步写入三处默认链与 `local_store_4663.sqlite3`；`.env.example`/README/测试同步更新。

验收：重启后 `/api/chain-selection?feature=dex_arbitrage` 选中 `dex-arbitrage-4663-uniswap-v4`；任意未显式传链的页面/后台组件都落到 4663 库，不再回退 46630。

  `SwapNotResolved() = 0xb20c2204`。页面因此出现“无具体盈亏数值”。

  给出结构化参考盈亏，导致无法区分“确实无利”和“结算失败被吞”。

  1. `_native_worker_evidence` 在无链上 signed profit 时，必须从 SQLite/

### 12.5 2026-11-02 用户确认：闭环不重复检测池质量

#### 功能定位

- 候选池和推荐池进入闭环前，必须已经满足同一套池质量口径：
  固定费率 `0 < fee <= 3000`、非 dynamic/special fee、无 hook
  （`hooks` 为空或零地址）、有已确认深度/流动性。
- 闭环拿到 route 后直接使用其中的 PoolKey 和池身份，不再在
  `dex_route_helpers.py`、`rust_closed_loop.py` 或 worker 入队层重复做一套
  池质量过滤。重复检测属于冗余设计，不纳入本轮实现。
- 闭环侧的职责是保证 route 数据完整、地址/PoolKey 连续、revert 可诊断，
  不负责把上游不合格池重新判定为合格。

#### 为什么测试网稳定、主网会出现差异

- 测试网 46630：池候选集合小且稳定，股票代币身份来自链属静态 JSON；

  高费/无深度池”这类问题不容易进入闭环 route。
- 主网 4663：`v4_exchange_pools` 是 live 全量池索引，原始表中包含
  dynamic/special fee、`fee > 3000`、非零 hook、`thin`/无确认流动性快照
  等池。候选池/推荐池表面是“从全量池推导出的合格子集”，不是 raw 表的
  同义词。任何路径若从 raw 表、旧缓存或尚未完成池索引刷新的 symbol 级
  候选直接构造闭环，就会把测试网不会出现的问题带到主网。
- 已观察到的主网差异主要是两类：
  1. symbol 级 route 在池索引刷新完成前进入 `build_group_task_config`，
     导致 `missing_pool_candidates_or_token_metadata`。
  2. 从 raw/旧 payload 取 PoolKey 时缺少候选层约束，可能把非固定费率、

- 候选/推荐构造入口继续以 `_observation_pool_usable`、

  判定标准，确保进入 `db_closed_loop_sequences` 的每个 hop 都是合格池。
- 主网缺池/symbol 级候选不进入闭环，等待下一轮池索引刷新后重试；已落地在
  `dex_opportunity_scanner_rust_mixin.py`，不写缺池失败 review。
- 后续若发现某个 route 仍携带不合格池，根因定位到候选层或 route 构造层，
  修复上游，不在闭环握手处追加重复过滤。

补充职责收敛：上述“候选层”由独立 Rust `pool_manager` 负责。闭环/UI 不再把
raw `v4_exchange_pools` 当作候选池源，也不重复执行池合规清洗、候选排序或删除；
只读取 `dex_candidate_pools` 等共享 SQLite 结果。若候选数量不足、池身份缺失或
共享结果失效，下游写入结构化 `pool_manager_refresh_required` 诊断并按 KEY ID
请求 `refresh-key`；刷新接口只返回成功/就绪信号，池明细继续由外部 SQLite
查询并自行排序。池管理工具不写闭环表，闭环构建仍由下游负责。

## 15. 2026-11-02 追加：池管理工具唯一上游与 refresh-key 契约

- 一组 KEY 会对应多个池子，合规池明细统一写入共享 SQLite 候选池表；外部

  工具处理。

  `pool_manager_extsload_live_state_batch` / `_rust`、`has_liquidity=1` 且
