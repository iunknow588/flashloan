## 2. `AUD-P0-6` 部署工具版本门禁

### 2.1 缺陷根因

`scripts/mainnet_arbitrage_healer.py` 通过 CLI 驱动 `pool-manager`：

```
repair()
  ├─ ensure_review_indexes()  → pool-manager ensure-indexes
  ├─ ensure_depth_schema()    → pool-manager ensure-depth-schema
  ├─ refresh_pool_depth()     → pool-manager depth
  └─ repair_pool_depth()      → pool-manager depth
```

部署目录 `flashloan/tools/target/debug/pool-manager.exe`（2026-11-11 10:53）
只实现了：

```
<audit|cleanup|add-pair|refresh-pair|materialize-scope|scope-status>
```

即**不认识** `ensure-indexes`、`ensure-depth-schema`、`depth`。

旧版 `repair()` 对每次 `run_tool()` 的返回值只检查 `ok`，失败时**继续执行
下一步**，而报告仍然输出「已完成」。实测：

```
=== reviewIndexes / pool-manager ===  ok=False  stderr=unknown command: ensure-indexes
=== depthSchema    / pool-manager ===  ok=False  stderr=unknown command: ensure-depth-schema
=== poolDepth      / pool-manager ===  ok=False  stderr=unknown command: depth
=== pools          / pool-manager ===  ok=True
```

**后果**：整个容量铺设是一个静默 no-op —— 深度快照从未刷新、容量列从未出现，
而报告看起来是绿的。

### 2.2 修复

- `scripts/mainnet_arbitrage_healer.py`
  - 新增常量 `POOL_MANAGER_REQUIRED_COMMANDS`
    （`audit` / `cleanup` / `materialize-scope` / `ensure-indexes` /
    `ensure-depth-schema` / `depth`）；
  - 新增 `pool_manager_command_support(tools)`：**只读**探测
    （无子命令调用二进制 → 解析 usage 行 → 比对命令集），输出
    `available` / `binaryModifiedAt` / `missingCommands` / `complete` /
    `reason`；
  - `build_report(db, hours, tools)` 新增 `tooling` 层，并给出显式 `valid`
    键（缺失 `valid` 会被层级扫描当成失败层，制造幽灵 blocker）；
  - `tooling_blocker()` 把部署缺口转成具名 blocker
    `pool_manager_commands_missing`；
  - `transaction_production_status()` 新增独立分支
    `tooling_deployment_gap`（优先级高于 `pool_scope_drift`，因为工具过期
    会让下游所有缺陷**永远不会自愈**）；
  - `print_report()` 新增 `L0 tooling` 行。
- 调用点全部接入 `tools`：`check` / `repair` / `watch` / `supervise`。

### 2.3 部署修复

`flashloan/tools/target/` 是 gitignore 的构建产物目录（`git check-ignore`
确认），其中的 `pool-manager.exe` 已重建到与源码一致：

| 二进制 | 修复前 | 修复后 |
|---|---|---|
| `target/debug/pool-manager.exe` | 2026-11-11 10:53 | 2026-11-11 20:07 |

## 4. `AUD-P2-6` Rust 容量计算 `u128::MAX` 饱和缺陷（本批次最重要的修复）

### 4.1 缺陷表现

链上实测（`pool-manager depth --dry-run`）：

```json
{"capacityRaw":"340282366920938463463374607431768211454",
 "capacityToken0Raw":"340282366920938463463374607431768211454",
 "capacityToken1Raw":"99768811833039500209576",
 "priceImpactBps":0.0}
```

`340282366920938463463374607431768211454` = `2^128 - 2`，即
**饱和哨兵值**，不是真实容量。`priceImpactBps` 同时是 `0.0`。

### 4.2 根因链

1. `spot_amount_out()` 用 256 位乘法计算 `amountIn * sqrtP^2 / Q192`。
   当 `amountIn` 接近 `u128::MAX` 时，中间积超出 256 位，
   `ruint` 的乘法**静默回绕**，结果落到 `2^64 - 1`。
2. `price_impact_for_input_with_backend()` 随后比较
   `amount_out >= spot_out`。由于 `spot_out` 已被压低，这个不等式对**任意
   巨额输入**都成立，于是价格冲击被报告为 **恰好 0**。
3. `solve_capacity()` 的二分搜索上界不断倍增，始终落在这个「零冲击」区间，
   最终把饱和值当成真实容量输出。

复现（修复前）：

```
amount=1000000000000000       impact=Ok(0.00010016124905418662)
amount=1000000000000000000    impact=Ok(0.10016025206550677)
amount=340282366920938463463374607431768211454  impact=Ok(0.0)   ← 饱和
```

### 4.3 修复

- `flashloan/tools/pool_manager/src/depth.rs`
  - `spot_amount_out()` 改用 SDK 的 **512 位精确 `mul_div`**，并在转型
    `u128` 之前做上限钳制；
  - 新增 `reserve_ceiling()`：池的虚拟储备上限
    （token1 out 为 `L * sqrtP / Q96`，token0 out 为 `L * Q96 / sqrtP`），
    用 512 位 `mul_div` 计算，避免 `L << 96` 在 256 位内溢出；
  - `price_impact_for_input_with_backend()` 在 `spot_out > ceiling` 时返回
    错误：**超出储备上限的金额没有有意义的冲击值**；
  - `solve_capacity()` 的搜索上界被钳制在 `ceiling` 以内，二分搜索不再
    进入饱和区。

### 4.4 修复效果（链上实测，同一批池）

| 池 | 修复前 `capacityRaw` | 修复后 `capacityRaw` | 冲击 |
|---|---|---|---|
| `0x2077…` | `340282366920938463463374607431768211454`（饱和） | `99938943274133825410` | 10.0 bps |
| `0x509c…` | `340282366920938463463374607431768211454`（饱和） | `2130400100532712269` | 10.0 bps |
| `0xd1ae…` | `2406735040102765` | `2406735040102765` | 10.0 bps |

第 3 个池修复前就是正确值 —— 说明缺陷**只在部分池上触发**（取决于
`sqrP` 与金额的组合），因此此前没有被基线发现。

### 4.5 Python 侧对照

Python 实现 `flashloan/src/dex/intent_trade/chains/robinhood/v4_pool_capacity.py`
使用任意精度整数，**没有**这个缺陷：

```
amount=340282366920938463463374607431768211454  impact=9999.999999999996  ← 正确
cap = {'capacityRaw': 99938936973127434099, 'priceImpactBps': 10.0, ...}
```

也就是说 Python 是正确参考实现，**Rust 是偏离的一方**。修复后两者一致。

## 5. `AUD-P3-6` Rust 工具链配置回退

### 5.1 缺陷

`pool-manager depth` 在没有环境变量时报错：

```
pool-manager error: no RPC endpoint configured; set ROBINHOOD_MAINNET_RPC_URLS or pass --rpc-url
```

但 Python 侧 `chains/robinhood/config.py::rpc_urls_from_env()` 在没有环境变量
时会回退到链配置行 `rpc_urls` / `rpc.primary` / `rpc.fallbacks`：

```
https://rpc.mainnet.chain.robinhood.com
https://robinhood-rpc.publicnode.com
https://rpc.ordofi.network
```

Rust 侧只读环境变量，**两侧口径不一致**，导致工具在一台「端点写在配置文件
而不是环境变量」的机器上直接不可用。

### 5.2 修复

- `flashloan/tools/pool_manager/src/chain.rs`
  - 新增 `rpc_urls_from_chain_config()`：读取
    `flashloan/src/chains/robinhood/chain.json` 的 `rpc.primary` /
    `rpc.fallbacks` / `rpc.urls` / `rpc_url` / `rpc_urls`；
  - 新增 `chain_data_roots()`：从当前目录与可执行文件位置**向上查找**
    `flashloan/src/chains`，兼容从仓库根、`flashloan/tools` 或安装目录启动；
  - 新增 `rpc_urls()`：**环境变量优先**，为空时回退链配置
    （与 Python 口径一致）。
- `flashloan/tools/pool_manager/src/lib.rs`：深度刷新改用 `chain::rpc_urls()`。

### 5.3 副作用

链配置里的第三个端点 `rpc.ordofi.network` 当前**无法解析**。批量刷新 114 个
候选池时会对它反复等待超时。实测 `--pool-id` 定向读取 3 个池耗时 8.9s，
全量读取会挂住并在后台留下孤儿进程（本批次已清理 PID 27456）。

> 该端点是**链配置自带**的既有条目，本批次不改动链配置；
> 建议在 S2.5' 生产链开启前从 `chain.json` 移除或修复该端点。
