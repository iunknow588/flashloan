## 4. 推进顺序

### Phase A：M3-1 恢复生产扫描（等待用户确认维护窗口）

1. 只读核对并记录恢复前 snapshot。
2. 备份 `flashloan/db/local_store_46630.sqlite3`（含 `-wal`/`-shm`）。
3. 先跑 `--dry-run`/`--verify-only`，不写在线库。
4. 小批量资金池扫描并逐步扩大，再顺序重建候选/市场观察/闭环。
5. 重跑四类 evidence 与 validate，确认 `rpc_transport_error=0`。
6. 恢复扫描后进入 Phase B。

### Phase B：M1/M2/M8-1/P1 观察（依赖恢复扫描）

1. M1 每轮 SOP：核对 5000/5001 与 attempts/reviews 计数，有新窗口才重跑 evidence；扫描 live-ready、`execution_success`/`tx_hash`。
2. M2 条件触发：新 unique success 后依次验证 P&L、auto-scan、expected-vs-actual、差异逐跳分析。
3. M8-1：连续观察“live-ready 复核 -> 自动广播 -> success 落库”无断点。
4. P1：在 2/4/8 worker 下记录 `executionQueue` 摘要，确认无饿死、无重复广播。

### Phase C：M4/M5 外部依赖（等待审批/登记，不阻断工程线）

- M4-1：canary/executor evidence 齐备后重跑 predeploy readiness。
- M4-2：业务完成 P0-14 审批后补主网 static-call/readback evidence。
- M4-3：P2-04 负责人登记后完成 SLO/告警、失败回滚演练与 USD 盈利观察。
- M5-1/M5-2：参数/搜索模式调整前必须有链上 evidence；所有复检一律 `--no-write`。

### Phase D：已知剩余风险（不在本轮范围）

- `test_api_scope_policy.py` 对 `/api/binance-market/bnb-rust-store`、`/api/binance-market/broadcast-failures` 暂缺 response schema 登记，属 BNB 既有工作树改动。
- 架构守卫仍有既有告警：`control_panel_app.py` silent broad exception、`flashloan/app_runtime/flashloan` 嵌套目录、两个源文件超行数限制。
- testnet chain.json/contract manifest 与 authoritative manifest 不一致；`app_runtime/.env` 含主网广播开关。上述为用户配置/既有工作树，不擅自修改。

## 7. 安全边界（禁止事项）

- 禁止手工修改 evidence、SQLite、`latest.json` 或运行时 API；readiness 只能由 CLI 写入。
- 禁止用旧 `live_verified` 记录或手工 attempt JSON 冒充当前包。
- 禁止把 SQLite 参考 P&L 标记为 eth_call 链上复核结果。
- 禁止跨 RPC 重发广播/提交；RPC failover 只用于只读复核。
- 禁止擅自启动、重启、kill 生产进程；受控操作前确认无进行中复核。
- 禁止在无链上 evidence 时调整参数或搜索模式。
- 禁止将历史 success（仅存 evidence）伪造成在线 SQLite 成功记录，或作为 M9-1 已满足依据。
- 禁止直接对遗留 `flashloan/db/local_store.sqlite3` 或 3.6GB 生产库执行非 dry-run 分库/迁移。
