## 1. 当前目标

围绕 Robinhood Mainnet `4663` 建立可验证的闭环运行链路：

```text
代币准入 -> 资金池 -> 候选池 YC/ZC -> YZ 中间池 -> 闭环 -> 复核 PnL -> 广播 -> 终态统计
```

同时推进 Rust 管理模块重构：

```text
Token Manager
  -> Pool Manager
  -> Candidate Edge Pool Manager
  -> Candidate Exchange Pool Manager
  -> Closed-loop Manager
  -> Review Manager
  -> Broadcast Manager
  -> Composite Manager
  -> UI API
```

最终要求：只有 Token Manager 已确认的代币可以进入后续套利模型；UI 页面保持不变，
但只调用管理模块接口，不直接读写 SQLite。

1. `manager_api` 只解析请求头、JSON、DTO 和 stable error；状态变更由

3. `dryRun=false` 只有状态实际变化时才递增库版本并写 event；相同状态返回
   `changed=false`，不制造无意义事件。
4. `actor` 固定为 `manager_api`，`requestId` 只进入审计 event 的
   idempotency/evidence 载荷，不写入 `admission_source`。

   `INVALID_REQUEST`，不允许用审计查询写入或修复表。

D1.2.4 的 authority 边界：

1. `TOKEN_MANAGER_AUTHORITY` 未设置或为空时按 `legacy` 处理，保证现有主网服务

2. `legacy` 只允许 Python 旧写入，Rust admission `apply` 返回
   `TOKEN_AUTHORITY_WRITE_DENIED`；`dryRun=true` 仍可用于切换前比对。

   metadata 修复工具的第二权威写入失败关闭。

   `chain_tokens` 行，避免破坏迁移期仍存在的外键和旧池引用。`dryRun` 与

   state 和 admission event 均不得删除。重新切回 `manager` 后，第一次投影可

6. 生产切换前必须依次完成 manager migration、四库 bootstrap、双读比对、

#### D9.23 Review/Broadcast 管理工具运行边界修正（2026-11-06）

- 架构结论：`Review Manager` 与 `Broadcast Manager` 不是仅做 SQLite 持久化的
  “状态层”，而是两个相互隔离的完整管理工具。复核管理工具拥有复核主线程、唯一
  复核队列和有界复核工作线程；广播管理工具拥有广播主线程、唯一执行队列和有界广播
  工作线程。主线程负责生命周期、派发、背压、心跳、恢复和终态，工作线程只执行任务。
- `manager_api` 是唯一 HTTP/JSON 命令和读取入口，但不拥有线程或队列。Flask、UI
  聚合对象和页面都不得启动、停止、调速或直接操作 Review/Broadcast 主线程与工作线程。
- 当前 M6/M7 crate 已完成 durable schema、幂等、证据和终态部分。全部管理工具及
  其主线程、队列和 worker 必须以 Rust 实现；Python `ReviewSupervisor`、
  `ClosedLoopReviewQueue` 和 `BroadcastSupervisor` 只能保留为测试、回归夹具或

### 5.1 Token Manager

Token Manager 维护四类分级库：

- 核心表 `token_core`：`USDG`、`USDE`、`ETH`、`WETH`。
- 股票表 `token_stocks`：股票代币。
- 扩展表 `token_extension`：与 core、股票或 TZ 存在通过流动性门槛的直接 V4
  池、且 metadata 已归一化通过的代币；允许包含 core、stock、TA、TB 的派生成员行。
  这里只判断直接交换关系和链上流动性，不要求 USD、美元 TVL 或
  `deep/thin/unpriced` 标签。
- 测试表 `token_test`：每个 network 仅 `TZ` 一个显式地址。

Pool Manager 从这些库中选择启动代币，但不管理库内原始资料。原始资料只由
Token Manager 维护。首期从现有 `chain_tokens` 和 `v4_exchange_pools` 导入
基线，后续只做增量维护，不做全量区块重放。

每个代币最多一个 `core/stocks/test` 主库；`extension` 是派生成员库，可与主库
重叠。重叠行只表达池邻接资格，不产生第二份 metadata/admission 权威来源；
下游按 `library_key` 读取库版本和 checksum。

每张表使用稳定的 `token_key_id`，由 `chain_id + normalized_token_address`
确定。Pool Manager 可以接收 symbol 用于配置和展示，但必须先通过 Token Manager
解析为 `token_key_id`；池子索引、交易对和候选引用不得以 symbol 字符串作为
持久化主键。

KEY ID 采用 V4 身份规范。Token Manager 维护 `v4_currency_key`（规范化代币
地址）；Pool Manager 用它组成 V4 `PoolKey`，再按现有 `V4PoolKey` 编码计算
`v4_pool_id`。fee、tick spacing、hooks 和 Pool ID 属于 Pool Manager，不写入
四张代币表。

必须提供：

- 代币元数据和可信来源。
- admitted/blocked/pending 状态。
- token library、token class 和 scope。
- 变更原因、版本和 checksum。
- `GET tokens`、`POST admit`、`POST block`、`GET audit` 接口。

### 5.2 Pool Manager

- 只消费 admitted token。
- 支持 `full`、`core4` 等启动方式。
- `core4` 的唯一定义和内容归属是 Token Manager；Pool Manager 只引用
  `core4` 库的 `library_key + library_version + checksum`，不建第二份 core4 表，
  不维护代币清单，因此不会形成双重所有权。
- 每种启动方式通过 `library_keys` 选择 `token_core`、`token_stocks`、
  `token_extension` 或 `token_test`；池管理不复制、不编辑库内原始资料。
- Pool Manager 使用 Token Manager 返回的 `token_key_id` 组合池子、交易对和
  候选边 KEY ID，symbol 仅用于配置匹配、日志和 UI 展示。
- 每种启动方式选择对应资金池配置表。
- 库引用和池筛选是两个独立配置项。“由 core4 提供启动代币”不自动等于“池子
  两端都必须属于 core4”；应通过 `edge_any` 或 `both_end` 等池筛选模式明确选择。
- 池质量、流动性和池有效性修复由 Pool Manager 负责。

### 5.3 Candidate Edge Pool Manager

- 消费 Pool Manager 的合格资金池。
- 独立管理“资金代币到候选代币”的边池：资金池到 YC、ZC 回到资金池。
- 候选代币必须同时满足 Token Manager admitted 状态和当前候选库范围。
- 生成 YC/ZC 集合、边池引用、推荐池和异常池。
- 迁移期只写 `manager_dex_candidate_*` shadow，不写旧 Python
  `dex_candidate_*`，不写 Y-Z 中间池、闭环或广播记录。
- `candidate_authority` 与 token/pool authority 独立；默认 `legacy` 时只允许
  dry-run 和 compare-only，不能因 token authority 已切换而顺带开放写权限。
- compare-only 必须输出两侧 checksum、单边行、字段差异、未解析 anchor 和原因
  计数；比对不写业务表、事件或幂等记录。美元深度、美元 TVL 和 USDG/USDE
  关系不得进入候选或比较门禁。

### 5.4 Candidate Exchange Pool Manager

- 消费 Candidate Edge Pool Manager 的 YC/ZC 集合、Pool Manager 的合格交换池
  和 Token Manager 的元数据。
- Candidate Exchange scope 固定使用 `both_end`，可从全部 admitted 库选择合格
  直接池；允许两端均非 core，但每个池两端都必须能解析为当前 admitted
  `token_key_id`。
- 独立管理候选代币自身的交换池，即为每个 anchor 生成全部有序 `YC -> ZC` 和
  Y-Z 中间池。无池方向必须保留结构化 empty reason，不能伪造池或最优选择。
- 迁移期只写 `manager_market_observation_*` shadow，不写 legacy
  `market_observation_*`、候选边池、闭环或广播记录；生产切换窗口后才接管
  legacy 表名。
- `CANDIDATE_EXCHANGE_MANAGER_AUTHORITY=legacy|manager|rollback` 与 token、pool、
  candidate authority 独立；默认 `legacy` 时只允许 dry-run 和 compare-only。
- `expectedUpstream` 必须锁定 Candidate Edge 版本/checksum、Pool scope checksum
  和四个 token library 版本/checksum。上游不一致或跨版本组合必须在写入前拒绝。
- compare-only 必须输出 YZ、正常池、异常 YZ、异常池的双方 checksum、单边行、
  字段差异和原因计数。美元深度门已取消，因此仅由旧美元深度条件造成的
  manager-only 池可归因 `legacyUsdDepthGateRemoved`；字段差异和 legacy-only
  仍需修复。
- 输出 observation version、YZ checksum 和 `consumersNeedRebuild`，供
  Closed-loop Manager 使用。候选池与 YZ 交换池均不要求美元估值或
  USDG/USDE 关联。

### 5.5 Closed-loop Manager

- 只消费 `manager_dex_candidate_*` 与 `manager_market_observation_*` 的单一
  版本组合；不允许跨 M3/M4 版本混用，也不允许 observation 内记录的上游与
  当前 Candidate Edge 状态不一致。
- 固定生成 `loop_key = anchor:y:z`、`route_key_id`、3 段 hop、备份池、候选
  优化项和 `ready_for_review` 运行状态。输出
  `manager_v4_closed_loop_*` shadow，不写 legacy `v4_closed_loop_*`。
- 不执行链上复核，不计算最终 PnL，不直接发送交易，不创建 Review/Broadcast
  请求。每次内容变化必须输出 `consumersNeedRebuild=true`。
- 闭环不要求美元深度、美元 TVL 或 USDG/USDE 关系；Y-Z 中间池只要 M3/M4
  admitted 且可解析 `TokenKeyId` 即可进入。
- `CLOSED_LOOP_MANAGER_AUTHORITY` 与 token/pool/candidate/candidate_exchange
  authority 独立；默认 `legacy` 时只允许 dry-run 和 compare-only。
- compare-only 必须输出 loops/hops 双方 checksum、单边行、字段差异和原因；legacy
  表缺失时标记 `legacyTablesAvailable=false`，字段差异与 legacy-only 阻止 cutover。

### 5.6 Review Manager

- 消费 Closed-loop Manager 的闭环。
- Review Manager 同时是复核结果/状态的唯一持久化 Manager 和复核 runtime owner。
  Rust `review_manager::ReviewSupervisor` 持有唯一复核主线程、命令队列和有界
  worker，`ReviewRuntime` 管理 permit 与生命周期计数。Python
  `ReviewSupervisor`、`ClosedLoopReviewQueue` 和 `ThreadPoolExecutor` 只用于测试
  或 legacy fallback，不进入 native 生产装配。
- M6 阶段先接收外部 `runArbitrage` 证据并做静态复核：校验 `ok`、
  `executable`、block 和 signed PnL，持久化原始证据与结构化诊断；链上 RPC
  复核仍由现有执行适配器在 P0 门禁内提供，不等同于 Manager 已直接发交易。
- 每个已完成的闭环复核必须持久化具体 signed PnL，包含数值、单位、币种和来源。
  revert、不可执行或报价失败只能作为诊断；缺少具体 PnL 时状态必须为
  `data_incomplete` 并进入修复重试，不能计为复核完成。
- 只有确认可执行的正收益才生成广播请求，不直接发送交易。
- `REVIEW_MANAGER_AUTHORITY` 与 token/pool/candidate/candidate_exchange/
  closed-loop authority 独立；默认 `legacy` 时只允许 dry-run 和只读。

### 5.7 Broadcast Manager

- 只接受 Review Manager 已确认的广播请求。
- M7 `broadcast_manager` 同时是持久化终态权威和广播 runtime owner。
  `broadcast_manager::ExecutionQueue` 持有唯一广播队列，
  `BroadcastSupervisor` 启动 `rust-broadcast-manager-exec-*` worker；
  `ClosedLoopWorkerPool` 只做 PyO3 宿主和执行适配。Python `BroadcastSupervisor`
  仅用于测试或 legacy fallback，不创建第二套队列。
- M7 Manager 负责广播请求、attempt 生命周期、nonce/RPC/gas/回执/终态和结构化
  诊断的持久化与只读快照，不启动线程、不直接触网。runtime 应通过
  `/v1/broadcasts/submit` 创建 pending attempt，并在链上提交或判定失败后调用
  `/v1/broadcasts/finalize` 落终态。
- 管理 signer、nonce、gas、RPC、failover、广播回执和重试。
- 迁移期只写 `manager_cow_execution_attempts` shadow 和
  `manager_broadcast_attempt_diagnostics`，生产切换窗口后才接管 legacy
  `cow_execution_attempts` 权威。
- 不计算 PnL，不修改候选池、YZ 或闭环拓扑。

### 5.8 Composite Manager

- 负责跨模块任务编排，例如一次刷新依次执行候选边池、YZ、闭环和复核。
- 通过版本、checksum 和 pipeline checkpoint 判断是否允许提交下游。
- 只写 pipeline/step/event 审计表，不复制或直接修改各模块业务表。
- 单模块任务仍调用各自模块，不经过综合管理模块。
- 跨模块流程采用步骤幂等键和断点续跑，不假设多个模块共享同一数据库事务。

### 5.9 UI 兼容层

- 现有页面和 URL 保持不变。
- Flask/UI 层只做参数、权限、Rust `RuntimeCore` view/command 调用和 DTO 兼容
  转换，不处理业务数据计算，不直查业务 SQLite，不直接读取实时链上或远程市场
  数据；未迁移命令才兼容调用 `manager_api`。
- 选择 `MANAGER_UI_DATA_SOURCE=manager` 后必须先调用模块统一读取接口；接口
  失败或数据缺失时 fail-closed，不得静默回退旧 SQLite 或旧业务函数。
- 管理模块负责业务状态、版本一致性、诊断、PnL 证据和实时内存对象更新；
  UI 只保持页面所需 DTO 的展示一致性。
- 页面不得依赖模块内部 SQLite 表结构；每个表范围切换到 manager 后立即删除
  对应 Python 直查路径，不保留双权威。

## 6. P0 执行顺序

1. 核对 Web 健康和当前活动进程，确认服务入口是 `start_server.py`。
2. 只读生成当前闭环与运行态差异报告，先处理孤儿状态，再处理缺失状态。
3. 完成剩余流动性扫描，记录 RPC busy、延后和失败的区别。
4. 重新运行候选池质量审计；确认新口径下候选池全部合格后，按候选 -> YZ -> 闭环 -> 总览顺序重建。
5. 检查每个 review 的具体 PnL；无具体值时标记数据不完整，修复数据链路并重试，
   不把诊断原因当作数值，也不伪造正收益。
6. 对确认正收益且 `runArbitrage` 可执行的路线启用广播；失败必须留下真实错误并修复后重测。
7. 运行连续 30 分钟窗口，连续 3 个窗口通过后才进入长期统计。
8. 在 P0 稳定之前，不删除大型 SQLite 备份或历史审计 JSONL。

## 7. 验收规则

- `0.0` 不能代替未知 PnL；必须标注来源和未确认原因。
- 没有具体 signed PnL 的复核不得进入完成态；结构化错误只能说明缺值原因。
- 正 `rate delta` 但 `runArbitrage` 未确认，不得广播。
- `SwapNotResolved` 必须保留 selector、路由、PoolKey 和跳次诊断。
- RPC busy、rate limit 和动态离线属于延后，不直接判定永久失败。
- UI 清空只影响明确选择的记录类型，不删除复核事实。
- 不手工修改 SQLite、evidence、readiness、nonce、gas 或交易签名。

Definition of Ready：

- 任务有唯一编号、依赖、负责模块、完成标准和证据落点。
- 不包含跨模块写表，不属于 Composite Manager 的编排也不能静默变成跨模块任务。
- 变更前有当前基线，包括版本、checksum、关键表数量或运行窗口。

Definition of Done：

- 代码按实施手册完成，`cargo fmt/check/test` 或等价验证通过。
- 先有 `dryRun=true` 结果，再执行 `apply`；业务表只有一个权威写入者。
- 验收记录包含时间窗口、数据库、版本、数量、成功/失败/idle 和修复动作。
- 未通过项保留真实错误和证据，不把诊断或占位值写成完成。
- 运行文件和报告写入 `plan/runtime_evidence/` 或 `runtime/evidence/`，不在根目录新增文件。
