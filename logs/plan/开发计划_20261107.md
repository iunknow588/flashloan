### 2.2 已确认高优缺陷

`BUG-RUNTIME-AVAILABILITY`：已关闭并归档。纯 V4 DEX scope、API 契约、提交
dry-run、延迟、跨 TTL 诊断和三个连续正式窗口均通过。服务重启、profile 或

`BUG-RUNTIMECORE-MIXED-SNAPSHOT`：当前 `/api/status` 显示 RuntimeCore
`state=error`、`snapshotAvailable=false`、`managerAvailable=false`。原因是
token library 的 `core/stocks/extension/test.enabled` 期望 `true`、实际 `false`，
RuntimeCore 拒绝混合 Manager snapshot。页面 fail-closed 只说明错误被暴露，
不等于修复；该缺陷在 `M1-P` 前修正 admission，或明确只读投影边界并补回归。

`BUG-CLOSEDLOOP-TESTNET-RESIDUE-AUTOPRUNE`：历史 Testnet
`aaa|bbb|ccc` 运行态可被例行维护自动删除。2026-11-07 审计记录该行存在，
2026-11-08 审计记录当前库已无该行，不能据此反推它从未存在。代码已改为默认
检测并保留；仅显式 `apply_cleanup=True` 且同时提供审批编号和快照 SHA256
时才允许清理，通用孤儿清理也不得删除该已知键。当前运行进程尚未重启加载该
修复，因此 `P0-2.5` 仍为进行中。

`BUG-CLOSEDLOOP-RUNTIME-SYNC` 的核心不是“闭环完全没有状态”，而是运行态身份
把 Y/Z 两个方向折叠为一个符号组：

- 一条 `anchor|sorted(Y,Z)` 状态可能被两个反向闭环共同命中。
- 扫描、预检、复核、PnL 和广播无法仅凭该键证明自己处理的是哪一条有向路径。
- 运行态键也不匹配闭环表的地址路径主键，因此不能用物理 `loop_key` 直接关联。
- 只回填数据不修改写入端和读取端会在下一轮刷新中重新产生错误身份。

修复方向固定为：活动运行态主键采用闭环表地址型 `loop_key`；无序 Y/Z 符号组
只保留为展示、兼容查询和迁移诊断，不再作为一一对应验收键。

## 3. 全局执行原则

### 3.1 Scope 与身份

- 所有查询、写入、审计和验收显式绑定
  `network + chain_id + protocol + market_id`。
- 主网验收只接受 `robinhood/4663/uniswap_v4/dex-arbitrage-4663-uniswap-v4`。
- Testnet 记录可以存在于同一 SQLite，但必须进入 `outOfScope`，不得计入缺失、
  孤儿或覆盖率。
- 有向路径保留 `Y -> Z` 顺序；地址路径和符号路径都不得通过排序覆盖方向。

### 3.2 Authority 与单写模块

- 每个表范围在任一时刻只允许一个权威写入模块。
- Python legacy、Rust Manager 和 rollback 模式不得长期双写。
- authority 切换后立即关闭旧写入，并在同一 authority 下重新采集受影响 P0 回归。
- 工程完成、shadow 通过、临时库通过或 dry-run 通过，都不能表述为生产切换完成。

### 3.3 变更顺序

所有数据或 authority 变更统一遵循：

1. 只读基线：记录 schema、版本、checksum、数量和当前 authority。
2. 静态检查：确认调用方、写入方、失败路径和 rollback 方案。
3. 隔离验证：单测、临时库、copy DB、compare-only 或 shadow。
4. Dry-run：生成确定性变更清单，记录命令、退出码和前后 checksum。
5. 维护窗口 apply：备份后执行一次受控变更，不临时扩大 scope。
6. 立即复测：数量、身份、终端状态、健康检查和错误摘要。
7. 证据登记：写入 `runtime_evidence/reports/`，更新 checklist 和归档。

### 3.4 证据绑定

每份验收证据至少包含：

- `taskId`、scope、authority、数据库路径和目标表。
- schema/data version、变更前后 checksum 和关键数量。
- 完整命令、开始/结束时间、退出码和观察窗口。
- `success/failed/pending/idle` 分类、finding、异常处置和 rollback 结果。
- 输入报告 checksum；派生报告必须能追溯到原始快照。

### 3.5 强制停止条件

出现以下任一情况时停止推进，不得用结果修正掩盖差异：

- scope 越界、跨链记录混入、重复主键或无法解析的地址/符号路径。
- dry-run 与 apply 目标数量、checksum 或 authority 不一致。
- copy DB 双读存在未解释差异，或 rollback 未演练。
- 生产 apply 后出现新增孤儿、悬挂广播、pending 未收敛或健康检查失败。
- 上游版本、schedule/scope 版本和下游消费版本不一致。
- 真实广播门禁缺少当前 authority 下的 P0 增量证据。

## 6. Rust Manager 生产 Authority

### 6.1 Authority 与单写范围

| 模块 | Authority 开关 | 单写范围 | 下游/入口 |

`X-Request-Id`、`Idempotency-Key` 和显式 Boolean `dryRun`；UI 读取使用
`RuntimeCore.manager_view`，显式操作使用 RuntimeCore command API。

### 6.2 统一迁移 Runbook

每个 M 级任务必须完成：

1. 目标库检查 `schema_migrations`；不存在本迁移时使用
   `manager_schema_migrations` 登记兼容边界。
2. 在临时库执行 migration、business bootstrap、重复 apply 和 checksum 比对。
3. 在真实副本执行 compare-only/双读，差异逐项解释并留存记录。
4. 维护窗口记录备份、当前 authority、依赖版本和目标表 checksum。
5. 切换单一 authority，立即关闭旧写入，禁止长期双写。
6. 执行 rollback 演练，再从最后 committed checkpoint 验证恢复。
7. 重新采集受影响 P0 增量证据后，才允许标记该 authority 切换完成。
