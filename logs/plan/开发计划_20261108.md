## 1. 计划目标

本轮开发只服务于 Robinhood Mainnet `4663` 的 Uniswap V4 DEX 套利链路，
按以下顺序收敛：

1. 先修复闭环方向级运行态身份，使 192 条有向闭环与 192 条运行态一一对应。
2. 再完成流动性扫描、候选池重建、PnL/广播门禁和连续主网观察。
3. 随后把 Token、Pool、Candidate、Closed-loop、Review、Broadcast 和
   Composite 的生产 authority 迁移到 Rust Manager。
4. 最后完成 UI/API 收口、长期盈利统计、日志轮转和命名兼容治理。

本计划不恢复 CoW 实时报价或订单业务，不启动 BNB Venus watcher、BNB 共享
采集器和通用清算扫描/执行。`cow_execution_*` 仅作为 V4 DEX 历史物理表名，
实际改名归入 `P3-3`。

### 1.1 最终完成定义

- 主网运行态达到 `directedClosed=192`、`directedRuntime=192`、
  `exactMatched=192`、`exactMissing=0`、`duplicateDirectedKey=0`、
  `orphan=0`、`scopeLeak=0`。
- 所有生产结论绑定当前 `scope + authority + PID + 数据库版本/checksum +
  观察窗口`，工程测试和 dry-run 不替代生产验收。
- 每个数据范围仅有一个权威写入模块，不长期双写；切换后旧写入立即关闭。
- UI 页面只通过 RuntimeCore/Manager API 读取和发出命令，Manager 不可用时
  fail-closed，不直接回退业务 SQLite。
- 真实广播只在 `M7-P` 完成且同 authority 的 P0 增量窗口通过后开放。

## 4. 第一批：关闭 `P0-2` 方向级运行态

### 4.1 `P0-2.4` 迁移 dry-run

交付物：

- 新增 `scripts/migrate_closed_loop_runtime_identity.py`，默认只读。
- 生成确定性迁移 JSON，至少包含 checklist 第 4.1 节规定的字段。
- 覆盖 96 个无序 Y/Z 组到 192 条地址型方向状态的映射、archive/re-key/insert
  计划、冲突清单和输入 checksum。
- 增加映射算法、重复键、缺地址、跨 scope、空报告、损坏 JSON、幂等和
  checksum 漂移测试。

执行步骤：

1. 固定当前数据库快照和 schema，记录 SHA256、行数和 canonical 报告 checksum。
2. 在 copy DB 或只读快照上实现并与 canonical 报告逐组对账。
3. 对每个无序组要求恰好一个 `directedSymbol` 精确命中；0 个或多个均停止。
4. 命中方向生成 `rekey`，反向方向生成 `insert`，两者目标状态均为
   `offchain_pending`。
5. 不复制 `preflight_failed` 等聚合终态，不把一条组状态映射成两条终态。
6. 输出 dry-run 证据，经复核后才进入 `P0-2.5`。

最低通过断言：

```text
closedLoops=192
proposedDirectionMappings=192
proposedRuntimeStates=192
archivePlans=96
rekeyPlans=96
reverseInsertPlans=96
sourceExactDirectedMatches=96
targetState=offchain_pending
unresolvedDirections=0
duplicateDirectedKey=0
unresolvedAddress=0
crossScopeConflict=0
```

### 4.2 `P0-2.5` copy DB/隔离验证

使用 `P0-2.4` 输出启动隔离维护和观察流程，验证：

- 96 条旧符号组状态被保留为迁移诊断，不静默删除。
- 已知 Testnet `aaa|bbb|ccc` 残留默认受保护。
- 显式清理同时要求审批编号和快照 SHA256。
- `observe_dex_closed_loops.py` 强制绑定
  `robinhood/4663/uniswap_v4/dex-arbitrage-4663-uniswap-v4`。
- copy DB 验证前后的数量、状态和 checksum 变化均可解释。

本批禁止指向生产进程或生产库。完成后才允许准备 copy DB 受控写入。

### 4.3 `P0-2.6` copy apply 与生产维护窗口

拆成不可跳过的四个执行包：

1. **copy apply**：备份、archive、re-key、insert、重复 apply、rollback 和
   checksum 比对。
2. **生产前冻结**：记录当前 PID、authority、端口 owner、数据库 SHA256、
   schema 和备份路径；暂停自动写入。
3. **单次生产 apply**：只执行已验收迁移，确认目标恰好 192 条方向状态且均为
   `offchain_pending`，旧符号组有快照和处置记录。
4. **重启加载**：目标计数校验后才重启 DEX-only 进程，验证
   `FLASHLOAN_RUNTIME_PROFILE=v4_dex`、PID/端口 owner、代码版本和
   `v4_closed_loop_worker` 回填结果与迁移计划一致。

任何 backup、rollback、checksum、计数或 scope 校验失败均停止，不通过修复
脚本来掩盖差异。

### 4.4 `P0-2.7` 防回归

对 `P0-2.6` 加载后的同一 PID 执行只读 `loop-key` 审计，连续观察 30 分钟：

- 运行态缺失、重复、孤儿和 scope 越界均为 0。
- 符号组只保留为诊断视图，不作为运行态主键。
- 观察期间无新增异常状态，错误和 idle 均有明确记录。
- 证据绑定当前进程、数据库和 authority，不复用迁移前窗口。

## 5. 第二批：DEX 运营验收

### 5.1 `P0-3` 扫描与动态发现

先盘点剩余流动性扫描缺口，再修复 RPC busy/rate-limit 的延后重试，最后恢复
动态池发现和断点续扫。`RPC busy` 不得写成永久业务失败，普通输入错误仍应
fail-closed。

### 5.2 `P0-4` 候选与下游重建

基于当前 token/pool authority 统一重建候选、YZ、闭环和总览。所有下游必须
消费同一上游版本和 checksum；重建前后数量差异逐项解释，未准入 token 池为 0。

### 5.3 `P0-5` signed PnL、预检和广播终态

先分类 3820 条缺失 signed PnL，再补齐执行预检和广播门禁，最后核对广播终态。
signed PnL、单位、币种、来源和预检结果缺任一项时，记录必须进入
`data_incomplete`，不得生成可广播请求。

### 5.4 `P0-6` 连续观察

在 `P0-2.7`、`P0-4` 和 `P0-5` 通过后执行三个连续 30 分钟窗口。窗口内无新增
缺失、重复、孤儿、越界运行态和悬挂广播；PnL 异常均有原因码与处置。

## 6. 第三批：Rust Manager 生产 Authority

### 6.1 串行顺序

```text
M0-P -> M1-P -> M2-P -> M3-P -> M4-P -> M5-P -> M6-P -> M7-P -> M8-P
```

每个 M 级任务统一执行：

1. 临时库/copy DB migration、dry-run、重复 apply 和 checksum 比对。
2. 真实副本 compare-only/双读，差异逐项解释。
3. 维护窗口记录备份、当前 authority、依赖版本和目标表 checksum。
4. 切换单一 authority 后立即关闭旧写入。
5. 执行 rollback 和 checkpoint 恢复演练。
6. 重新采集受影响 P0 增量证据。

### 6.2 关键门禁

- `M0-P` 只处理 manager schema，不提前改变业务 authority；`/healthz` 不访问
  主网业务数据库。
- `M1-P` 必须先关闭 `BUG-RUNTIMECORE-MIXED-SNAPSHOT`，四库导入和 symbol
  歧义可解释，Python 才能停止 `chain_tokens` 权威写入。
- `M2-P` 的 PoolKey/PoolId 一致率必须为 100%，scope 两端 KEY ID 可解析。
- `M3-P/M4-P` 分别由 Rust 独占候选边池和 `market_observation_*`，不得跨模块写。
- `M5-P` 的闭环只依赖单一上游版本组合，并保持方向级运行态。
- `M6-P` 缺 signed PnL 必须进入 `data_incomplete`，不得生成广播资格。
- `M7-P` 只消费 Review 确认请求；真实广播另需切换后的 P0 增量窗口。
- `M8-P` 从最后 committed checkpoint 恢复，重复命令保持幂等。

## 10. 失败停止条件

出现以下任一情况立即停止当前批次：

- scope 不完整，或混入其它 network/chain/protocol/market。
- source report、数据库、schema 或 checksum 不一致。
- 一个无序组没有精确命中，或存在多个有向命中。
- 地址无法解析、方向键重复、跨 scope 冲突，或无法证明一对一映射。
- copy DB 与生产前基线存在未解释差异。
- rollback 未演练，或 checkpoint 无法恢复。
- PnL、单位或来源不完整时尝试生成广播请求。
- Manager 不可用却回退业务 SQLite 或生成可写命令。
- 生产 apply、重启或观察结果与迁移计划不一致。

停止后保留原始输出和失败样本，不通过改口径、删除 finding 或覆盖证据继续。

## 11. 计划治理

- 本计划负责顺序、交付物、门禁和并行边界；checklist 负责唯一状态。

- 任务完成后先写证据，再更新 checklist，最后归档并调整本计划下一批次。
