# Rust 管理模块实施手册（2026-11-03）

> 文档状态：`implementation-spec`，目标设计，尚非已完成实现。
> 当前唯一实现了的 Pool scope 是 `full` 和 `core4`；其余 scope 属于本手册定义的
> 迁移目标。
>
> 本文是
> [token_and_manager_rust_rearchitecture_20261103.md](token_and_manager_rust_rearchitecture_20261103.md)
> 的实施细则。架构文档负责说明模块边界，本手册负责给出可直接编码、迁移和验收的
> 表结构、数据流、接口及测试顺序。

## 1. 实施结论

采用“四张代币库表 + 模块控制表”的设计：

1. Token Manager 独占 `token_core`、`token_stocks`、`token_extension`、
   `token_test` 四张代币库表。
2. 每个代币最多一个 `core/stocks/test` 主库，三者互斥；`extension` 是派生成员库，
   可与任意主库保存同一 `token_key_id`。extension 重叠不得复制或覆盖主库权威 metadata。
3. Pool Manager 不保存代币清单，只保存所引用的 `library_key`、库版本和校验和。
4. 每个启动方式在 `pool_scope_config` 中有固定配置，并对应一张独立的资金池表。
5. Pool Manager 通过 Token Manager 的 symbol 解析接口得到 `token_key_id`，
   再用 `v4_currency_key` 组成 V4 `PoolKey` 和 `pool_id`。symbol 只用于配置、
   日志和展示，不作为持久化外键。
6. 代币库和资金池表可由 SQLite 存储，但写入职责必须由 Rust 模块持有。UI 和
   Python 兼容层不得直接写这些表。
7. `fee`、`tick_spacing`、`hooks`、`pool_manager` 属于池身份，不写入代币表。
8. 模块 crate 发布 Rust library API，由唯一 `manager_api` 统一提供 HTTP/JSON；
   不允许每个业务 crate 各自启动生产服务。

## 2. 固定标识

### 2.1 标识规则

```text
normalized_address = lowercase(0x + 40 hex)
v4_currency_key    = normalized_address
token_key_id       = <network>:<chain_id>:<v4_currency_key>
pair_key_id        = pair:v1:<chain_id>:<currency0>:<currency1>
route_key_id       = route:v1:<chain_id>:<token_key_id_1>:...:<token_key_id_n>
v4_pool_id         = keccak256(abi_encode(V4PoolKey))
```

约束：

- 原生 ETH 的 `v4_currency_key` 使用零地址
  `0x0000000000000000000000000000000000000000`，`token_kind=native`。
- WETH 使用其 ERC-20 合约地址，不能与 ETH 合并。
- `currency0 < currency1`，比较规范化后的地址字符串。
- `token_symbol` 大小写只影响展示，不参与身份判断。
- symbol 缺失、重复或未准入时返回明确错误，禁止模糊匹配和自动猜测。
- `route_key_id` 保留方向；`pair_key_id` 用于无方向池索引。

### 2.2 版本与 checksum

库版本和 checksum 是可重建性契约，不使用 SQLite 文件修改时间代替。

#### Token library checksum

输入是同一 `network + chain_id + library_key` 下全部代币的规范化数组。数组按
`token_key_id` 升序排列，每项只包含会影响准入或下游池判断的字段：

```json
{
  "tokenKeyId": "robinhood:4663:0x...",
  "v4CurrencyKey": "0x...",
  "tokenAddress": "0x...",
  "tokenSymbol": "USDG",
  "tokenName": "USDG",
  "tokenDecimals": 18,
  "tokenKind": "stable",
  "isNative": false,
  "isWrappedNative": false,
  "isStable": true,
  "admissionStatus": "admitted",
  "admissionSource": "bootstrap:chain_tokens",
  "metadataSource": "chain_tokens",
  "metadataChecksum": "sha256:..."
}
```

计算方式：

```text
payload = UTF-8(canonical_json(array))
metadata_checksum = "sha256:" + hex(sha256(payload))
```

规则：

- `canonical_json` 使用固定字段顺序、无多余空白、布尔值而非 0/1。
- 不纳入 `updated_at`、`generated_at` 等非语义时间字段。
- 任何 admission、symbol、decimals、分类或来源变化都递增 `library_version`。
- `library_version` 只递增，不按 token 数量推算，也不回退。
- `token_count` 和 `admitted_count` 只作为可重建摘要，不能代替 checksum。

#### Pool scope checksum

输入包含 scope 身份、上游版本和已物化池身份：

```json
{
  "scopeKey": "core4",
  "poolTable": "v4_exchange_pools_core4",
  "filterMode": "edge_any",
  "libraryKeys": ["core"],
  "libraryVersions": {"core": 3},
  "libraryChecksums": {"core": "sha256:..."},
  "pools": [
    {
      "poolId": "0x...",
      "poolKey": {
        "currency0": "0x...",
        "currency1": "0x...",
        "fee": 3000,
        "tickSpacing": 60,
        "hooks": "0x0000000000000000000000000000000000000000"
      }
    }
  ]
}
```

`pools` 按 `pool_id` 升序。排序后的 canonical JSON 再计算 SHA-256。dry-run 和
apply 必须返回同一结构、同一 checksum；apply 后再次重建必须得到相同 checksum。

#### 版本推进规则

| 事件 | 必须递增 |
|---|---|
| token admission/block/class/metadata 变化 | 对应 token library |
| scope 的库选择、排除项或 filter mode 变化 | `pool_scope_config` 版本 |
| scope 池集合或 PoolKey 变化 | materialized scope checksum |
| 下游候选、YZ、闭环变化 | 各自输出 checksum |

下游只能在 `expected*` 与当前上游版本完全一致时提交。发现变化返回
`UPSTREAM_VERSION_CHANGED`，重新读取后再试。

### 2.3 symbol 到 PoolId 的唯一解析链

```text
配置 symbol
  -> Token Manager 唯一解析
  -> token_key_id
  -> v4_currency_key
  -> 规范排序 currency0/currency1
  -> Pool Manager 补 fee/tick_spacing/hooks
  -> abi_encode(V4PoolKey)
  -> keccak256
  -> v4_pool_id
  -> 与池表 pool_id 校验
```

`V4PoolKey` 编码必须复用
`flashloan/rs-src/src/pool_index.rs`，不得在 Python 和 Rust 中各实现一份。
若表内 `pool_id` 与重新计算结果不一致，池必须标记
`identity_mismatch` 并退出候选范围，不能静默修正。

## 3. 数据库结构

### 3.1 四张代币库表

下列 DDL 以 `token_core` 为例。`token_stocks`、`token_extension` 和
`token_test` 使用完全相同的列、索引和约束，只替换表名。

```sql
CREATE TABLE IF NOT EXISTS token_core (
    network                 TEXT    NOT NULL,
    chain_id                INTEGER NOT NULL,
    token_key_id            TEXT    NOT NULL,
    v4_currency_key         TEXT    NOT NULL,
    token_address           TEXT    NOT NULL,
    token_symbol            TEXT    NOT NULL,
    token_name              TEXT,
    token_decimals          INTEGER NOT NULL CHECK (token_decimals BETWEEN 0 AND 36),
    token_kind              TEXT    NOT NULL,
    is_native               INTEGER NOT NULL DEFAULT 0 CHECK (is_native IN (0, 1)),
    is_wrapped_native       INTEGER NOT NULL DEFAULT 0
                                CHECK (is_wrapped_native IN (0, 1)),
    is_stable               INTEGER NOT NULL DEFAULT 0 CHECK (is_stable IN (0, 1)),
    admission_status        TEXT    NOT NULL
                                CHECK (admission_status IN (
                                    'admitted',
                                    'blocked',
                                    'candidate_only',
                                    'pending_review'
                                )),
    admission_source        TEXT    NOT NULL,
    metadata_source         TEXT    NOT NULL,
    metadata_checksum       TEXT    NOT NULL,
    source_json             TEXT    NOT NULL DEFAULT '{}',
    first_seen_at           TEXT    NOT NULL,
    first_admitted_at       TEXT,
    updated_at              TEXT    NOT NULL,
    blocked_reason          TEXT,
    PRIMARY KEY (network, chain_id, token_key_id),
    UNIQUE (network, chain_id, v4_currency_key),
    UNIQUE (network, chain_id, token_address)
);

CREATE INDEX IF NOT EXISTS idx_token_core_symbol
    ON token_core(network, chain_id, token_symbol, admission_status);

CREATE INDEX IF NOT EXISTS idx_token_core_status
    ON token_core(network, chain_id, admission_status, token_kind);
```

四张表的业务定位：

| 库 | 表 | 准入范围 |
|---|---|---|
| `core` | `token_core` | 固定包含 `USDG`、`USDE`、`ETH`、`WETH` |
| `stocks` | `token_stocks` | 股票代币；不重复收录核心代币 |
| `test` | `token_test` | 每个 network 仅显式 `TZ` 地址；不包含 `TA/TB` |
| `extension` | `token_extension` | 与 core、stock 或 TZ 存在通过流动性门槛的直接 V4 池且 metadata 完整的代币；可包含 core、stock、TA/TB |

“core/stocks/test 主库唯一”是实施约束。股票、core 或 TA/TB 满足池邻接条件时可
同时写入 `token_extension` 作为派生成员；TZ 保持 test 主库成员，不作为 extension
成员。主库之间的改属必须通过 Token Manager 原子重分类，不能直接双向插入。

`extension` 的“可交换”只表示存在直接 V4 池，不要求经过美元资产。流动性门槛
只检查固定费、动态/特殊费为零、hook 为零、`has_liquidity=1` 和
`liquidity_index>0`。`estimated_tvl_usd` 与 `deep/thin/unpriced` 只保留为诊断，
不得作为 extension、候选池或 YZ 交换池的准入条件。

### 3.2 代币库控制表

以下是库级控制表，不承载代币清单：

```sql
CREATE TABLE IF NOT EXISTS token_library_state (
    network             TEXT    NOT NULL,
    chain_id            INTEGER NOT NULL,
    library_key         TEXT    NOT NULL
                            CHECK (library_key IN (
                                'core', 'stocks', 'extension', 'test'
                            )),
    library_version     INTEGER NOT NULL,
    token_count         INTEGER NOT NULL,
    admitted_count      INTEGER NOT NULL,
    metadata_checksum   TEXT    NOT NULL,
    source_checkpoint   TEXT,
    generated_at        TEXT    NOT NULL,
    updated_at          TEXT    NOT NULL,
    PRIMARY KEY (network, chain_id, library_key)
);

CREATE TABLE IF NOT EXISTS token_admission_events (
    event_id            TEXT    NOT NULL,
    network             TEXT    NOT NULL,
    chain_id            INTEGER NOT NULL,
    token_key_id        TEXT    NOT NULL,
    library_key         TEXT    NOT NULL,
    previous_status     TEXT,
    new_status          TEXT    NOT NULL,
    reason              TEXT    NOT NULL,
    actor               TEXT    NOT NULL,
    evidence_json       TEXT    NOT NULL DEFAULT '{}',
    created_at          TEXT    NOT NULL,
    PRIMARY KEY (network, chain_id, event_id)
);

CREATE INDEX IF NOT EXISTS idx_token_admission_events_token
    ON token_admission_events(network, chain_id, token_key_id, created_at);
```

Token Manager 提供只读目录视图，供 Pool Manager 校验库归属：

```sql
CREATE VIEW IF NOT EXISTS token_library_catalog AS
SELECT 'core' AS library_key, *
FROM token_core
UNION ALL
SELECT 'stocks' AS library_key, *
FROM token_stocks
UNION ALL
SELECT 'extension' AS library_key, *
FROM token_extension
UNION ALL
SELECT 'test' AS library_key, *
FROM token_test;
```

SQLite 不能为这个视图声明真实外键。Pool Manager 必须在同一写事务内调用 Token
Manager 的准入校验，且每次重建前执行跨表重复检查：

```sql
SELECT token_key_id, COUNT(*) AS copies
FROM token_library_catalog
GROUP BY network, chain_id, token_key_id
HAVING COUNT(*) > 1;
```

只要结果非空，Token Manager 健康检查失败，禁止重建下游。

### 3.2.1 通用业务写请求幂等表

`manager_write_requests` 是 manager 级控制表，不承载代币、池、闭环或广播业务
事实。它只记录已经提交成功的写请求摘要和首次响应，用于跨模块统一重放：

```sql
CREATE TABLE IF NOT EXISTS manager_write_requests (
    network             TEXT    NOT NULL,
    chain_id            INTEGER NOT NULL,
    operation           TEXT    NOT NULL,
    idempotency_key     TEXT    NOT NULL,
    request_id          TEXT    NOT NULL,
    request_digest      TEXT    NOT NULL,
    request_json        TEXT    NOT NULL,
    response_json       TEXT    NOT NULL,
    created_at          TEXT    NOT NULL,
    PRIMARY KEY (network, chain_id, operation, idempotency_key)
);

CREATE INDEX IF NOT EXISTS idx_manager_write_requests_request_id
    ON manager_write_requests(network, chain_id, request_id);
```

约束：

- 业务表、业务配置和本表记录必须在同一 `IMMEDIATE` 事务内提交；提交前崩溃时
  三者全部回滚，不允许出现“业务已写但幂等键不可重放”的半完成状态。
- 同键同摘要返回首次持久化响应，并标记 `idempotentReplay=true`；同键不同摘要
  返回 `IDEMPOTENCY_KEY_REUSED`，不得覆盖首次记录。
- `dryRun=true` 不写业务表，也不写 `manager_write_requests`。
- `manager_write_requests` 不是 `token_admission_events` 的替代品；token admission
  仍保留自身 event/evidence，scope 等模块不得向 token event 表塞入非 token 事件。

### 3.3 启动方式配置

`pool_scope_config` 是“启动参数目录”，不是代币表。每行固定映射到一张池表：

```sql
CREATE TABLE IF NOT EXISTS pool_scope_config (
    network                     TEXT    NOT NULL,
    chain_id                    INTEGER NOT NULL,
    scope_key                   TEXT    NOT NULL,
    pool_table                  TEXT    NOT NULL,
    library_keys_json           TEXT    NOT NULL,
    library_versions_json       TEXT    NOT NULL,
    library_checksums_json      TEXT    NOT NULL,
    filter_mode                 TEXT    NOT NULL
                                    CHECK (filter_mode IN ('edge_any', 'both_end')),
    excluded_token_key_ids_json TEXT    NOT NULL DEFAULT '[]',
    enabled                     INTEGER NOT NULL DEFAULT 1
                                    CHECK (enabled IN (0, 1)),
    materialized_checksum       TEXT,
    last_rebuilt_at             TEXT,
    created_at                  TEXT    NOT NULL,
    updated_at                  TEXT    NOT NULL,
    PRIMARY KEY (network, chain_id, scope_key),
    UNIQUE (network, chain_id, pool_table)
);
```

`pool_table` 不允许由 API 任意拼接。Rust 代码使用固定枚举映射：

| `scope_key` | `library_keys_json` | 目标池表 | 用途 |
|---|---|---|---|
| `core4` | `["core"]` | `v4_exchange_pools_core4` | 当前主网优先启动方式 |
| `stocks` | `["stocks"]` | `v4_exchange_pools_stocks` | 仅股票库 |
| `test` | `["test"]` | `v4_exchange_pools_test` | 单 TZ 隔离回归 |
| `core_stock` | `["core","stocks"]` | `v4_exchange_pools_core_stock` | 核心加股票 |
| `core_ext` | `["core","extension"]` | `v4_exchange_pools_core_ext` | 核心加扩展库 |
| `core_test` | `["core","test"]` | `v4_exchange_pools_core_test` | 核心加测试库 |
| `all_except_tz` | 四库 | `v4_exchange_pools_all_except_tz` | 排除 TZ 的全量模式 |
| `full` | 四库 | `v4_exchange_pools_full` | 全量模式，不作为默认启动 |

当前 Python 实现只支持 `full` 和 `core4`；`all_except_tz` 是保留但不是可执行
状态。上表其余 scope 是 M2 及其后续交付目标，不能把配置表存在误认为模式已完成。
切换前必须保证 `normalize_pool_scope()`、Rust scope enum 和 UI 展示使用同一组
`scope_key`。

`library_keys_json` 决定“加载哪些代币库”，`filter_mode` 决定“池子两端如何
过滤”。两者不能合并成一个参数：

- `edge_any`：池子任一端属于所选库，即可进入该 scope 的池表。
- `both_end`：池子两端都属于所选库，才能进入该 scope 的池表。

`core4` 首期建议使用 `edge_any`，因为核心代币与扩展代币组成的池仍可能是第一跳
或第三跳的锚点池；候选代币是否允许进入后续路由由 Candidate Edge Pool Manager
再按候选库范围过滤。

### 3.4 每个 scope 的独立池表

每张 scope 池表使用同一结构。下面以 `core4` 为例：

```sql
CREATE TABLE IF NOT EXISTS v4_exchange_pools_core4 (
    network                 TEXT    NOT NULL,
    chain_id                INTEGER NOT NULL,
    protocol                TEXT    NOT NULL DEFAULT 'uniswap_v4',
    pool_id                 TEXT    NOT NULL,
    pool_manager            TEXT    NOT NULL,
    pool_key_json           TEXT    NOT NULL,
    token0                  TEXT    NOT NULL,
    token1                  TEXT    NOT NULL,
    token0_key_id           TEXT    NOT NULL,
    token1_key_id           TEXT    NOT NULL,
    fee                     INTEGER NOT NULL,
    dynamic_fee             INTEGER NOT NULL DEFAULT 0,
    special_fee             INTEGER NOT NULL DEFAULT 0,
    tick_spacing            INTEGER NOT NULL,
    hooks                   TEXT    NOT NULL,
    source_block_number     INTEGER,
    source_tx_hash          TEXT,
    pool_status             TEXT    NOT NULL DEFAULT 'active'
                                CHECK (pool_status IN (
                                    'active',
                                    'stale',
                                    'invalid',
                                    'identity_mismatch',
                                    'blocked'
                                )),
    materialized_at         TEXT    NOT NULL,
    updated_at              TEXT    NOT NULL,
    PRIMARY KEY (network, chain_id, protocol, pool_id)
);

CREATE INDEX IF NOT EXISTS idx_v4_pools_core4_tokens
    ON v4_exchange_pools_core4(
        network, chain_id, token0_key_id, token1_key_id, pool_status
    );
```

其他 `v4_exchange_pools_*` 表复制上述结构。旧
`v4_exchange_pools` 继续作为 raw 全量池源，新 scope 表是 Pool Manager 发布的
物化结果；候选池和观察池只读取与本次 scope 绑定的物化池版本。

- migration runner 对同一 migration 只有一次写入；重复执行必须为 no-op，并且
  校验不变。
- 本 migration 不导入业务数据、不切换 Python 或 UI 数据源。

迁移原则：

- 一个业务表同一时间只能有一个权威写入模块，不能长期双写。
- 旧 Python 函数可在切换期保留为只读比较器，但必须记录 `dataSource=legacy`。
- `rs-src/src/pool_index.rs` 是 PoolKey/PoolId 的现有 Rust 基准，新模块通过共享
  类型调用它，不复制算法。
- `rust_closed_loop.py` 在迁移期可以继续作为执行适配器，但闭环拓扑和最终 PnL
  的所有权必须逐步转到对应 Manager。

### 5.1 Token Manager

查询已准入代币：

```http
GET /v1/tokens?chainId=4663&library=core&status=admitted
```

D1.2.1 运行时通过 `MANAGER_DB_PATH` 指向只读业务 SQLite；该变量未配置时，
`/healthz` 和 `/v1/capabilities` 仍可用，token 查询返回
`UPSTREAM_UNAVAILABLE`。manager_api 不直接执行 token 表 SQL，只调用
`token_manager` library。

```json
{
  "ok": true,
  "version": "manager_dto_v1",
  "data": {
    "libraryKey": "core",
    "libraryVersion": 3,
    "metadataChecksum": "sha256:...",
    "tokens": [
      {
        "tokenKeyId": "robinhood:4663:0x0000000000000000000000000000000000000000",
        "v4CurrencyKey": "0x0000000000000000000000000000000000000000",
        "symbol": "ETH",
        "decimals": 18,
        "tokenKind": "native",
        "admissionStatus": "admitted"
      }
    ]
  }
}
```

解析 symbol：

```http
POST /v1/tokens/resolve
Content-Type: application/json

{"chainId":4663,"symbol":"USDG","requiredStatus":"admitted"}
```

唯一匹配时返回一个 `tokenKeyId`；无匹配返回 `TOKEN_NOT_FOUND`，多匹配返回
`TOKEN_SYMBOL_AMBIGUOUS`。Pool Manager 不得自行选择第一条记录。
同一 `token_key_id` 在 primary 与 extension 的合法 overlap 先合并成员关系，
不会被误判为多个候选；不同地址共享 symbol 时才返回歧义候选列表。

变更准入：

```http
POST /v1/tokens/admit
Content-Type: application/json
X-Request-Id: request-20261104-001
Idempotency-Key: admit-robinhood-4663-token-001

{
  "chainId": 4663,
  "libraryKey": "extension",
  "tokenKeyId": "robinhood:4663:0x...",
  "reason": "verified_pool_with_core",
  "evidence": {
    "poolId": "0x...",
    "source": "v4_exchange_pools"
  },
  "dryRun": true
}
```

`POST /v1/tokens/block` 使用相同请求结构。两个请求头与显式 Boolean `dryRun`
缺一不可。`dryRun=true` 必须生成与 apply 相同的版本/checksum 预演并回滚；
`dryRun=false` 在单个 `IMMEDIATE` 事务内写 status、library state、checksum、
`token_admission_events` 和幂等记录。相同 `Idempotency-Key` 与请求摘要重放
原结果；摘要不同返回 `IDEMPOTENCY_KEY_REUSED`。

审计查询：

```http
GET /v1/tokens/audit?chainId=4663&recentEventLimit=20
```

审计必须只读打开 manager schema，返回四库 status counts、library
version/checksum、重复 symbol、主库冲突、admission source、最近 event 和
state/rows 一致性。`recentEventLimit` 默认 `20`，超过 `100` 必须拒绝。

Token authority 切换：

```text
TOKEN_MANAGER_AUTHORITY=legacy|manager|rollback
TOKEN_MANAGER_ROLLBACK_REASON=<required only for rollback writes>
```

`legacy` 是未配置时的安全默认值。`manager` 下 `manager_api` 才能执行
`dryRun=false` admission apply；Python `seed_chain_tokens` 和 token metadata
修复写路径失败关闭。Python 只能调用
`project_chain_tokens_from_manager(database, network, chainId, dryRun)` 发布
`chain_tokens` 兼容投影。投影规则：

- 只发布 `admitted` 和 `candidate_only`，blocked/pending_review 不得进入旧读路径。
- 同一 `token_key_id` 按 `core -> stocks -> test -> extension` 选主行；extension
  overlap 只去重，不制造第二份 metadata 权威。
- 不删除目标库已有的其他 `chain_tokens` 行，避免破坏迁移期外键；新增/更新后
  `dryRun` 与 apply 的 canonical checksum 必须一致。
- 如果 blocked/pending token 仍存在于旧 `chain_tokens`，dry-run 必须返回
  `readyForProjection=false`，apply 以
  `TOKEN_PROJECTION_EXCLUDED_ROWS_PRESENT` 失败关闭，不能静默保留错误可见性。
- `rollback` 必须带非空原因，只恢复 Python 旧写；manager token 表、library
  state、event 和幂等记录必须原样保留。

切换前门禁固定为：M0 表完整、四库 bootstrap 已完成、manager audit 零主库冲突、
`chain_tokens` 双读差异可归因、投影 dry-run/apply 同 checksum、临时库完成
`legacy -> manager -> rollback -> manager` 演练。生产运行时仍为 `legacy` 时，
不得声称 Token Manager 已接管权威。

### 5.4 通用请求、幂等和错误契约

请求头：

```text
X-Request-Id: <uuid>
Idempotency-Key: <stable-key>   # 所有 apply 写请求必填
```

响应规则：

- `GET` 只读，不触发 refresh、repair、rebuild 或网络副作用。
- 所有 `POST` 修改请求必须显式传入 `"dryRun": true|false`，缺省值不推断。
- `dryRun=true` 不写业务表，不得递增版本，不得发广播。
- 同一 `Idempotency-Key + 请求摘要` 重复提交返回第一次结果；请求摘要变化返回
  `IDEMPOTENCY_KEY_REUSED`。
- 新模块的业务 apply 必须把自身写入和 `manager_write_requests` 放在同一事务；
  token admission 继续使用自身 event/evidence 中的兼容幂等记录，不强制迁移。
- 返回 HTTP 成功不等于业务完成。`ok=true` 必须同时有可验证终态或明确 `idle`。
- 错误必须返回稳定 code、是否可重试、失败阶段和上游版本，不能只返回文本。

统一错误对象：

```json
{
  "ok": false,
  "version": "manager_dto_v1",
  "requestId": "7bb6...",
  "error": {
    "code": "UPSTREAM_VERSION_CHANGED",
    "message": "core library changed during rebuild",
    "retryable": true,
    "stage": "pool_materialization",
    "details": {},
    "upstream": []
  }
}
```

错误码矩阵：

| code | HTTP | 可重试 | 语义 |
|---|---:|---|---|
| `INVALID_REQUEST` | 400 | 否 | 字段缺失、格式错误或未知枚举 |
| `UNAUTHORIZED` | 401/403 | 否 | 操作人或执行门禁未授权 |
| `TOKEN_NOT_FOUND` | 404 | 否 | Token Manager 无匹配代币 |
| `TOKEN_SYMBOL_AMBIGUOUS` | 409 | 否 | symbol 对应多个地址，需改用 KEY ID |
| `TOKEN_NOT_ADMITTED` | 409 | 否 | token 存在但不在 admitted 状态 |
| `TOKEN_LIBRARY_CONFLICT` | 409 | 否 | 同一 KEY ID 出现在多个主库 |
| `IDEMPOTENCY_KEY_REUSED` | 409 | 否 | 同一幂等键被不同请求摘要复用 |
| `SCOPE_NOT_FOUND` | 404 | 否 | 启动方式不存在 |
| `SCOPE_NOT_IMPLEMENTED` | 422 | 否 | 配置保留但代码尚未实现 |
| `UPSTREAM_VERSION_CHANGED` | 409 | 是 | 读取后上游版本变化，需重新读取 |
| `POOL_IDENTITY_MISMATCH` | 409 | 否 | PoolKey/PoolId 重算不一致 |
| `POOL_INVALID` | 422 | 条件 | 池无效；修复后可重试 |
| `REVIEW_PNL_INCOMPLETE` | 422 | 是 | 缺少具体 signed PnL |
| `REVIEW_NOT_EXECUTABLE` | 409 | 条件 | 当前不满足执行资格，不能广播 |
| `BROADCAST_REQUEST_NOT_ELIGIBLE` | 409 | 否 | 请求未经 Review 确认 |
| `BROADCAST_SUBMISSION_FAILED` | 502 | 条件 | 链上提交失败，保留真实错误 |
| `RPC_UNAVAILABLE` | 503 | 是 | RPC 暂时不可用或限流 |
| `UPSTREAM_UNAVAILABLE` | 503 | 是 | 上游模块或数据库暂不可用 |
| `INTERNAL_ERROR` | 500 | 条件 | 未分类内部错误，必须保留 requestId |

重试分类：

- `retryable=true` 才允许自动退避重试。
- `REVIEW_PNL_INCOMPLETE`、`UPSTREAM_VERSION_CHANGED` 和 RPC 限流可以重试，但必须
  重新读取依赖，不能原样无限循环。
- `POOL_IDENTITY_MISMATCH`、symbol 歧义和未准入 token 必须先修正数据。
- 广播失败是否可重试由 Broadcast Manager 根据 nonce、chain receipt 和交易哈希
  决定；不得只按字符串匹配统一重发。

### 5.5 Review Manager

M6 的 Review Manager 是复核工作的唯一管理工具，包含复核主线程、唯一复核队列、
有界复核工作线程池、durable 状态和对外命令/查询接口。主线程负责启动停止、优先级
排队、派发、结果回收、背压、心跳、超时、僵死恢复和终态推进；工作线程只通过注入的
复核适配器执行静态预览、候选路由和 `runArbitrage`，不自行创建队列或线程。Manager
不计算或伪造 PnL：它锁定 M5 上游版本、校验工作线程返回的证据完整性、分类终态、
持久化诊断并生成广播请求。

`POST /v1/reviews/run` 当前仍是“提交复核证据并落状态”的 durable 写入口，不是
运行时命令队列；页面“手动复核”应通过后续冻结的 Manager command API 投递到唯一
复核主线程队列。只有 `ok=true`、`executable=true` 且 signed PnL 完整时才是
`completed`；只有 `completed` 且 PnL 严格大于零才生成
`manager_v4_review_broadcast_requests` 的 `generated` 请求，不发送交易。

```http
POST /v1/reviews/run
Content-Type: application/json
X-Request-Id: request-20261104-m6-001
Idempotency-Key: reviews-4663-20261104-001

{
  "chainId": 4663,
  "expectedUpstream": {
    "closedLoopVersion": 9,
    "closedLoopChecksum": "sha256:...",
    "candidateEdgeVersion": 7,
    "candidateEdgeChecksum": "sha256:...",
    "observationVersion": 4,
    "observationChecksum": "sha256:...",
    "poolScopeChecksum": "sha256:...",
    "libraryVersions": {"core": 3},
    "libraryChecksums": {"core": "sha256:..."}
  },
  "evidence": [
    {
      "loopKey": "0x...:0x...:0x...",
      "staticPreview": {"route": "acceptable"},
      "reviewedAt": "2026-11-04T00:00:00Z",
      "runArbitrage": {
        "ok": true,
        "executable": true,
        "blockNumber": 100,
        "signedPnl": {
          "raw": "12.5 USDG",
          "amount": 12.5,
          "currency": "USDG",
          "address": "0x...",
          "unit": "token",
          "source": "runArbitrage"
        },
        "diagnostics": [],
        "gasEstimate": "120000"
      }
    }
  ],
  "dryRun": true
}
```

约束：

- `signedPnl` 必须包含数值、单位、币种、来源和 raw 原文；地址可选。任何缺少项按
  `data_incomplete` 处理并写 `evidence_missing` 诊断。
- `SwapNotResolved`、revert、quote failure、RPC unavailable 必须保留
  `loop_key`、hop、pool、selector、code、message 和 payload，但诊断不能替代
  signed PnL。
- `dryRun=true` 不写 review 表、状态或幂等记录；`dryRun=false` 在单个
  `IMMEDIATE` 事务内替换当前 scope 的 shadow 并写 `manager_write_requests`。
- 同一 `Idempotency-Key + 请求摘要` 重放首次结果；请求摘要变化返回
  `IDEMPOTENCY_KEY_REUSED`。`requestId` 不参与请求摘要。
- M5 上游版本或 checksum 与 `expectedUpstream` 不一致时返回
  `UPSTREAM_VERSION_CHANGED` 且不写任何表。

### 5.6 Broadcast Manager

M7 的 Broadcast Manager 是广播工作的唯一管理工具，包含广播主线程、唯一执行队列、
有界广播工作线程池、durable attempt 状态和对外命令/查询接口。主线程负责启动停止、
只接收 Review 已确认请求、派发、nonce/gas、RPC failover、回执回收、重试、背压、
心跳、僵死恢复和终态推进；工作线程只执行受控广播任务。Manager 不重算 PnL、不修改
闭环拓扑，也不允许 UI 或其他模块直接操作工作线程或队列。

广播运行能力已经收口到 Rust：`broadcast_manager::ExecutionQueue` 是唯一执行队列，
`broadcast_manager::BroadcastSupervisor` 创建并持有有界广播 worker 线程和终态计数。
`rs-src/src/worker_pool.rs` 只保留 PyO3 宿主、业务执行适配器和兼容 facade，不得
重新定义队列或第二套广播主线程。Python `BroadcastSupervisor` 只允许用于直接测试和
legacy non-native fallback，不进入 native 生产装配。

M6/M7 工具化以“重新组装现有文件”为主：先建立旧文件到新管理工具目录的职责映射，
再移动主线程、队列、worker、执行适配器和 durable 模块并修正导入；不得先写一套新

### 5.7 RuntimeCore 与原生池生命周期

`RuntimeCore` 是 Python/Flask 进程中的 Rust 内存大对象，不是第二套持久化权威。每个
chain 在 Rust 进程内最多注册一个实例；业务真相仍由所属 Manager 的 SQLite 事务和
版本/checksum 维护。UI 和 Python 兼容层只能消费 RuntimeCore 返回的 DTO，不得在
Python 重建 Manager 快照、业务缓存或跨 Manager 顺序。

PyO3 公共接口：

| 接口 | 约束 |
|---|---|
| `runtime_core_register(chain_id, network, database_path, protocol="uniswap_v4", broadcast_authority="legacy", candidate_authority="legacy", candidate_exchange_authority="legacy")` | 同 chain 同 database/network/protocol 和三个独立 authority 才复用；任一不一致返回 `RUNTIME_CORE_IDENTITY_CONFLICT`。原有 6 参数调用保持兼容 |
| `runtime_core_status(chain_id)` | 只返回生命周期、generation、事件和错误，不刷新、不访问业务表 |
| `runtime_core_state(chain_id)` | 返回最近一次已提交快照；尚未刷新时明确失败 |
| `runtime_core_manager_snapshot(chain_id, refresh)` | `refresh=true` 通过各 Manager 只读 API 构建新一代；失败保留旧快照 |
| `runtime_core_manager_view(chain_id, view, limit, options_json)` | 页面只读投影；view、limit 和选项按白名单校验，直接调用所属 Manager 公开只读函数 |
| `runtime_core_command(chain_id, command, request_id, idempotency_key, dry_run, options_json=None)` | 命令头必填；支持只读 `refresh_snapshot`、权威 `clear_broadcasts`、`rebuild_candidate_edges`、`rebuild_candidate_exchange_pools`，以及异步状态迁移 `manual_review`、`manual_broadcast` |
| `runtime_core_close(chain_id)` | 只关闭当前 chain 的 RuntimeCore |

刷新顺序固定为 Token/Pool/Candidate Edge/Candidate Exchange/Closed-loop/Review/
Broadcast，再由 Composite Manager 的 pipeline snapshot 提供聚合版本与 fingerprint。
RuntimeCore 从 Manager DTO 重新计算 upstream fingerprint 并与 Composite 结果比对；
不一致时返回 `InconsistentSnapshot`，不得把新 Manager 数据和旧 pipeline 状态拼成
一个快照。Snapshot 在单个写锁内替换 generation，页面读取不会看到半更新对象。

原生执行池同样归 Rust 所有：

- `native_pool_registry.rs` 以规范化数据库路径为键，持有
  `Py<ClosedLoopWorkerPool>`；同一路径重复获取返回同一个池对象。
- `native_pool_get_or_create` 不负责业务配置推断；chain/network/protocol、并发和
  maintenance/execution 参数由显式调用传入并记录在 registry entry。
- `native_pool_registry_manage(stop, chain_id, database_path)` 支持按 chain/database
  停止，`native_pool_registry_status` 返回当前 entry 摘要。
- Python `_POOLS_BY_DATABASE`/`_POOLS_BY_CHAIN` 只保留旧扩展 fallback 兼容，不是
  native 生产路径的 owner。`ChainRuntimeContext` 不缓存 pool；`close()` 通过
  `stop_native_pool_for_chain` 仅关闭本 chain。

### 阶段 D（M3-M8）：下游切换

按以下顺序切换唯一写入口：

```text
Candidate Edge Pool Manager
  -> Candidate Exchange Pool Manager
  -> Closed-loop Manager
  -> Review Manager
  -> Broadcast Manager
  -> Composite Manager
```

每完成一个模块，旧 Python 写入路径只保留只读兼容。禁止同时保留两个权威写入者。

## 7. 迁移与回滚

### 7.1 迁移前

- 记录 SQLite `PRAGMA quick_check`、关键表计数、数据库大小和当前服务 PID。
- 生成只读基线 JSON，记录 `packages_scope.py`/`pool_scope` 现有启动口径。
- 检查服务打开的文件，活动 WAL/SHM 和日志不得删除。
- 迁移只增加新表和新索引，不就地改写旧业务表。

### 7.2 双读比对

在切换权威写入前，对同一 chain/scope 同时读取旧路径和 Rust 输出：

| 比对项 | 通过条件 |
|---|---|
| token address 集合 | 差异集合为空 |
| token symbol/decimals | admitted token 全量一致 |
| PoolKey | currency0/currency1/fee/tick_spacing/hooks 全量一致 |
| PoolId | 重算一致率 100% |
| 池集合 | raw 过滤差异均有逐池原因 |
| 候选边池 | 差异可归因于准入口径变化 |
| 闭环拓扑 | 版本一致，无跨版本混用 |
| 复核 PnL | 每条完成复核都有具体 signed 数值和来源 |

### 7.3 回滚

由于 migration 为加法迁移，回滚策略是：

1. 停止新 Rust 写入 worker。
2. 设置 `TOKEN_MANAGER_AUTHORITY=rollback`，并提供非空
   `TOKEN_MANAGER_ROLLBACK_REASON`；不得同时开放 Rust admission apply。
3. 保留旧表、旧只读路径、manager token 行、library state、event 和幂等记录。
4. 将 UI/dataSource 切回旧路径，并记录失败版本、checksum、切换原因。
5. 重新切回 `manager` 后先执行兼容投影 dry-run，再 apply；第二次投影必须
   `changedRows=0` 且 checksum 稳定。
6. 只有在确认无人引用时，才允许按固定表清单删除本阶段新增表。

禁止通过 `git reset --hard`、`git checkout --` 或手工删除 SQLite 文件回滚。
